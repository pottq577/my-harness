# DBA Knowledge Base 스킬

DB 관련 코드 작업과 답변에서 10년차 DBA가 작성한 72개 지식 문서를 판단 근거로 사용한다. 지식 문서는 설계 원칙과 위험을 제공하며, 실제 저장소와 DBMS의 사실을 대신하지 않는다.

## 적용 범위

- 데이터베이스와 데이터 저장 계층의 설계, 구현, 리뷰, 마이그레이션, 튜닝, 장애 분석에 적용한다.
- 데이터 저장 계층과 무관한 일반 애플리케이션 로직에는 적용하지 않는다. DB라는 단어가 우연히 등장했다는 이유만으로 범위를 넓히지 않는다.

## 작업 유형 분류

질문을 먼저 다음 두 유형으로 분류한다. 분류에 따라 저장소 확인 여부가 달라진다.

### knowledge-only

개념 설명, 기술 비교, 설계 상담처럼 저장소 분석이 필요 없는 질문. 이 경우 저장소가 존재한다고 가정하지 않고 탐색하지 않는다.

### repository-grounded

구현, 코드 리뷰, 장애 분석, 마이그레이션, 성능 분석처럼 실제 저장소 상태가 판단에 필요한 작업. 이 경우에만 현재 작업과 관련된 다음 정보로 제한해 확인한다.

- DBMS와 버전
- 관련 스키마
- 관련 마이그레이션
- 관련 SQL
- 관련 ORM 코드
- 관련 설정
- 관련 테스트

DB 작업이라는 이유만으로 저장소 전체의 DB 파일을 무조건 탐색하지 않는다.

## 복합 질문 분해

- 서로 다른 DB 문제를 여러 개 포함하면 문제 단위로 분해한다.
- 각 문제마다 주 문서를 따로 결정할 수 있다.
- 하나의 넓은 문서에 모든 문제를 억지로 연결하지 않는다.

## 조회 절차

`rg` 없이도 성립하는 기본 절차는 다음과 같다. `rg`는 사용 가능한 환경에서 후보 필터링 최적화에만 쓸 수 있고 필수는 아니다.

1. [knowledge-map.md](knowledge-map.md)에서 관련 섹션을 고른다.
2. 해당 섹션의 후보 문서를 확인한다.
3. 후보의 frontmatter를 비교한다.
4. 주 문서를 결정한다.
5. 주 문서 본문을 끝까지 읽는다.
6. 근거가 더 필요하면 주 문서의 `read_also`에서 최대 2개를 추가로 읽는다.

본문 전체 문자열 검색을 기본 라우팅 방식으로 사용하지 않는다. 72개 문서 전체를 탐색하거나 본문 전체 검색 결과를 그대로 컨텍스트에 넣지 않는다.

### 후보 문서 선택 순서

후보가 여러 개면 다음 순서로 주 문서를 선택한다.

1. 현재 코드 또는 DBMS와 직접 일치하는 구체적인 `code_signals`
2. 작업 목적과 일치하는 `applies_to`
3. 질문 상황과 일치하는 `triggers`와 `read_when`
4. [knowledge-map.md](knowledge-map.md)의 섹션 키워드

- `EXPLAIN`, `ORDER BY`, `UNIQUE`, `FOR UPDATE`, `application.yml`처럼 여러 문서에 등장하는 범용 신호 하나만으로 문서를 선택하지 않는다.
- `knowledge-map.md`의 키워드는 coarse routing 용도로 쓴다. 최종 문서 선택의 단독 근거로 사용하지 않는다.
- 동률이면 더 좁고 구체적인 문제를 직접 다루는 문서를 주 문서로 선택한다.

### 주 문서와 보조 문서 제한

- 기본적으로 주 문서 1개를 읽는다.
- 추가 근거가 필요한 경우에만 주 문서의 `read_also`에서 최대 2개를 읽는다.
- 보조 문서의 `read_also`는 다시 따라가지 않는다(one-hop).
- 이미 읽은 문서는 다시 읽지 않는다.
- 단순 질문에서 관련 문서를 모두 읽지 않는다.
- 복합 질문은 각 하위 문제별로 주 문서를 선택할 수 있다. 이 경우에도 각 하위 문제의 보조 문서 확장은 one-hop으로 제한한다.

### 직접 근거가 없는 경우

질문과 직접 맞는 DBA 문서가 없으면 가까운 문서를 억지로 출처로 선택하지 않는다.

- `DBA-XXX` 참고 문헌을 출력하지 않는다.
- 필요하면 `DBA Knowledge Base 직접 근거 없음`이라고 명시한다.
- 저장소 사실이나 공식 문서로 판단할 수 있으면 그 근거를 사용한다.

## 적용 규칙

- 지식 문서의 원칙을 현재 코드와 운영 조건에 대입한다. 승인된 요구사항과 저장소의 실제 상태가 우선한다.
- MySQL의 DDL, InnoDB 락, PostgreSQL의 MVCC, Redis 명령처럼 엔진에 종속된 예시는 다른 제품에 그대로 옮기지 않는다.
- 버전, 가격, 지원 기능, 제한과 운영 명령처럼 변할 수 있는 사실은 해당 제품의 현재 공식 문서로 검증한다.
- DBA 문서와 공식 문서를 함께 사용했다면 두 근거를 구분한다.
- 문서 근거와 현재 저장소에서 도출한 판단을 구분한다. 둘이 충돌하면 차이를 밝히고 저장소와 공식 문서를 따른다.
- 코드 변경은 요청 범위 안에서 가장 작은 수정으로 수행하고, 해당 프로젝트의 테스트와 검증 규칙을 따른다.

## 출처 계약

- 지식 베이스의 원문은 Threads의 BEAR DBA(@bear_dba, https://www.threads.com/@bear_dba) 게시글에서 가져왔다. 원문 계보는 `raw/`에 있다.
- 답변, 구현 설명과 리뷰 결과 끝에 `참고: DBA-XXX` 형식으로 실제 판단에 사용한 문서만 적는다.
- 공식 문서를 실제 검증에 사용했다면 답변에서도 해당 공식 자료를 확인할 수 있도록 출처를 함께 제공한다.
- 출처 표기를 위해 제품 코드나 마이그레이션에 주석을 추가하지 않는다.
- 질문의 근거는 `annotated/`만 사용한다. `raw/`는 원문 계보 확인용이며 답변 근거가 아니다.
- ID와 파일 매핑은 [document-index.md](document-index.md)를 따른다.
- 문서를 유지보수할 때만 [metadata-schema.md](metadata-schema.md)를 읽고 `annotated/`, 인덱스와 지도를 함께 갱신한다.
