# ORM이 만드는 쿼리의 실체: JPA가 보내는 SQL을 본 적 있는가

개발자는 객체를 다룬다. DB는 SQL을 실행한다. 그 사이에 ORM이 있다.
DBA는 슬로우 쿼리 로그에서 이상한 SQL을 발견한다.
아무도 짠 적 없는 쿼리다. ORM이 만든 것이다.
ORM이 생성하는 SQL을 직접 본 적 있는가.
한 번이라도 봤다면, 이 글의 모든 내용이 익숙할 것이다.
본 적 없다면, 지금 당장 켜야 한다.

1. 쿼리 로그를 반드시 켜라.
2. N+1을 방치하지 마라.
3. `SELECT *`를 의심하라.
4. 벌크 연산은 네이티브로 하라.
5. ORM을 쓰되 SQL을 알아야 한다.

ORM은 도구다.
SQL을 모르는 사람이 쓰면 흉기가 된다.

## 왜 DBA가 ORM을 경계하는가

개발자가 코드를 커밋한다. 서비스가 배포된다. DBA는 슬로우 쿼리 알람을 받는다.
로그를 열어본다. 본 적 없는 SQL이 찍혀 있다. 서브쿼리가 세 겹이다.
JOIN이 다섯 개 붙어 있다. 누가 짰는지 물어보면 아무도 모른다.
ORM이 만든 쿼리다.
개발자는 자바 코드만 봤다. DB가 받은 SQL은 본 적 없다.
DBA가 ORM을 경계하는 이유는 단순하다.
개발자와 DB 사이에 번역기가 하나 끼어 있는데, 그 번역기의 출력물을 아무도 검수하지 않는다.

## N+1 문제

가장 악명 높은 ORM 사고다.
목록을 조회한다. 쿼리 하나가 나간다.
그런데 연관된 데이터를 가져오려고 건건이 쿼리가 추가된다.
100건 목록이면 101개 쿼리.
1000건이면 1001개.

```sql
SELECT * FROM orders;
SELECT * FROM order_items WHERE order_id = 1;
SELECT * FROM order_items WHERE order_id = 2;
SELECT * FROM order_items WHERE order_id = 3;
-- ... 100번 반복
```

JOIN 한 방이면 끝날 일이다.
ORM은 객체 그래프를 탐색하면서 하나씩 가져온다.
DB 입장에서는 폭탄이다.

## Lazy Loading의 실체

필요할 때 로딩한다. 좋은 의도다.
하지만 현실은 다르다.
트랜잭션 밖에서 접근하면 `LazyInitializationException`이 터진다.
트랜잭션 안에서 접근하면 N+1이 발생한다.
결국 양쪽 다 문제다.
개발자가 Lazy를 설정해 놓고, 서비스 레이어에서 연관 객체를 순회한다.
코드상으로는 자연스럽다.
DB에는 쿼리가 수십 개 날아간다.
Lazy는 "안 가져온다"가 아니다. "나중에 가져온다"다.
그 나중이 루프 안이면 재앙이다.

## EAGER의 함정

N+1이 싫어서 EAGER로 바꾼다.
항상 JOIN으로 가져오니 N+1은 사라진다.
대신 다른 문제가 생긴다.
주문 목록만 필요한 화면에서도 주문 상세, 배송 정보, 결제 내역까지 전부 JOIN으로 딸려온다.
안 쓰는 데이터가 매번 메모리에 올라간다. 쿼리는 비대해진다.
네트워크 전송량이 늘어난다. DB CPU가 올라간다.
EAGER는 N+1의 해결책이 아니다.
문제를 다른 형태로 바꾼 것일 뿐이다.

## ORM이 만드는 불필요한 JOIN

엔티티 간 연관관계가 복잡해지면 ORM이 생성하는 JOIN도 복잡해진다.
주문에 상품이 연결되고, 상품에 카테고리가 연결되고, 카테고리에 브랜드가 연결된다.
주문 하나를 조회했을 뿐인데 JOIN이 네 개 붙는다.
사람이 SQL을 짰다면 필요한 테이블만 JOIN한다.
ORM은 객체 그래프를 따라간다. 연관이 있으면 일단 연결한다.
실행 계획을 보면 풀스캔이 보인다. 인덱스를 타지 않는 JOIN이 보인다.
사람이라면 절대 짜지 않을 쿼리가 나온다.

## `SELECT *` 문제

ORM은 엔티티 단위로 데이터를 가져온다.
엔티티에 컬럼이 30개면 30개를 전부 SELECT 한다.

```sql
SELECT col1, col2, col3, col4, col5,
col6, col7, col8, col9, col10,
-- ... 30개 전부
FROM products WHERE product_id = 1;
```

필요한 건 상품명과 가격 두 개뿐이다.
나머지 28개는 네트워크를 타고 와서 메모리에 올라가고 버려진다.
BLOB이나 TEXT 컬럼이 섞여 있으면 더 심하다.
한 건 조회에 수 MB가 전송될 수 있다. Projection DTO를 쓰면 해결된다.
하지만 대부분의 팀이 엔티티를 그대로 반환한다.

## 벌크 연산의 비효율

1000건의 상태를 변경해야 한다. SQL이라면 한 줄이다.

```sql
UPDATE orders SET status = 'CANCELLED'
WHERE created_at < '2026-01-01';
```

ORM으로 하면 다르다.
1000건을 먼저 조회한다. 각 객체의 상태를 바꾼다. 영속성 컨텍스트가 변경을 감지한다. 1000개의 UPDATE 쿼리가 개별로 나간다.
쿼리 한 방이면 끝날 일을 1001번의 쿼리로 처리한다.
DB 입장에서는 폭력이다. 벌크 연산은 ORM의 약점이다.
이걸 인정하지 않으면 장애가 된다.

## 페이징과 ORM

게시판 페이징은 단순해 보인다. ORM에서는 단순하지 않다.
fetch join과 페이징을 함께 쓰면 Hibernate가 경고를 띄운다.
"firstResult/maxResults specified with collection fetch; applying in memory!"
DB에서 페이징하지 않고 전체를 메모리에 올린 뒤 잘라낸다는 뜻이다.
10만 건 테이블에서 20건을 보여주려고 10만 건을 다 가져온다.
offset 기반 페이징은 원래 깊은 페이지에서 느리다.
ORM이 메모리 페이징까지 더하면 장애 직행이다.

## 쿼리 로그를 켜라

`hibernate.show_sql`을 켠다. p6spy를 붙인다. 실제 나가는 SQL을 눈으로 확인한다.
이것만 해도 절반은 해결된다.
개발자가 findAll 하나를 호출했는데 콘솔에 쿼리가 수십 줄 찍히면 놀란다.
놀라야 정상이다. 놀라지 않으면 본 적이 없는 것이다.
쿼리 로그를 켜지 않는 팀은 ORM을 쓸 자격이 없다.
DB에 뭘 보내는지 모르면서 ORM이 알아서 한다고 믿는 건 위험하다.
로그를 켜라. 그게 첫 번째다.

## Native Query가 필요한 순간

모든 쿼리를 ORM으로 처리할 필요는 없다.
복잡한 집계 쿼리. 대량 배치 처리. 성능이 크리티컬한 조회.
이런 경우에는 네이티브 쿼리를 써야 한다.

```sql
SELECT DATE(created_at), COUNT(*), SUM(amount)
FROM orders
WHERE created_at >= '2026-08-01'
GROUP BY DATE(created_at);
```

이걸 ORM으로 표현하면 코드가 복잡해지고 성능도 나빠진다.
SQL로 직접 쓰면 명확하고 빠르다.
ORM을 벗어나야 할 때를 아는 것도 실력이다.
도구에 갇히면 안 된다.

## ORM을 잘 쓰는 팀의 특징

fetch join 전략이 문서화되어 있다.
어떤 API에서 어떤 연관관계를 join으로 가져올지 정해져 있다.
Projection DTO를 적극적으로 쓴다.
엔티티 전체를 반환하지 않고 필요한 필드만 담는다.
쿼리 로그를 상시 모니터링한다.
N+1이 발생하면 코드 리뷰에서 잡는다.
벌크 연산은 네이티브 쿼리로 분리한다.
ORM의 한계를 인정한다.
이런 팀은 ORM을 도구로 쓴다. 도구에 끌려다니지 않는다.

## MyBatis라는 대안

한국에서 MyBatis 점유율이 높은 데는 이유가 있다.
SQL을 직접 쓴다. 쿼리가 눈에 보인다. DBA가 리뷰할 수 있다. 매핑은 자동화한다. ResultSet을 객체로 변환하는 반복 코드를 줄여준다.
하지만 SQL 자체는 개발자가 통제한다. JPA처럼 객체 그래프를 자동 탐색하지 않는다.
그래서 N+1 같은 사고가 구조적으로 발생하기 어렵다.
트레이드오프는 있다. SQL을 직접 관리해야 하니 코드량이 늘어난다.
하지만 DB에 뭘 보내는지 항상 알 수 있다.

## DBA 관점에서의 정리

[쿼리 로그]
쿼리 로그를 반드시 켜라.
DB에 뭘 보내는지 모르면서 ORM을 쓰는 건 눈 감고 운전하는 것과 같다.

[N+1]
N+1을 방치하지 마라.
목록 조회 하나에 쿼리가 수백 개 나가면 DB는 버틸 수 없다.

[SELECT *]
`SELECT *`를 의심하라.
필요한 컬럼이 두 개인데 서른 개를 가져오는 건 낭비다.

[벌크 연산]
벌크 연산은 네이티브로 하라. 1000건을 하나씩 UPDATE 하는 건 ORM의 한계이자 개발자의 책임이다.

[SQL 이해]
ORM을 쓰되 SQL을 알아야 한다.
도구의 출력물을 읽지 못하면 도구를 쓰는 게 아니라 도구에 쓰이는 것이다.
ORM은 도구다. SQL을 모르는 사람이 쓰면 흉기가 된다.

## SQL과 ORM의 책임 경계

개발자가 SQL을 직접 쓰는 시대는 지났다고 말한다.
JPA, SQLAlchemy, Prisma, TypeORM. ORM이 다 해준다.
근데 DBA한테 날아오는 슬로우 쿼리를 보면 대부분 ORM이 만든 쿼리다.
`SELECT *`에 N+1에 불필요한 JOIN에 서브쿼리가 서브쿼리를 부른다.
ORM이 문제가 아니다. ORM이 만드는 SQL을 모르는 게 문제다.
면접에서 "SQL을 직접 쓰세요, ORM을 쓰세요?"라고 물으면 둘 중 하나를 고르는 게 아니라 둘 다 안다는 걸 보여줘야 한다.

### ORM이 해결한 것

ORM이 등장한 이유는 명확하다.
SQL을 문자열로 조립하는 건 실수가 많고 유지보수가 힘들다.

```java
String sql = "SELECT * FROM users WHERE id = " + userId;
```

SQL 인젝션, 타입 불일치, 오타. 문자열 SQL은 컴파일 타임에 잡히지 않는다.
ORM은 이걸 해결했다.
객체로 매핑하고, 타입을 보장하고, SQL을 자동으로 생성한다.
개발 속도가 빨라졌다. 실수가 줄었다.
이건 진짜 장점이다.

### ORM이 숨기는 것

ORM은 SQL을 숨긴다.
숨기는 게 장점이자 문제다.

```python
users = User.objects.filter(age__gt=25).select_related('team')
```

이 한 줄이 어떤 SQL이 되는지 확인하지 않는 개발자가 많다.

```sql
SELECT users.*, team.*
FROM users
INNER JOIN team ON users.team_id = teaem._id
WHERE users.age > 25;
```

지금은 괜찮다.
users가 100만 건이 되고 team에 인덱스가 없으면 이 한 줄이 장애가 된다.
ORM이 숨긴 건 SQL이 아니라 성능의 책임이다.

### N+1 문제: ORM의 고전적 실수

ORM을 쓰면 거의 반드시 만나는 문제다.

```python
orders = Order.objects.all() # 쿼리 1번
for order in orders:
print(order+user.name) # 주문 수만큼 반복
```

주문이 100건이면 쿼리가 101번 나간다.
SQL로 직접 쓰면 JOIN 한 번이다.

```sql
SELECT o.*, u+name FROM orders o
JOIN users u ON o.user_id = u+id;
```

ORM에서도 해결할 수 있다. `select_related`, `prefetch_related` 등.
하지만 이걸 쓰려면 N+1이 뭔지 먼저 알아야 한다.

### Lazy Loading vs Eager Loading

N+1의 뿌리는 Lazy Loading이다.

[Lazy Loading]
연관 객체를 실제로 접근할 때 쿼리를 날린다.
메모리는 아끼지만 쿼리가 늘어난다.
대부분의 ORM이 기본값으로 쓴다.

[Eager Loading]
연관 객체를 처음부터 JOIN으로 가져온다.
쿼리는 줄지만 불필요한 데이터까지 읽을 수 있다.

정답은 없다.
"이 화면에서 연관 데이터를 쓰는가"에 따라 전략이 달라져야 한다.
문제는 전략 없이 기본값에 맡기는 것이다.
기본값은 대부분 Lazy다.
Lazy의 기본값이 N+1의 기본값이다.

### `SELECT *`의 비용

ORM은 기본적으로 모든 컬럼을 가져온다.
엔티티에 매핑된 필드 전체.

```java
User user = userRepository.findById(1L);
// SELECT * FROM users WHERE id = 1
```

이름만 필요한데 프로필 사진 BLOB까지 읽는다.
20개 컬럼 중 2개만 쓰는데 전부 전송된다.
커버링 인덱스를 탈 수 있던 쿼리가 `SELECT *` 때문에 테이블 lookup을 한다.
SQL이라면 필요한 컬럼만 쓴다.

```sql
SELECT name, email FROM users WHERE id = 1;
```

ORM에서도 프로젝션을 쓸 수 있다. DTO 프로젝션, `values()`, `only()`.
하지만 기본 동작이 아니다.

### ORM이 만드는 비효율적인 쿼리

ORM이 생성하는 SQL에서 DBA가 자주 보는 패턴들이 있다.

[불필요한 서브쿼리]
ORM이 조건을 중첩하면서 서브쿼리가 서브쿼리를 감싼다.
플래너가 최적화하기 어려운 구조가 된다.

[DISTINCT 남발]
JOIN이 잘못돼서 중복이 생기면 ORM이 DISTINCT를 붙여서 해결한다.
근본은 JOIN 구조가 틀린 것이다.

[ORDER BY + LIMIT 없는 전체 조회]
페이지네이션 없이 전체를 가져온 뒤 애플리케이션에서 자르는 패턴.
100만 건을 읽고 10건만 쓴다.

전부 SQL을 보면 바로 보이는 문제다.
ORM만 보면 안 보인다.

### SQL을 직접 쓰면 좋은 경우

ORM이 만능이 아닌 영역이 있다.

[복잡한 집계]
여러 테이블을 조인하고 GROUP BY, HAVING, 윈도우 함수를 쓰는 쿼리.
ORM으로 표현하면 코드가 SQL보다 길어진다.

[대량 배치 처리]
100만 건을 UPDATE할 때 ORM은 건건이 처리하려 한다.
SQL 한 줄이면 끝나는 일이다.

```sql
UPDATE orders SET status = 'EXPIRED'
WHERE created_at < '2025-01-01' AND status = 'PENDING';
```

[성능 크리티컬 쿼리]

밀리초가 중요한 쿼리는 SQL로 직접 쓰고 실행 계획을 확인해야 한다.
ORM이 어떤 SQL을 만들지 예측하는 것보다 직접 쓰는 게 확실하다.

### ORM을 쓰면 좋은 경우

반대로 ORM이 확실히 나은 영역도 있다.

[CRUD 중심 서비스]
단순 생성, 조회, 수정, 삭제.
이걸 매번 SQL로 쓰면 보일러플레이트가 넘친다. ORM의 본업이다.

[스키마 마이그레이션]
ORM의 마이그레이션 도구가 DDL 관리를 자동화해준다.
Django의 makemigrations, Alembic, Flyway.

[타입 안전성]
컴파일 타임에 쿼리 오류를 잡을 수 있다.
문자열 SQL은 런타임에 터진다.

[빠른 프로토타이핑]
비즈니스 로직에 집중해야 할 때 SQL 작성 시간을 절약해준다.

### 하이브리드가 정답이다

현실의 프로젝트는 ORM과 SQL을 섞어 쓴다.

- CRUD → ORM
- 복잡한 조회 → Native SQL 또는 QueryDSL
- 배치 처리 → 직접 SQL
- 리포트 → 직접 SQL

JPA에서도 `@Query`로 네이티브 SQL을 쓸 수 있다.
Django에서도 `raw()`나 `connection.cursor()`가 있다.
ORM 100%도, SQL 100%도 현실적이지 않다.
"이 쿼리는 ORM으로 충분한가, 직접 써야 하는가"를 판단할 수 있는 게 실력이다.

### ORM 쿼리를 반드시 확인하는 법

ORM을 쓰더라도 생성되는 SQL을 반드시 확인해야 한다.

[Django]

```python
print(queryset.query)
# 또는 settings.py에서
LOGGING = {'loggers': {'django.db.backends': ...}}
```

[JPA/Hibernate]

```yml
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

[SQLAlchemy]

```python
engine = create_engine(url, echo=True)
```

쿼리 로그를 켜고 개발하라.
느린 건 프로덕션에서 발견하지 말고 개발 환경에서 잡아라.

### 면접에서 이 질문이 나오면

"SQL을 직접 쓰세요, ORM을 쓰세요?"

[감점 답변]
"ORM만 씁니다. 편하니까요."
→ SQL을 모르는 것으로 판단된다.
"SQL만 씁니다. ORM은 느리니까요."
→ 생산성을 포기하는 것으로 판단된다.

[득점 답변]
"CRUD는 ORM, 복잡한 쿼리는 SQL로 씁니다.
ORM이 만드는 쿼리를 항상 확인하고 N+1이나 불필요한 풀스캔이 있으면 네이티브 쿼리로 전환합니다."

도구를 고르는 게 아니라 상황에 따라 판단한다는 것을 보여줘라.

### DBA가 개발자에게 바라는 것

DBA 입장에서 말하면 ORM을 쓰든 SQL을 쓰든 상관없다.
다만 한 가지. 프로덕션에 나가는 쿼리가 뭔지는 알아달라.
슬로우 쿼리가 잡혔을 때 "그거 ORM이 만든 거라 잘 모르겠어요"가 가장 힘든 대답이다.
EXPLAIN을 찍어보고 인덱스를 확인하고 실행 계획을 읽을 줄 알면 ORM이든 SQL이든 문제없다.
도구는 도구일 뿐이다.
책임은 쿼리를 쓴 사람에게 있다.

### 마무리

ORM은 좋은 도구다. SQL도 좋은 도구다.
문제는 도구가 아니라 도구 뒤에서 일어나는 일을 모르는 것이다.
ORM이 만든 쿼리를 읽을 수 있는가.
그 쿼리의 실행 계획을 이해하는가.
느릴 때 직접 SQL로 대체할 수 있는가.
이 세 가지에 "네"라고 답할 수 있으면 ORM을 써도 된다.
아니라면 SQL부터 배워라.
편한 건 좋은 것이다.
편한 게 뭘 하는지 아는 것이 더 좋은 것이다.
