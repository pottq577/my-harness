# 커넥션 풀이 필요한 진짜 이유: HikariCP, pgBouncer, 그리고 적정 사이즈

"DB 커넥션 풀 사이즈 얼마로 하면 돼요?" 가장 자주 받는 질문 중 하나다.
그런데 왜 풀이 필요한지부터 물어보는 사람은 거의 없다.
커넥션 하나 여는 데 무슨 일이 벌어지는지 모르면 적정 사이즈도, 장애 원인도, 튜닝 방향도 모른다.

## 커넥션 하나를 여는 데 무슨 일이 벌어지나

애플리케이션이 DB에 연결하려면 네트워크부터 인증까지 여러 단계를 거친다.

1. TCP 3-way handshake로 소켓을 연다.
2. SSL/TLS가 켜져 있으면 추가 왕복이 생긴다.
3. DB 서버가 인증 요청을 처리한다.

MySQL은 스레드를 할당하고, PostgreSQL은 프로세스를 fork한다.
세션 변수, 타임존, charset을 초기화한다.
커넥션 하나 여는 건 전화기를 들고 상대가 받을 때까지 기다리는 것과 같다.
매 쿼리마다 이걸 반복하면 어떻게 될까.

## 커넥션 생성의 비용

- MySQL은 스레드 기반이다.
  - 커넥션 하나당 OS 스레드 하나가 붙는다.
  - 스레드 생성 자체는 빠르지만 인증과 초기화까지 합치면 수 밀리초가 걸린다.
- PostgreSQL은 프로세스 기반이다.
  - `fork()` 시스템 콜로 새 프로세스를 만든다.
  - 프로세스 생성은 스레드보다 무겁다.
  - 공식 문서에서도 connection 비용을 경고한다.

숫자 자체보다 중요한 건 빈도다.
초당 수천 요청이 들어오는 서비스에서 매번 커넥션을 만들고 끊으면 DB CPU의 상당 부분이 커넥션 관리에 소비된다.

## 커넥션 풀이 존재하는 이유

답은 간단하다. 비싼 걸 미리 만들어두고 돌려쓰자.
커넥션을 매번 만들지 않고 미리 만들어둔 커넥션을 빌려 쓰고 돌려준다.
TCP handshake, 인증, 프로세스 생성을 부팅 시 한 번만 치르는 것이다.
DB 입장에서도 좋다.
동시 커넥션 수가 예측 가능해지고 프로세스/스레드 생성과 소멸의 진동이 사라진다.
안정적인 부하 패턴이 성능의 기본이다.

## 커넥션 풀의 동작 원리

풀은 세 가지 동작으로 구성된다.

[초기화]
애플리케이션이 뜰 때 최소 개수만큼 커넥션을 미리 연다.
이걸 minimum idle이라 부른다.

[대여]
쿼리를 실행할 때 풀에서 유휴 커넥션을 하나 꺼낸다.
없으면 새로 만들거나, 최대치면 대기한다.

[반납]
쿼리가 끝나면 커넥션을 끊지 않고 풀에 돌려놓는다.
다음 요청이 재사용한다.
도서관의 대출과 반납과 같다.
책을 읽을 때마다 사지 않고 빌려 쓰고 돌려놓는 것이다.

## HikariCP: Java 생태계의 표준

Spring Boot의 기본 커넥션 풀이다.
왜 HikariCP가 살아남았을까.

[ConcurrentBag]
락 없이 커넥션의 대여와 반납을 처리하는 자료구조다.
ThreadLocal 캐시로 같은 스레드가 쓰던 커넥션을 우선 재사용한다.
CPU 캐시 히트율이 올라간다.

[바이트코드 최소화]
풀 내부 코드가 극도로 짧다.
JIT 컴파일러가 인라인하기 좋은 크기로 설계됐다.

[빠른 실패]
커넥션을 못 빌리면 길게 기다리지 않는다.
기본 connectionTimeout이 30초다.
장애 전파를 끊는 설계다.

## pgBouncer: PostgreSQL 앞단의 프록시

PostgreSQL의 fork 비용은 크다. 그래서 DB 앞에 프록시를 놓는다.
pgBouncer가 그 역할을 한다.
애플리케이션은 pgBouncer에 연결하고 pgBouncer가 실제 PostgreSQL 커넥션을 관리한다.
수천 클라이언트가 붙어도 실제 DB 커넥션은 수십 개만 유지할 수 있다.
세 가지 모드가 있다.

[Session mode]
클라이언트가 끊을 때까지 커넥션을 점유한다.
풀링 효과가 가장 낮다.

[Transaction mode]
트랜잭션이 끝나면 커넥션을 반납한다.
가장 널리 쓰이는 모드다.

[Statement mode]
쿼리 하나마다 커넥션을 반납한다.
multi-statement 트랜잭션을 못 쓴다.

## 풀 사이즈 공식

PostgreSQL wiki에 유명한 공식이 있다.

$\mathrm{connections} = (2 \times \mathrm{core\_count}) + \mathrm{effective\_spindle\_count}$

4코어 서버에 SSD 1개라면 `(4 * 2) + 1 = 9`개다.
직관과 다르다.
"커넥션이 많을수록 빠르지 않나?"
아니다.
DB는 CPU 코어 수만큼만 동시에 일할 수 있다.
그 이상은 대기열에 쌓이고 컨텍스트 스위칭만 늘어난다.
이 공식은 출발점이다.
워크로드에 따라 조정이 필요하지만 방향은 명확하다. 적을수록 빠르다.

## 커넥션이 너무 많으면

MySQL의 max_connections 기본값은 151이다.
이걸 500, 1000으로 올리는 팀이 많다.

[메모리 폭발]
커넥션 하나당 스레드 스택, sort buffer, join buffer, read buffer가 할당된다.
커넥션 수에 비례해서 메모리가 늘어난다.

[컨텍스트 스위칭]
CPU 코어보다 스레드가 많으면 OS가 끊임없이 스레드를 교체한다.
실제 일하는 시간보다 전환 비용이 커진다.

[락 경합]
동시에 같은 행을 건드리는 트랜잭션이 늘면 대기 시간이 기하급수적으로 증가한다.

max_connections를 올리는 건 해결이 아니다.
도로가 좁은데 차를 더 넣는 것과 같다.

## 커넥션이 너무 적으면

애플리케이션 스레드가 커넥션을 못 빌리면 대기열에 쌓인다.
HikariCP의 connectionTimeout이 지나면 예외가 터진다.
한 서비스의 지연이 다른 서비스로 전파된다.
MSA에서 이게 cascading failure의 시작이다.
풀 사이즈가 3인데 한 트랜잭션이 느린 쿼리로 10초를 잡으면 나머지 2개로 전체 트래픽을 감당해야 한다.
금방 고갈된다.
적정 사이즈는 "평균"이 아니라 "피크 시 느린 쿼리가 몇 개나 동시에 뜨는가"로 결정해야 한다.

## 커넥션 누수: 돌아오지 않는 커넥션

풀에서 빌려간 커넥션이 반납되지 않는 것.
이걸 커넥션 누수라 한다.
흔한 원인은 예외 처리 누락이다.

```sql
-- 이런 코드가 문제다
conn = pool.getConnection()
result = conn.execute("SELECT ...")
conn.close() -- 예외 발생 시 여기까지 안 온다
```

HikariCP는 leakDetectionThreshold를 제공한다.
빌려간 지 N초가 지나도 안 돌아오면 경고 로그를 남긴다.
기본값은 0(비활성)이다.
운영 환경에서는 반드시 켜야 한다.
DBA 입장에서 보면 `SHOW PROCESSLIST`에 Sleep 상태가 쌓여 있고 앱은 "커넥션 부족"을 외치는 상황이 바로 누수다.

## wait_timeout과 커넥션 수명

DB 쪽에서도 유휴 커넥션을 정리한다.
MySQL의 wait_timeout 기본값은 28800초(8시간)다.
이 시간 동안 아무 쿼리도 안 오면 서버가 끊는다.
문제는 풀이 이걸 모른다는 것이다.
풀은 커넥션이 살아 있다고 믿지만 서버는 이미 끊었다.
다음 쿼리에서 "MySQL server has gone away"가 뜬다.
그래서 풀에도 수명 설정이 있다.

[maxLifetime]
HikariCP 기본값은 30분이다.
이 시간이 지나면 커넥션을 폐기하고 새로 만든다.
반드시 DB의 wait_timeout보다 짧아야 한다.

[validationQuery]
빌려주기 전에 살아 있는지 확인하는 쿼리다.
`SELECT 1`이 대표적이다.

## Serverless의 커넥션 폭발

Lambda 같은 서버리스 환경에서는 인스턴스가 동시에 수백 개 뜬다.
각 인스턴스가 커넥션 풀을 따로 만든다.
`100개 인스턴스 x 풀 사이즈 10 = 커넥션 1000개`.
cold start가 몰리면 순간적으로 폭발한다.
DB는 max_connections를 넘기고 죽는다.
AWS RDS Proxy가 이 문제를 풀기 위해 나왔다.
Lambda와 DB 사이에 프록시를 두고 실제 DB 커넥션 수를 제어한다.
pgBouncer의 클라우드 관리형 버전이라 보면 된다.
서버리스에서 DB를 쓸 거라면 커넥션 관리 전략이 아키텍처의 핵심이다.

## DBA 관점에서의 정리

커넥션은 공짜가 아니다.
TCP, 인증, 프로세스 생성. 매번 치르기엔 너무 비싸서 풀이 생겼다.
풀 사이즈는 크면 좋은 게 아니다.
CPU 코어 수 기반으로 시작하고 모니터링으로 조정하는 게 정석이다.
HikariCP는 애플리케이션 레벨, pgBouncer는 DB 앞단 프록시 레벨.
둘은 경쟁이 아니라 레이어가 다르다.
운영에서 가장 무서운 건 누수다.
Sleep 커넥션이 쌓이는데 앱은 풀 부족을 호소하면 코드의 finally 블록부터 의심하라.

## 마무리

"풀 사이즈 얼마요?"에 답하려면 커넥션 하나가 얼마나 비싼지, DB가 동시에 몇 개를 감당하는지, 장애 시 어디서 터지는지를 알아야 한다.
숫자 하나 정하는 문제가 아니다.
시스템 전체를 이해하는 문제다.
