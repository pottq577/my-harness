# 마이크로서비스 전환이 DB에 주는 영향: 모놀리스를 쪼개면 JOIN이 사라진다

"서비스를 분리하면 독립적으로 배포할 수 있어요." 맞다.
그런데 DB도 분리해야 한다는 말은 그 뒤에 나온다.
모놀리스에서는 하나의 DB에 모든 테이블이 있었다.
주문과 사용자를 JOIN 한 줄이면 됐다.
서비스를 쪼개는 순간 그 JOIN이 사라진다.
데이터는 물리적으로 분리되고 정합성은 자동으로 보장되지 않는다.
모놀리스의 편안함은 DB가 하나였기 때문에 가능했던 것이다.
JOIN을 API 호출로 바꾸면 지연과 실패가 들어온다.
분산 트랜잭션은 구현할 수는 있지만 운영하기 어렵다.
Shared Database는 분리한 의미를 없앤다.
데이터 중복을 허용하되 동기화 전략을 세워라.
DB 분리는 코드 분리보다 훨씬 어렵다.

## JOIN 한 줄이 API 두 번이 된다

모놀리스에서는 이렇게 했다.

```sql
SELECT o.order_id, u.user_name, o.amount
FROM orders o
JOIN users u ON o.user_id = u.user_id
WHERE o.order_id = 12345
```

주문 서비스와 사용자 서비스를 분리하면 이 JOIN은 불가능해진다.
orders는 주문 DB에, users는 사용자 DB에 있다.
주문 서비스가 사용자 이름을 보여주려면 사용자 서비스에 API를 호출해야 한다.
1ms짜리 JOIN이 50ms짜리 HTTP 호출이 된다.
주문 목록을 20건 보여주는데 사용자 정보를 20번 호출하면 1초다.
N+1 문제가 DB 안이 아니라 서비스 사이에서 생긴다.

## 정합성이 자동으로 깨진다

모놀리스에서는 하나의 트랜잭션이면 됐다.

```sql
BEGIN;
INSERT INTO orders (...) VALUES (...);
UPDATE inventory SET stock = stock - 1 WHERE ...;
COMMIT;
```

주문과 재고가 같은 DB에 있으니까 둘 다 성공하거나 둘 다 실패한다.
서비스를 분리하면 주문 DB와 재고 DB가 다르다.
주문은 생성됐는데 재고 차감이 실패하면?
한쪽만 커밋된 상태가 된다.
외래 키 제약도 없다.
주문이 참조하는 사용자가 삭제돼도 DB가 막아주지 않는다.
FK가 DB 경계를 넘지 못하기 때문이다.

## 분산 트랜잭션이라는 환상

2PC(Two-Phase Commit)로 풀 수 있지 않을까. 이론적으로는 가능하다.
Coordinator가 모든 참여자에게 prepare를 보내고 전부 OK하면 commit을 보낸다.
하나라도 실패하면 전부 rollback.
문제는 현실이다.
prepare와 commit 사이에 네트워크가 끊기면 참여자가 결정을 내리지 못한 채 lock을 잡고 기다린다.
이걸 in-doubt 트랜잭션이라 한다.
응답 시간이 느려진다.
참여 서비스가 늘어날수록 실패 확률도 올라간다.
MSA에서 2PC를 쓰는 팀은 거의 없다.
비용이 너무 크다.

## Saga라는 현실적 대안

2PC 대신 Saga 패턴을 쓴다.
각 서비스가 로컬 트랜잭션을 실행하고 실패하면 보상 트랜잭션으로 되돌린다.
주문 생성 → 재고 차감 → 결제 승인.
결제가 실패하면? 재고를 복구하고 주문을 취소한다.
깔끔해 보이지만 보상 트랜잭션을 만드는 건 쉽지 않다.
"재고를 원복한다"가 항상 가능하지는 않다.
이미 다른 사용자가 그 재고를 가져갔을 수 있다.
중간 상태가 보인다는 것도 문제다.
주문은 생겼는데 결제 전이라 사용자에게 "처리 중"을 보여줘야 한다.
모놀리스에서는 없던 상태다.

## Shared Database의 유혹

"DB는 그냥 하나로 두면 안 되나?"
서비스는 분리하되 DB는 공유하는 패턴이다.
JOIN도 되고 트랜잭션도 된다.
그런데 이러면 분리한 의미가 사라진다.
주문 서비스가 스키마를 바꾸면 사용자 서비스가 깨진다.
배포 독립성이 없다.
테이블에 컬럼을 추가하려면 모든 서비스 팀에 확인해야 한다.
모놀리스 때와 다를 게 없다.
Shared Database는 마이그레이션 중간 단계다.
최종 목표가 아니다.
여기에 머물면 모놀리스의 단점과 마이크로서비스의 복잡성을 동시에 갖게 된다.

## 데이터 중복을 허용한다는 것

Database per Service로 가면 각 서비스가 필요한 데이터를 복제해서 갖는다.
주문 서비스가 사용자 이름을 보여줘야 하면 주문 DB에 user_name 컬럼을 둔다.
사용자 서비스에서 이름이 바뀌면 이벤트를 발행하고 주문 서비스가 갱신한다.
데이터가 중복된다. 정규화의 반대다.
RDB를 배울 때 가장 먼저 배운 "중복을 제거하라"를 의도적으로 어기는 것이다.
그 대가로 API 호출이 사라지고 각 서비스가 자기 DB만으로 응답할 수 있다.
다만 이벤트가 지연되면 주문에 옛 이름이 보인다.
이걸 Eventually Consistent라 한다.
"결국은 맞아지지만 지금은 아닐 수 있다."

## 이벤트 기반 동기화의 비용

중복 데이터를 맞추려면 이벤트 파이프라인이 필요하다.
Kafka나 SNS 같은 메시지 브로커를 두고 변경이 생기면 이벤트를 발행한다.
각 서비스는 이벤트를 구독해서 자기 DB를 갱신한다.
여기에 실패 시나리오가 생긴다.
이벤트 발행은 됐는데 소비가 안 됐다면?
이벤트를 두 번 받으면?
순서가 뒤바뀌면?
재시도, 멱등성, 순서 보장.
모놀리스에서는 필요 없던 것들이 인프라 요구사항으로 들어온다.
DB 하나를 쪼개는 순간 메시지 브로커가 인프라에 추가되고 운영해야 할 시스템이 하나 더 늘어난다.

## DBA 관점에서의 정리

모놀리스에서 MSA로 전환한다는 건 코드를 나누는 것이 아니라 데이터를 나누는 것이다.
JOIN을 API 호출로 바꾸면 지연과 실패가 들어온다.
분산 트랜잭션은 구현할 수는 있지만 운영하기 어렵다.
Shared Database는 분리한 의미를 없앤다.
데이터 중복을 허용하되 동기화 전략을 세워라.
DB 분리는 코드 분리보다 훨씬 어렵다.
서비스가 10개면 DB도 10개다. 모니터링도 10배, 백업도 10배, 장애 포인트도 10배.
DBA 입장에서 MSA 전환은 관리할 DB가 늘어나는 것이 아니라 데이터의 정합성을 보장하는 방식 자체가 바뀌는 것이다.
모놀리스에서는 DB가 정합성을 보장했다.
MSA에서는 사람이 설계해야 한다.
