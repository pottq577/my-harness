# 결제와 DB: 1원이 틀리면 안 되는 세계

"결제 데이터인데, 그냥 숫자 컬럼에 넣으면 안 되나요?"
금액을 저장하고 상태를 바꾸고 내역을 남긴다.
다른 서비스와 다를 게 없어 보인다.
그런데 1원이 틀리면 회계가 안 맞고 한 건이 중복되면 고객이 두 번 결제한다.
결제 DB는 빠를 필요는 없다. 대신 틀리면 안 된다. 한 건도, 1원도.

- 금액은 DECIMAL이다. float는 쓰지 마라.
- 상태 전이는 DB 제약으로 막아라.
- 중복 결제는 멱등 키로 차단하라.
- PG사 불일치는 대사 배치로 잡아라.
- 결제 데이터는 삭제할 수 없다.

## `0.1 + 0.2`는 0.3이 아니다

프로그래밍에서 float의 함정은 유명하다.
결제에서는 이게 사고가 된다.

```sql
SELECT 0.1 + 0.2
-- 0.30000000000000004
```

1000원짜리 상품에 10% 할인.
float로 계산하면 899.9999999원. 소수점을 버리면 899원. 반올림하면 900원.
1원 차이가 정산에서 수천 건 쌓이면 회계 감사에 걸린다.
금액은 DECIMAL이다. `DECIMAL(12,2)`면 소수점 둘째 자리까지 정확하다.
float는 빠르지만 돈에는 쓰면 안 된다.

## 결제 상태라는 상태 머신

결제에는 단계가 있다.
`대기 → 승인 → 완료`. 여기까지는 단순하다.
취소가 생기면 갈래가 생긴다.
`완료 → 취소 요청 → 취소 완료`. `부분 취소면 완료 → 부분 취소`.
환불이 들어오면 더 복잡해진다.
취소와 환불은 다르다. 취소는 결제를 되돌리는 것이고 환불은 이미 정산된 돈을 돌려주는 것이다.
상태 전이에는 규칙이 있다.
"대기"에서 "환불"로 직접 갈 수 없다.
DB에 CHECK 제약이나 트리거로 허용되지 않는 전이를 막아야 한다.
코드에서만 막으면 버그 한 줄로 뚫린다.

## 같은 요청이 두 번 오면

네트워크가 불안정하다.
사용자가 결제 버튼을 두 번 누른다. 혹은 타임아웃 후 재시도한다.
같은 주문에 대해 결제 요청이 두 번 온다. 두 번 다 처리하면 이중 결제다.
멱등성이 필요하다.
요청마다 고유한 idempotency_key를 발급하고 이미 처리된 key면 이전 결과를 그대로 반환한다.

```sql
INSERT INTO payments
(idempotency_key, amount, status)
VALUES
('ord-123-pay-1', 15000, 'pending')
ON DUPLICATE KEY UPDATE
idempotency_key = idempotency_key
```

유니크 제약이 두 번째 INSERT를 막는다.
멱등성은 DB 레벨에서 보장하는 것이 가장 확실하다.

## PG사 콜백과 트랜잭션의 타이밍

결제를 PG사에 요청한다. PG사가 승인한다. 콜백으로 결과를 보내준다.
그 사이에 우리 서버가 재시작됐다면?
PG사는 승인했는데 우리 DB에는 대기 상태 그대로다.
돈은 빠졌는데 주문은 실패다.
결제 요청 전에 "시도" 레코드를 먼저 만들고 콜백이 오면 상태를 갱신한다.
콜백이 안 오면 주기적으로 PG사에 조회한다. 이걸 reconciliation이라 한다.
DB에 "확인 안 된 결제" 목록이 항상 있어야 하고 배치가 주기적으로 정리해야 한다.

## 정산은 왜 실시간이 아닌가

오늘 판매한 금액을 실시간으로 보고 싶다.
SUM 하나면 될 것 같다.

```sql
SELECT SUM(amount) FROM payments
WHERE status = 'completed'
AND created_at >= '2026-08-01'
```

결제 건이 하루 100만 건이면 매번 100만 건을 집계한다. 인덱스를 타도 느리다.
그래서 정산은 배치다.
하루에 한 번, 일별 집계 테이블에 결과를 넣는다.
실시간 조회는 집계 테이블에서 읽는다.
원본과 집계 사이에 차이가 생기면?
그래서 정산 배치 후에 원본과 집계를 대조하는 검증 배치가 또 돈다.

## 부분 환불이 시작되면

주문 금액 30,000원. 상품 A 10,000원을 환불한다.
원래 결제 건과 환불 건은 어떻게 연결되는가.
환불 테이블이 따로 필요하다.
원결제 ID를 참조하고 환불 금액과 사유를 기록한다.
두 번째 부분 환불이 들어오면 총 환불 금액이 원결제를 초과하면 안 된다.

```sql
SELECT SUM(refund_amount) FROM refunds
WHERE original_payment_id = 101
```

이 `합계 + 신규 환불 ≤ 원결제 금액`. 이 검증을 코드에서만 하면 동시 요청에 뚫린다.
`SELECT FOR UPDATE`로 원결제 행을 잠가야 한다.

## 금융 감사와 데이터 보존

일반 서비스는 오래된 데이터를 지울 수 있다. 결제 데이터는 못 지운다.
전자금융거래법. 5년 보존 의무. 거래 기록, 접속 기록, 오류 기록.
5년치 결제 데이터가 하나의 테이블에 있으면 성능이 점점 나빠진다.
파티셔닝으로 연도별 분리하거나 아카이브 테이블로 이관하되 원본은 삭제하지 않는다.
삭제할 수 없다는 제약이 DB 설계를 처음부터 다르게 만든다.
결제 테이블은 커질 수밖에 없다는 전제로 시작해야 한다.

결제 DB는 특별하다.
빠르지 않아도 되지만 정확해야 한다.
금액은 DECIMAL이다. float는 쓰지 마라.
상태 전이는 DB 제약으로 막아라.
중복 결제는 멱등 키로 차단하라.

결제 데이터는 삭제할 수 없다.
