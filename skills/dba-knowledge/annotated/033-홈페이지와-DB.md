# 홈페이지와 DB: 간단해 보이는 것이 복잡해지는 순간

"홈페이지 하나 만들건데 DB는 뭘 챙겨야 해요?"
게시판, 로그인, 검색. 셋 다 쉬워 보인다.
그런데 서비스가 커지면 가장 먼저 터지는 곳이 DB다.
쉽다고 생각한 순간부터 챙겨야 할 것들이 쌓이기 시작한다.
처음부터 챙겨야 할 건 정해져 있다.
읽기와 쓰기를 분리할 것.
검색은 DB 밖으로 뺄 것.
세션은 Redis에 둘 것.
커넥션 수를 계산할 것.
조회수 같은 고빈도 UPDATE는 버퍼를 둘 것.

## 읽기가 대부분이라는 착각

홈페이지는 읽기 위주라고 생각한다. 맞다. 대부분 SELECT다.
그런데 눈에 안 보이는 쓰기가 있다.
페이지를 열면 조회수가 올라간다. 로그인하면 세션이 저장된다. 검색하면 검색 로그가 쌓인다.
사용자 한 명이 한 번 방문할 때 읽기 3건, 쓰기 3건.
읽기 위주라는 말은 비율이다. 쓰기가 없다는 뜻이 아니다.
쓰기는 적어도 무거울 수 있다.

## 검색이 DB를 죽이는 순간

검색창을 넣는 건 쉽다. LIKE에 %를 붙이면 된다.
데이터가 1만 건이면 괜찮다. 100만 건이 되면 풀 테이블 스캔이다.
LIKE 앞에 %가 붙으면 인덱스를 탈 수 없다. 매번 전체를 뒤진다.
검색 한 번에 CPU가 치솟고 다른 쿼리가 밀린다.
사용자는 느려진 걸 느끼고 다시 검색을 누른다.
악순환이 시작된다.
검색은 기능이 아니라 설계 결정이다.
전문 검색 엔진을 따로 둘지, Full-Text Index를 쓸지, 처음부터 정해야 한다.

## 관리자 페이지의 무게

사용자 페이지는 신경을 쓴다. 인덱스도 타게 하고 페이징도 넣는다.
관리자 페이지는 안 그렇다.
"전체 주문 목록 조회."
"이번 달 가입자 통계."
"상품 전체 엑셀 다운로드."
건수 제한 없이 전체를 가져온다.
정렬도 넣고 필터도 넣고 조인도 세 개씩 걸린다.
관리자는 한 명인데 그 한 명의 쿼리가 사용자 천 명 분의 부하를 만든다.
관리자 페이지는 반드시 Reader에서 읽게 하거나 별도 커넥션으로 분리해야 한다.

## 세션을 DB에 넣으면 생기는 일

로그인 유지를 위해 세션을 DB에 저장하는 경우가 많다. 사용자가 1000명이면 문제없다.
10만 명이 되면 매 요청마다 세션 테이블을 SELECT한다.
세션은 짧다. 30분이면 만료된다.
그런데 만료된 세션을 안 지우면 테이블이 끝없이 커진다.
100만 건의 만료된 세션 사이에서 유효한 세션 하나를 찾는다.
인덱스가 없으면 재앙이다.
세션은 DB보다 Redis가 낫다.
TTL로 자동 만료되고 메모리 기반이라 빠르다.
DB에는 영구 보관할 데이터만 넣어야 한다.

## 조회수 카운터의 함정

게시글 조회수. 글을 열 때마다 +1.

```sql
UPDATE posts
SET view_count = view_count + 1
WHERE post_id = 12345
```

100명이 동시에 같은 글을 열면 같은 행에 UPDATE 100건이 몰린다.
row lock 경합이 시작된다. 인기 글일수록 심하다.
트래픽이 많은 글이 DB를 가장 괴롭힌다.
조회수는 실시간일 필요가 없다.
Redis에 먼저 쌓고 주기적으로 DB에 반영하면 100건이 1건으로 줄어든다.

## 파일은 밖에 있지만 메타는 안에 있다

이미지를 DB에 넣는 사람은 이제 거의 없다. S3에 올린다. 여기까진 맞다.
그런데 파일 이름, 크기, 업로드 시각, 썸네일 경로, 연결된 게시글 ID.
이 메타데이터는 전부 DB에 들어간다.
게시글은 삭제해도 이미지 메타데이터는 안 지우는 경우가 많다.
고아 레코드가 쌓인다.
몇 년 지나면 파일 테이블이 가장 큰 테이블이 된다.
업로드할 때 넣는 건 쉽다. 삭제할 때 같이 지우는 게 어렵다.
정기적으로 고아 레코드를 정리하는 배치가 필요하다.

## 커넥션, 얼마나 열 것인가

WAS를 띄우면 커넥션 풀이 생긴다. 기본값이 보통 10개에서 20개다.
WAS가 하나면 20개. 세 대면 60개. 오토스케일링으로 열 대가 되면 200개.
DB의 max_connections는 유한하다.
평소에는 여유롭다. 배포하거나 스케일링이 터지면 순간 폭발한다.
새 WAS가 뜨면서 풀을 한꺼번에 열고 이전 WAS가 꺼지면서 풀을 반환한다.
겹치는 구간이 위험하다.
커넥션 풀 크기는 WAS 최대 대수 곱하기 풀 크기가 DB 한계의 80%를 넘지 않게 잡아야 한다.

## 갑자기 트래픽이 늘 때

홈페이지는 예측 불가능하다.
기사 하나 나가면 트래픽이 10배 뛴다.
SNS에 공유되면 한 시간 만에 평소의 50배가 온다.
이때 DB가 버틸 수 있는지는 이미 결정돼 있다.
Reader가 없으면 Writer 하나가 전부 받는다.
캐시가 없으면 모든 요청이 DB까지 내려온다.
커넥션 풀이 작으면 대기열이 생기고 사용자는 빈 화면을 본다.
갑자기 늘어난 트래픽에 대비하는 방법은 하나다.
평소에 구조를 만들어두는 것이다.
Read Replica 하나. Redis 캐시 한 겹.
이 두 가지만 있어도 10배는 버틴다.

## DBA 관점에서의 정리

홈페이지는 모든 서비스의 시작이다. 단순해 보여서 DB를 대충 설계한다.
트래픽이 적을 때는 아무 문제 없다. 문제는 커진 다음에 터진다.
검색이 느려지고. 세션 테이블이 비대해지고. 관리자 한 명이 DB를 잡아먹고. 파일 메타데이터가 끝없이 쌓인다.
처음부터 챙겨야 할 건 정해져 있다.
읽기와 쓰기를 분리할 것.
검색은 DB 밖으로 뺄 것.
세션은 Redis에 둘 것.
커넥션 수를 계산할 것.
조회수 같은 고빈도 UPDATE는 버퍼를 둘 것.
나중에 고치려면 서비스를 멈춰야 한다.
처음에 챙기면 코드 몇 줄이다.
그 차이가 반년 뒤에 장애 보고서 한 장이 된다.
