# ID를 만든다는 것: AUTO_INCREMENT가 1, 2, 3이 아닌 이유

테이블에 row를 넣으면 ID가 1, 2, 3으로 붙는다.
당연한 것 같지만, 실제 프로덕션 테이블을 열어보면 `1, 2, 5, 8, 14, 27`.
"3번은 어디 갔나요? 데이터 유실인가요?"
개발자가 가장 자주 하는 질문이다. 유실이 아니다.

- AUTO_INCREMENT는 연속을 보장한 적이 없다.
- gap을 두려워하지 마라.
- UUID를 PK로 쓸 때는 순서를 확보하라.
- ID에 비즈니스 의미를 담지 마라.
- 순차 ID를 외부에 노출하지 마라.
- PK 설계는 테이블을 만들기 전에 끝내라.

ID는 단순해 보이지만 시스템의 뼈대다.

## 왜 ID에 빈 번호가 있는가

"3번 주문이 없어요. 데이터가 사라진 건가요?"
개발자가 DBA에게 가장 자주 묻는 질문이다.
답은 항상 같다. "사라진 게 아니라 처음부터 없었습니다."
AUTO_INCREMENT는 연속된 번호를 약속하지 않는다.
번호를 발급하되, 그 번호가 실제 row로 남을지는 보장하지 않는다.
빈 번호는 유실이 아니라 정상 동작의 흔적이다.

## AUTO_INCREMENT의 동작 원리

InnoDB는 메모리에 카운터를 유지한다.
INSERT가 들어오면 카운터를 1 올리고 그 값을 새 row에 부여한다.
핵심은 이것이다. 번호는 INSERT 시점에 소비된다.
INSERT가 성공했느냐는 별개의 문제다.
트랜잭션이 롤백되면?
row는 사라지지만 번호는 돌아오지 않는다.
이미 써버린 번호를 되돌리면 동시에 같은 번호를 받은 다른 트랜잭션과 충돌할 수 있기 때문이다.
카운터는 앞으로만 간다.

## gap이 생기는 이유

빈 번호가 생기는 경로는 여러 가지다.

[롤백]
INSERT 후 ROLLBACK하면 번호는 소비되고 row는 없다.

[INSERT IGNORE]
중복 키 충돌로 무시되어도 번호는 이미 올라갔다.

[REPLACE]
DELETE + INSERT이므로 새 번호가 발급된다.

[벌크 INSERT]
여러 row를 한 번에 넣으면 번호를 미리 예약한다.
일부가 실패하면 예약된 번호가 비어진다.

[서버 재시작]
MySQL 5.7까지는 카운터가 메모리에만 있었다.
재시작하면 MAX(id)+1로 재계산했고 중간에 삭제된 번호가 재사용될 수 있었다.
8.0부터 redo log에 기록하여 이 문제를 해결했다.

## 복제 환경에서의 충돌

Source가 두 개 이상인 환경에서 양쪽이 같은 번호를 발급하면 충돌한다.
MySQL은 이를 위해 두 개의 시스템 변수를 제공한다.

```sql
-- Source A
auto_increment_increment = 2
auto_increment_offset = 1
-- 1, 3, 5, 7 ...
-- Source B
auto_increment_increment = 2
auto_increment_offset = 2
-- 2, 4, 6, 8 ...
```

홀수/짝수로 나누어 절대 겹치지 않게 한다.
Source가 3개면 increment를 3으로 놓고 offset을 1, 2, 3으로 분배한다.
gap은 더 넓어지지만 충돌은 사라진다.

## INT의 한계와 BIGINT

AUTO_INCREMENT 타입이 INT면 최대 약 21억. UNSIGNED면 약 42억.
하루 100만 건이면 UNSIGNED INT는 약 11년이다.
한계에 도달하면 INSERT가 실패한다.
`Duplicate entry for key 'PRIMARY'` 에러 한 줄로 서비스가 멈춘다.
BIGINT는 약 922경이다. 사실상 무한.
INT에서 BIGINT로 바꾸는 건 고통스럽다.
ALTER TABLE이 락을 잡고 전체를 재구성한다.
새 테이블의 PK는 BIGINT로 시작하라.

## UUID: 무작위의 대가

AUTO_INCREMENT의 한계를 넘으려면 애플리케이션에서 ID를 만들면 된다.
UUID가 대표적이다.
충돌 확률은 사실상 0.
서버 간 조율 없이 어디서든 생성 가능.
글로벌 유니크.
하지만 대가가 있다. 36바이트 문자열.
BIGINT(8바이트)의 4.5배.
정렬 불가. 시간 순서가 없다.
인덱스 효율이 나쁘다.
UUID는 충돌 문제를 해결하지만 성능 문제를 만든다.

## UUID의 인덱스 문제

InnoDB의 PK는 클러스터드 인덱스다.
데이터가 PK 순서대로 물리적으로 저장된다.
순차 ID면 새 row는 항상 끝에 붙는다.
B-Tree의 맨 오른쪽 리프에만 쓰기가 발생한다.

랜덤 UUID는 다르다.
새 row가 B-Tree의 아무 곳에나 들어간다.
이미 꽉 찬 페이지에 끼어들면 페이지 분할(page split)이 발생한다.
한 페이지를 둘로 쪼개고 데이터를 재배치한다.
페이지 분할은 쓰기 증폭이다.
단편화가 누적되면 읽기도 느려진다.
INSERT 속도가 테이블 크기에 비례해 급격히 떨어지는 이유다.

## UUIDv7과 ULID

UUID의 인덱스 문제를 해결하려면 순서가 있으면 된다.
UUIDv7은 앞 48비트에 밀리초 타임스탬프를 넣는다.
시간 순서대로 정렬된다.
B-Tree 끝에 순차 삽입이 가능하다.
ULID도 같은 아이디어다.
타임스탬프 + 랜덤으로 구성된다.
Crockford Base32 인코딩이라 문자열 정렬도 된다.
UUIDv7은 2024년 RFC 9562로 표준이 됐다.
신규 시스템에 UUID를 쓸 거면 v7을 쓰는 게 맞다.

## Snowflake ID

Twitter가 2010년에 만든 분산 ID 체계다.
64비트 BIGINT 하나에 세 가지 정보를 담는다.

| 1 bit  | 41 bit     | 10 bit  | 12 bit |
| ------ | ---------- | ------- | ------ |
| 미사용 | 타임스탬프 | 머신 ID | 시퀀스 |

41비트 타임스탬프는 약 69년.
10비트 머신 ID는 1,024대.
12비트 시퀀스는 밀리초당 4,096개.
BIGINT에 담기니까 인덱스 효율이 좋다.
시간 순서가 있어 정렬도 된다.
Discord, Instagram도 같은 구조를 쓴다.
단점은 시계 동기화(NTP)에 의존한다는 것.
시계가 뒤로 가면 중복 위험이 있다.
대부분의 구현체는 시계 후퇴 시 대기하는 방어 로직을 넣는다.

## ID로 정보가 유출된다

순차 ID를 외부에 노출하면 의도하지 않은 정보를 준다.
주문 ID가 100,000이라면 "이 서비스는 지금까지 10만 건 주문이 들어왔구나."
오늘 아침에 100,000이었고 저녁에 100,500이라면 "하루 주문이 500건이구나."
경쟁사가 매일 한 번 주문해보면 일별 성장률을 추적할 수 있다.
사용자 ID도 마찬가지다. 가입 순서, 총 사용자 수, 성장 속도.
순차 ID 하나로 전부 추정 가능하다.
외부 API에는 UUID나 난수 기반 ID를 쓰고 내부 PK는 따로 관리하는 게 안전하다.
