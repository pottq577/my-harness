# 락을 이해한다는 것: 데드락, 락 대기, 그리고 면접에서의 깊이

락의 종류를 아는 것과 락이 왜 문제가 되는지 아는 것은 다르다.
면접관이 "데드락이 뭔가요?"라고 물을 때 원형 대기를 설명하는 건 누구나 한다.
"그래서 운영에서 어떻게 대응하셨나요?"
이 질문에 답하려면 경험이 필요하다.
1,000개 클러스터를 운영하면서 배운 건 락 자체는 문제가 아니라는 것이다.
락이 풀리지 않을 때가 문제다.

## 락이 문제가 되는 순간

락은 데이터를 보호하는 장치다. 없으면 동시 접근이 데이터를 깨뜨린다.
그런데 보호하는 도구가 막는 도구가 되는 순간이 있다.
트랜잭션이 길어질 때, 순서가 꼬일 때, 인덱스가 없을 때.
락은 존재 자체가 아니라 해제되지 않는 상태가 문제다.
자물쇠는 잠그는 게 목적이지만 열쇠를 잃어버리면 재앙이 된다.

## Shared Lock과 Exclusive Lock의 충돌

1. S Lock은 "나 읽고 있어."
2. X Lock은 "나 쓰고 있어."
3. S끼리는 공존한다.
4. S와 X는 충돌한다.
5. X끼리도 충돌한다.

읽기는 서로를 막지 않지만 쓰기는 모든 것을 막는다.
이 비대칭이 락 문제의 출발점이다.
면접에서 이걸 물으면 호환성 매트릭스를 그릴 수 있어야 한다.
S-S는 OK, S-X는 Block, X-X는 Block.
단순하지만 이 위에 모든 게 올라간다.

## 락 범위가 성능을 결정한다

[테이블 락]
MyISAM의 방식이다. 단순하지만 치명적이다.
한 행을 수정하는데 테이블 전체를 잠근다.

[행 락]
InnoDB의 방식이다.
수정하는 행만 잠그므로 동시성이 높다.

[페이지 락]
SQL Server의 기본 단위.
행 락과 테이블 락 사이의 타협이다.

락 범위가 좁을수록 동시성이 높고, 넓을수록 관리가 단순하다.
InnoDB가 표준이 된 이유는 행 수준 잠금 덕분이다.

## Intent Lock이 필요한 이유

행 락만으로는 부족하다.
테이블에 ALTER를 걸려면 "이 테이블에 행 락이 걸려 있는가?"를 전체 행을 스캔해서 확인해야 한다.
그래서 InnoDB는 Intent Lock을 쓴다.
행에 S Lock을 걸기 전에 테이블에 IS를, 행에 X Lock을 걸기 전에 테이블에 IX를 건다.
계층 간 신호다.
"아래쪽에 누가 잠겨 있다"는 표시.
테이블 수준 연산이 행 전체를 확인하지 않아도 되게 만드는 장치다.

## 락 대기의 구조

두 트랜잭션이 같은 행을 원할 때 먼저 잡은 쪽이 이긴다.
늦은 쪽은 기다린다.
InnoDB의 `innodb_lock_wait_timeout`은 기본 50초다.
50초 동안 기다리다가 포기한다.

```sql
ERROR 1205 (HY000):
Lock wait timeout exceeded;
try restarting transaction
```

이 에러가 나면 락을 잡고 있는 세션이 아직 커밋하지 않았다는 뜻이다.
느린 쿼리가 아니라 풀리지 않는 락이 원인이다.

## 데드락의 구조

1. A가 행 1을 잡고 행 2를 기다린다.
2. B가 행 2를 잡고 행 1을 기다린다.
3. 서로를 기다리며 영원히 멈춘다.

이걸 원형 대기(circular wait)라고 한다.
DB는 이 상태를 자동으로 감지한다.
하나를 골라서 롤백시킨다.
데드락은 버그가 아니다. 동시성 환경에서 자연스럽게 발생한다.
중요한 건 감지와 재시도다. DB가 감지하고, 앱이 재시도한다.
이 역할 분담이 정답이다.

## 데드락 패턴 1: 역순 UPDATE

가장 흔한 패턴이다.

```sql
-- TX1
UPDATE accounts SET bal=bal-100 WHERE id=1;
UPDATE accounts SET bal=bal+100 WHERE id=2;
-- TX2
UPDATE accounts SET bal=bal-50 WHERE id=2;
UPDATE accounts SET bal=bal+50 WHERE id=1;
```

TX1은 1 -> 2 순서, TX2는 2 -> 1 순서.
서로 반대 방향으로 잠그면 데드락이 된다.
해결은 단순하다. 항상 id 오름차순으로 접근한다.
1 -> 2 순서를 강제하면 데드락이 사라진다.

## 데드락 패턴 2: Gap Lock + INSERT

REPEATABLE READ에서 발생하는 의외의 패턴이다.

```sql
-- TX1
SELECT * FROM orders
WHERE order_id = 100 FOR UPDATE;
-- order_id=100이 없으면 Gap Lock 발생
-- TX2
SELECT * FROM orders
WHERE order_id = 101 FOR UPDATE;
-- 같은 갭에 Gap Lock 발생
```

Gap Lock끼리는 호환된다.
하지만 둘 다 INSERT를 시도하면?
상대방의 Gap Lock이 INSERT를 막는다.
서로의 INSERT를 막으면서 데드락이 된다.
READ COMMITTED로 내리면 해결되지만 팬텀 리드 방지를 포기하게 된다.

## MySQL 데드락 로그 읽기

```sql
SHOW ENGINE INNODB STATUS\G
```

`LATEST DETECTED DEADLOCK` 섹션을 본다.

[확인할 것]

- 어떤 트랜잭션이 어떤 락을 보유하고 있었는가.
- 어떤 트랜잭션이 어떤 락을 기다리고 있었는가.
- 어느 쪽이 롤백됐는가.

`WE ROLL BACK TRANSACTION (2)`가 보이면 TX2가 희생됐다는 뜻이다.
InnoDB는 보통 undo가 적은 쪽을 고른다.
`innodb_print_all_deadlocks=ON`으로 설정하면 에러 로그에 모든 데드락이 기록된다.
운영에서는 반드시 켜둔다.

## PostgreSQL 데드락 분석

PostgreSQL은 `deadlock_timeout` 후 감지한다.
기본 1초 대기 후 탐지가 동작한다.

```log
ERROR: deadlock detected
DETAIL: Process 1234 waits for ShareLock
on transaction 5678; blocked by process 9012.
```

`log_lock_waits`를 켠다.

```sql
SELECT * FROM pg_locks WHERE NOT granted;
SELECT pid, query FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

누가 잡고 있는지, 누가 기다리는지.
이 두 질문에 답할 수 있으면 된다.

## 운영 환경의 락 모니터링

문제가 생긴 후 원인을 찾는 건 늦다.
실시간으로 보고 있어야 한다.

[MySQL]

```sql
SELECT * FROM information_schema.INNODB_TRX
WHERE trx_state = 'LOCK WAIT';
SELECT * FROM performance_schema.data_locks;
SELECT * FROM sys.innodb_lock_waits;
```

[핵심 지표]

- 오래 열려 있는 트랜잭션이 몇 개인가.
- 락 대기 중인 세션이 몇 개인가.
- 대기 시간이 몇 초인가.

10초 이상 열려 있는 트랜잭션이 있다면 그 안에서 뭘 하고 있는지 확인해야 한다.
대부분 앱이 커밋을 안 한 것이다.

## 데드락을 예방하는 원칙

완전히 없앨 수는 없다. 빈도를 낮추는 것이 목표다.

[접근 순서 통일]
여러 행을 수정할 때 항상 PK 오름차순으로.
순서만 맞춰도 데드락의 대부분이 사라진다.

[트랜잭션을 짧게]
락 보유 시간을 줄인다.
트랜잭션 안에서 외부 API를 호출하지 않는다.

[불필요한 FOR UPDATE 제거]
읽기만 할 건데 FOR UPDATE를 거는 코드가 많다.
"혹시 모르니까"는 데드락의 씨앗이다.

[적절한 인덱스]
인덱스 없는 UPDATE는 사실상 테이블 락이다.

## 낙관적 락 vs 비관적 락

DB 락이 아니라 애플리케이션 전략이다.

[비관적 락]
"충돌날 거야. 미리 잠그자."
`SELECT ... FOR UPDATE`로 행을 선점한다.
충돌 비용이 큰 금융 시스템에 적합하다.

[낙관적 락]
"충돌은 드물어. 일단 진행하자."
version 컬럼으로 충돌을 사후 감지한다.

```sql
UPDATE orders SET status='done', version=2
WHERE id=1 AND version=1;
```

affected rows가 0이면 충돌이 발생한 것이다.
읽기 비중이 높은 시스템에 적합하다.
면접에서는 "언제 어느 쪽을 쓰는가"를 묻는다.
정답은 충돌 빈도와 충돌 비용이다.

## DBA 관점에서의 정리

면접관이 듣고 싶은 건 데드락의 정의가 아니다.
"새벽 3시에 데드락 알람이 울리면 당신은 뭘 먼저 하는가?"

1. `SHOW ENGINE INNODB STATUS`를 본다.
2. 어떤 쿼리가 어떤 행을 잡고 있었는지 확인한다.
3. 패턴을 분석한다.
4. 역순 접근인지, Gap Lock 충돌인지.
5. 그리고 앱 팀에게 접근 순서를 제안한다.

최고의 락은 잡지 않아도 되는 락이다.
트랜잭션을 짧게 하고, 접근 순서를 통일하고, 인덱스를 정확히 잡으면 대부분의 락 문제는 발생하지 않는다.

## 마무리

락의 종류를 나열하는 건 지식이다.
락이 왜 문제가 되는지 설명하는 건 이해다.
데드락을 보고 원인을 추적하는 건 경험이다.
면접에서 깊이는 "아는 것"과 "겪은 것"의 경계에서 드러난다.
`SHOW ENGINE INNODB STATUS`의 출력을 읽어본 적이 있는가.
pg_locks와 pg_stat_activity를 조인해서 범인을 찾아본 적이 있는가.
락을 이해한다는 것은 잠그는 법을 아는 게 아니라 풀리지 않을 때 어떻게 하는지를 아는 것이다.
