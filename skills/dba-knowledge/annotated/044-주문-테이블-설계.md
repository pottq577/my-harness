# 주문 테이블 설계: orders 하나로 시작하면 첫 환불에서 깨진다

"주문 테이블 하나 만들어주세요."
`orders`에 `user_id`, `product_id`, `qty`, `price`. 컬럼 넷이면 끝난 것 같다.
그런데 상품 두 개를 한 번에 사면?
한 달 뒤 상품명이 바뀌면?
둘 중 하나만 취소하면?
쿠폰과 포인트를 같이 쓰면?
질문 하나마다 컬럼이 하나씩 늘고 어느 순간 ALTER TABLE로는 못 고치는 구조가 된다.
주문 헤더와 주문 상품을 분리하라.
주문 시점의 값은 참조하지 말고 복사하라.
상태는 덮어쓰지 말고 이력으로 쌓아라.
금액은 계산하지 말고 저장하고 검증하라.
PK와 주문번호를 분리하라.
주문 테이블은 CRUD가 아니라 장부다.
장부는 고쳐 쓰지 않고 덧붙여 쓴다.

## orders 하나로 시작하면

가장 흔한 첫 설계.

```sql
-- MySQL
CREATE TABLE orders (
order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id BIGINT NOT NULL,
product_id BIGINT NOT NULL,
qty INT NOT NULL,
price DECIMAL(12,2) NOT NULL
);
```

상품 하나만 사는 세계에서는 완벽하다.
두 개를 담는 순간 깨진다.
주문 한 건이 행 두 개가 되고 "주문 총액"을 어디에 둘지부터 막힌다.
주문은 헤더와 라인으로 나뉜다.
헤더는 "누가 언제 얼마를"이고 라인은 "무엇을 몇 개"다.

## 헤더와 라인

```sql
-- MySQL
CREATE TABLE orders (
order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id BIGINT NOT NULL,
status VARCHAR(20) NOT NULL
);
CREATE TABLE order_items (
order_item_id BIGINT PRIMARY KEY,
order_id BIGINT NOT NULL,
product_id BIGINT NOT NULL,
qty INT NOT NULL
);
```

주문 하나에 라인 N개. 이 1:N이 주문 설계의 뼈대다.
그런데 라인에 함정이 남아 있다.
product_id만 있다.

## 참조하지 말고 복사하라

라인에 product_id만 있으면 상품명과 가격은 JOIN으로 가져온다.
한 달 뒤 상품명이 바뀌고 가격이 오른다.
고객 주문 내역에 산 적 없는 이름이 뜨고 환불 금액도 지금 가격으로 계산된다.

```sql
-- MySQL
ALTER TABLE order_items
ADD product_name VARCHAR(200) NOT NULL,
ADD unit_price DECIMAL(12,2) NOT NULL,
ADD option_snapshot JSON NULL;
```

주문 시점의 값을 라인에 복사한다.
product_id는 추적용으로만 남긴다.
정규화 위반이 아니라 장부의 기본이다.

## PK와 주문번호는 다르다

`order_id`는 1, 2, 3으로 올라간다.
이걸 URL과 영수증에 그대로 노출하면 경쟁사가 하루 주문량을 셀 수 있고 번호 하나 바꿔서 남의 주문을 열어볼 수도 있다.

```sql
-- PostgreSQL
CREATE TABLE orders (
order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
order_no VARCHAR(32) NOT NULL UNIQUE,
-- ...
);
```

내부 PK는 JOIN용이다. 짧고 순차적이어야 인덱스가 좋다.
외부 주문번호는 사람용이다. 날짜가 들어가고 추측이 안 되어야 한다.
둘을 하나로 쓰면 어느 한쪽을 포기하게 된다.

## 금액은 네 개다

총액 하나면 될 것 같다.
환불할 때 상품 금액, 할인, 배송비를 각각 묻게 된다.

```sql
-- PostgreSQL
ALTER TABLE orders
ADD item_amount NUMERIC(12,2),
ADD discount_amount NUMERIC(12,2),
ADD shipping_fee NUMERIC(12,2),
ADD total_amount NUMERIC(12,2),
ADD CHECK (total_amount = item_amount
- discount_amount + shipping_fee);
```

계산하면 되지 않나.
정산 배치가 매일 수백만 라인을 다시 더한다.
파생값이라도 장부에는 적는다.
틀리는 길은 CHECK로 막는다.

## 상태는 덮어쓰지 않는다

`status` 하나를 `PAID`, `SHIPPED`로 `UPDATE`한다. 편하다.
그런데 CS에서 묻는다. "이 주문 언제 출고됐어요?"
답이 없다. 덮어썼으니까.

```sql
-- MySQL
CREATE TABLE order_status_history (
history_id BIGINT AUTO_INCREMENT PRIMARY KEY,
order_id BIGINT NOT NULL,
from_status VARCHAR(20) NULL,
to_status VARCHAR(20) NOT NULL,
changed_at DATETIME(6) NOT NULL
);
```

헤더의 status는 "지금 상태" 캐시다.
진실은 이력 테이블에 있다.

## 취소는 라인 단위로 온다

티셔츠와 바지를 한 주문에 샀다.
바지만 취소한다.
헤더 status에 CANCELLED를 넣으면 티셔츠까지 취소된 셈이 된다.
`PARTIALLY_CANCELLED`를 추가해도 "어느 것이" 취소됐는지는 없다.

```sql
-- PostgreSQL
ALTER TABLE order_items
ADD status VARCHAR(20) NOT NULL DEFAULT 'ORDERED',
ADD cancelled_qty INT NOT NULL DEFAULT 0
CHECK (cancelled_qty <= qty);
```

취소, 반품, 교환은 전부 라인에서 일어난다.
헤더 상태는 라인 상태들의 요약일 뿐이다.
방향은 항상 라인에서 헤더로다.

## 할인은 주문에 어떻게 붙는가

헤더에 coupon_id 컬럼을 하나 둔다.
쿠폰 한 장만 쓰면 문제없다.
쿠폰과 포인트를 같이 쓰면?
컬럼이 coupon_id_2, point_amount로 번식한다.

```sql
-- MySQL
CREATE TABLE order_discounts (
discount_id BIGINT PRIMARY KEY,
order_id BIGINT NOT NULL,
order_item_id BIGINT NULL,
discount_type VARCHAR(20) NOT NULL,
amount DECIMAL(12,2) NOT NULL
);
```

할인도 라인이다.
order_item_id가 NULL이면 주문 할인, 있으면 상품 할인.

## 인덱스는 조회 패턴이 정한다

주문 테이블을 읽는 사람은 둘이다.

[고객]
"내 주문 목록" 최신순.
user_id로 찾고 created_at으로 정렬한다.

[운영 배치]
"결제 후 3일 지난 미출고 건".
status로 찾고 created_at으로 자른다.

```sql
CREATE INDEX ix_orders_user ON orders (user_id, created_at DESC);
CREATE INDEX ix_orders_status ON orders (status, created_at);
```

status 단독 인덱스는 거의 쓸모가 없다.
DELIVERED가 전체의 대부분이라 옵티마이저가 인덱스를 버리기도 한다.
created_at을 뒤에 붙여야 범위가 잘린다.

## 최종 구조 한눈에

```text
orders 누가, 언제, 얼마를 (헤더)
├── order_items 무엇을 몇 개, 그때 가격으로 (스냅샷)
│ └── order_discounts 상품 단위 할인
├── order_discounts 주문 단위 할인 (order_item_id NULL)
└── order_status_history 언제 어떤 상태로 바뀌었나
```

테이블 넷.
처음의 orders 하나보다 복잡해 보인다.
하지만 이 넷은 첫 환불, 첫 상품명 변경, 첫 쿠폰 중복 사용에서 `ALTER TABLE` 없이 버틴다.

## DBA 관점에서의 정리

주문 테이블은 설계 시점에 가장 단순하고 운영 3년 차에 가장 복잡해지는 테이블이다.
주문 헤더와 주문 상품을 분리하라.
주문 시점의 값은 참조하지 말고 복사하라.
상태는 덮어쓰지 말고 이력으로 쌓아라.
금액은 계산하지 말고 저장하고 검증하라.
PK와 주문번호를 분리하라.
DBA가 이 테이블을 만나는 건 대개 수억 건이 쌓인 뒤다.
그때 라인을 분리하고 스냅샷 컬럼을 채워 넣는 마이그레이션은 처음 설계의 수십 배 비용이 되기도 한다.
주문 테이블은 CRUD가 아니라 장부다.
장부는 고쳐 쓰지 않고 덧붙여 쓴다.
