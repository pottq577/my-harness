# 쿼리 플래너의 머릿속: 데이터베이스는 어떻게 길을 고르는가

SQL을 작성하면 데이터베이스가 알아서 실행한다.
"알아서"라는 말 뒤에는 쿼리 플래너가 있다.
같은 SQL이라도 어떤 인덱스를 탈지, 어떤 순서로 JOIN할지, 풀스캔을 할지 인덱스 스캔을 할지.
선택지는 수십, 수백 가지다.
그중 하나를 고르는 게 쿼리 플래너의 일이다.
대부분의 개발자는 이 판단 과정을 모른다.
EXPLAIN을 찍어도 읽지 못한다.
쿼리 플래너의 머릿속을 들여다본다.

## 쿼리 플래너란

SQL은 선언형 언어다. "이 데이터를 줘"라고 말하지 "이렇게 가져와"라고 말하지 않는다.
어떻게 가져올지는 DB가 결정한다.
그 결정을 내리는 컴포넌트가 쿼리 플래너(Query Planner)다. 옵티마이저(Optimizer)라고도 부른다.
SQL이 들어오면 플래너는 가능한 실행 경로를 나열하고, 각 경로의 비용을 추정하고, 가장 싼 경로를 고른다.
이 과정이 쿼리 실행 전에 일어난다.
실행 계획(Execution Plan)이 그 결과물이다.

## 비용 기반 최적화

플래너는 "비용(Cost)"으로 판단한다.
비용이란 디스크 I/O, CPU 연산, 메모리 사용량을 하나의 숫자로 환산한 추정값이다.
풀스캔의 비용은 테이블 전체를 읽는 I/O.
인덱스 스캔의 비용은 인덱스 탐색 + 테이블 lookup I/O.
플래너는 모든 후보 경로의 비용을 계산하고 가장 낮은 비용의 계획을 선택한다.
핵심은 "추정"이라는 단어다.
실제 비용이 아니라 통계에 기반한 예측이다.
통계가 틀리면 플래너도 틀린다.

## 통계: 플래너의 눈

플래너는 테이블을 직접 보지 않는다. 통계(Statistics)를 본다.

[행 수(Cardinality)]
테이블에 몇 건이 있는가.
100건짜리와 1억 건짜리는 같은 쿼리라도 최적 경로가 다르다.

[선택도(Selectivity)]
조건이 얼마나 많은 행을 걸러내는가.
`status = 'ACTIVE'`가 전체의 90%면 인덱스를 타는 게 오히려 느리다.
1%면 인덱스가 압도적으로 빠르다.

[분포(Distribution)]
값이 균등한가, 편향됐는가.
`country = 'KR'`이 99%인 테이블에서 `country = 'US'`를 찾으면 플래너는 그 1%를 알아야 올바른 판단을 한다.

## 스캔 방식

[Full Table Scan]
테이블 전체를 순차적으로 읽는다.
단순하지만 확실하다.
데이터가 적거나 대부분의 행을 읽어야 할 때 가장 빠르다.

[Index Scan]
인덱스를 통해 필요한 행만 찾아간다.
소수의 행을 뽑을 때 빠르다.
다만 인덱스에서 주소를 찾고 다시 테이블에서 데이터를 읽는 두 번의 I/O가 발생한다.

[Index Only Scan]
인덱스만으로 결과를 반환한다.
커버링 인덱스가 걸려 있을 때.
테이블 접근이 없으니 가장 빠르다.

플래너는 이 셋 중 비용이 가장 낮은 걸 고른다.

## JOIN 전략

테이블 두 개를 JOIN할 때도 방법이 여러 가지다.

[Nested Loop Join]
한쪽을 한 행씩 읽으면서 다른 쪽에서 매칭을 찾는다.
소규모 JOIN이나 인덱스가 있을 때 빠르다.
MySQL은 거의 이것만 쓴다.

[Hash Join]
한쪽으로 해시 테이블을 만들고 다른 쪽을 순회하며 매칭한다.
대량 데이터 JOIN에서 빠르다.
MySQL은 8.0.18부터 지원한다.

[Merge Join]
양쪽 모두 정렬된 상태에서 동시에 순회하며 합친다.
이미 정렬돼 있으면 가장 효율적이다.
PostgreSQL이 잘 활용한다.

## 플래너가 틀리는 순간

플래너는 완벽하지 않다.
통계 기반 추정이기 때문에 현실과 괴리가 생기면 잘못된 계획을 세운다.

[통계가 오래됨]
대량 INSERT 후 통계가 갱신 안 됐을 때.
100만 건이었던 테이블이 1000만 건이 됐는데 플래너는 아직 100만 건으로 안다.

[데이터 편향]
균등 분포를 가정했는데 실제로는 극단적 편향.
히스토그램이 없으면 플래너가 놓친다.

[상관관계 무시]
`city = '서울' AND district = '강남'`
두 조건을 독립으로 가정하고 선택도를 곱한다.
실제로는 강한 상관관계가 있다.
추정 행 수가 현실과 수십 배 벌어진다.

## 통계를 갱신하라

플래너가 틀리는 가장 흔한 이유는 통계가 오래된 것이다.

MySQL (InnoDB):

```sql
ANALYZE TABLE orders;
```

`innodb_stats_auto_recalc`가 켜져 있으면 10% 이상 변경 시 자동 갱신된다.
하지만 대량 배치 직후에는 수동이 확실하다.

PostgreSQL:

```sql
ANALYZE orders;
```

autovacuum이 ANALYZE도 같이 돌린다.
하지만 대형 테이블은 타이밍이 늦을 수 있다.
대량 데이터 변경 후 ANALYZE.
이 한 줄이 느린 쿼리를 의외로 자주 해결한다.

## EXPLAIN: 플래너의 판단을 읽는 법

플래너가 어떤 계획을 세웠는지 보려면 EXPLAIN을 쓴다.

MySQL:

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 12345;
```

type이 ref면 인덱스 참조.
key가 idx_user_id면 그 인덱스를 탔다.
rows가 15면 15건을 읽을 것으로 추정했다.

PostgreSQL:

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 12345;
```

EXPLAIN은 계획을 보여주고 EXPLAIN ANALYZE는 실제 실행 결과를 보여준다.
추정(estimated)과 실제(actual)의 차이가 크면 통계가 틀린 것이다.

## 플래너를 강제하는 것에 대하여

플래너가 틀릴 때 힌트(Hint)로 강제하고 싶은 유혹이 있다.

MySQL:

```sql
SELECT * FROM orders FORCE INDEX (idx_status)
WHERE status = 'ACTIVE';
```

PostgreSQL은 공식 힌트가 없다.
`pg_hint_plan` 확장을 쓰거나 `SET enable_seqscan = off` 같은 우회를 한다.
힌트는 응급처치다.
데이터 분포가 바뀌면 힌트가 오히려 독이 된다.
오늘 빠른 인덱스가 내일도 빠르리란 보장이 없다.
근본 치료는 통계 갱신이거나 쿼리 구조 자체를 바꾸는 것이다.
힌트를 걸었으면 반드시 주석으로 이유를 남겨라.

## MySQL과 PostgreSQL의 차이

같은 SQL이라도 두 DB의 플래너는 판단이 다르다.

[MySQL]
비용 모델이 비교적 단순하다.
JOIN은 거의 Nested Loop만 쓴다.
히스토그램은 8.0부터 지원하지만 자동 갱신이 안 된다.
인덱스 힌트를 공식 지원한다.

[PostgreSQL]
비용 모델이 정교하다.
Nested Loop, Hash Join, Merge Join을 골라 쓴다.
히스토그램, MCV(Most Common Values) 통계가 풍부하다.
파티션 프루닝, 병렬 쿼리도 플래너가 결정한다.
PostgreSQL의 플래너가 더 똑똑하다는 평가가 많지만 그만큼 예상 밖의 계획을 세울 때도 있다.
단순함에는 단순함의 장점이 있다.

## 서브쿼리와 플래너

서브쿼리는 플래너를 힘들게 한다.

```sql
SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users
);
```

플래너는 이걸 두 가지로 풀 수 있다.
서브쿼리를 먼저 실행하고 결과로 필터링 또는 세미조인(Semi Join)으로 변환해서 JOIN처럼 처리.
MySQL 5.5까지는 서브쿼리 최적화가 약했다.
IN 서브쿼리가 매 행마다 실행되는 일이 있었다.
5.6부터 세미조인 최적화가 들어갔다.
PostgreSQL은 일찍부터 서브쿼리를 JOIN으로 풀어내는 데 능했다.
서브쿼리가 느리면 플래너가 변환에 실패한 것일 수 있다.
명시적 JOIN으로 바꾸면 해결되는 경우가 많다.

## 플랜 플립: 어제는 빨랐는데 오늘은 느리다

코드를 안 바꿨다. 인덱스도 그대로다. 데이터만 늘었다.
그런데 쿼리가 갑자기 느려졌다.
원인은 대부분 플래너의 판단 변경이다.
데이터가 일정량을 넘으면 인덱스 스캔의 비용이 풀스캔을 역전한다.
플래너가 경로를 바꾼다.
이걸 "플랜 플립(Plan Flip)"이라 부른다.
DBA가 가장 싫어하는 장애 유형 중 하나다.
코드 변경 없이 터지기 때문에 원인 파악이 어렵다.
EXPLAIN을 일상적으로 모니터링하지 않으면 이 순간을 놓친다.

## 파라미터 스니핑

Prepared Statement를 쓸 때 생기는 문제다.
첫 실행에 `status = 'RARE'`가 들어왔다.
1000건 중 3건. 인덱스 스캔 계획이 캐싱된다.
두 번째에 `status = 'ACTIVE'`가 들어왔다.
1000건 중 950건. 풀스캔이 맞다.
하지만 캐싱된 인덱스 스캔 계획이 재사용된다.
첫 번째 파라미터가 계획을 결정해버리는 것.
이걸 파라미터 스니핑(Parameter Sniffing)이라 한다.
SQL Server에서 악명 높고 PostgreSQL도 generic plan에서 발생한다.
MySQL은 쿼리 캐시가 폐지(8.0)되면서 이 문제가 상대적으로 적다.

## DBA 관점에서의 정리

쿼리 플래너는 데이터베이스의 두뇌다.
개발자가 "무엇을" 말하면 플래너가 "어떻게"를 결정한다.
대부분의 경우 플래너는 옳다.
하지만 틀릴 때가 있고 그 순간이 장애다.
플래너와 잘 지내는 법은 세 가지다.

1. EXPLAIN을 읽을 줄 알 것.
2. 통계를 믿되, 갱신을 게을리하지 말 것.
3. 힌트는 최후의 수단으로 둘 것.

플래너를 이해하면 "왜 느린지 모르겠다"가 사라진다.
실행 계획을 읽으면 쿼리가 아니라 DB의 판단을 디버깅할 수 있다.
SQL을 잘 쓴다는 건 결국 플래너가 좋은 판단을 내리도록 돕는 일이다.

## 마무리

SQL을 작성하면 데이터베이스가 알아서 해준다.
그 "알아서"가 쿼리 플래너다.
통계를 보고, 비용을 계산하고, 경로를 고른다.
완벽하진 않지만 대부분 옳다.
틀릴 때를 알아채는 게 DBA의 일이고, EXPLAIN이 그 도구다.
플래너의 머릿속을 이해하면 쿼리 튜닝은 마법이 아니라 논리가 된다.
