# 채팅과 DB: 읽었는지 안 읽었는지, 그게 이렇게 어려운 일

"채팅 기능 하나 붙이려는데, DB는 뭘 신경 써야 해요?"
메시지를 저장하고 불러오면 끝이라고 생각한다. 그건 게시판이다.
채팅은 다르다.
누가 읽었는지를 추적해야 하고 안 읽은 메시지를 세야 하고 방 목록을 실시간으로 정렬해야 한다.
보내는 건 INSERT 하나지만 읽었는지를 관리하는 게 채팅 DB의 진짜 문제다.

- 안 읽은 수는 카운터로 분리하라.
- 그룹 채팅의 읽음 확인은 곱셈이다.
- 방 목록 정렬은 쓰기와 충돌한다.
- 오래된 메시지는 파티셔닝으로 분리하라.
- 채팅 검색은 DB 밖에서 하라.

## 메시지 저장은 쉽다

채팅 메시지는 append-only다. 시간 순서대로 쌓기만 한다.
수정도 드물고 삭제는 더 드물다.
INSERT는 빠르다.
auto_increment에 timestamp 인덱스만 있으면 초당 만 건도 문제 없다.
문제는 읽기다.
"이 방의 최근 50건"은 쉽다.
"이 방의 2024년 3월 메시지"는 어렵다.
방 하나에 메시지 500만 건이 쌓이면 인덱스를 타도 범위가 넓다.
쓰기는 쉬운데 읽기가 어려운 구조.
보통의 서비스와 반대다.

## 안 읽은 메시지 N건의 실체

카카오톡을 열면 숫자가 보인다. "안 읽은 메시지 3건."
이걸 구현하려면 어떤 데이터가 필요한가.
사용자별, 채팅방별로 마지막으로 읽은 메시지 ID를 저장해야 한다.

```sql
SELECT COUNT(*) FROM messages
WHERE room_id = 42
AND message_id > 1523
```

방이 100개면 이 쿼리가 100번 돈다.
사용자 10만 명이 앱을 열면 100만 번의 COUNT가 동시에 실행된다.
채팅방 목록을 열 때마다 이 비용이 든다.
캐시하지 않으면 DB가 버틸 수 없다.

## 채팅방 목록의 정렬 비용

채팅방 목록은 최신 메시지 순으로 정렬된다.
메시지가 오면 그 방이 맨 위로 올라간다.
이걸 DB로 하면 메시지가 올 때마다 채팅방 테이블의 last_message_at을 UPDATE해야 한다.
초당 메시지 1000건이면 초당 UPDATE 1000건이다.
방마다 다른 row라서 lock 경합은 적지만 인덱스 재정렬 비용이 쌓인다.
사용자가 방 목록을 열면

```sql
SELECT * FROM rooms
WHERE user_id = 7
ORDER BY last_message_at DESC
```

이 쿼리가 빨라야 한다.
메시지 INSERT와 방 목록 정렬.
둘 다 빨라야 하는데 서로 충돌한다.

## 1:1은 되는데 그룹채팅에서 터진다

1:1 채팅은 단순하다.
메시지를 쓰면 상대 한 명에게 간다.
그룹 채팅은 다르다.
500명이 있는 방에 메시지를 보내면 499명의 읽음 상태를 관리해야 한다.
읽음 확인 테이블이 폭발한다.
메시지 1건 × 참여자 500명 = 500건.
하루에 메시지 1000건이면 읽음 레코드 50만 건이 하루 만에 쌓인다.
방이 100개면 5000만 건. 한 달이면 15억 건.
그룹 채팅의 읽음 확인을 메시지 단위로 관리하면 DB가 감당할 수 없다.
카카오톡이 "몇 명이 안 읽었는지"만 보여주는 건 기술적 타협이다.
