# 인덱스의 진짜 동작 원리: B-tree, 순서, 커버링의 실체

"인덱스 추가하면 되지 않나요?"
면접에서 이 말이 나오는 순간 후속 질문이 쏟아진다.
B-tree 구조가 뭔지, 왜 컬럼 순서가 중요한지, 커버링 인덱스가 왜 빠른지.
인덱스를 "안다"는 것과 인덱스를 "이해한다"는 것은 완전히 다른 영역이다.

## 면접에서 인덱스가 중요한 이유

"느린 쿼리를 어떻게 해결하셨나요?" DB 면접의 단골 질문이다.
대부분 "인덱스를 추가했습니다"라고 답한다. 여기서 끝나면 주니어다.
왜 그 인덱스가 효과가 있었는지, 어떤 구조로 동작하는지, 부작용은 없었는지.
이 세 가지를 설명할 수 있으면 시니어 레벨의 답이 된다.

## B-tree란

인덱스의 물리적 구조다.
Binary tree가 아니라 Balanced tree. 세 계층으로 이루어진다.

[Root]
트리의 꼭대기. 검색의 시작점.

[Branch]
중간 길잡이. 어느 리프로 가야 할지 안내한다.

[Leaf]
실제 키 값이 정렬된 채로 저장된다.
리프 페이지끼리는 양방향 링크드 리스트로 연결돼 있다.
도서관의 색인 카드와 같다.
카드가 정렬돼 있으니 원하는 책을 빠르게 찾는다.

## B-tree의 탐색 과정

1,000만 행 테이블에서 id=7777을 찾는다고 하자.
풀 스캔이면 최대 1,000만 번 비교한다.
B-tree는 다르다.
루트에서 시작해 브랜치를 거쳐 리프까지.
깊이가 3~4면 3~4번의 페이지 접근으로 끝난다.
O(N)이 O(log N)이 된다.
1,000만 행도 약 23번 비교면 충분하다. 이게 인덱스의 존재 이유다.
정렬된 구조가 검색을 압도적으로 빠르게 만든다.

## 복합 인덱스와 컬럼 순서

```sql
CREATE INDEX idx_name_age ON users(name, age);
```

이 인덱스는 name으로 먼저 정렬하고, 같은 name 안에서 age로 정렬한다.
전화번호부와 같다. 성이 같으면 이름순으로 정렬되는 것.

```sql
WHERE name = 'dot' AND age = 30 -- → 사용됨
WHERE name = 'dot' -- → 사용됨
WHERE age = 30 →--  사용 안 됨
```

이것이 최좌측 접두사(Leftmost Prefix) 규칙이다.
왼쪽부터 순서대로 매칭되지 않으면 인덱스를 탈 수 없다.

## 커버링 인덱스

인덱스만으로 쿼리가 완결되는 상태다.
테이블 본체를 전혀 읽지 않는다.

```sql
CREATE INDEX idx_cover ON orders(user_id, status);
SELECT user_id, status FROM orders
WHERE user_id = 100;
```

필요한 컬럼이 전부 인덱스 안에 있다. Extra 컬럼에 "Using index"가 뜬다.
이것이 Index Only Scan이다.
왜 빠른가?
인덱스는 테이블보다 훨씬 작고, 순서대로 정렬돼 있어 디스크 I/O가 최소화된다.
테이블 랜덤 접근이 사라지는 것이 핵심이다.

## 인덱스 선택도와 카디널리티

인덱스가 있어도 쓸모없을 때가 있다. 선택도(Selectivity)가 낮은 컬럼이다.
gender 컬럼에 M/F 두 값만 있다면 인덱스를 타도 전체 행의 50%를 읽는다.
옵티마이저는 이럴 때 풀 스캔을 선택한다. 인덱스 경유 랜덤 I/O보다 순차 스캔이 낫기 때문이다.
카디널리티 = 고유 값의 수. 높을수록 인덱스가 효과적이다.
email은 카디널리티가 높다. 인덱스에 적합하다.
is_active는 낮다. 단독 인덱스로는 낭비다.

## Clustered vs Non-Clustered

InnoDB에서 PK가 특별한 이유다.

[Clustered Index]
테이블 데이터 자체가 PK 순서로 저장된다.
PK 검색 = 데이터 직접 접근. 추가 단계 없음.
InnoDB는 테이블당 하나만 가능하다.

[Non-Clustered (Secondary Index)]
인덱스 리프에 PK 값이 들어 있다.
인덱스 검색 → PK 값 획득 → PK로 다시 검색.
이 두 번째 단계를 "테이블 룩업"이라 한다.
커버링 인덱스가 빠른 이유가 여기 있다. 테이블 룩업을 생략하기 때문이다.

## Index Scan vs Index Seek

같은 인덱스를 타도 성능 차이가 크다.

[Index Seek]
B-tree를 타고 내려가 정확한 위치를 찾는다.
`WHERE id = 100`. 핀포인트다.

[Index Range Scan]
시작점을 찾고 범위만큼 쭉 읽는다.
`WHERE id BETWEEN 1 AND 10000`.
범위가 넓으면 느려진다.

[Index Full Scan]
인덱스 전체를 순서대로 읽는다.
테이블 풀 스캔보다는 낫지만 인덱스를 제대로 활용하는 것은 아니다.
EXPLAIN의 type 컬럼에서 확인한다.
ref, eq_ref는 좋고, range는 범위 확인, ALL은 경고다.

## 인덱스의 쓰기 비용

인덱스는 읽기를 빠르게 하지만 쓰기를 느리게 한다.
INSERT: 테이블에 행 추가 + 모든 인덱스에 키 추가.
UPDATE: 변경된 컬럼의 인덱스를 갱신.
DELETE: 테이블 행 삭제 + 모든 인덱스에서 키 제거.
인덱스가 5개면 INSERT 한 번에 6번의 쓰기가 발생한다.
테이블 1회 + 인덱스 5회.
OLTP에서 초당 수천 건의 INSERT가 발생하는 테이블에 인덱스를 10개 걸어두면 쓰기 성능이 바닥을 친다.

## 인덱스 과다의 문제

인덱스가 많으면 세 가지가 나빠진다.

[저장 공간]
인덱스도 디스크를 차지한다. 테이블보다 인덱스 합계가 큰 경우도 흔하다.

[쓰기 증폭]
모든 DML이 모든 인덱스를 갱신한다. Write Amplification이 심해진다.

[옵티마이저 혼란]
인덱스가 너무 많으면 플래너가 잘못된 인덱스를 선택할 확률이 높아진다.
실행 계획이 불안정해진다.
"인덱스는 약이자 독이다."
DBA가 가장 자주 하는 말 중 하나다.

## Invisible Index와 미사용 인덱스 탐지

사용하지 않는 인덱스를 찾아 정리하는 것도 DBA의 일이다.
MySQL 8.0의 Invisible Index:

```sql
ALTER TABLE orders ALTER INDEX idx_old INVISIBLE;
```

인덱스를 삭제하지 않고 옵티마이저에서만 숨긴다.
문제 없으면 DROP. 문제 있으면 VISIBLE로 복구. 안전한 정리 방법이다.
PostgreSQL은 pg_stat_user_indexes로 확인한다.

```sql
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0;
```

idx_scan이 0인 인덱스는 한 번도 사용되지 않은 것이다.

## MySQL vs PostgreSQL 인덱스 차이

두 DB 모두 B-tree를 쓰지만 세부 동작이 다르다.

[InnoDB 세컨더리 인덱스]
리프에 PK를 저장한다.
PK가 크면 세컨더리 인덱스도 커진다. UUID PK가 위험한 이유다.

[PostgreSQL의 HOT Update]
인덱스 컬럼이 변경되지 않은 UPDATE는 힙 페이지 내에서만 처리한다.
인덱스를 건드리지 않으므로 빠르다.

[Partial Index — PostgreSQL 전용]

```sql
CREATE INDEX idx_active ON orders(user_id)
WHERE status = 'active';
```

조건을 만족하는 행만 인덱스에 넣는다. 크기와 쓰기 비용이 줄어든다.
MySQL에는 없는 기능이다.

## 면접에서 나오는 인덱스 질문들

실제로 받았거나 자주 등장하는 질문들이다.
"복합 인덱스 (a, b, c)에서 WHERE b = 1 AND c = 2는 인덱스를 타나요?"
→ 안 탄다. 최좌측 접두사 규칙 위반.
"PK를 UUID로 쓰면 어떤 문제가 있나요?"
→ 정렬 순서가 랜덤이라 페이지 분할이 잦고, 세컨더리 인덱스 크기가 커진다.
"인덱스를 추가했는데 오히려 느려진 경우가 있나요?"
→ 카디널리티가 낮아 풀 스캔보다 느리거나, 인덱스가 너무 많아 쓰기 성능이 떨어진 경우.
질문의 본질은 "왜"다. 구조를 알면 모든 파생 질문에 답할 수 있다.

## DBA 관점에서의 정리

DBA에게 인덱스는 매일 만지는 도구다. 슬로우 쿼리의 90%는 인덱스로 해결된다.
하지만 인덱스 과다의 30%는 인덱스를 줄여서 해결된다.
커버링 인덱스를 설계할 줄 아는 개발자는 드물다.
`SELECT *` 대신 필요한 컬럼만 조회하라는 말의 진짜 이유가 여기 있다.
인덱스를 추가하는 건 쉽다. 언제 추가하지 말아야 하는지 아는 게 어렵다.

## 마무리

인덱스는 정렬된 구조다.
B-tree가 그 구조를 구현하고, 리프 노드의 링크드 리스트가 범위 스캔을 가능하게 한다.
컬럼 순서가 중요한 이유는 정렬 순서 때문이고, 커버링 인덱스가 빠른 이유는 테이블 룩업을 없애기 때문이고, 카디널리티가 낮으면 인덱스가 무의미한 이유는 옵티마이저가 더 나은 방법을 알기 때문이다.
"인덱스 추가하면 되죠"에서 "이 인덱스는 이 구조로 동작하고, 이 쿼리 패턴에 이렇게 효과적입니다"로.
그 차이가 면접의 합격과 불합격을 가른다.
