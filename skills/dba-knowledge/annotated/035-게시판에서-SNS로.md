# 게시판에서 SNS로: 피드가 DB를 바꾸는 순간

"게시판은 만들어봤는데, 피드는 뭐가 다른가요?"
게시판은 목록이다. 전체 글을 최신순으로 보여주면 된다.
피드는 다르다. 내가 팔로우한 사람의 글만 보여줘야 한다. 시간순으로, 실시간으로.
게시판은 SELECT 하나로 되지만 피드는 관계를 따라가야 한다.
팔로우가 1000명이면 1000명의 글을 모아서 정렬해야 한다.
게시판이 커지면 페이징이 느려진다.
피드가 커지면 구조가 바뀌어야 한다.
피드는 Fan-out 전략을 정해야 한다.
유명인은 저장이 아니라 경로를 분리한다.
팔로우 관계는 양방향 인덱스가 필요하다.
좋아요는 카운터와 이력, 두 테이블이지만 실시간일 필요는 없다.
차단은 쿼리에서 빼는 것이고 빼는 것이 더 비싸다.
추천은 서비스 DB에서 돌리지 마라.

## 게시판은 되는데 피드는 왜 안 되나

게시판은 단순하다.

```sql
SELECT * FROM posts
ORDER BY created_at DESC
LIMIT 20
```

모든 사용자가 같은 목록을 본다. 인덱스 하나면 충분하다.
피드는 다르다. 사용자마다 다른 목록을 본다.
내가 팔로우한 사람의 글만 나와야 한다.

```sql
SELECT * FROM posts
WHERE author_id IN (1, 5, 23, 47, 102)
ORDER BY created_at DESC
LIMIT 20
```

팔로우가 500명이면 IN 절에 500개. 이 쿼리는 인덱스를 타도 무겁다.
사용자마다 팔로우가 달라서 쿼리 결과를 캐시하기도 어렵다.

## Fan-out: 쓸 때 복사할 것인가, 읽을 때 모을 것인가

피드를 만드는 방법은 두 가지다.

[Fan-out on Write]
글을 쓰면 팔로워 전원의 피드 테이블에 복사한다.
팔로워가 1만 명이면 INSERT 1만 건.
쓰기가 무겁지만 읽기는 가볍다.

[Fan-out on Read]
피드를 열 때 팔로우 목록을 가져와서 실시간으로 글을 모은다.
쓰기는 가볍지만 읽기가 무겁다. 정답은 없다.
팔로워가 많은 유명인은 Fan-out on Write가 비싸다.
글 하나에 수백만 건의 INSERT. 팔로워가 적은 일반인은 괜찮다.
그래서 대부분의 SNS는 둘을 섞는다.
일반인은 Write, 유명인은 Read.

## 유명인의 피드는 경로가 다르다

유명인의 테이블을 따로 두는 게 아니다.
유명인의 글을 피드 테이블에 안 넣는 것이다.
팔로워가 피드를 열면 피드 테이블의 일반인 글과 캐시에서 꺼낸 유명인 글을 합쳐서 정렬한다.
분리는 저장이 아니라 경로에서 일어난다.

## 팔로우 관계의 폭발

사용자 100만 명. 평균 팔로우 200명. 팔로우 테이블: 2억 건.
"내가 팔로우한 사람 목록." "나를 팔로우한 사람 목록." 두 방향의 쿼리가 모두 빨라야 한다.
인덱스가 두 개 필요하다.
`(follower_id, following_id)`, `(following_id, follower_id)`
"A가 B를 팔로우하는가?"를 확인하는 쿼리는 버튼 하나를 그릴 때마다 실행된다.
게시글 목록의 작성자마다 확인하면 글 20개에 쿼리 20번.
팔로우 관계는 단순한 테이블이지만 조회 패턴이 다양해서 인덱스 설계가 중요하다.

## 좋아요 카운터의 동시성

인기 게시글에 좋아요가 몰린다.
같은 행에 UPDATE가 집중된다.

```sql
UPDATE posts
SET like_count = like_count + 1
WHERE post_id = 999
```

조회수 카운터와 같은 문제다. row lock 경합. 인기 글일수록 심하다.
좋아요는 조회수보다 한 가지 더 어렵다.
"이 사용자가 이미 좋아요를 눌렀는가."
좋아요 테이블이 따로 필요하다.
(user_id, post_id)에 유니크 키. 좋아요를 누르면 두 테이블에 쓴다.
좋아요 이력 INSERT + 카운터 UPDATE. 취소하면 DELETE + UPDATE.
단순한 하트 버튼 하나에 두 테이블, 두 인덱스, 동시성 제어.

## 좋아요는 실시간이 아니다

하지만 좋아요 숫자는 실시간일 필요가 없다. 1만과 1만 47의 차이를 사용자는 모른다.
실시간을 포기하면 설계가 달라진다.
이력 테이블에 INSERT만 하고 카운터는 1분마다 배치로 갱신한다.
아니면 Redis에서 INCR로 세고 DB에는 모아서 flush한다.
row lock 경합이 사라진다.
정확해야 하는 것과 빨라야 하는 것을 구분하면 DB가 해야 할 일이 줄어든다.

## 해시태그와 다대다

글 하나에 태그 여러 개. 태그 하나에 글 여러 개. 전형적인 다대다 관계.
중간 테이블이 필요하다. `posts`, `tags`, `post_tags`.
여행 해시태그로 검색하면

```sql
SELECT p.* FROM posts p
JOIN post_tags pt
ON p.post_id = pt.post_id
JOIN tags t
ON pt.tag_id = t.tag_id
WHERE t.tag_name = '여행'
ORDER BY p.created_at DESC
LIMIT 20
```

조인이 두 번이다.
인기 태그에 글이 100만 건이면 정렬 비용이 크다.
태그별 최신 글은 별도 캐시로 관리하거나 역정규화로 post_tags에 created_at을 복사해서 조인을 줄이는 방법을 쓴다.

## 신고와 차단이 쿼리를 바꾼다

사용자 A가 사용자 B를 차단했다. A의 피드에 B의 글이 나오면 안 된다.
피드 쿼리에 조건이 하나 추가된다.

```sql
AND author_id NOT IN (
SELECT blocked_id FROM blocks
WHERE blocker_id = 42
)
```

차단한 사람이 10명이면 괜찮다. 100명이면 NOT IN이 무거워진다. 신고된 글도 숨겨야 한다.
관리자가 검토 중인 글도 제외해야 한다.
피드 쿼리에 예외 조건이 하나씩 붙을 때마다 실행 계획이 바뀌고 성능이 달라진다.
기능은 "안 보이게 하기"인데 DB는 "보이는 것만 골라내기"로 구현해야 한다.
빼는 것이 더하는 것보다 비싸다.

## 추천 알고리즘이 DB에 요구하는 것

시간순 피드를 넘어서 "당신이 좋아할 만한 글"을 보여주려면 사용자 행동 데이터가 필요하다.
어떤 글에 오래 머물렀는가. 어떤 태그를 자주 클릭하는가. 비슷한 취향의 사용자는 뭘 좋아하는가.
이 데이터는 이벤트 로그다.
서비스 DB에 넣으면 가장 큰 테이블이 된다.
추천은 OLTP가 아니라 OLAP의 영역이다.
서비스 DB에서 추천 쿼리를 돌리면 다른 기능이 전부 느려진다.
추천 데이터는 분석 DB로 분리하고 결과만 서비스 DB에 캐시하는 게 원칙이다.

## DBA 관점에서의 정리

게시판은 하나의 테이블로 시작한다.
피드가 되면 구조가 달라진다.
피드는 Fan-out 전략을 정해야 한다.
유명인은 저장이 아니라 경로를 분리한다.
팔로우 관계는 양방향 인덱스가 필요하다.
좋아요는 카운터와 이력, 두 테이블이지만 실시간일 필요는 없다.
차단은 쿼리에서 빼는 것이고 빼는 것이 더 비싸다.
추천은 서비스 DB에서 돌리지 마라.
게시판에서 SNS로 가는 길은 기능을 추가하는 것이 아니라 DB 구조를 다시 설계하는 것이다.
게시판이 커지면 페이징이 느려진다.
피드가 커지면 구조가 바뀌어야 한다.
