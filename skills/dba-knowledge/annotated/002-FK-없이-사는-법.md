# FK 없이 사는 법: 외래키를 안 쓰는 팀이 많아진 이유

외래키는 관계형 데이터베이스의 핵심 기능이다.
테이블 간의 참조 무결성을 DB가 보장해준다.
교과서에서는 반드시 써야 한다고 가르친다.
그런데 실무에서는 안 쓰는 팀이 점점 많아지고 있다.
왜 그런 걸까.
FK를 빼면 뭘 얻고, 뭘 잃는 걸까.

1. FK의 성능 비용을 이해하라.
2. CASCADE를 두려워하라.
3. 스키마 변경의 자유를 확보하라.
4. 서비스가 나뉘면 FK도 끊어진다는 걸 받아들여라.
5. FK를 빼되, 무결성을 버리지는 마라.

FK를 안 쓰는 게 답이 아니다. 안 쓰는 대가를 아는 게 답이다.

## 외래키의 원래 역할

외래키는 참조 무결성을 지키는 장치다.
존재하지 않는 부모를 가리키는 자식 행을 DB가 막아준다.

```sql
ALTER TABLE order_item
ADD CONSTRAINT fk_order
FOREIGN KEY (order_id) REFERENCES orders(id);
```

이 한 줄이면 order_item에 엉뚱한 order_id가 들어가는 걸 막을 수 있다.
애플리케이션 버그가 있어도 DB가 최후의 방어선이 된다.
이론적으로는 완벽하다.
문제는 이론과 실무 사이의 간극이다.

## FK의 성능 비용

자식 테이블에 INSERT할 때마다 부모 테이블에 shared lock이 걸린다.
한 건이면 괜찮다. 초당 수천 건이면 이야기가 달라진다.
부모 행을 DELETE할 때도 마찬가지다.
자식 테이블에 해당 부모를 참조하는 행이 있는지 검사해야 한다.
FK가 많으면 이 검사가 여러 테이블에 걸쳐 일어난다.
대량 INSERT 배치가 FK 검증 때문에 느려지는 건 흔한 일이다.
FK 하나 빼고 배치 시간이 절반으로 줄었다는 경험담도 드물지 않다.

## CASCADE의 위험

`ON DELETE CASCADE`. 부모 한 건 지우면 자식도 함께 지워진다. 편리해 보인다.

```sql
FOREIGN KEY (order_id) REFERENCES orders(id)
ON DELETE CASCADE;
```

그런데 그 부모에 자식이 100만 건이면 어떻게 될까.
한 번의 DELETE가 100만 건의 연쇄 삭제를 일으킨다.
트랜잭션이 길어지고, 락이 퍼지고, 서비스가 멈춘다.
의도한 건 한 건 삭제였다. 실제 일어난 건 대량 삭제였다.
CASCADE는 편의 기능이 아니라 시한폭탄이다.

## DDL과 FK

테이블 구조를 바꿔야 할 때 FK는 걸림돌이 된다.
ALTER TABLE이 FK 검증을 동반하기 때문이다.
무중단 스키마 변경 도구를 쓸 때 문제가 더 크다.
gh-ost나 pt-online-schema-change는 임시 테이블을 만들고 데이터를 복사한다.
FK가 있으면 이 과정에서 충돌이 생긴다.
pt-osc는 자식 테이블의 FK를 재생성하는 옵션이 있지만 복잡도가 올라간다.
gh-ost는 FK가 있는 테이블을 아예 지원하지 않는다.
운영 중에 스키마를 못 바꾸는 건 치명적이다.

## 마이크로서비스와 FK

서비스가 나뉘면 DB도 나뉜다.
주문 서비스의 DB와 상품 서비스의 DB는 물리적으로 다른 인스턴스다.
서로 다른 DB 사이에 FK를 걸 수 있을까?
불가능하다. 물리적으로 안 된다.
결국 참조 무결성은 애플리케이션이 책임져야 한다.
주문을 생성할 때 상품이 존재하는지 API로 확인한다.
DB가 해주던 일을 코드가 대신한다.
마이크로서비스 전환은 FK 포기를 전제한다.
이걸 명시적으로 인정하는 팀이 많아졌다.

## 대용량 DML과 FK

수백만 건을 DELETE해야 하는 배치가 있다.
FK가 걸려 있으면 매 건마다 자식 테이블을 검사한다.
처리 시간이 기하급수적으로 늘어난다.
그래서 FOREIGN_KEY_CHECKS=0이라는 유혹이 생긴다.

```sql
SET FOREIGN_KEY_CHECKS = 0;
DELETE FROM old_orders WHERE created_at < '2024-01-01';
SET FOREIGN_KEY_CHECKS = 1;
```

빠르다. 하지만 이 사이에 무결성이 깨질 수 있다.
FK를 걸어놓고 검사를 끄는 건 안전벨트를 매고 버클을 안 채우는 것과 같다.
쓸 거면 쓰고, 뺄 거면 빼라.

## FK 없이 무결성을 지키는 법

FK를 빼면 무결성을 포기하는 걸까.
아니다. 방법이 달라질 뿐이다.

[애플리케이션 레벨 검증]
주문 생성 전에 상품 존재 여부를 확인한다.
트랜잭션 안에서 SELECT 후 INSERT.

[배치 정합성 체크]
주기적으로 고아 행을 탐지하는 배치를 돌린다.

```sql
SELECT ci.iid FROM child_items ci
LEFT JOIN parents p ON ci.parent_id = p.iid
WHERE p.iid IS NULL;
```

[모니터링]
고아 행이 발견되면 알림을 보낸다.
사후 감지지만, 실시간 락보다 운영 부담이 적다.

## FK가 여전히 필요한 경우

모든 서비스에서 FK를 빼라는 뜻이 아니다.
금융, 결제처럼 데이터 한 건의 정합성이 돈과 직결되는 도메인이 있다.
고아 행 하나가 정산 오류로 이어진다. 이런 곳에서는 FK가 최후의 방어선이다.
모놀리식 아키텍처에서 DB가 하나라면 FK를 쓰지 않을 이유가 약하다.
소규모 서비스에서 트래픽이 적다면 FK의 성능 비용은 무시할 수 있다.
FK를 뺄지 말지는 도메인과 규모가 결정한다.
기술적 유행이 결정하는 게 아니다.

## Soft FK와 문서화

물리 FK를 안 걸더라도 관계는 존재한다.
이 관계를 어떻게 표현할 것인가.

[컬럼 네이밍 컨벤션]
parent_id라는 이름만으로도 관계를 암시할 수 있다.
팀 내에서 `_id` 접미사는 다른 테이블의 PK를 가리킨다는 약속을 정한다.

[ERD와 문서]
물리 FK는 없지만 논리 ERD에는 관계를 표시한다.
신규 입사자가 테이블 간 관계를 파악할 수 있어야 한다.
Soft FK는 DB가 강제하지 않는 관계다. 강제하지 않으니 문서화가 더 중요해진다.
FK를 빼면서 문서도 안 만드는 건 무책임이다.

## MySQL vs PostgreSQL FK 차이

같은 FK라도 엔진마다 동작이 다르다.

[MySQL InnoDB]
FK를 걸면 자식 테이블에 인덱스가 자동 생성된다.
인덱스가 없으면 FK 생성 자체가 거부된다.
덕분에 부모 삭제 시 자식 검사가 인덱스 스캔으로 처리된다.

[PostgreSQL]
FK를 걸어도 자식 컬럼에 인덱스를 자동으로 만들어주지 않는다.
인덱스 없이 FK만 걸면 부모 삭제 시 자식 테이블 풀스캔이 발생한다.
대형 테이블에서 이걸 모르면 장애가 난다.
PostgreSQL에서 FK를 쓴다면 자식 컬럼에 인덱스를 반드시 직접 만들어야 한다.
당연히 해줄 거라고 기대하면 안 된다.

## ORM과 FK

JPA의 ManyToOne은 FK를 전제로 설계됐다.
ORM은 FK가 있다고 가정하고 쿼리를 생성한다.
그런데 FK를 안 걸면 어떻게 될까.
ORM은 여전히 JOIN을 생성한다.
FK가 없어도 JOIN 자체는 동작한다.
다만 참조 무결성을 ORM이 보장하지는 않는다.
문제는 개발자의 기대다.
ManyToOne을 쓰면서 "DB가 관계를 보장해주겠지"라고 생각한다.
실제로는 아무도 보장하지 않는 상태가 된다.
ORM을 쓰면서 FK를 빼려면 팀 전체가 그 사실을 알고 있어야 한다.
암묵적 기대가 가장 위험하다.

## DBA 관점에서의 정리

1. FK의 성능 비용을 이해하라.
2. CASCADE를 두려워하라.
3. 스키마 변경의 자유를 확보하라.
4. 서비스가 나뉘면 FK도 끊어진다.
5. FK를 빼되, 무결성을 버리지는 마라.

이 다섯 가지를 모르고 FK를 걸거나 빼는 건 둘 다 위험하다.

## 마무리

FK를 안 쓰는 게 답이 아니다.
안 쓰는 대가를 아는 게 답이다.
