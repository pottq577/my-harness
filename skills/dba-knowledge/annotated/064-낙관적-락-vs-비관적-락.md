# Optimistic Lock vs Pessimistic Lock: 충돌을 막느냐, 충돌을 받아들이느냐

두 사람이 같은 좌석을 예매하려 한다.
한 명이 먼저 앉으면 다른 한 명은 못 앉는다.
여기서 갈림길이 생긴다.
미리 좌석을 잠글 것인가, 일단 둘 다 예매하게 두고 나중에 충돌을 처리할 것인가.
전자가 비관적 락이고 후자가 낙관적 락이다.
이름에 "락"이 들어 있지만 비관적 락만 DB 락을 쓴다.
낙관적 락은 락을 안 건다.
충돌을 감지하는 전략이지 잠그는 전략이 아니다.

## 비관적 락의 철학

"충돌이 날 거야. 미리 막자."
이 생각이 출발점이다.
데이터를 읽을 때부터 잠근다.
내가 다 쓸 때까지 아무도 건드리지 못하게 한다.

```sql
SELECT * FROM seats
WHERE seat_id = 'A1' FOR UPDATE;
```

이 순간 `seat_id = 'A1'` 행에 X Lock이 걸린다.
다른 트랜잭션이 같은 행을 읽으려 해도 `FOR UPDATE`가 걸려 있으면 기다려야 한다.
확실하다. 충돌 자체가 발생하지 않는다.

## 비관적 락이 빛나는 곳

[재고 차감]
남은 수량이 1개인데 동시에 3명이 주문한다.
읽고 확인하고 차감하는 사이에 누군가 먼저 가져가면 재고가 마이너스가 된다.
`FOR UPDATE`로 선점하면 순서가 강제된다.

[포인트 차감]
잔액 10,000원에서 7,000원과 5,000원을 동시에 쓴다.
둘 다 잔액을 읽고 "충분하다"고 판단하면 합계 12,000원이 빠진다.
비관적 락으로 직렬화하면 두 번째는 잔액 부족으로 실패한다.

[좌석 예매]
같은 좌석을 두 명이 동시에 잡는 건 허용 불가다.
충돌 비용이 크다. 미리 막는 게 맞다.

## 비관적 락의 대가

1. 잠그는 순간 다른 트랜잭션은 기다린다.
2. 기다리는 시간이 곧 응답 시간이다.
3. 트랜잭션이 길어지면 대기열이 쌓인다.
4. 대기열이 쌓이면 커넥션 풀이 고갈된다.
5. 커넥션 풀이 고갈되면 서비스가 멈춘다.
6. 그리고 데드락.

A가 행 1을 잡고 행 2를 기다린다.
B가 행 2를 잡고 행 1을 기다린다.
비관적 락의 고전적인 함정이다.
비관적 락은 안전하지만 성능과 맞교환하는 전략이다.

## 낙관적 락의 철학

"충돌은 드물어. 일단 진행하자."
잠그지 않는다.
읽을 때 버전을 기억해두고 쓸 때 버전이 바뀌었는지만 확인한다.

```sql
UPDATE orders
SET status = 'confirmed', version = 2
WHERE order_id = 1001 AND version = 1;
```

affected rows가 1이면 성공. 0이면 누군가 먼저 수정한 것이다.
락을 안 걸었으니 대기가 없다.
대기가 없으니 데드락도 없다.

## 낙관적 락이 빛나는 곳

[게시글 수정]
같은 글을 동시에 편집하는 일은 드물다.
읽기가 압도적으로 많은 시스템이다.
매번 `FOR UPDATE`를 거는 건 낭비다.

[장바구니 업데이트]
내 장바구니를 다른 사람이 수정할 일은 없다.
충돌 확률이 거의 0에 가깝다.

[설정값 변경]
관리자가 설정을 바꾸는 건 하루에 몇 번이다.
동시에 같은 설정을 바꿀 확률은 극히 낮다.

핵심은 충돌 빈도다.
충돌이 드물면 낙관적 락이 이긴다.

## 낙관적 락의 대가

충돌이 나면 재시도해야 한다.
그런데 재시도를 구현 안 하는 팀이 많다.

```
UPDATE ... WHERE version = 1;
→ affected rows = 0
→ 그냥 실패 처리
→ 사용자에게 "다시 시도하세요"
```

이건 낙관적 락이 아니다. 그냥 실패를 방치하는 것이다.
낙관적 락을 쓰려면 반드시 재시도 로직이 있어야 한다.

- 읽기부터 다시 한다.
- 최신 버전을 가져오고 다시 시도한다.
- 최대 재시도 횟수도 정해야 한다.

재시도 없는 낙관적 락은 안전벨트 없는 차와 같다.

## 실무에서 흔한 실수 1: 낙관적인데 재시도가 없다

JPA의 `@Version`을 쓰면 `OptimisticLockException`이 자동으로 던져진다.
그런데 그 예외를 catch하는 코드가 없다.
컨트롤러에서 500 에러로 빠진다.
사용자는 "서버 오류"를 본다.
`@Version`을 선언하는 건 시작이지 끝이 아니다.
예외를 잡고, 다시 읽고, 다시 시도하는 것까지가 낙관적 락의 구현이다.

## 실무에서 흔한 실수 2: 비관적인데 범위가 넓다

인덱스 없이 FOR UPDATE를 건다.

```sql
SELECT * FROM orders
WHERE status = 'pending' FOR UPDATE;
```

status에 인덱스가 없으면 InnoDB는 풀 테이블 스캔을 한다.
스캔한 모든 행에 락이 걸린다.
의도한 건 pending 주문 10건인데 실제로는 100만 건에 락이 걸린다.
FOR UPDATE에는 인덱스가 필수다.
인덱스 없는 비관적 락은 문 하나를 잠그려다 건물 전체를 잠그는 것이다.

## 실무에서 흔한 실수 3: 비관적 락 안에서 외부 호출

```
BEGIN;
SELECT ... FOR UPDATE; -- 락 획득
call_payment_api(); -- 외부 API 호출 (2초)
UPDATE ...;
COMMIT; -- 락 해제
```

외부 API가 2초 걸리면 락도 2초 동안 유지된다.
그 사이 같은 행을 원하는 트랜잭션은 전부 대기한다.
트랜잭션 안에서 외부 호출을 하면 안 된다.
락 보유 시간을 최소화하는 것이 철칙이다.
외부 호출은 트랜잭션 밖에서 한다.

## 두 전략의 판단 기준

결정하는 변수는 두 개다.
충돌 빈도와 충돌 비용.

[충돌이 잦고 비용이 크다]
재고, 포인트, 좌석.
비관적 락.
충돌을 허용할 수 없으니 미리 막는다.

[충돌이 드물고 비용이 작다]
게시글, 설정, 프로필.
낙관적 락.
대부분 충돌이 안 나니 잠글 이유가 없다.

[충돌이 잦은데 낙관적 락을 쓰면]
재시도가 폭발한다.
한 번에 될 걸 세 번 네 번 시도한다.
오히려 비관적 락보다 느려진다.

## 하이브리드 전략

둘 다 쓸 수 있다. 같은 시스템 안에서도 상황에 따라 다르다.

- 주문 생성은 낙관적 락.
  - 주문이 겹칠 확률은 낮다.
- 결제 차감은 비관적 락.
  - 잔액이 마이너스가 되면 안 된다.
- 재고 차감은 비관적 락.
  - 동시 접근이 몰리는 핫스팟이다.
- 상품 정보 수정은 낙관적 락.
  - 관리자 한 명이 수정하는 경우가 대부분이다.

도메인별로 다르게 적용하는 게 현실이다.
전부 비관적이면 느리고, 전부 낙관적이면 불안하다.

## 면접에서 이 질문이 나오면

"낙관적 락과 비관적 락의 차이가 뭔가요?"
정의를 설명하는 건 누구나 한다. 면접관이 듣고 싶은 건 그다음이다.

- "그래서 어떤 상황에 어느 쪽을 쓰시겠습니까?"
  - 충돌 빈도와 비용으로 답한다.
- "낙관적 락에서 충돌이 나면 어떻게 처리하나요?"
  - 재시도 로직을 설명한다.
  - 최대 재시도 횟수, 백오프 전략까지 말하면 좋다.
- "비관적 락의 단점은?"
  - 데드락과 트랜잭션 길이 문제를 말하고 접근 순서 통일, 인덱스 필수, 외부 호출 금지를 덧붙인다.

## DBA 관점에서의 정리

DBA에게 낙관적 락은 보이지 않는다.
version 컬럼의 WHERE 절일 뿐이다.
DB 입장에서는 평범한 UPDATE다.
비관적 락은 보인다.
락 대기가 쌓이고 데드락이 터진다.
`SHOW ENGINE INNODB STATUS`에 흔적이 남는다.
그래서 DBA가 더 신경 쓰는 건 비관적 락이다.
FOR UPDATE가 인덱스를 타는지, 트랜잭션이 얼마나 열려 있는지, 외부 호출이 끼어 있진 않은지.
락을 쓰는 건 개발자의 판단이다.
락이 문제가 됐을 때 전화받는 건 DBA다.
그래서 어느 쪽이든 원리를 알아야 한다.
