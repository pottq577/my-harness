# 데이터베이스 OOM의 실체: t4g.medium이 자꾸 재부팅되는 이유

새벽에 알림이 온다. "DB 인스턴스가 재시작되었습니다."
코드를 배포한 것도 아니고 유지보수 윈도우도 아니다. 그냥 재부팅됐다.
로그를 보면 OOM. 운영체제가 메모리를 다 쓴 프로세스를 죽인 것이다. 데이터베이스가 그 대상이 됐다.
t4g.medium은 메모리가 4GB다.
DB를 올리기엔 충분해 보이지만 실제로는 아슬아슬한 줄타기다.

## OOM Killer란

리눅스에는 OOM Killer가 있다.
시스템 메모리가 고갈되면 커널이 프로세스를 골라서 죽인다.
어떤 프로세스를 죽일지는 oom_score로 결정한다.
메모리를 많이 쓰는 프로세스가 높은 점수를 받는다.
DB 서버에서 메모리를 가장 많이 쓰는 건 당연히 데이터베이스 프로세스다.
메모리가 부족해지면 DB가 가장 먼저 죽는다.
RDS에서는 이게 인스턴스 재부팅으로 나타난다.

## 4GB는 왜 부족한가

t4g.medium의 메모리는 4GB다. 숫자만 보면 작지 않다.
하지만 DB가 쓰는 메모리는 하나가 아니다.

```text
총 메모리 사용량 =
Buffer Pool
+ (커넥션당 버퍼 × 동시 커넥션 수)
+ OS 오버헤드
+ 글로벌 버퍼
+ Performance Schema
```

각각이 메모리를 먹는다.
4GB는 이 합계를 감당하기에 생각보다 빠듯하다.

## Buffer Pool: 가장 큰 덩어리

InnoDB Buffer Pool은 DB 메모리의 대부분을 차지한다.
Aurora와 RDS MySQL의 기본 설정은 대체로 사용 가능 메모리의 75% 수준이다.
4GB 인스턴스면 약 2.5~3GB.
Buffer Pool은 디스크 읽기를 줄여주는 캐시다. 크면 클수록 쿼리가 빠르다. 그래서 가능한 한 크게 잡으려 한다.
문제는 Buffer Pool이 크면 나머지에 쓸 메모리가 줄어든다는 것이다.
3GB를 Buffer Pool에 주면 나머지 전부를 1GB로 돌려야 한다.

## 커넥션당 메모리: 숨은 폭탄

Buffer Pool은 고정이다. 서버가 뜨면 할당되고 크기가 안 변한다.
위험한 건 커넥션당 메모리다. 이건 변동이다.
하나의 커넥션이 쿼리를 실행하면 정렬 버퍼, 조인 버퍼, 임시 테이블, 읽기 버퍼, 통신 버퍼가 할당된다.

```text
sort_buffer_size: 256KB
join_buffer_size: 256KB
read_buffer_size: 128KB
tmp_table_size: 16MB
thread_stack: 256KB
```

커넥션 하나가 가벼울 때는 1~2MB. 무거운 쿼리를 돌리면 20MB 이상 먹는다.

## 곱셈의 공포

커넥션이 10개면 괜찮다. 20MB × 10 = 200MB.
커넥션이 100개면 이야기가 달라진다. 20MB × 100 = 2GB.
Buffer Pool 3GB + 커넥션 메모리 2GB = 5GB.
인스턴스 메모리는 4GB다. 이게 OOM이다.
핵심은 max_connections 숫자가 아니라 동시에 무거운 쿼리를 실행하는 커넥션 수다.
100개가 연결돼 있어도 대부분 idle이면 괜찮다.
100개가 동시에 정렬을 하면 터진다.

## tmp_table_size: 가장 위험한 파라미터

커넥션당 메모리 중 가장 큰 변동폭을 만드는 게 tmp_table_size와 max_heap_table_size다.
GROUP BY나 서브쿼리 결과가 이 크기를 넘으면 디스크 임시 테이블로 전환된다. 안 넘으면 메모리에 잡힌다.
기본값이 16MB라면 50개 커넥션이 동시에 임시 테이블을 만들면 16MB × 50 = 800MB가 순간적으로 필요하다.
4GB 인스턴스에서 이건 치명적이다.
tmp_table_size를 낮추면 디스크 I/O는 늘지만 OOM은 막는다.

## Performance Schema의 메모리

잘 모르는 사이에 메모리를 먹는 주범.
Performance Schema가 켜져 있으면 계측 데이터를 메모리에 저장한다.
커넥션 수와 계측 항목 수에 비례해서 늘어난다.
RDS와 Aurora의 상세 DB 부하 분석 기능은 Performance Schema 계측을 사용할 수 있으므로 현재 파라미터와 메모리 사용량을 함께 확인한다.
기존 Performance Insights 콘솔 경험은 종료됐고 현재는 CloudWatch Database Insights가 기본 진입점이다.
작은 인스턴스에서는 이 오버헤드가 수백 MB에 달할 수 있다.
4GB 인스턴스에서 Performance Schema가 200~400MB를 먹으면 체감이 크다.
끄기 어렵다면 `performance_schema_max_table_instances`나 `performance_schema_max_thread_instances`를 줄여서 메모리 사용량을 제한할 수 있다.

## OOM 징후 읽기

OOM은 갑자기 터지지만 징후는 있다.

[FreeableMemory]
CloudWatch에서 가장 먼저 볼 지표.
이 값이 지속적으로 줄어들면서 100MB 아래로 내려가면 위험하다.

[SwapUsage]
스왑이 늘어나면 이미 물리 메모리가 부족한 것이다.
DB에서 스왑은 성능 저하를 의미한다.

[DatabaseConnections]
커넥션 수가 갑자기 뛰는 시점과 FreeableMemory가 빠지는 시점이 겹치면 커넥션당 메모리가 원인이다.
이 세 지표를 같은 시간축에 놓고 보면 OOM의 원인이 보인다.

## 튜닝: 4GB 인스턴스 생존 가이드

4GB에서 OOM 없이 운영하려면 총합을 관리해야 한다.

```text
OS 예약 ~500MB + PerfSchema ~200MB + 글로벌 ~100MB
→ 남는 메모리 약 3.2GB
```

여기서 Buffer Pool과 커넥션 메모리를 나눈다.

```text
innodb_buffer_pool_size = 2G
max_connections = 100
sort_buffer_size = 256K
tmp_table_size = 8M
```

Buffer Pool을 2GB로 줄이면 커넥션 100개가 동시에 일해도 여유 메모리가 남는다.

## max_connections을 줄여라

가장 효과적인 방법.
t4g.medium에서 max_connections가 200 이상이면 위험하다.
대부분의 서비스는 실제로 동시에 활성화되는 커넥션이 전체의 10~20%다.
max_connections = 200인데 실제 동시 활성이 30개라면 max_connections = 80이면 충분하다.
애플리케이션 쪽 커넥션 풀 설정도 같이 봐야 한다.
풀 max가 50인 서버가 4대면 최대 200개가 들어올 수 있다.
DB의 max_connections보다 앱 서버 풀의 합계를 먼저 계산하라.

## 쿼리를 고치는 게 근본이다

메모리를 많이 쓰는 쿼리를 잡는 게 파라미터 튜닝보다 근본적이다.

[임시 테이블을 만드는 쿼리]
슬로우 쿼리 로그에서 `Created_tmp_tables`가 높은 쿼리.
GROUP BY, DISTINCT, 서브쿼리, UNION이 주범이다.
인덱스를 태우면 임시 테이블 자체가 사라진다.

[대량 정렬 쿼리]
ORDER BY가 인덱스를 못 타면 sort_buffer를 통째로 할당한다.
커버링 인덱스로 정렬을 없애면 sort_buffer 할당 자체가 안 일어난다.

[불필요하게 오래 열린 커넥션]
트랜잭션이 안 닫히고 idle 상태로 남으면 할당된 메모리가 반환되지 않는다.
`wait_timeout`을 적절히 짧게 잡아라.

## 스케일업 vs 최적화

파라미터를 다 줄이고 쿼리도 다 고쳤는데 여전히 OOM이면 인스턴스가 작은 것이다.
t4g.medium(4GB) → t4g.large(8GB).
메모리가 두 배면 Buffer Pool을 5GB로 올리고도 커넥션 메모리에 넉넉한 여유가 생긴다.

- 판단 기준:
  - FreeableMemory가 상시 500MB 이하면 스케일업.
  - 피크 타임에만 떨어지면 파라미터 튜닝.
  - 특정 쿼리 실행 시에만 떨어지면 쿼리 최적화.

스케일업은 비용이 든다.
하지만 새벽에 OOM으로 재부팅되는 것보다 월 몇만 원이 싸다.

## DBA 관점에서의 정리

OOM은 메모리 총합의 문제다.
Buffer Pool 하나가 아니라 `커넥션 수 × 커넥션당 버퍼의 곱셈`이 핵심이다.
4GB 인스턴스에서 살아남으려면:

- Buffer Pool을 2GB 이하로 잡아라.
- max_connections를 실제 필요한 만큼만 열어라.
- tmp_table_size를 8MB 이하로 내려라.
- Performance Schema 오버헤드를 인지하라.
- 그리고 CloudWatch를 봐라.

FreeableMemory가 떨어지는 시점과 커넥션이 뛰는 시점이 겹치면 그게 OOM의 시나리오다.
예방은 모니터링에서 시작된다.

## 마무리

OOM은 메모리가 부족해서 터지는 게 아니다. 메모리를 얼마나 쓸지 모르는 상태에서 터지는 것이다.
Buffer Pool은 고정이다. 예측할 수 있다.
커넥션당 메모리는 변동이다. 예측하기 어렵다.
고정은 크게, 변동은 작게.
이 원칙을 지키면 4GB에서도 OOM 없이 운영할 수 있다.

```text
innodb_buffer_pool_size를 줄이고
max_connections를 줄이고
tmp_table_size를 줄여라.
```

줄이는 게 답이다.
4GB에서는 넉넉함이 아니라 절제가 안정을 만든다.
