# 예약 시스템과 DB: 같은 시간에 두 명이 예약하면 생기는 일

"예약 기능 만들려는데, 그냥 INSERT 하면 되지 않나요?"
시간과 자리를 고르고 저장한다. 달력에 표시한다.
끝이라고 생각한다.
그런데 같은 시간에 두 명이 동시에 예약하면 둘 다 성공한다.
DB에는 같은 슬롯에 두 건이 들어간다.
예약은 데이터를 넣는 게 아니라 자리를 점유하는 것이다.
점유를 보장하는 건 INSERT가 아니라 락이다.

- 슬롯은 유니크 제약으로 보호하라.
- 대기열은 상태 머신으로 관리하라.
- 반복 예약은 규칙과 예외를 분리하라.
- no-show는 외부 스케줄러가 처리하라.
- 시간은 timezone 없이 저장하지 마라.

## 같은 시간, 같은 자리, 두 명

A가 오후 3시를 선택한다.
빈 자리를 확인하고 예약 버튼을 누른다.
그 사이 B도 오후 3시를 선택한다.
빈 자리를 확인하고 예약 버튼을 누른다.
둘 다 SELECT 시점에는 비어 있었다.
둘 다 INSERT에 성공한다.
더블 부킹이다.
UNIQUE 제약조건을 걸면 간단하다.
(resource_id, slot_time)에 유니크 인덱스.
두 번째 INSERT가 실패한다.
하지만 연속 슬롯을 잡아야 하면 유니크만으로는 부족하다.
2시간짜리 예약이 기존 1시간 예약과 겹치는지 범위 검증이 필요하다.

## 시간 슬롯을 어떻게 설계하는가

방법은 두 가지다.

[슬롯 테이블 방식]
30분 단위로 슬롯을 미리 만들어둔다.
예약하면 해당 슬롯의 상태를 occupied로 바꾼다.
단순하지만 유연하지 않다.
45분짜리 예약은 슬롯 두 개를 먹는다.

[시작-종료 시간 방식]
start_time과 end_time을 저장한다.
예약 전에 겹치는 구간이 있는지 쿼리한다.

```sql
SELECT COUNT(*) FROM reservations
WHERE resource_id = 5
AND start_time < '15:00'
AND end_time > '13:00'
```

유연하지만 겹침 검증 쿼리가 매번 필요하다.
동시 요청이 많으면 경합이 생긴다.

## 캘린더 뷰라는 비싼 쿼리

사용자가 달력을 열면 한 달치 예약을 한 번에 보여줘야 한다.
리소스가 회의실 10개라면 10개 × 30일 × 시간 슬롯.
한 번의 화면 렌더링에 수백 건의 예약 레코드를 읽는다.
여기에 "빈 시간 보기" 필터를 넣으면 예약이 없는 슬롯을 계산해야 한다.
없는 것을 찾는 건 있는 것을 찾는 것보다 비싸다.
인덱스는 (resource_id, start_time)이 기본이다.
날짜 범위 쿼리가 빈번하므로 파티셔닝까지 고려하게 된다.

## 취소와 대기열의 순서

예약이 꽉 찼다.
대기열에 3명이 있다.
1번 예약자가 취소한다.
누구에게 기회가 가는가.
대기 1번에게 알림을 보낸다.
5분 안에 확정하지 않으면 2번에게 넘어간다.
이 로직은 DB만으로 안 된다.
타이머가 필요하다. 상태 전이가 필요하다.
대기 → 알림 발송 → 확정 대기 → 확정 or 만료.
상태가 4개이고 시간 제한이 있으면 스케줄러나 메시지 큐 없이는 관리할 수 없다.
예약 취소 한 건이 이렇게 복잡하다.

## 반복 예약의 저장 문제

"매주 월요일 오전 10시."
사용자는 한 문장이다. DB는 어떻게 저장하는가.

[방법 1: 전부 펼쳐서 저장]
52주면 52건의 레코드를 만든다.
단순하지만 "매주 월요일" 전체를 취소하려면 52건을 다 지워야 한다.

[방법 2: 규칙으로 저장]
반복 규칙을 별도 테이블에 넣는다.
RRULE 형식. 매주, 월요일, 시작일, 종료일.
단순하지만 "다음 주만 취소"가 어렵다.
예외 테이블이 하나 더 필요하다.
반복 규칙 + 예외 목록 + 실체화된 인스턴스.
테이블 세 개가 엮인다.
캘린더 앱이 복잡한 이유다.

## no-show 처리는 누가 하는가

예약 시간이 지났는데 안 왔다.
상태를 no-show로 바꿔야 한다.
사용자가 트리거하는 게 아니라 시간이 트리거하는 이벤트다.
DB에 스케줄러를 넣을 수 있다. MySQL EVENT나 pg_cron.
그런데 분 단위로 수만 건을 스캔하면 DB에 부하를 준다.
외부 스케줄러가 주기적으로 "시간 지난 예약"을 배치로 상태 변경하는 게 낫다.

```sql
UPDATE reservations
SET status = 'no_show'
WHERE status = 'confirmed'
AND end_time < NOW() - INTERVAL 30 MINUTE
```

비즈니스 로직인데 실행 주체가 DB 밖에 있다.
누가 돌릴지를 정해야 한다.

## 시간대의 함정

서울에서 오후 3시에 예약했다. DB에는 UTC 06:00으로 저장됐다.
도쿄 사용자가 같은 시스템을 쓴다.
오후 3시를 선택했는데 서울의 오후 3시와 같은 슬롯이 아니다.
UTC로 저장하는 건 맞다.
문제는 보여줄 때다.
사용자의 timezone을 알아야 하고 서머타임이 있는 나라면 계절마다 바뀐다.
"매주 월요일 10시"를 UTC로 저장했는데 서머타임이 바뀌면 현지 시각이 달라진다.
사용자는 예약 시간이 바뀐 줄 안다.
시간은 숫자가 아니라 맥락이다.
timezone 없는 시간 데이터는 불완전하다.

## DBA 관점에서의 정리

예약 시스템은 달력 UI 뒤에 동시성 제어가 숨어 있다.

- 슬롯은 유니크 제약으로 보호하라.
- 대기열은 상태 머신으로 관리하라.
- 반복 예약은 규칙과 예외를 분리하라.
- no-show는 외부 스케줄러가 처리하라.
- 시간은 timezone 없이 저장하지 마라.

더블 부킹이 처음 발생했을 때 고치는 비용보다 처음부터 유니크 제약을 거는 비용이 싸다.
예약은 데이터를 넣는 게 아니라 자리를 점유하는 것이다.
점유를 보장하는 건 INSERT가 아니라 락이다.
