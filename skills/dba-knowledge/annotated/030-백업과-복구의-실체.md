# 백업과 복구의 실체: 풀백업은 쉬운데 복구는 왜 어려운가

"백업 있죠?" 장애 나면 가장 먼저 나오는 질문이다.
백업은 있다. 매일 자동으로 돌아간다. 알람도 없고 용량도 잘 쌓인다.
그런데 복구해본 적은 없다. 복구가 되는지 확인한 적도 없다.
백업은 쉽다. 복구가 어렵다.

## 논리 백업

데이터를 SQL 문으로 내보내는 방식이다.
MySQL: mysqldump. PostgreSQL: pg_dump

```bash
mysqldump --single-transaction mydb > backup.sql
pg_dump -Fc mydb > backup.dump
```

- 장점:
  - 사람이 읽을 수 있다.
  - 다른 버전, 다른 서버로 복원 가능.
  - 특정 테이블만 복원 가능.
- 단점:
  - 느리다. 10GB 넘으면 시간이 오래 걸린다.
  - 복원은 더 느리다.
  - INSERT 문을 하나씩 실행하니까.

## 물리 백업

데이터 파일을 통째로 복사하는 방식이다.
MySQL: Percona XtraBackup. PostgreSQL: pg_basebackup

```bash
xtrabackup --backup --target-dir=/backup/
pg_basebackup -D /backup/ -Ft -z
```

- 장점:
  - 빠르다. 파일 복사니까.
  - 복원도 빠르다. 파일을 제자리에 놓으면 된다.
- 단점:
  - 같은 버전, 같은 아키텍처에서만 복원 가능.
  - 특정 테이블만 꺼내기 어렵다.
  - 백업 중에도 서비스 가능하지만 I/O 부하가 증가한다.
  - 운영 환경에서는 물리 백업이 기본이다.
  - 논리 백업은 보조 수단으로 병행한다.

## 스냅샷 백업 — 클라우드 시대의 표준

AWS RDS를 쓰면 매일 자동으로 스냅샷이 찍힌다. 스냅샷은 EBS 볼륨의 포인트인타임 복사본이다.
실제로는 변경된 블록만 저장하므로 전체 크기보다 훨씬 적은 공간을 차지한다.
스냅샷 복원 시간은 데이터 크기가 아니라 I/O 패턴에 따라 달라진다.
"Lazy Loading" — 처음 읽는 블록은 스냅샷에서 실시간으로 가져온다.
복원 직후 성능이 느릴 수 있다. 워밍업이 필요한 이유다.

## PITR(Point-In-Time Recovery) — 시점 복구

"어제 14시 상태로 돌려주세요."
원리는 단순하다. 풀 백업 + 트랜잭션 로그 재실행.

[어제 02:00 풀 백업]
→ binlog/WAL 순서대로 재실행
→ [어제 14:00에 멈춤]

삭제 직전, 실수 직전으로 정확하게 되돌릴 수 있다.
AWS RDS는 자동으로 PITR을 지원한다.
백업 보존 기간(기본 7일) 내에서 1초 단위로 복원 가능하다.
새 인스턴스로 복원된다.

## PITR의 실제 소요 시간

"1초 단위로 복원 가능"이 "1초 만에 복원 가능"은 아니다.
AWS RDS PITR 절차:

1. 직전 스냅샷 선택 (자동)
2. 스냅샷에서 새 인스턴스 생성
3. 트랜잭션 로그를 목표 시점까지 적용

인스턴스 생성에 수십 분, 로그 적용에 수 분~수 시간.
DB 크기와 변경량에 따라 크게 달라진다.
트랜잭션 로그가 많을수록 (= 스냅샷과 목표 시점 사이 변경이 많을수록) 복원이 오래 걸린다.
장애 상황에서 "30분이면 되겠지"가 2시간이 되는 경우를 봤다.

## 복원 테스트를 안 하면

백업이 있어도 복원이 안 되는 경우:

[케이스 1]
mysqldump가 매일 성공하지만 실은 빈 파일이었다.
cron 로그만 보고 성공으로 간주.

[케이스 2]
물리 백업은 있지만 복원 후 바이너리 호환이 안 맞아 시작이 안 된다.
MySQL 마이너 버전 차이.

[케이스 3]
스냅샷 복원 했는데 보안 그룹이 다르게 설정돼서 애플리케이션이 접근을 못 한다.
복원 테스트를 주기적으로 하지 않으면 백업은 정신적 안정제일 뿐이다.

## 복원 순서가 중요하다

"이 테이블만 복원해주세요." 이 요청이 생각보다 까다롭다.
풀 백업에서 특정 테이블만 꺼내려면:
논리 백업(mysqldump): 단일 테이블 복원 가능하지만 느리다.
물리 백업(xtrabackup): InnoDB에서 특정 테이블 추출은 가능하나 exportable tablespace 옵션 필요.
스냅샷: 전체 인스턴스 복원만 가능. 특정 테이블만 꺼내려면 복원 인스턴스에서 mysqldump로 뽑아야 한다.
"테이블 하나" 복원이 "전체 DB 복원"보다 오래 걸리기도 한다.

## 대형 DB의 백업 전략

TB 급 DB의 백업은 그 자체로 도전이다.
mysqldump로 1TB를 뽑으면 수 시간. 복원은 그 이상.
실전 전략:

[계층 분리]
핫 데이터(최근 3개월)는 매일 백업.
콜드 데이터(이전)는 주 1회.
아카이브 데이터는 별도 스토리지.

[병렬 백업]
mydumper(MySQL) — 멀티 스레드 논리 백업.
pg_dump -j(PostgreSQL) — 병렬 dump.

[증분 백업]
xtrabackup의 incremental 모드.
변경된 페이지만 백업.
복원 시 전체 + 증분을 합쳐야 한다.

## 바이너리 로그 백업

풀 백업 사이의 변경은 트랜잭션 로그가 커버한다.
MySQL: mysqlbinlog로 binlog를 실시간 백업.

```bash
mysqlbinlog --read-from-remote-server --raw \
--host=db-server --result-file=/backup/binlog/
```

PostgreSQL: WAL 아카이빙.
archive_command로 WAL 파일을 S3나 별도 스토리지에 자동 복사.
이 로그가 없으면 마지막 풀 백업 이후의 변경이 전부 유실된다.
풀 백업만 있으면 RPO가 24시간. 로그 백업까지 있으면 RPO가 수 초~수 분.

## RPO와 RTO

장애 복구 계획의 두 축이다.

[RPO — Recovery Point Objective]
"최대 얼마만큼의 데이터를 잃어도 되는가"
RPO 1시간 = 최근 1시간 데이터 유실 허용.
RPO 0 = 데이터 유실 불가 → 동기 복제 필수.

[RTO — Recovery Time Objective]
"복구까지 최대 얼마나 걸려도 되는가"
RTO 30분 = 30분 안에 서비스 재개.
RTO 4시간 = 백업 복원으로 충분.

RPO를 줄이려면 로그 백업 주기를 짧게. RTO를 줄이려면 복원 절차를 자동화.
둘 다 0에 가깝게 하려면 비용이 급증한다.

## Delayed Replica

의도적으로 지연된 복제 서버.
"1시간 전 상태"를 항상 유지한다.
MySQL:

```sql
CHANGE REPLICATION SOURCE TO
SOURCE_DELAY = 3600; -- 1시간 지연
```

PostgreSQL:
`recovery_min_apply_delay = '1h'`
실수로 DROP TABLE을 했을 때 Delayed Replica에서 해당 테이블을 꺼내면 PITR보다 빠르게 복구할 수 있다.
풀 복원은 수 시간이지만 Replica에서 덤프는 수 분이다.
보험용 Replica다. 유지 비용은 들지만 장애 시 값어치를 한다.

## 삭제 사고 대응 플레이북

`DELETE FROM orders WHERE created_at < '2026-01-01'` 을 실수로 WHERE 없이 실행했다.

[즉시 대응]

1. 해당 세션 KILL (진행 중이라면)
2. 트래픽 차단 (추가 변경 방지)
3. binlog/WAL에서 삭제 시점 확인

[복구 경로 선택]

1. Delayed Replica 있으면 → 거기서 덤프
2. 없으면 → PITR로 새 인스턴스 복원
3. binlog로 역방향 SQL 생성 (MySQL)

[복구 후]

데이터 정합성 검증 (행 수, 체크섬)
원인 분석 + 재발 방지

시간이 생명이다.
이 절차를 미리 문서화해두지 않으면 장애 상황에서 판단이 느려진다.

## 마무리

백업은 보험이다. 들어놓고 안 쓰면 좋지만, 쓸 때 작동하지 않으면 의미가 없다.
풀백업은 버튼 하나로 된다. 하지만 복구는 다르다.
어떤 백업에서 복원할 것인가, 특정 테이블만 가능한가, 얼마나 걸리는가, 복원 후 정합성은 어떻게 확인하는가.
이 질문에 답할 수 있으려면 복원을 해봐야 한다.
"백업은 매일 한다"가 아니라 "복원을 마지막으로 테스트한 게 언제인가"가 DBA에게 더 중요한 질문이다.
