# 무중단 스키마 변경: ALTER TABLE이 서비스를 멈추는 이유

"온라인 DDL 해보셨어요?"
면접에서 이 질문이 나오면 주니어와 시니어가 갈린다.
컬럼 하나 추가하는 게 뭐가 어렵냐고 생각하겠지만, 수억 건짜리 테이블에서 ALTER TABLE을 날리면 서비스가 멈출 수 있다.
왜 멈추는지 모르면 운영을 맡길 수 없다.

## ALTER TABLE의 실체

MySQL에서 ALTER TABLE은 원래 이렇게 동작했다.

1. 새 테이블을 만든다.
2. 기존 데이터를 전부 복사한다.
3. 원본을 삭제하고 새 테이블을 원본 이름으로 바꾼다.

10GB 테이블이면 10GB를 통째로 복사한다.
그 동안 쓰기는 차단된다.
복사 시간이 곧 장애 시간이다.
이걸 "Table Copy" 방식이라 한다.
MySQL 5.5 이전의 기본 동작이었다.

## MySQL Online DDL의 등장

MySQL 5.6부터 InnoDB에 Online DDL이 추가됐다.

```sql
ALTER TABLE orders
ADD COLUMN memo VARCHAR(200),
ALGORITHM=INPLACE, LOCK=NONE;
```

`ALGORITHM=INPLACE`는 테이블 복사 없이 InnoDB 내부에서 직접 변경한다.
`LOCK=NONE`은 변경 중에도 읽기/쓰기를 허용한다.
모든 변경이 이렇게 되면 좋겠지만, 그렇지 않다.

## 되는 것과 안 되는 것

Online DDL이라고 다 "온라인"은 아니다.

[INPLACE 가능]
컬럼 추가, 인덱스 추가/삭제, 컬럼 이름 변경, VARCHAR 길이 확장(제한적).

[COPY 필요: 쓰기 차단]
컬럼 타입 변경 (INT→BIGINT), 문자셋 변경, PK 삭제.
컬럼 타입을 바꾸면 모든 행을 다시 써야 한다.
INPLACE로 할 수 없다.

면접에서 "어떤 ALTER가 온라인이고 어떤 게 아닌지" 물어보면 이 구분을 대답해야 한다.

## Instant DDL

MySQL 8.0.12부터 `ALGORITHM=INSTANT`가 추가됐다.

```sql
ALTER TABLE orders
ADD COLUMN memo VARCHAR(200),
ALGORITHM=INSTANT;
```

메타데이터만 변경한다. 데이터를 건드리지 않는다.
테이블이 1TB여도 1초 안에 끝난다.
단, 제약이 있다.
컬럼 추가는 테이블 끝에만 가능하고, 컬럼 삭제나 순서 변경은 8.0.29부터다.
인덱스 추가는 Instant로 안 된다.

## Metadata Lock 문제

Online DDL이라도 시작과 끝에서 Metadata Lock(MDL)을 잡는다.
문제는 이 MDL이 "줄 서기"를 만든다는 것이다.

1. 트랜잭션 A가 SELECT 실행 중 (MDL shared 보유)
2. ALTER TABLE이 MDL exclusive 대기
3. 이후 모든 SELECT가 ALTER 뒤에 줄을 선다

장시간 실행 쿼리 하나가 ALTER를 막고, ALTER가 뒤따르는 모든 트래픽을 막는다.
쿼리 하나 → DDL → 전체 서비스 중단.
DBA가 DDL 전에 long query부터 확인하는 이유다.

## pt-online-schema-change

Percona에서 만든 도구다.
MySQL의 Online DDL 한계를 우회한다.

[동작 원리]

1. 원본과 같은 구조의 빈 테이블을 만든다
2. 빈 테이블에 ALTER를 적용한다
3. 원본에 트리거 3개를 건다 (INSERT/UPDATE/DELETE)
4. 원본 데이터를 청크 단위로 복사한다
5. 트리거가 실시간 변경분을 반영한다
6. 복사 완료 후 RENAME TABLE로 교체한다

원본 테이블은 변경 중에도 정상 운영된다.
RENAME은 원자적이라 순간적으로 전환된다.

## gh-ost

GitHub에서 만든 도구다.
pt-osc의 트리거 방식이 싫어서 만들었다.

[동작 원리]

1. 빈 shadow 테이블을 만든다
2. 원본 데이터를 청크 단위로 복사한다
3. binlog를 구독해서 변경분을 반영한다
4. 복사 완료 후 cut-over로 교체한다

트리거 대신 binlog를 쓴다.
트리거가 원본 테이블에 부하를 주는 문제가 없다.
쓰로틀링도 외부에서 제어할 수 있다.
replication lag이 올라가면 자동으로 멈추고, 내려가면 다시 진행한다.

## pt-osc vs gh-ost

둘 다 쓰는 곳이 있고, 하나만 쓰는 곳도 있다.

[pt-osc가 유리한 경우]
FK(Foreign Key)가 있는 테이블.
gh-ost는 FK를 지원하지 않는다.
설정이 단순하고 빠르게 실행할 때.

[gh-ost가 유리한 경우]
대형 테이블에서 부하 제어가 중요할 때.
트리거 오버헤드를 피하고 싶을 때.
실시간 쓰로틀링이 필요할 때.

면접에서 "둘 중 뭘 쓰나요?"보다 "왜 그걸 선택했나요?"가 더 중요하다.
근거를 말할 수 있어야 한다.

## PostgreSQL은 다르다

PostgreSQL에서 대부분의 ALTER TABLE은 논블로킹이다.

```sql
ALTER TABLE orders ADD COLUMN memo TEXT;
```

이건 메타데이터만 바꾼다.
테이블 크기와 무관하게 즉시 끝난다.
MySQL과 근본적으로 다른 점이다.
인덱스 추가도 CONCURRENTLY 옵션으로 락 없이 가능하다.

```sql
CREATE INDEX CONCURRENTLY idx_memo
ON orders(memo);
```

PostgreSQL DBA는 pt-osc 같은 도구가 왜 필요한지 잘 모를 수 있다.

## PostgreSQL 11 이전의 함정

PostgreSQL도 함정은 있었다.
11 이전에는 DEFAULT가 있는 컬럼 추가가 모든 행을 다시 써야 했다.

```sql
-- PG 10 이하: 전체 행 rewrite 발생
ALTER TABLE orders
ADD COLUMN status TEXT DEFAULT 'pending';
```

테이블이 크면 오래 걸렸다.
그래서 컬럼을 NULL로 추가하고 나중에 DEFAULT를 설정하는 우회가 필요했다.
PostgreSQL 11부터 non-volatile DEFAULT는 메타데이터만 변경한다.
이 개선 하나로 운영 부담이 크게 줄었다.

## 대형 테이블 마이그레이션 패턴

도구 하나로 안 되는 경우도 있다.
수십억 건, 수백GB 테이블의 구조 변경은 전략이 필요하다.

[배치 업데이트]
새 컬럼 추가 후 값을 채울 때 한 번에 UPDATE하면 락과 로그가 폭발한다.
1만 건씩 나눠서 실행한다.

[듀얼 라이트]
새 테이블에 쓰기를 병행하고, 배치로 구 데이터를 이관한 뒤, 읽기를 전환하고, 구 테이블을 제거한다.

[블루-그린]
새 구조의 레플리카를 준비하고, 동기화 완료 후 트래픽을 전환한다.

## 무엇이 잘못될 수 있는가

스키마 변경 도구를 쓰더라도 실패하는 경우는 있다.

[디스크 공간]
shadow 테이블은 원본과 같은 크기다.
100GB 테이블이면 100GB가 추가로 필요하다.
디스크가 부족하면 도중에 실패한다.

[레플리케이션 랙]
복사 부하로 replica가 밀린다.
gh-ost는 자동 쓰로틀링이 되지만, pt-osc는 설정을 안 하면 계속 밀어붙인다.

[교체 시점 데드락]
RENAME TABLE 순간에 진행 중인 트랜잭션과 충돌할 수 있다.
짧지만 실패 가능성이 존재한다.

## DBA 관점에서의 정리

운영에서 DDL은 가장 긴장되는 작업이다.
실행 전 확인하는 체크리스트가 있다.
long query 없는지, 디스크 여유 있는지, 레플리케이션 정상인지, 트래픽 낮은 시간대인지.
도구 선택도 중요하지만 "언제, 어떤 조건에서 실행하는가"가 사고를 막는 핵심이다.
면접에서 "ALTER TABLE 날려본 적 있나요?"가 아니라 "서비스 중에 스키마를 바꿔본 적 있나요?"가 진짜 질문이다.

## 마무리

ALTER TABLE은 단순한 명령어가 아니다.
테이블 복사, 메타데이터 락, 레플리케이션 부하.
이 세 가지가 서비스를 멈추는 원인이다.
MySQL은 pt-osc와 gh-ost로 우회하고, PostgreSQL은 대부분 즉시 끝나지만 DEFAULT 컬럼의 함정은 알아야 한다.
무중단 스키마 변경의 핵심은 "데이터를 복사하지 않는 것"이다.
복사하지 않으면 시간이 걸리지 않고, 시간이 걸리지 않으면 서비스가 멈추지 않는다.
도구를 아는 것보다 왜 그 도구가 필요한지 아는 것이 면접에서도, 운영에서도 더 중요하다.
