# 쇼핑몰과 DB: 장바구니 하나가 이렇게 어려운 이유

"쇼핑몰 하나 만드는데 DB는 뭘 챙겨야 해요?"
상품 등록, 장바구니, 주문. 셋 다 CRUD다.
그런데 사용자가 늘면 가장 먼저 깨지는 게 재고다.
그 다음이 주문이고 마지막이 정산이다.
쉽다고 생각한 순간부터 한 줄짜리 UPDATE가 사고가 된다.
재고는 읽지 말고 바로 빼라.
장바구니는 수명을 정하라.
주문과 결제는 트랜잭션을 분리하라.
주문 내역은 스냅샷으로 남겨라.
정산은 처음부터 분리하라.

## 재고는 숫자 하나인데 왜 이렇게 어려운가

재고는 정수 컬럼 하나다. 10개 남았으면 10이다.
문제는 두 명이 동시에 사는 순간이다.
A가 SELECT해서 10을 봤다. B도 SELECT해서 10을 봤다.
A가 UPDATE로 9를 쓴다. B도 UPDATE로 9를 쓴다.
재고는 8이어야 하는데 9가 됐다.
하나를 공짜로 판 셈이다.
해법은 두 가지다.
`SELECT FOR UPDATE`로 잠그거나 `UPDATE stock SET qty = qty - 1 WHERE qty > 0`으로 애초에 읽지 않고 바로 빼거나.
읽고 나서 쓰면 늦다.

## 장바구니는 어디에 저장하는가

장바구니를 DB에 넣으면 영구적이다. 로그인하고 일주일 뒤에 와도 그대로 있다.
편하지만 테이블이 빠르게 커진다.
대부분의 장바구니는 버려진다. 담기만 하고 주문하지 않는다.
한 달 지난 장바구니 100만 건. DB에는 쓰레기다.
세션에 넣으면 가볍다. 대신 로그아웃하면 사라진다.
Redis에 넣으면 절충이 된다. TTL로 30일 뒤 자동 삭제.
로그인 상태에서는 유지.
어디에 넣느냐는 기능이 아니라 데이터 수명의 문제다.

## 주문 순간의 트랜잭션 경계

사용자가 "결제" 버튼을 누르면 일어나야 하는 일이 많다.
재고 차감. 주문 레코드 생성. 결제 요청. 포인트 차감. 쿠폰 사용 처리.
이걸 하나의 트랜잭션에 넣으면 결제 API 응답이 3초 걸릴 때 DB 커넥션도 3초 동안 잠긴다.
전부 롤백하면 깔끔하지만 결제는 이미 PG사에서 승인됐다.
DB만 롤백해도 돈은 빠져나갔다.
주문과 결제는 하나의 트랜잭션이 아니다. 분리하고 보상 트랜잭션으로 묶어야 한다.

## 트랜잭션 경계를 넘는 패턴들

주문과 결제를 분리하면 실패를 어떻게 되돌리는가.

[Saga 패턴]
각 단계가 독립 트랜잭션이다.
재고 차감 → 주문 생성 → 결제 요청.
결제가 실패하면 보상 트랜잭션으로 재고를 되돌린다.
이벤트로 연결하는 Choreography, 중앙에서 순서를 관리하는 Orchestration.

[Outbox 패턴]
주문 INSERT와 이벤트를 같은 트랜잭션에 넣는다.
outbox 테이블에 이벤트를 함께 INSERT하고 별도 프로세스가 폴링해서 Kafka로 발행한다.
DB 트랜잭션이 이벤트 전달을 보장한다. 2PC는 느리고 장애에 취약하다.
실무에서는 Saga + Outbox 조합이 현실적이다.

## 상품 옵션이라는 조합 폭발

티셔츠 하나. 색상 5개, 사이즈 4개. 옵션 조합 20개.
각 조합마다 재고가 다르고 가격이 다를 수도 있다.
상품 테이블 1건에 옵션 테이블 20건. 옵션마다 재고 테이블 20건.
상품이 1만 개면 옵션은 20만 건이다.
상품 목록 페이지에서 "재고 있는 것만 보기"를 누르면 옵션 테이블까지 조인해야 한다.
인덱스가 없으면 무너진다.

## 주문 내역은 정규화하면 안 된다

주문 당시 상품 이름은 "여름 반팔 티". 한 달 뒤 상품명이 "쿨링 반팔 티"로 바뀌었다.
주문 테이블이 상품 테이블을 FK로 참조하면 주문 내역에 바뀐 이름이 뜬다.
고객은 산 적 없는 상품이 보인다.
가격이 오르면 과거 주문 금액까지 바뀌고 할인율이 바뀌면 정산이 꼬인다.
복사해야 할 것: 상품명, 단가, 수량, 옵션, 할인, 배송비.
컬럼을 늘리거나 JSON 컬럼에 주문 시점의 스냅샷을 통째로 넣는다.
환불할 때도 이 스냅샷이 기준이다.
"그때 이 가격이 얼마였는가"의 답이 주문 레코드 안에 있어야 한다.
정규화 원칙에 어긋나지만 비즈니스가 요구하는 비정규화다.

## 판매자가 늘어나면

쇼핑몰 하나에 판매자 하나면 단순하다. 마켓플레이스가 되면 달라진다.
주문 하나에 판매자가 셋이면 배송도 셋이고 정산도 셋이다.
정산 테이블이 생긴다. 판매자별 수수료율이 다르다. 정산 주기도 다르다.
매월 1일에 정산 배치가 돌면 수백만 건의 주문을 집계한다.
Writer에서 돌리면 서비스가 멈춘다.
Reader에서 돌리면 replica lag이 터진다.
정산은 별도 DB를 만들거나 이벤트 기반으로 실시간 집계해야 한다.
나중에 분리하려면 비용이 열 배다.

## 이벤트 트래픽이라는 시한폭탄

평소 주문 100건/분. 타임세일이 시작되면 10,000건/분. 100배가 갑자기 온다.
재고 차감이 한 행에 몰린다.
row lock 대기열이 길어진다.
커넥션 풀이 바닥난다.
타임아웃이 터진다.
사용자는 결제 버튼을 다시 누른다.
중복 주문이 생긴다.
대기열(Queue)을 앞에 두고 주문 요청을 순서대로 처리하면 DB는 일정한 속도로 소화할 수 있다.
DB가 빨라지는 게 아니라 DB에 도달하는 속도를 조절하는 것이다.

## 소규모에서 대규모로

작을 때는 하나의 DB로 충분하다. MySQL 하나에 상품, 주문, 정산이 다 있어도 된다.
트래픽이 늘면 분리가 시작된다.

[소규모: 하나의 RDBMS]
MySQL 또는 PostgreSQL.
장바구니, 주문, 정산이 같은 스키마. JOIN 하나로 주문과 상품을 조회한다.

[중규모: 캐시와 읽기 분리]
장바구니는 Redis로. 검색은 Elasticsearch로. 읽기는 Read Replica로 분산한다.
DB 하나는 유지하되 부하를 나눈다.

[대규모: 도메인별 DB 분리]
주문 DB, 상품 DB, 정산 DB.
정산도 정합성이 필요하면 RDBMS이 답이다. 분석 워크로드만 Redshift나 BigQuery로 빼면 된다.
서비스 간 통신은 이벤트 기반.
나누는 타이밍을 놓치면 모놀리식 DB의 한 쿼리가 전체를 멈춘다.

## DBA 관점에서의 정리

쇼핑몰은 CRUD의 집합처럼 보인다. 실제로는 동시성과 정합성의 전쟁터다.
재고는 읽지 말고 바로 빼라.
장바구니는 수명을 정하라.
주문과 결제는 트랜잭션을 분리하라.
주문 내역은 스냅샷으로 남겨라.
정산은 처음부터 분리하라.
작은 쇼핑몰일 때는 아무것도 안 터진다.
커진 다음에는 전부 터진다.
쉽다고 생각한 순간부터 한 줄짜리 UPDATE가 사고가 된다.
