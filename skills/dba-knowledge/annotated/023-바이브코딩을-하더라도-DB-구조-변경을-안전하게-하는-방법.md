# 바이브코딩을 하더라도 DB 구조 변경을 안전하게 하는 방법: ALTER TABLE 앞뒤로 확인해야 할 것들

Claude에서 "컬럼 추가해줘" 하면 ALTER TABLE 한 줄이 나온다.
로컬에서는 잘 된다. 그걸 운영에 그대로 날리면 서비스가 멈출 수 있다.
바이브코딩이 코드를 만들어줘도 DDL을 언제, 어떻게 실행할지는 알려주지 않는다.
그 판단이 장애를 막는다.

1. long query를 먼저 정리하라.
2. ALGORITHM을 반드시 명시하라.
3. 디스크 여유를 원본 크기의 2배 이상 확보하라.
4. Metadata Lock 대기를 반드시 모니터링하라.
5. 롤백 시나리오 없이 실행하지 마라.

쉽다고 생각한 순간부터
ALTER TABLE 한 줄이 장애가 된다.

## AI가 만든 DDL도 DDL이다

Cursor든 Claude든 "컬럼 하나 추가해줘" 하면 ALTER TABLE이 나온다. 로컬 SQLite에서는 0.01초면 끝난다.
운영은 다르다.
수억 건의 데이터가 있고, 초당 수천 건의 쿼리가 들어오고, 레플리카가 복제하고 있다.
AI가 DDL을 만들어주는 건 좋다.
하지만 그 DDL을 운영에 적용하는 건 사전 점검, 방법 선택, 실행, 모니터링, 검증. 다섯 단계의 작업이다.
코드를 만드는 것과 코드를 적용하는 것은 다르다.

## Online DDL의 세 가지 Algorithm

MySQL의 ALTER TABLE은
내부적으로 세 가지 Algorithm 중 하나를 탄다.

[COPY]
새 테이블을 만들고 데이터를 전부 복사한다.
복사하는 동안 쓰기가 차단된다.
테이블 크기가 곧 장애 시간이다.

[INPLACE]
InnoDB 내부에서 직접 변경한다.
테이블 복사가 없다.
`LOCK=NONE`과 함께 쓰면
변경 중에도 읽기/쓰기가 가능하다.

[INSTANT]
메타데이터만 변경한다.
데이터를 건드리지 않는다.
테이블이 1TB여도 1초 안에 끝난다.

```sql
ALTER TABLE orders
ADD COLUMN memo VARCHAR(200),
ALGORITHM=INPLACE, LOCK=NONE;
```

ALGORITHM을 명시하면 지원하지 않는 작업에서 에러를 반환한다.
명시하지 않으면 MySQL이 자동으로 고른다. 명시하는 쪽이 안전하다.

## 버전별 Online DDL의 진화

[MySQL 5.5 이전]
COPY만 존재했다.
ALTER TABLE = 테이블 전체 복사.
대형 테이블에서는 서비스 중단이 불가피했다.

[MySQL 5.6]
INPLACE가 도입됐다.
인덱스 추가/삭제, 컬럼 추가가 서비스를 멈추지 않고 가능해졌다.
"Online DDL"이라는 이름이 여기서 시작됐다.

[MySQL 8.0.12]
INSTANT가 등장했다.
컬럼 추가가 메타데이터 변경만으로 끝난다.
단, 테이블 마지막 위치에만 추가할 수 있었다.

[MySQL 8.0.29]
INSTANT의 범위가 크게 넓어졌다.
컬럼을 아무 위치에나 추가할 수 있고, 컬럼 삭제와 순서 변경도 Instant로 된다.
5.6 이전이면 pt-osc가 유일한 선택지였다.
지금은 Instant, INPLACE, pt-osc 순으로 고른다.

## Instant DDL의 함정

Instant는 빠르다. 하지만 공짜는 아니다.
Instant로 컬럼을 추가하면 기존 row에는 그 컬럼의 데이터가 물리적으로 없다.
읽을 때 메타데이터를 보고 기본값을 채운다.
Instant ALTER가 누적되면 row 내부에 "버전 격차"가 쌓인다.
읽을 때마다 버전 확인 비용이 붙는다.
Instant로 추가한 컬럼에 인덱스를 걸면 그 인덱스 생성은 Instant가 아니다. INPLACE나 COPY로 내려간다.
"Instant로 끝났다"고 방심하면 바로 다음 ALTER에서 걸린다.
Instant ALTER가 여러 번 쌓였으면 OPTIMIZE TABLE로 테이블을 다시 쓰는 것을 고려한다.
Instant의 빚을 갚는 작업이다.

## 사전 점검: long query

DDL 전에 가장 먼저 확인하는 건 장시간 실행 중인 쿼리다.
ALTER TABLE은 시작할 때 Metadata Lock을 요청한다.
실행 중인 쿼리가 있으면 그 Lock을 받지 못하고 대기한다.
대기가 길어지면 뒤따르는 쿼리까지 전부 막힌다.
long query 하나가 전체 서비스를 멈추는 구조다.

```sql
SELECT *
FROM information_schema.processlist
WHERE command != 'Sleep' AND time > 3;
```

3초 이상 실행 중인 쿼리가 있으면 DDL을 시작하면 안 된다.
필요하면 해당 세션을 종료하고 나서 실행한다.

## 사전 점검: 디스크, 레플리카, 시간대

pt-osc는 원본의 복제본을 만든다.
100GB 테이블이면 100GB가 추가로 필요하다.
원본 크기의 최소 2배를 확보하라.
여유 없이 시작하면 중간에 실패하고, 실패가 남긴 임시 테이블이 디스크를 더 먹는다.
레플리카 지연도 확인한다.
시작 전 지연이 0이 아니면 실행 중에 더 벌어진다.
시간대는 트래픽이 가장 낮을 때. 야간 배치가 도는 시간과 겹치면 DDL 부하와 배치 부하가 합산된다.
배치 스케줄을 먼저 확인하라.

## 방법을 고르는 결정 트리

모든 DDL에 외부 도구가 필요한 건 아니다.
변경의 종류와 테이블 크기로 방법을 고른다.

[Instant]
컬럼 추가/삭제, 순서 변경(8.0.29+).
가능하면 무조건 Instant.
ALGORITHM=INSTANT를 명시해서 확인한다.

[INPLACE]
인덱스 추가/삭제, VARCHAR 확장.
LOCK=NONE이면 서비스 영향 적음.
수GB 이하 테이블에서 적합.

[pt-osc]
컬럼 타입 변경, PK 변경, 대형 테이블 구조 변경.
수십GB 이상이면 사실상 필수.
트리거 기반이라 FK 있는 테이블도 지원한다.
Instant로 되면 Instant.
안 되면 INPLACE 가능 여부 확인.
그것도 안 되거나 테이블이 크면 pt-osc.

## Metadata Lock이라는 복병

DDL 사고의 절반은 Metadata Lock에서 온다.
Online DDL이라도 시작과 끝에서 MDL exclusive를 잡는다.
잡는 시간은 짧지만 그 순간 열려 있는 트랜잭션이 있으면 대기한다.
명시적 BEGIN뿐 아니라 autocommit=0 상태에서 SELECT만 하고 커밋도 롤백도 안 한 방치 세션이 원인인 경우가 많다.

```sql
SELECT *
FROM performance_schema.metadata_locks
WHERE lock_status = 'PENDING';
```

PENDING이 보이면 DDL이 막혀 있다.
`lock_wait_timeout`을 10~30초로 줄여 DDL이 오래 기다리지 않게 하거나, 방치 세션을 찾아서 종료한다.
무한정 대기하게 두는 것이 가장 위험하다.

## pt-osc로 안전하게 실행하기

Online DDL로 안 되거나 테이블이 크면 pt-osc를 쓴다.
원본에 트리거 3개를 걸고 빈 shadow 테이블에 ALTER를 적용한 뒤 원본 데이터를 청크 단위로 복사한다.
복사 중 변경분은 트리거가 반영한다. 완료 후 RENAME TABLE로 원자적 교체.
핵심 옵션 세 가지.

`--max-lag`: 레플리카 지연 한도.
넘으면 복사를 일시 중단한다.

`--chunk-size`: 한 번에 복사할 row 수.
너무 크면 lock이 길어지고 너무 작으면 전체 시간이 늘어난다.

`--critical-load`: 임계값을 넘으면
pt-osc가 스스로 중단한다.
세 옵션 없이 실행하면 서비스를 보호할 안전장치가 없는 것이다.

## 실행 중에 봐야 할 것

DDL이나 pt-osc를 시작한 뒤에는 세 가지를 계속 감시한다.

[레플리카 지연]
pt-osc의 `--max-lag`이 동작하더라도 실제 지연을 직접 확인해야 한다.
Online DDL은 쓰로틀링이 없다.

[Threads_running]
동시 실행 스레드 수가 평소의 2~3배를 넘으면 DDL이 서비스 쿼리를 압박하고 있다는 신호다.
pt-osc의 `--critical-load`가 이걸 감시하지만 서비스 특성에 맞게 임계값을 조정해야 한다.

[디스크 사용량]
shadow 테이블이 예상보다 커지는 경우가 있다. 인덱스 리빌드 때문이다.
남은 디스크가 10% 아래로 내려가면 작업을 중단할 준비를 해야 한다.

## 끝난 뒤에 확인할 것

DDL이 끝났다고 작업이 끝난 게 아니다.

[스키마 검증]
`SHOW CREATE TABLE`로 의도한 구조인지 확인한다.
레플리카에서도 동일한지 확인한다.
스키마 불일치는 나중에 복제를 깨뜨린다.

[인덱스 통계]
ALTER 직후 인덱스 통계가 부정확할 수 있다.
ANALYZE TABLE을 실행해서 통계를 갱신한다.
통계가 틀리면 옵티마이저가 잘못된 실행 계획을 고른다.

[애플리케이션 동작]
컬럼이 추가됐으면 앱이 그 컬럼을 인식하는지.
타입이 바뀌었으면 ORM 매핑이 깨지지 않았는지.
DDL은 DB 작업이지만 영향은 앱에서 나온다.

## 롤백이라는 환상

"문제 생기면 롤백하면 되지."
DDL에는 그게 안 된다.
ALTER TABLE은 트랜잭션으로 감싸지지 않는다. ROLLBACK이 없다.
컬럼을 추가했으면 다시 삭제해야 하고, 타입을 바꿨으면 다시 바꿔야 한다.
pt-osc가 중간에 실패하면 원본 테이블은 그대로 남아 있다. 교체 전이기 때문이다.
하지만 shadow 테이블과 트리거는 수동으로 정리해야 한다.
진짜 롤백 시나리오는 이렇다.
실패 시 어떤 잔여물이 남는지 파악하고, 잔여물 정리 SQL을 미리 준비하고, 정리 후 원래 상태를 검증하는 쿼리를 만들어둔다.
롤백 "계획"이지 롤백 "버튼"이 아니다.

## 흔한 실수 세 가지

운영에서 반복되는 DDL 실수가 있다.

[실수 1: ALGORITHM 미명시]
ALGORITHM을 빼면 MySQL이 자동 선택한다.
Instant로 될 줄 알았는데 COPY로 빠지면 수십 분간 쓰기가 차단된다.
ALGORITHM=INSTANT를 명시하면 Instant로 안 되는 작업에서 에러가 나서 안전하다.

[실수 2: 여러 ALTER를 한 문에 묶기]
컬럼 추가와 인덱스 생성을 하나의 ALTER로 묶으면 Instant가 가능한 작업까지 COPY로 내려간다.
분리할 수 있으면 분리하라.

[실수 3: 기존 트리거 확인 누락]
pt-osc는 원본에 트리거를 건다.
이미 트리거가 있으면 충돌한다. 사전에 기존 트리거 여부를 반드시 확인해야 한다.

## DBA 관점에서의 정리

1. long query를 먼저 정리하라.
2. ALGORITHM을 반드시 명시하라.
3. 디스크 여유를 원본 크기의 2배 이상 확보하라.
4. Metadata Lock 대기를 반드시 모니터링하라.
5. 롤백 시나리오 없이 실행하지 마라.
6. DDL의 위험은 명령어에 있지 않다.
7. 명령어를 실행하는 맥락에 있다.
8. 5.5에서는 COPY밖에 없었고, 5.6에서 INPLACE가 생겼고, 8.0에서 INSTANT가 나왔다.

도구가 좋아졌다고 안전해지는 건 아니다.
Instant도 누적되면 빚이 되고, Online DDL도 Metadata Lock에 걸리면 장애가 된다.
바이브코딩이 DDL을 만들어줘도 그 DDL을 언제, 어떤 조건에서 실행하고, 실패하면 어떻게 수습하는가는 사람이 설계해야 한다.
ALTER TABLE은 한 줄이지만 그 한 줄의 앞뒤에 붙는 점검이 서비스를 지키는 전부다.
쉽다고 생각한 순간부터 ALTER TABLE 한 줄이 장애가 된다.

## 배포 중 스키마 호환성

배포는 애플리케이션의 일이고 DB는 가만히 있는다고 생각하기 쉽다. 그렇지 않다.
Rolling Update 중에는 v1 서버와 v2 서버가 동시에 떠 있다. 둘 다 같은 DB를 바라본다.
v2가 새 컬럼을 기대하는데 아직 없으면 에러가 난다.
v1이 삭제된 컬럼을 읽으려 하면 에러가 난다.
코드는 두 버전인데 DB는 하나다. 이 간극이 장애를 만든다.

1. 컬럼 추가는 코드 배포 전에 먼저 하라.
2. 컬럼 삭제는 코드 배포 후에 나중에 하라.
3. 컬럼 이름 변경은 하지 마라. 새 컬럼 추가로 대체하라.
4. NOT NULL 제약은 DEFAULT 없이 추가하지 마라.
5. 스키마 버전과 앱 버전을 분리해서 관리하라.

DB 스키마는 앱보다 먼저 준비되고, 앱보다 늦게 정리되어야 한다.

### v1과 v2가 동시에 DB를 바라보는 순간

Rolling Update는 서버를 한 대씩 교체한다.
10대 중 3대가 v2로 올라갔고 7대는 아직 v1이다.
이 순간 DB에는 v1의 쿼리와 v2의 쿼리가 섞여 들어온다.
v2가 새 컬럼 memo를 INSERT한다.
v1은 memo 컬럼을 모른다.
v1의 INSERT에는 memo가 없다.
memo에 NOT NULL 제약이 걸려 있으면 v1의 INSERT가 실패한다.
배포 자체는 성공했는데 v1 서버에서 500 에러가 쏟아진다.
롤백해도 이미 v2가 쓴 데이터에 memo 값이 들어가 있다.
코드 배포와 스키마 변경이 동시에 일어나면 이런 창이 반드시 생긴다.

### 컬럼 추가는 안전한데 컬럼 삭제는 왜 위험한가

컬럼을 추가하는 건 비교적 안전하다.
v1은 새 컬럼을 모르지만 무시하면 된다.
`SELECT *`를 쓰지 않는 한 영향이 없다.
INSERT 시 새 컬럼에 DEFAULT가 있으면 문제없다.
컬럼 삭제는 다르다. v1이 아직 그 컬럼을 읽고 있다.
`SELECT old_column FROM users` 라는 쿼리가 돌고 있다.
컬럼을 지우는 순간 v1의 쿼리가 전부 실패한다.
컬럼 이름 변경도 마찬가지다.
old_name을 new_name으로 바꾸면 old_name을 참조하는 모든 코드가 깨진다.
이름 변경은 사실상 삭제 후 추가와 같다.
핵심 원칙은 간단하다.
추가는 코드보다 먼저. 삭제는 코드보다 나중에.

### Expand-Contract 패턴

스키마 변경의 표준 패턴이다.
확장하고, 마이그레이션하고, 수축한다.

[Expand]
새 컬럼을 추가한다. 기존 컬럼은 그대로 둔다.
v1과 v2 모두 정상 동작한다.

[Migrate]
v2를 전체 배포한다.
새 컬럼에 데이터를 채운다.
기존 컬럼의 데이터를 새 컬럼으로 옮긴다.

[Contract]
v1이 완전히 사라진 뒤에 기존 컬럼을 삭제한다.

세 단계가 각각 별도의 배포다.
한 번에 하려는 유혹을 참아야 한다.
급할수록 Expand-Contract가 빠르다.
한 번에 하면 롤백이 불가능하기 때문이다.

### Blue-Green 배포에서 DB가 병목이 되는 이유

Blue-Green은 두 환경을 통째로 준비한다.
Green이 준비되면 트래픽을 한 번에 전환한다.
Rolling Update의 혼재 문제가 없다.
애플리케이션은 그렇다. DB는 아니다.
Blue와 Green이 같은 DB를 쓰면 결국 두 버전이 같은 DB를 바라보는 것이다.
Rolling Update와 같은 문제가 생긴다.
DB도 분리하면 해결되지 않을까.
그러면 Blue DB의 데이터를 Green DB로 동기화해야 한다.
실시간 동기화는 복제 래그 문제가 있고 전환 순간의 데이터 정합성을 보장하기 어렵다.
결국 DB는 하나를 공유할 수밖에 없고 스키마 호환성은 애플리케이션이 책임져야 한다.
배포 전략이 뭐든 DB 호환성 문제는 피할 수 없다.

### 스키마 버전과 앱 버전을 분리해서 관리하는 법

앱 버전이 v2.3.1이고 DB 스키마가 migration_047이다.
이 둘은 독립적으로 관리해야 한다.
Flyway나 Liquibase 같은 마이그레이션 도구를 쓰면 스키마 변경에 고유 번호가 붙는다.
어떤 앱 버전이 어떤 스키마 버전을 필요로 하는지 명시한다.
중요한 규칙이 있다. 마이그레이션은 항상 전진만 한다.
롤백 마이그레이션은 만들지 않는다.
삭제가 필요하면 새 마이그레이션으로 삭제를 명시한다.
v2.3.1은 migration_045 이상이면 동작한다.
v2.4.0은 migration_047 이상이면 동작한다.
이런 식으로 호환 범위를 정의해두면 배포 순서를 자유롭게 조절할 수 있다.

### 실전에서 흔한 실수들

[NOT NULL 함정]
새 컬럼을 NOT NULL로 추가하면서 DEFAULT를 안 준다.
기존 행에 값이 없으니 마이그레이션이 실패한다.
반드시 DEFAULT를 함께 지정하거나 NULL 허용으로 시작한다.

[ENUM 추가]
MySQL의 ENUM에 값을 추가하는 건 DDL이다.
v2가 새 ENUM 값을 쓰는데 스키마에 아직 없으면 INSERT가 실패한다.
ENUM 추가는 코드 배포 전에 먼저 해야 한다.

[ORM의 자동 마이그레이션]
Django의 migrate, Rails의 db:migrate.
개발 환경에서는 편하지만 운영에서 자동 실행하면 위험하다.
ALTER TABLE이 언제 어떤 락을 잡는지 ORM은 신경 쓰지 않는다.

### DBA 관점에서의 정리

DBA에게 배포일은 긴장의 날이다.
슬로우 쿼리 알람이 울리면 가장 먼저 확인하는 게 "오늘 배포 있었나"다.
스키마 변경이 포함된 배포는 반드시 DBA와 사전 협의한다.
DDL이 어떤 락을 잡는지, 얼마나 걸리는지 DBA가 판단해야 한다.

1. 컬럼 추가는 코드 배포 전에 먼저 하라.
2. 컬럼 삭제는 코드 배포 후에 나중에 하라.
3. 컬럼 이름 변경은 하지 마라. 새 컬럼 추가로 대체하라.
4. NOT NULL 제약은 DEFAULT 없이 추가하지 마라.
5. 스키마 버전과 앱 버전을 분리해서 관리하라.
6. DB 스키마는 앱보다 먼저 준비되고, 앱보다 늦게 정리되어야 한다.
