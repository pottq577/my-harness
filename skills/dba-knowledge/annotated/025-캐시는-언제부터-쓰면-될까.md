# 캐시는 언제부터 쓰면 될까: RDBMS에서 Redis로 가는 시점

서비스를 처음 만들면 DB 하나로 시작한다.
MySQL이든 PostgreSQL이든, 테이블 만들고, 인덱스 걸고, 쿼리 치면 된다.
그런데 트래픽이 늘면 어느 순간 DB가 버겁다.
"Redis 도입해야 하지 않나요?" 이 질문이 나온다.
문제는 타이밍이다. 너무 빠르면 불필요한 복잡성을 떠안고, 너무 늦으면 장애로 배운다.

## 캐시란

같은 걸 또 계산하지 않기 위해 결과를 미리 저장해두는 것이다.
식당에 비유하면 이렇다. 손님이 "메뉴판 주세요" 할 때마다 주방에 가서 레시피를 전부 꺼내 메뉴판을 새로 인쇄하는 건 비효율이다.
한 번 인쇄해서 테이블에 올려두면 다음 손님은 바로 본다.
메뉴가 바뀌면? 그때만 다시 인쇄하면 된다.
DB에 매번 쿼리를 날리는 대신 결과를 메모리에 저장해두고 같은 요청이 오면 저장된 걸 돌려주는 것. 이게 캐시다.

## RDBMS만으로 충분한 시기

대부분의 서비스는 생각보다 오래 DB 하나로 버틴다.
사용자 수천 명. 초당 쿼리 수백 개. 데이터 수 GB.
이 정도면 MySQL 하나로 충분하다. 인덱스만 제대로 걸면.
오히려 이 시기에 Redis를 도입하면 관리 포인트만 늘어난다.
캐시 무효화 로직을 짜야 하고, Redis 서버를 모니터링해야 하고, 캐시와 DB 사이 정합성을 신경 써야 한다.
사용자 1,000명인 서비스에 Redis를 넣는 건 동네 편의점에 물류 창고를 짓는 것이다.

## RDBMS가 할 수 있는 것들

Redis를 도입하기 전에 DB 자체를 먼저 최적화해야 한다.
이걸 건너뛰고 캐시를 붙이면 근본 원인을 덮어버리는 것이다.
[인덱스 최적화]
[쿼리 튜닝]
[커넥션 풀링]
[Read Replica]
[애플리케이션 레벨 캐시]
로컬 메모리 캐시도 있다. Guava Cache, Caffeine, lru-cache.
Redis 서버를 따로 두지 않고도 자주 쓰는 데이터를 메모리에 올려둘 수 있다.
서버가 한두 대일 때는 이걸로 충분하다.
이 다섯 가지를 다 했는데도 느리다면, 그때 Redis를 생각해도 늦지 않다.

## Redis란

인메모리 데이터 스토어. 모든 데이터를 메모리에 저장한다.
디스크가 아니라 메모리이기 때문에 읽기/쓰기가 마이크로초 단위다. RDBMS의 밀리초와는 차원이 다르다.
단순 Key-Value뿐 아니라 String, Hash, List, Set, Sorted Set, Stream, HyperLogLog, Bitmap까지 다양한 자료구조를 지원한다.
단순한 캐시를 넘어서 세션, 큐, 실시간 랭킹, Rate Limiting 등 다양한 용도로 쓸 수 있다.
그래서 "캐시"라고만 부르기엔 Redis가 할 수 있는 일이 너무 많다.

## 신호 1 --- 같은 쿼리가 반복된다

가장 명확한 신호.
메인 페이지를 열 때마다 같은 SQL이 실행된다.
인기 상품 목록, 카테고리 트리, 공지사항, 배너 정보.
이런 데이터는 분 단위로도 안 바뀌는데 초당 수천 번 같은 쿼리가 들어온다.
DB 입장에서는 매번 실행 계획을 세우고 인덱스를 타고, 결과를 조립해서 돌려준다.
결과가 같은데. 이 패턴이 보이면 캐시의 효과가 가장 크다.

## 신호 2 --- Read Replica로도 부족하다

Replica를 2대, 3대 붙였는데도 읽기 부하가 높다.
CPU가 70%를 넘기고, 슬로우 쿼리가 쌓이고, 응답 시간이 p99 기준 500ms를 넘긴다.
Replica를 계속 추가할 수도 있지만, DB 인스턴스는 공짜가 아니다.
Reader와 Redis의 가격은 리전, 인스턴스, 구매 옵션에 따라 달라진다.
캐시 한 층을 두면 DB에 도달하는 쿼리 자체가 줄어든다.
실제 청구 항목과 운영 비용을 비교해 Reader 증설과 캐시 중 효과적인 쪽을 선택한다.

## 신호 3 --- 응답 시간 요구가 빡빡하다

DB 쿼리가 잘 튜닝되어 있어도 네트워크 왕복 + 실행 시간을 합치면 5~20ms는 걸린다.
대부분의 서비스에서 이 정도면 충분하다. 하지만 아래 상황에서는 부족하다.

[검색 자동완성]
사용자가 키를 누를 때마다 응답. 100ms 넘으면 체감된다.

[실시간 랭킹]
게임 리더보드, 실시간 인기 검색어. 수만 명이 동시에 조회한다.

[API Rate Limiting]
초당 수천 건의 요청마다 "이 사용자가 한도를 넘었는지" 확인. 이런 곳에서는 DB로 감당이 안 된다.
마이크로초 응답이 필요하다.

## 신호 4 --- DB 부하가 특정 시간에 몰린다

평소에는 괜찮은데 점심 시간, 저녁 6~8시에 트래픽이 5~10배로 뛴다.
배달 서비스라면 식사 시간. 커머스라면 타임딜. 티켓팅이라면 오픈 시각.
피크 트래픽에 맞춰 DB 스펙을 올리면 나머지 22시간은 과잉 투자다.
캐시는 이 스파이크를 흡수하는 완충 장치 역할을 한다.
피크 때 DB로 가는 쿼리의 70%를 캐시가 처리하면 DB는 평소와 비슷한 부하만 받는다.

## 신호 5 --- 연산 비용이 큰 쿼리가 있다

단순 SELECT가 아니라 복잡한 집계를 매번 실행하는 경우.
"오늘 카테고리별 판매 건수" "지난 7일간 사용자별 주문 금액 합계" "실시간 매장별 재고 현황"
이런 쿼리는 인덱스를 잘 걸어도 수십~수백 ms가 걸린다.
같은 결과를 여러 사용자가 보는데 매번 새로 계산할 필요가 없다.
1분마다 계산해서 캐시에 넣고, 사용자는 캐시에서 읽는다.
DB는 1분에 1번만 일하고, 사용자는 마이크로초 응답을 받는다.

## 신호 6 --- 세션을 서버 외부에 저장해야 한다

서버가 한 대일 때는 세션을 메모리에 들고 있으면 된다.
서버가 두 대 이상이면? 사용자가 서버 A에서 로그인했는데 다음 요청이 서버 B로 가면 로그인이 풀린다.
Sticky Session으로 우회할 수 있지만, 서버가 죽으면 그 서버의 세션이 전부 날아간다.
Redis에 세션을 저장하면 어느 서버로 요청이 가든 같은 세션을 읽는다.
서버 하나가 죽어도 세션은 살아있다.
서버를 2대 이상으로 늘리는 시점이 Redis 세션 스토어를 도입하는 자연스러운 시점이다.

## 도입 기준 --- 정량적 체크리스트

감이 아니라 숫자로 판단한다.

[DB CPU]
피크 시간 CPU 사용률이 지속적으로 70% 이상.
인덱스와 쿼리 최적화를 다 했는데도 그렇다면 쿼리 자체를 줄여야 한다.

[캐시 히트율 추정]
전체 쿼리 중 "같은 결과를 반환하는 반복 쿼리"의 비율.
이게 50% 이상이면 캐시 효과가 크다. 10% 미만이면 캐시를 넣어도 체감이 적다.

[응답 시간]
p99 응답 시간이 SLA를 넘긴다.
DB 쿼리가 병목이고, 쿼리 튜닝으로 더 줄일 수 없다.

[비용]
Read Replica 추가 비용 vs Redis 도입 비용.
리전, 인스턴스, 구매 옵션과 데이터 전송을 현재 가격표로 계산한다.
단순 읽기 분산이 목적이면 실측한 적중률과 총비용으로 두 구성을 비교한다.

[운영 역량]
Redis를 운영할 수 있는 사람이 팀에 있는가.
장애 때 대응할 수 있는가.

## 도입하면 안 되는 상황

캐시가 답이 아닌 경우도 있다.

[쓰기가 대부분인 워크로드]
데이터가 매번 바뀌면 캐시에 넣어봤자 금방 무효화된다.
히트율이 바닥이고 무효화 로직만 복잡해진다.

[데이터가 항상 달라야 하는 경우]
잔액 조회, 실시간 재고 차감.
캐시된 값이 0.1초만 낡아도 초과 판매나 이중 결제가 날 수 있다.
이런 데이터는 항상 DB에서 읽어야 한다.

[쿼리가 전부 다른 경우]
사용자마다 완전히 다른 결과를 반환하는 쿼리.
캐시 키가 사용자 수만큼 생기고 재사용이 거의 없다.
메모리만 차지하고 히트율은 안 나온다.

[DB 최적화를 안 한 경우]
인덱스도 안 걸고, 쿼리도 안 고치고 "DB가 느리니까 캐시 붙이자"는 가장 흔한 실수다.
캐시는 느린 DB를 숨겨줄 뿐 근본 원인을 고치지 않는다.
캐시가 날아가는 순간 장애가 터진다.

## 처음 도입할 때 --- Cache-Aside 패턴

가장 단순하고 가장 많이 쓰는 패턴. "Lazy Loading"이라고도 부른다.

1. 캐시에서 먼저 찾는다
2. 있으면(hit) → 캐시 값을 반환
3. 없으면(miss) → DB에서 조회 → 캐시에 저장 → 반환

애플리케이션이 캐시를 관리한다. DB는 캐시의 존재를 모른다.

- 장점:
  - 읽은 데이터만 캐시되니까 메모리 낭비가 적다.
  - 캐시가 죽어도 DB에서 읽으면 되니까 장애 내성이 있다.
- 단점:
  - 첫 요청은 항상 cache miss → DB 조회가 발생한다.
  - 캐시와 DB 사이에 데이터 불일치 구간이 생긴다.

처음 도입할 때는 이 패턴 하나만 잘 쓰면 된다.

## TTL --- 캐시의 유통기한

캐시에 데이터를 넣을 때 반드시 TTL(Time-To-Live)을 건다.
TTL이 없으면 데이터가 바뀌어도 캐시는 옛날 값을 영원히 돌려준다.
TTL은 "얼마나 낡아도 괜찮은가"로 정한다.

[실시간성이 덜 중요한 데이터]
카테고리 목록, 공지사항, 배너. TTL 5~30분.
몇 분 늦게 반영돼도 아무도 모른다.

[적당한 실시간성]
상품 상세, 가게 정보, 리뷰 목록. TTL 1~5분.
약간의 지연은 허용되지만 너무 오래되면 안 된다.

[높은 실시간성]
세션, 인증 토큰, Rate Limit 카운터. TTL 수 초~수 분. 또는 변경 시 즉시 무효화.

TTL을 너무 짧게 잡으면 히트율이 떨어지고, 너무 길게 잡으면 오래된 데이터를 보여준다.
서비스에 맞는 적정값을 찾는 건 운영하면서 튜닝하는 영역이다.

## 캐시 무효화 --- 가장 어려운 문제

데이터가 바뀌었을 때 캐시를 언제, 어떻게 갱신하느냐.

[TTL 만료에 의존]
TTL이 지나면 자동으로 사라지고, 다음 요청 때 DB에서 새로 읽는다.
일정 시간 동안 옛날 데이터가 보이는 걸 감수할 수 있으면 이걸로 충분하다.

[쓰기 시 삭제(Cache Invalidation)]
데이터를 수정할 때 해당 캐시를 지운다.
다음 읽기 요청 때 새 값이 캐시에 채워진다.

```python
def update_product(product_id, data):
db.update(product_id, data)
cache.delete(f"product:{product_id}")
```

[쓰기 시 갱신(Write-Through)]
데이터를 수정할 때 캐시도 같이 갱신한다.
캐시에 항상 최신값이 있다. 하지만 쓰기 지연이 늘어난다.
처음에는 "TTL + 쓰기 시 삭제"로 시작하고, 필요에 따라 전략을 세분화하는 게 실용적이다.

## 캐시 스탬피드 --- 도입 후 첫 번째 장애

캐시가 만료되는 순간 수십~수백 개의 요청이 동시에 DB로 몰린다.
평소에는 캐시가 막아주던 쿼리가 TTL 만료 순간 한꺼번에 DB를 때린다.
인기 상품 캐시가 만료됐을 때 동시 접속자 1,000명이 전부 DB로 가면 DB가 순간적으로 과부하에 빠진다.
이걸 Cache Stampede라고 부른다. Thundering Herd라고도 한다.
대응 방법은 두 가지.

[Lock 방식]
캐시 미스 시 한 요청만 DB에서 가져오고 나머지는 잠깐 기다린다.

[사전 갱신]
TTL 만료 직전에 백그라운드에서 미리 새 값을 채워 넣는다.
트래픽이 많은 키일수록 이 대비가 필요하다.

## 캐시 관통(Cache Penetration)

존재하지 않는 데이터를 반복 요청하는 경우. product:999999 같은 없는 상품 ID. 캐시에도 없고 DB에도 없다.
매 요청마다 캐시 miss → DB 조회 → 결과 없음. 캐시에 저장할 것도 없으니 다음에도 반복.
악의적인 요청이면 DB가 공격받는 것과 같다.

[널 캐시]
결과가 없는 것도 캐시한다.
`product:999999 → NULL (TTL 1분)` 다음 요청은 캐시에서 "없음"을 바로 반환.

[블룸 필터]
존재 가능한 키를 확률적으로 필터링한다.
"이 키는 확실히 없다"를 빠르게 판단. DB까지 갈 필요 없이 걸러낸다.

## Redis를 캐시 외에 쓰는 경우

Redis 도입을 검토할 때 캐시만 생각하면 범위가 좁다.

[세션 스토어]
서버가 2대 이상이면 거의 필수.
Redis의 가장 흔한 첫 번째 용도다.

[분산 락]
여러 서버에서 같은 리소스에 동시에 접근하는 걸 방지.
Redlock 알고리즘이 대표적.

[Rate Limiting]
API 호출 횟수를 사용자별로 제한.
INCR + EXPIRE 조합으로 간단히 구현.

[실시간 랭킹]
Sorted Set이면 리더보드가 자연스럽다.
ZADD로 점수를 넣고 ZREVRANGE로 TOP N. 수백만 건이어도 밀리초 이내.

[메시지 큐]
List의 LPUSH/BRPOP으로 간단한 큐. Stream으로 Consumer Group 기반 메시징.
Kafka 수준은 아니지만 가벼운 비동기 처리에 충분.

이런 용도 중 하나가 먼저 필요해서 Redis를 도입하고, 캐시는 자연스럽게 따라오는 경우도 많다.

## 도입 순서 --- 단계별 전략

한 번에 전체 시스템에 캐시를 붙이지 않는다.

[1단계: 핫스팟 식별]
슬로우 쿼리 로그를 분석한다.
가장 자주 호출되면서 결과가 잘 안 바뀌는 쿼리를 찾는다. 이게 캐시 대상 1순위다.

[2단계: 단일 엔드포인트 적용]
가장 효과가 클 것으로 예상되는 하나의 API 엔드포인트에만 캐시를 건다.
히트율, 응답 시간 개선, DB 부하 감소를 측정한다.

[3단계: 모니터링 확인]
캐시 히트율, 메모리 사용량, eviction 발생 여부. 이걸 대시보드로 본다.
히트율이 80% 이상이면 잘 동작하고 있다는 뜻. 50% 미만이면 캐시 전략을 재검토한다.

[4단계: 점진적 확대]
효과가 검증된 패턴을 다른 엔드포인트에 확대 적용.
한 번에 열 개씩 붙이지 말고 하나씩 넣고 효과를 확인한다.
급하지 않다. 캐시는 "있으면 빠른 것"이지 "없으면 안 되는 것"이 아니다.

## 흔한 실수들

[실수 1: 모든 쿼리에 캐시 적용]
효과 없는 곳에 캐시를 걸면 코드만 복잡해지고 히트율은 안 나온다.

[실수 2: TTL 없이 캐시한다]
"변경 시 삭제하니까 괜찮겠지"
삭제 로직에 버그가 있으면 오래된 데이터가 영원히 남는다.
TTL은 안전망이다. 항상 건다.

[실수 3: 캐시를 DB처럼 쓴다]
Redis에 저장된 데이터가 유일한 원본.
Redis가 죽으면 데이터가 사라진다. 캐시는 언제든 날아가도 괜찮아야 한다.
원본은 항상 DB에 있어야 한다.

[실수 4: DB 최적화 없이 캐시로 덮는다]
인덱스도 없는 쿼리에 캐시를 씌우면 캐시가 만료될 때마다 DB가 고통받는다.
캐시가 숨겨주는 동안 문제는 더 커진다.

[실수 5: 캐시 장애를 대비하지 않는다]
Redis가 죽었을 때 애플리케이션이 같이 죽으면 안 된다.
캐시 미스 시 DB로 fallback하는 구조가 반드시 있어야 한다.
Circuit breaker를 걸어두면 더 좋다.

## DBA 관점에서의 정리

DBA로서 수년간 봐온 패턴이 있다.
캐시를 너무 일찍 도입한 팀은 불필요한 복잡성에 시달린다.
캐시를 너무 늦게 도입한 팀은 장애로 배운다.
둘 다 경험하면 결국 같은 결론에 도달한다.
"DB 최적화가 먼저, 캐시는 그 다음."
Redis를 도입할 타이밍은 DB를 충분히 최적화했는데도 한계가 보이기 시작할 때다.
인덱스를 다 걸었고, 쿼리를 다 튜닝했고, Read Replica도 붙였는데, 그래도 특정 패턴의 반복 읽기가 DB를 압박하고 있다면. 그때가 Redis를 꺼낼 때다.
캐시는 DB를 대체하는 게 아니라 DB를 보호하는 것이다.
이 한 문장을 기억하면 도입 시점은 크게 틀리지 않는다.
