# 트랜잭션 로그의 세계: Binlog, WAL, Archive Log

데이터베이스에 데이터를 저장하면 그 변경 내역은 어딘가에 기록된다. 이걸 트랜잭션 로그라고 부른다.
MySQL은 Binary Log(binlog), PostgreSQL은 Write-Ahead Log(WAL), Oracle은 Redo Log / Archive Log.
이름은 다르지만 하는 일은 같다. "언제, 무엇이, 어떻게 바뀌었는가"를 순서대로 기록하는 것.

## 트랜잭션 로그란

데이터베이스는 데이터를 변경할 때 테이블에 바로 쓰지 않는다.
먼저 "이런 변경을 할 것이다"를 로그 파일에 기록한 뒤, 나중에 테이블에 반영한다.
DB가 갑자기 꺼져도 로그만 남아 있으면 어디까지 처리했는지 알 수 있다.
이게 트랜잭션 로그의 본래 목적이다. 크래시 복구(Crash Recovery).
그런데 시간이 지나면서 이 로그가 할 수 있는 일이 점점 더 많아졌다.

## MySQL — Binary Log (binlog)

MySQL의 binlog은 커밋된 트랜잭션의 변경 내역을 순서대로 기록한 파일이다.
MySQL에는 사실 로그가 두 종류다.
Redo Log → InnoDB 엔진이 쓴다. 크래시 복구용.
Binary Log → MySQL 서버가 쓴다. 복제, 복구, CDC용.
Redo Log는 엔진 내부 전용이고, 우리가 실제로 활용하는 건 binlog이다.

## binlog 포맷 3가지

STATEMENT: SQL 문 자체를 기록
ROW: 변경 전/후 행 데이터를 기록
MIXED: 상황에 따라 자동 선택
요즘은 거의 ROW 포맷이 표준이다. CDC를 쓰려면 ROW가 필수이기도 하다.
ROW 포맷이면 이런 정보가 남는다:

```sql
UPDATE users SET name='베어' WHERE id=1
-- → before: {id:1, name:'도트'}
-- → after: {id:1, name:'베어'}
```

변경 전후 데이터가 모두 기록되기 때문에 "뭐가 바뀌었는지"를 정확히 알 수 있다.

## GTID

MySQL 5.6부터 도입된 기능. 각 트랜잭션에 고유 ID를 붙여준다.

```text
3e11fa47-71ca:42
(서버UUID):(순번)
```

예전에는 "binlog 파일명 + 위치"로 어디까지 적용했는지를 추적했는데, GTID 덕분에 훨씬 단순해졌다.
복제나 CDC에서 장애 복구할 때 "이 GTID 이후부터 다시 보내줘" 한마디면 된다.

## PostgreSQL — Write-Ahead Log (WAL)

이름이 핵심을 그대로 말해준다. Write-Ahead — 쓰기 전에 먼저 기록.
MySQL과 가장 큰 차이점은 WAL 하나로 전부 처리한다는 것이다. 크래시 복구, 복제, 시점 복구, CDC.
MySQL처럼 redo log / binlog가 따로 있는 게 아니다. WAL 하나가 다 한다.

## Logical Decoding

WAL은 기본적으로 물리적 기록이다. 사람이 읽기 어렵다.
PostgreSQL 9.4부터 Logical Decoding이 도입됐다.
물리적 WAL 레코드를 "users 테이블에 INSERT 했다" 같은 논리적 변경으로 변환해주는 기능이다.
CDC는 이 위에서 동작한다. 사용하려면 wal_level = logical 설정 필요.
PG 9.4부터 지원되며 PG 15+에서도 기본값은 replica라 CDC를 쓰려면 바꿔야 한다.
다만 PG 15부터는 logical로 올려도 성능 차이가 거의 없어졌다..

## Replication Slot

PostgreSQL CDC의 핵심 개념.
"이 Consumer가 여기까지 읽었다"를 DB가 기억해준다.
slot이 살아있는 동안은 해당 위치 이후의 WAL을 절대 삭제하지 않는다.
안전하지만, 뒤에서 다룰 디스크 폭증 사고의 원인이기도 하다.

## Oracle — Redo Log & Archive Log

Oracle은 두 단계로 나뉜다.
Online Redo Log는 순환 구조. 2~3개 그룹이 돌아가며 덮어쓴다.
ARCHIVELOG 모드를 켜면 그룹이 전환될 때마다 이전 내용을 Archive Log로 복사한다.
운영 DB는 거의 100% ARCHIVELOG 모드로 돌아간다.
이게 꺼져있으면 PITR이 불가능하다.

## Supplemental Logging

Oracle CDC에서 중요한 설정.
기본 Redo Log에는 변경된 컬럼만 기록된다.
CDC에서는 "어떤 행이 바뀌었는지" PK 같은 식별 컬럼도 필요하기 때문에 별도로 켜줘야 한다.
MySQL의 binlog_row_image=FULL과 비슷한 역할이다.

## 이 로그로 뭘 할 수 있나 — 복제

가장 기본적인 용도.
Source DB의 로그를 Replica가 받아서 그대로 재실행한다.
MySQL이든 PostgreSQL이든 Oracle이든 원리는 동일하다.

## 시점 복구 (PITR)

풀 백업 + 트랜잭션 로그를 합치면 원하는 시점으로 되돌릴 수 있다.

```text
[백업 시점] → 로그 재실행 → [목표 시점]
어제 02:00 → → → → → → 오늘 13:05
```

"오늘 13:05에 실수로 DELETE 했다"
→ 13:04까지만 로그를 재실행하면 삭제 직전 상태로 복구 가능.
DBA가 가장 의존하는 기능이다.

## 변경 추적 / 되돌리기

ROW 포맷 binlog에는 before 이미지가 있기 때문에 실수한 DML을 역방향으로 되돌리는 SQL을 자동 생성할 수 있다.
원래: `UPDATE SET name='베어' WHERE id=1`
역방향: `UPDATE SET name='도트' WHERE id=1`
MySQL의 Binlog2SQL, Oracle의 Flashback이 이 원리를 사용한다.

## CDC — 로그 기반 실시간 데이터 전달

CDC(Change Data Capture)란 데이터베이스의 변경 사항을 실시간으로 다른 시스템에 전달하는 것.
주문 DB의 변경을 검색 엔진에 동기화. 결제 DB의 변경을 데이터 레이크로 전송. 재고 DB의 변경을 이벤트로 발행.

## 왜 로그 기반인가

전통적으로는 배치 ETL을 썼다. "5분마다 변경된 데이터를 SELECT해서 전달"
이 방식의 문제:
지연 → 분~시간 단위 딜레이
부하 → SELECT 쿼리가 DB를 때린다
삭제 감지 불가 → 지워진 행은 조회 안 됨
로그 기반 CDC는 다르다. binlog/WAL은 어차피 생성되는 것이고, CDC는 그걸 읽기만 한다.
지연 → 초~밀리초
부하 → 거의 없음
삭제 → DELETE 이벤트로 자연스럽게 캡처

## Debezium — CDC 플랫폼

각 DB의 트랜잭션 로그를 읽어서 표준화된 이벤트(JSON)로 변환한다.

- MySQL binlog → Debezium → Kafka
- PostgreSQL WAL → Debezium → Kafka
- Oracle Redo → Debezium → Kafka

DB마다 로그 포맷이 전부 다르지만 Debezium이 통일된 형태로 바꿔준다.

- MySQL → Replica처럼 위장해서 binlog 수신
- PostgreSQL → Logical Replication Slot 사용
- Oracle → LogMiner API로 Redo 파싱

## Debezium이 만드는 이벤트

UPDATE가 발생하면 이런 이벤트가 나온다:

```text
before: {id:1, name:"도트"}
after: {id:1, name:"베어"}
op: "u"
source: {db:"mydb", table:"users"}
op 필드로 변경 종류를 구분:
c = INSERT
u = UPDATE
d = DELETE
r = 초기 스냅샷
```

Consumer 쪽에서는 DB 종류에 관계없이 같은 구조의 이벤트를 받게 된다.

## Kafka 없이도 가능해졌다

초기에는 Kafka Connect 위에서만 동작했지만 지금은 선택지가 넓다.
Debezium Server를 쓰면 Amazon Kinesis, Google Pub/Sub, Redis Streams, HTTP Webhook으로 직접 전달할 수 있다.
Debezium Embedded를 쓰면 애플리케이션 코드 안에 CDC 엔진을 직접 넣을 수도 있다.

## Outbox 패턴

마이크로서비스에서 자주 쓰이는 패턴.
"주문 상태 변경 + 이벤트 발행"을 하나의 DB 트랜잭션으로 묶는 것이다.
하나의 트랜잭션 안에서:

1. orders 테이블 UPDATE
2. outbox 테이블에 이벤트 INSERT

Debezium이 outbox INSERT를 캡처해서 Kafka로 발행한다.
DB 트랜잭션이 보장되니 "데이터는 바뀌었는데 이벤트는 안 나감" 같은 상황이 발생하지 않는다.

## 실전 — 로그가 디스크를 꽉 채운 날

DBA라면 한 번쯤 겪는 사고.
트랜잭션 로그가 디스크를 가득 채우면 DB가 멈춘다.
MySQL의 경우 binlog는 기본적으로 계속 쌓인다.
보존 기간을 안 걸어두면 디스크가 찰 때까지 삭제되지 않는다.
`binlog_expire_logs_seconds = 604800` 이렇게 7일 보존을 걸어둬야 한다.

## PostgreSQL — replication slot의 함정

PostgreSQL에서 가장 흔한 WAL 폭증 원인은 비활성 replication slot이다.
CDC 커넥터가 죽었는데 slot만 살아있으면? slot은 "여기까지 읽었다"를 기억하고 그 이후 WAL을 절대 삭제 안 한다.
커넥터가 일주일째 죽어있으면 일주일치 WAL이 쌓인다.
PG 13부터는 안전장치가 생겼다:
`max_slot_wal_keep_size = '10GB'` 이 값을 넘기면 slot이 무효화된다.

## CDC 도입 후 달라지는 점

CDC가 없을 때 로그 보존 정책:
보존 기간 = max(복제 지연, PITR 요구)
→ 보통 3~7일이면 충분
CDC가 있으면:
보존 기간 = max(복제 지연, PITR 요구, CDC 커넥터 장애 복구 시간)
커넥터가 3일 죽었다 살아나면 3일치 로그를 다시 읽어야 한다.
이미 삭제됐다면? 전체 스냅샷부터 다시 시작.
대형 테이블이면 수 시간~수 일이 걸린다.

## 마무리

트랜잭션 로그는 원래 크래시 복구를 위한 안전장치였다.
거기에 복제가 얹어졌고, PITR이 얹어졌고, 이제는 CDC까지 얹어졌다.
마이크로서비스 시대에 "DB 변경을 이벤트로 발행한다"는 요구가 당연해지면서, binlog와 WAL은 DBA만의 관심사가 아니라 개발자와 데이터 엔지니어 모두의 관심사가 되었다.
CDC를 도입하면 로그 관리의 이해관계자가 늘어난다.
"보존 7일이면 충분하겠지"가 아니라 CDC 커넥터의 SLA까지 고려한 정책 수립이 필요하다.
로그는 조용하지만, 멈추면 DB가 멈춘다.
