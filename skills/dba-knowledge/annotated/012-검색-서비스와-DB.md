# 검색 서비스와 DB: 검색은 DB의 일이 아니다

"검색창 하나 넣으려는데, LIKE 쓰면 되지 않나요?"
데이터가 적을 때는 된다. 1만 건이면 LIKE도 충분하다.
10만 건이 되면 느려지기 시작하고 100만 건이 되면 페이지가 멈춘다.
검색은 모든 서비스에 있지만 DB가 잘하는 일이 아니다.
DB는 정확한 조건으로 찾는 데 최적화돼 있다. "비슷한 것"을 찾는 건 다른 문제다.
LIKE는 데이터가 커지면 풀 스캔이다. Full-Text는 타협이지 해답이 아니다.
자동완성은 DB가 감당할 영역이 아니다. 검색 로그는 서비스 DB에서 분리하라.
한국어 검색은 결국 DB 밖으로 나가야 한다.

## LIKE의 한계

```sql
SELECT * FROM products
WHERE product_name LIKE '%반팔%'
```

데이터가 적으면 괜찮다. 많아지면 풀 테이블 스캔이다.
LIKE 앞에 %가 붙으면 인덱스를 탈 수 없다.
B-Tree 인덱스는 "시작이 같은 것"은 찾을 수 있지만 "중간에 포함된 것"은 찾을 수 없다.
100만 건의 상품명을 전부 읽고 한 글자씩 비교한다.
사용자가 검색할 때마다 DB가 책을 처음부터 끝까지 넘기는 셈이다.
목차가 없는 책에서 단어를 찾는 것과 같다.

## Full-Text Index라는 타협

MySQL의 Full-Text Index. PostgreSQL의 tsvector. 단어 단위로 역인덱스를 만든다.
"반팔"이 포함된 행의 ID 목록을 미리 만들어두는 것이다.
LIKE보다 훨씬 빠르다. 그런데 한계가 있다.
"반팔티"를 검색했는데 "반팔 티셔츠"가 안 나온다. 띄어쓰기가 다르면 다른 단어다.
"반팔"과 "반소매"는 같은 의미지만 Full-Text는 모른다.
오타 교정도 안 된다. 동의어 처리도 안 된다.
DB의 Full-Text는 "있으면 좋은 수준"이지 검색 엔진을 대체하지 못한다.

## 자동완성의 숨은 비용

검색창에 "반"을 치면 "반팔", "반바지", "반지"가 뜬다. 글자 하나 칠 때마다 쿼리가 날아간다.
빠르게 치면 초당 5~10번.

```sql
SELECT DISTINCT product_name
FROM products
WHERE product_name LIKE '반%'
ORDER BY popularity DESC
LIMIT 5
```

이 쿼리가 키 입력마다 실행된다.
사용자 1만 명이 동시에 검색하면 초당 수만에서 수십만 쿼리.
자동완성은 기능은 작지만 부하는 크다.
Redis에 인기 검색어를 캐시하거나 별도 자동완성 서비스를 두는 게 일반적이다.
DB가 감당할 영역이 아니다.

## 정렬 기준이 바뀌면 쿼리가 바뀐다

"관련도순" "최신순" "인기순" "가격순."
정렬 기준마다 다른 인덱스가 필요하다.
관련도순은 검색 엔진이 채점한 점수. 최신순은 created_at. 가격순은 price.
네 가지 정렬에 네 가지 인덱스. 인덱스가 늘면 쓰기가 느려진다.
관련도순은 DB가 할 수 없다.
DB는 "이 행이 검색어와 얼마나 관련 있는지" 점수를 매기는 구조가 아니다.
그래서 검색 결과의 정렬이 필요한 순간 DB 밖의 검색 엔진이 필요해진다.

## 검색 로그라는 또 다른 빅 테이블

사용자가 뭘 검색했는지 기록한다. 추천에도 쓰고 분석에도 쓴다.
검색 한 번에 로그 한 건. 하루 검색 100만 건이면 검색 로그 100만 건.
검색 결과를 클릭했는지까지 기록하면 로그가 두 배다.
이 테이블은 쓰기만 하고 실시간으로 읽을 일은 거의 없다.
서비스 DB에 넣으면 공간을 잡아먹는다. 별도 분석 DB나 데이터 웨어하우스로 빼는 게 맞다.
Kafka로 스트리밍하고 Athena나 BigQuery에서 분석하는 구조가 일반적이다.

## DB와 검색 엔진의 동기화

Elasticsearch를 도입했다. 상품 데이터는 DB에 있다. 검색은 Elasticsearch에서 한다.
상품이 등록되면 DB에 INSERT하고 Elasticsearch에도 인덱싱해야 한다.
이 사이에 시간 차가 있다. 상품을 등록한 직후 검색하면 안 나온다.
삭제는 더 위험하다. DB에서 지웠는데 검색 엔진에 남아 있으면 없는 상품이 검색된다.
동기화 실패 시 재시도 로직. 전체 재색인 배치.
DB와 검색 엔진 사이에는 항상 정합성 관리 비용이 따른다.

## 한국어 검색의 어려움

영어는 띄어쓰기로 단어가 나뉜다. 한국어는 그렇지 않다.
"아이폰케이스"와 "아이폰 케이스"는 같은 의미다.
"가방"을 검색했는데 "핸드백"은 안 나온다. "노트북"을 검색했는데 "랩탑"은 안 나온다.
형태소 분석기가 필요하다.
"먹었다"를 "먹다"로 변환해서 인덱싱한다. Nori(한국어 형태소 분석기)가 대표적이다.
DB의 Full-Text는 형태소 분석을 지원하지 않거나 지원해도 품질이 낮다.
한국어 검색을 제대로 하려면 결국 DB 밖으로 나가야 한다.
