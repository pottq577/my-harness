# BEAR DBA

## 바이브코더들을 위한 ORM 생존리스트

바이브코딩과 ORM: AI가 만든 코드는 DB를 모른다
바이브코딩이란 Andrej Karpathy가 만든 말이다. "코드를 쓰지 않는다. 분위기에 맡기고 AI가 쓰게 한다."
프롬프트를 넣으면 프로젝트가 나온다. 풀스택이 하루 만에 완성된다. 동작하면 성공이다.
왜 동작하는지는 모른다. 어떻게 동작하는지도 모른다.
대부분의 바이브코딩 결과물에는 ORM이 들어간다. AI가 DB를 다루는 기본 방식이 ORM이기 때문이다.
SQL을 직접 쓰면 복잡해 보인다. AI는 깔끔해 보이는 걸 고른다. ORM이 깔끔해 보인다.

### AI가 ORM을 고르는 방식

"할 일 관리 앱 만들어줘." AI가 기술 스택을 고른다.

[Next.js + Prisma]
자바스크립트 진영의 기본 조합.
AI가 가장 자주 고르는 패턴이다.

[Django + Django ORM]
파이썬이면 거의 자동으로 따라온다.

[Spring Boot + JPA]
자바면 JPA. Entity 어노테이션, Repository, 영속성 컨텍스트.
설정이 많지만 AI가 알아서 만든다.
문제는 AI가 "돌아가는 설정"을 만든다는 것이다.
"좋은 설정"이 아니다. Lazy Loading이 기본인데 AI는 그게 뭔지 설명 안 한다. 돌아가니까.

### N+1: AI가 가장 자주 만드는 실수

AI한테 "주문 목록 페이지 만들어줘"라고 하면 이런 코드가 나온다.

```python
orders = Order.objects.all()
for order in orders:
print(order.customer.customer_name)
```

깔끔하다. 동작한다.
주문이 5건이면 쿼리 6번. 10,000건이면 10,001번.
SQL로 직접 쓰면 JOIN 한 번이다.

```sql
SELECT order_id, customer_name
FROM orders JOIN customers USING (customer_id);
```

AI는 N+1을 모르는 게 아니다. 물어보면 설명도 잘 한다.
다만 코드를 만들 때 기본으로 피하지 않는다.

### AI가 만드는 ORM 코드의 패턴

DBA가 슬로우 쿼리 로그를 열면 바이브코딩으로 만든 서비스가 바로 보인다.
패턴이 있다.

[SELECT * 남발]
이름만 필요한데 엔티티 전체를 가져온다. 20개 컬럼을 읽고 1개만 쓴다.
커버링 인덱스를 탈 수 있었던 쿼리가 테이블 lookup을 한다.

[DISTINCT로 JOIN 실수 숨기기]
JOIN 구조가 틀려서 중복이 생기면 ORM이 DISTINCT를 붙여서 해결한다.
근본은 JOIN이 잘못된 것이다.

[서브쿼리 중첩]
ORM이 조건을 중첩하면서 서브쿼리가 서브쿼리를 감싼다.
플래너가 최적화하기 어려운 구조가 된다.
전부 SQL을 보면 바로 보이는 문제다. ORM만 보면 안 보인다.

### "동작합니다"의 함정

바이브코딩의 검증 기준은 "동작한다"다.
로컬에서 돌린다. 데이터가 10건이다. 응답이 50ms다. "잘 되는데요?"
프로덕션에 올린다. 데이터가 100만 건이다. 인덱스가 없다. 응답이 8초다.
개발 환경에서의 "동작한다"는 아무것도 증명하지 못한다.
10건으로 테스트한 쿼리와 100만 건이 있는 테이블의 쿼리는 같은 코드인데 전혀 다른 동작을 한다.
실행 계획이 바뀐다. Full Table Scan이 시작된다. 메모리가 부족해진다. 커넥션 풀이 바닥난다.

### Lazy Loading이라는 기본값의 함정

대부분의 ORM은 Lazy Loading이 기본이다. 연관 객체를 실제로 접근할 때 쿼리를 날린다.
메모리는 아끼지만 쿼리가 늘어난다. N+1의 직접적인 원인이 이것이다.
AI는 이 기본값을 건드리지 않는다. 기본값이 곧 "동작하는 값"이니까.
Eager Loading으로 바꾸면 N+1은 사라진다.
대신 항상 JOIN이 붙는다. 필요 없는 곳에서도 연관 테이블을 전부 읽는다.
정답은 둘 다 아니다.
"이 화면에서 연관 데이터를 쓰는가"에 따라 전략이 달라져야 한다.
문제는 바이브코딩을 하는 사람이 이 판단을 내릴 맥락이 없다는 것이다.
AI도 맥락 없이는 판단하지 못한다.

### Eager Loading 지옥

AI가 Lazy의 N+1을 발견하면 반대쪽으로 과잉 교정한다.

```java
@ ManyToOne(fetch = FetchType.EAGER)
private Category category;
@ ManyToOne(fetch = FetchType.EAGER)
private User seller;
@ OneToMany(fetch = FetchType.EAGER)
private List<Review> reviews;
```

주문 하나를 조회하면 카테고리, 판매자, 리뷰가 전부 온다.
필요 없어도 온다. 목록 20건이면 60번의 JOIN이 붙는다.
Lazy의 반대가 정답이 아니다.
필요한 곳에서만 fetch join을 쓰는 것이 정답이다.

### 연관관계 매핑의 늪

AI는 엔티티 사이의 관계를 양방향으로 매핑한다.
User에서 Order로. Order에서 User로. Order에서 OrderItem으로. OrderItem에서 Product로. "편하니까."
Cascade가 따라온다.

```java
@ OneToMany(cascade = CascadeType.ALL,
orphanRemoval = true)
```

AI가 "안전하게" CascadeType.ALL을 넣는다.
부모를 지우면 자식이 전부 사라진다.
의도한 거면 괜찮다. 의도 안 한 거면 데이터가 날아간다.
양방향 매핑은 편의성의 대가로 복잡성과 위험을 가져온다.
단방향으로 충분한데 AI는 양방향을 기본으로 만든다.

### 페이지네이션 없는 전체 조회

"게시판 목록 보여줘." AI가 만든 코드.

```python
posts = Post.objects.all()
```

전체를 가져온다. 프론트에서 잘라서 보여준다. 게시글이 100건이면 괜찮다.
50만 건이면 DB가 50만 행을 읽고 네트워크로 전부 보내고 브라우저가 전부 받는다.
20개만 보여줄 건데 50만 개를 가져온다.

```python
posts = Post.objects.order_by(
'-created_at')[:20]
```

이 한 줄이면 되는 걸 AI가 빠뜨리는 경우가 많다. "동작하니까."
LIMIT 없는 SELECT는 데이터가 쌓이는 순간 시한폭탄이 된다.

### 트랜잭션 경계를 모르는 코드

AI가 만든 주문 서비스.

```python
def place_order(user_id, product_id):
product = Product.objects.get(pk=product_id)
product.stock -= 1
product.sav e()
order = Order.objects.create(...)
send_email(user_id, order)
```

트랜잭션이 없다. 두 명이 동시에 들어오면 재고가 깨진다.
이메일이 5초 걸리면 커넥션을 5초 물고 있다.
AI는 비즈니스 로직을 잘 만든다. 트랜잭션 경계와 락 전략은 못 만든다.
"어디까지가 하나의 원자적 단위인가"는 비즈니스를 이해해야 답이 나온다.

### 인덱스를 안 만드는 AI

AI가 모델을 정의한다. 테이블이 만들어진다. CRUD가 동작한다. 인덱스는 없다.

```python
class Order(models.Model):
user_id = models.IntegerField()
status = models.CharField(
max_length=20)
created_at = models.DateTimeField(
auto_now_add=True)
```

user_id로 조회하고 status로 필터하고 created_at으로 정렬한다.
셋 다 인덱스가 없다. 10만 건까지는 버틴다.
100만 건부터 Full Table Scan이 시작된다.
물어보면 만들어준다. 먼저 만들어주지는 않는다.

### 마이그레이션이라는 시한폭탄

AI가 만든 프로젝트에는 자동 마이그레이션이 켜져 있다.

```yaml
spring.jpa.hibernate.ddl-auto=update
```

엔티티를 바꾸면 스키마가 자동으로 바뀐다.
개발 환경에서는 편하다. 프로덕션에서는 재앙이다.
컬럼을 추가하면 ALTER TABLE이 실행된다. 100만 행짜리 테이블에서.
MySQL이면 테이블 락이 걸릴 수 있다.
컬럼 이름을 바꾸면 ORM은 이전 컬럼을 DROP하고 새 컬럼을 CREATE한다.
데이터가 사라진다.
AI는 ddl-auto=update를 기본값으로 넣는다. 이걸 프로덕션에 그대로 가져가는 사람이 있다.
프로덕션의 DDL은 사람이 통제해야 한다.

### show-sql을 켜라: 최소한의 방어선

ORM을 쓰면서 할 수 있는 가장 쉬운 일이다.

[Django]

```python
LOGGING = {'loggers': {
'django.db.backends': {'level': 'DEBUG'}}}
```

[JPA / Hibernate]

```yaml
spring.jpa.show-sql=true
```

[Prisma]

```typescript
new PrismaClient({ log: ["query"] });
```

켜기만 하면 된다. ORM이 만드는 SQL이 전부 보인다.
한 페이지에 쿼리가 50번 찍히면 뭔가 잘못된 것이다.
바이브코딩을 하더라도 이것 하나는 반드시 켜라.

### AI한테 SQL을 보여달라고 하라

바이브코딩의 강점을 역으로 활용하는 법이다.
코드를 만들어달라고 한 다음 한마디를 추가한다.
"이 코드가 만드는 SQL 쿼리를 전부 보여줘."
"N+1 문제가 있는지 확인해줘."
"100만 건일 때도 괜찮아?"
AI는 이 질문에 잘 대답한다.
코드를 만들 때는 빠뜨려도 물어보면 찾아준다.
"이 페이지에서 쿼리가 몇 번 나가?" 이 한마디가 N+1을 잡는다.
"인덱스 없이 이 쿼리가 100만 건에서 버텨?" 이 한마디가 인덱스를 만든다.
AI를 검수자로 쓰는 것이다. 만든 놈한테 확인시키는 것이다.

### 바이브코딩 + ORM이 괜찮은 경우

전부 안 된다는 건 아니다.

[개인 프로젝트 / 프로토타입]
사용자가 나 혼자다. 데이터가 1,000건을 넘지 않는다.
빠르게 아이디어를 검증하는 게 목표다.

[내부 어드민 도구]
사용자가 10명이다. 동시 접속이 거의 없다.
CRUD가 전부다.

[학습 목적]
ORM이 뭔지 배우는 단계다. 일단 돌아가는 걸 만들어보는 게 중요하다.
나중에 SQL을 배우면 된다.
이런 경우에는 바이브코딩 + ORM이 최선이다.
빠르니까. 그게 핵심이니까.

### 바이브코딩 + ORM이 위험한 경우

[돈이 오가는 서비스]
결제, 정산, 포인트. 트랜잭션 하나가 틀리면 돈이 틀린다.
AI가 만든 트랜잭션 경계를 신뢰하면 안 된다.

[사용자가 천 명을 넘는 서비스]
동시성이 생긴다. 인덱스가 없으면 무너진다.
N+1이 있으면 서버가 죽는다.

[데이터가 빠르게 쌓이는 서비스]
로그, 이벤트, 주문 이력.
100만 건을 넘기는 순간 ORM의 기본 동작이 병목이 된다.

[이미 운영 중인 서비스에 기능 추가]
기존 스키마를 모르는 AI가 새 엔티티를 만들면 기존 테이블과 충돌한다.
마이그레이션이 데이터를 날릴 수 있다.

### 바이브코더를 위한 ORM 생존 체크리스트

AI한테 코드를 받으면 배포 전에 이것만 확인하라.

[쿼리 로그를 켰는가]
show-sql 또는 query logging.
안 켰으면 지금 켜라.

[한 페이지에 쿼리가 몇 번 나가는가]
5번 이내면 정상. 20번 넘으면 N+1이다.

[LIMIT이 있는가]
목록 API에 페이지네이션 없으면 시한폭탄이다.

[인덱스가 있는가]
WHERE, JOIN, ORDER BY 컬럼에 인덱스가 없으면 만들어라.

[ddl-auto가 update인가]
프로덕션이면 none 또는 validate로 바꿔라.

[트랜잭션이 있는가]
돈이 오가는 로직에 없으면 동시 요청에서 데이터가 깨진다.

이 여섯 개만 확인해도 바이브코딩의 치명적인 실수 대부분을 막는다.

### DBA 관점에서의 정리

바이브코딩이 나쁜 게 아니다. AI가 만든 ORM 코드를 그대로 프로덕션에 올리는 게 나쁜 것이다.
AI가 만든 ORM 코드의 SQL을 반드시 확인하라. show-sql 없이 프로덕션에 올리지 마라.
N+1은 AI가 가장 많이 만드는 실수다. 찾아서 고쳐라.
"동작한다"와 "성능이 괜찮다"는 다른 말이다.
DB를 모르는 코드는 사용자가 늘면 반드시 깨진다.
다시 그 장면으로 돌아가자.
3시간 만에 만든 앱. 사용자가 몰렸고 DB가 죽었다.
쿼리가 247번 나가는 걸 보고 "이게 N+1이구나"라고 말할 수 있었다면 30분이면 고쳤다.
AI한테 시키는 건 자유다.
그 코드가 DB에 뭘 하는지는 당신이 알아야 한다.

## 바이브코딩을 하더라도 DB 구조 변경을 안전하게 하는 방법: ALTER TABLE 앞뒤로 확인해야 할 것들

Claude에서 "컬럼 추가해줘" 하면 ALTER TABLE 한 줄이 나온다.
로컬에서는 잘 된다. 그걸 운영에 그대로 날리면 서비스가 멈출 수 있다.
바이브코딩이 코드를 만들어줘도 DDL을 언제, 어떻게 실행할지는 알려주지 않는다.
그 판단이 장애를 막는다.

1. long query를 먼저 정리하라.
2. ALGORITHM을 반드시 명시하라.
3. 디스크 여유를 원본 크기의 2배 이상 확보하라.
4. Metadata Lock 대기를 반드시 모니터링하라.
5. 롤백 시나리오 없이 실행하지 마라.

쉽다고 생각한 순간부터
ALTER TABLE 한 줄이 장애가 된다.

### AI가 만든 DDL도 DDL이다

Cursor든 Claude든 "컬럼 하나 추가해줘" 하면 ALTER TABLE이 나온다. 로컬 SQLite에서는 0.01초면 끝난다.
운영은 다르다.
수억 건의 데이터가 있고, 초당 수천 건의 쿼리가 들어오고, 레플리카가 복제하고 있다.
AI가 DDL을 만들어주는 건 좋다.
하지만 그 DDL을 운영에 적용하는 건 사전 점검, 방법 선택, 실행, 모니터링, 검증. 다섯 단계의 작업이다.
코드를 만드는 것과 코드를 적용하는 것은 다르다.

### Online DDL의 세 가지 Algorithm

MySQL의 ALTER TABLE은
내부적으로 세 가지 Algorithm 중 하나를 탄다.

[COPY]
새 테이블을 만들고 데이터를 전부 복사한다.
복사하는 동안 쓰기가 차단된다.
테이블 크기가 곧 장애 시간이다.

[INPLACE]
InnoDB 내부에서 직접 변경한다.
테이블 복사가 없다.
`LOCK=NONE`과 함께 쓰면
변경 중에도 읽기/쓰기가 가능하다.

[INSTANT]
메타데이터만 변경한다.
데이터를 건드리지 않는다.
테이블이 1TB여도 1초 안에 끝난다.

```sql
ALTER TABLE orders
ADD COLUMN memo VARCHAR(200),
ALGORITHM=INPLACE, LOCK=NONE;
```

ALGORITHM을 명시하면 지원하지 않는 작업에서 에러를 반환한다.
명시하지 않으면 MySQL이 자동으로 고른다. 명시하는 쪽이 안전하다.

### 버전별 Online DDL의 진화

[MySQL 5.5 이전]
COPY만 존재했다.
ALTER TABLE = 테이블 전체 복사.
대형 테이블에서는 서비스 중단이 불가피했다.

[MySQL 5.6]
INPLACE가 도입됐다.
인덱스 추가/삭제, 컬럼 추가가 서비스를 멈추지 않고 가능해졌다.
"Online DDL"이라는 이름이 여기서 시작됐다.

[MySQL 8.0.12]
INSTANT가 등장했다.
컬럼 추가가 메타데이터 변경만으로 끝난다.
단, 테이블 마지막 위치에만 추가할 수 있었다.

[MySQL 8.0.29]
INSTANT의 범위가 크게 넓어졌다.
컬럼을 아무 위치에나 추가할 수 있고, 컬럼 삭제와 순서 변경도 Instant로 된다.
5.6 이전이면 pt-osc가 유일한 선택지였다.
지금은 Instant, INPLACE, pt-osc 순으로 고른다.

### Instant DDL의 함정

Instant는 빠르다. 하지만 공짜는 아니다.
Instant로 컬럼을 추가하면 기존 row에는 그 컬럼의 데이터가 물리적으로 없다.
읽을 때 메타데이터를 보고 기본값을 채운다.
Instant ALTER가 누적되면 row 내부에 "버전 격차"가 쌓인다.
읽을 때마다 버전 확인 비용이 붙는다.
Instant로 추가한 컬럼에 인덱스를 걸면 그 인덱스 생성은 Instant가 아니다. INPLACE나 COPY로 내려간다.
"Instant로 끝났다"고 방심하면 바로 다음 ALTER에서 걸린다.
Instant ALTER가 여러 번 쌓였으면 OPTIMIZE TABLE로 테이블을 다시 쓰는 것을 고려한다.
Instant의 빚을 갚는 작업이다.

### 사전 점검: long query

DDL 전에 가장 먼저 확인하는 건 장시간 실행 중인 쿼리다.
ALTER TABLE은 시작할 때 Metadata Lock을 요청한다.
실행 중인 쿼리가 있으면 그 Lock을 받지 못하고 대기한다.
대기가 길어지면 뒤따르는 쿼리까지 전부 막힌다.
long query 하나가 전체 서비스를 멈추는 구조다.

```sql
SELECT *
FROM information_schema.processlist
WHERE command != 'Sleep' AND time > 3;
```

3초 이상 실행 중인 쿼리가 있으면 DDL을 시작하면 안 된다.
필요하면 해당 세션을 종료하고 나서 실행한다.

### 사전 점검: 디스크, 레플리카, 시간대

pt-osc는 원본의 복제본을 만든다.
100GB 테이블이면 100GB가 추가로 필요하다.
원본 크기의 최소 2배를 확보하라.
여유 없이 시작하면 중간에 실패하고, 실패가 남긴 임시 테이블이 디스크를 더 먹는다.
레플리카 지연도 확인한다.
시작 전 지연이 0이 아니면 실행 중에 더 벌어진다.
시간대는 트래픽이 가장 낮을 때. 야간 배치가 도는 시간과 겹치면 DDL 부하와 배치 부하가 합산된다.
배치 스케줄을 먼저 확인하라.

### 방법을 고르는 결정 트리

모든 DDL에 외부 도구가 필요한 건 아니다.
변경의 종류와 테이블 크기로 방법을 고른다.

[Instant]
컬럼 추가/삭제, 순서 변경(8.0.29+).
가능하면 무조건 Instant.
ALGORITHM=INSTANT를 명시해서 확인한다.

[INPLACE]
인덱스 추가/삭제, VARCHAR 확장.
LOCK=NONE이면 서비스 영향 적음.
수GB 이하 테이블에서 적합.

[pt-osc]
컬럼 타입 변경, PK 변경, 대형 테이블 구조 변경.
수십GB 이상이면 사실상 필수.
트리거 기반이라 FK 있는 테이블도 지원한다.
Instant로 되면 Instant.
안 되면 INPLACE 가능 여부 확인.
그것도 안 되거나 테이블이 크면 pt-osc.

### Metadata Lock이라는 복병

DDL 사고의 절반은 Metadata Lock에서 온다.
Online DDL이라도 시작과 끝에서 MDL exclusive를 잡는다.
잡는 시간은 짧지만 그 순간 열려 있는 트랜잭션이 있으면 대기한다.
명시적 BEGIN뿐 아니라 autocommit=0 상태에서 SELECT만 하고 커밋도 롤백도 안 한 방치 세션이 원인인 경우가 많다.

```sql
SELECT *
FROM performance_schema.metadata_locks
WHERE lock_status = 'PENDING';
```

PENDING이 보이면 DDL이 막혀 있다.
`lock_wait_timeout`을 10~30초로 줄여 DDL이 오래 기다리지 않게 하거나, 방치 세션을 찾아서 종료한다.
무한정 대기하게 두는 것이 가장 위험하다.

### pt-osc로 안전하게 실행하기

Online DDL로 안 되거나 테이블이 크면 pt-osc를 쓴다.
원본에 트리거 3개를 걸고 빈 shadow 테이블에 ALTER를 적용한 뒤 원본 데이터를 청크 단위로 복사한다.
복사 중 변경분은 트리거가 반영한다. 완료 후 RENAME TABLE로 원자적 교체.
핵심 옵션 세 가지.

`--max-lag`: 레플리카 지연 한도.
넘으면 복사를 일시 중단한다.

`--chunk-size`: 한 번에 복사할 row 수.
너무 크면 lock이 길어지고 너무 작으면 전체 시간이 늘어난다.

`--critical-load`: 임계값을 넘으면
pt-osc가 스스로 중단한다.
세 옵션 없이 실행하면 서비스를 보호할 안전장치가 없는 것이다.

### 실행 중에 봐야 할 것

DDL이나 pt-osc를 시작한 뒤에는 세 가지를 계속 감시한다.

[레플리카 지연]
pt-osc의 `--max-lag`이 동작하더라도 실제 지연을 직접 확인해야 한다.
Online DDL은 쓰로틀링이 없다.

[Threads_running]
동시 실행 스레드 수가 평소의 2~3배를 넘으면 DDL이 서비스 쿼리를 압박하고 있다는 신호다.
pt-osc의 `--critical-load`가 이걸 감시하지만 서비스 특성에 맞게 임계값을 조정해야 한다.

[디스크 사용량]
shadow 테이블이 예상보다 커지는 경우가 있다. 인덱스 리빌드 때문이다.
남은 디스크가 10% 아래로 내려가면 작업을 중단할 준비를 해야 한다.

### 끝난 뒤에 확인할 것

DDL이 끝났다고 작업이 끝난 게 아니다.

[스키마 검증]
`SHOW CREATE TABLE`로 의도한 구조인지 확인한다.
레플리카에서도 동일한지 확인한다.
스키마 불일치는 나중에 복제를 깨뜨린다.

[인덱스 통계]
ALTER 직후 인덱스 통계가 부정확할 수 있다.
ANALYZE TABLE을 실행해서 통계를 갱신한다.
통계가 틀리면 옵티마이저가 잘못된 실행 계획을 고른다.

[애플리케이션 동작]
컬럼이 추가됐으면 앱이 그 컬럼을 인식하는지.
타입이 바뀌었으면 ORM 매핑이 깨지지 않았는지.
DDL은 DB 작업이지만 영향은 앱에서 나온다.

### 롤백이라는 환상

"문제 생기면 롤백하면 되지."
DDL에는 그게 안 된다.
ALTER TABLE은 트랜잭션으로 감싸지지 않는다. ROLLBACK이 없다.
컬럼을 추가했으면 다시 삭제해야 하고, 타입을 바꿨으면 다시 바꿔야 한다.
pt-osc가 중간에 실패하면 원본 테이블은 그대로 남아 있다. 교체 전이기 때문이다.
하지만 shadow 테이블과 트리거는 수동으로 정리해야 한다.
진짜 롤백 시나리오는 이렇다.
실패 시 어떤 잔여물이 남는지 파악하고, 잔여물 정리 SQL을 미리 준비하고, 정리 후 원래 상태를 검증하는 쿼리를 만들어둔다.
롤백 "계획"이지 롤백 "버튼"이 아니다.

### 흔한 실수 세 가지

운영에서 반복되는 DDL 실수가 있다.

[실수 1: ALGORITHM 미명시]
ALGORITHM을 빼면 MySQL이 자동 선택한다.
Instant로 될 줄 알았는데 COPY로 빠지면 수십 분간 쓰기가 차단된다.
ALGORITHM=INSTANT를 명시하면 Instant로 안 되는 작업에서 에러가 나서 안전하다.

[실수 2: 여러 ALTER를 한 문에 묶기]
컬럼 추가와 인덱스 생성을 하나의 ALTER로 묶으면 Instant가 가능한 작업까지 COPY로 내려간다.
분리할 수 있으면 분리하라.

[실수 3: 기존 트리거 확인 누락]
pt-osc는 원본에 트리거를 건다.
이미 트리거가 있으면 충돌한다. 사전에 기존 트리거 여부를 반드시 확인해야 한다.

### DBA 관점에서의 정리

1. long query를 먼저 정리하라.
2. ALGORITHM을 반드시 명시하라.
3. 디스크 여유를 원본 크기의 2배 이상 확보하라.
4. Metadata Lock 대기를 반드시 모니터링하라.
5. 롤백 시나리오 없이 실행하지 마라.
6. DDL의 위험은 명령어에 있지 않다.
7. 명령어를 실행하는 맥락에 있다.
8. 5.5에서는 COPY밖에 없었고, 5.6에서 INPLACE가 생겼고, 8.0에서 INSTANT가 나왔다.

도구가 좋아졌다고 안전해지는 건 아니다.
Instant도 누적되면 빚이 되고, Online DDL도 Metadata Lock에 걸리면 장애가 된다.
바이브코딩이 DDL을 만들어줘도 그 DDL을 언제, 어떤 조건에서 실행하고, 실패하면 어떻게 수습하는가는 사람이 설계해야 한다.
ALTER TABLE은 한 줄이지만 그 한 줄의 앞뒤에 붙는 점검이 서비스를 지키는 전부다.
쉽다고 생각한 순간부터 ALTER TABLE 한 줄이 장애가 된다.

## 대용량 DML의 기술: 1억 건을 지우는 세 가지 방법

"1억 건 DELETE 해주세요." 개발팀에서 요청이 온다.
단순한 SQL 한 줄이면 될 것 같다.
`DELETE FROM logs WHERE created_at < '2025-01-01';`
하지만 이 한 줄이 서비스를 멈출 수 있다. 복제를 깨뜨릴 수 있다. 디스크를 가득 채울 수 있다.
대용량 DML은 실력이 아니라 기술이다.

### 왜 대용량 DML이 위험한가

1억 건 DELETE는 1억 번의 행 잠금이다.
1억 건의 undo log 생성이다.
1억 건의 binlog 이벤트다.
트랜잭션 하나가 모든 것을 안고 간다.
그 트랜잭션이 끝나기 전까지 다른 트랜잭션은 기다린다.
DBA가 두려워하는 것은 쿼리 자체가 아니다.
"하나의 거대한 트랜잭션"이 만드는 연쇄 효과다.

### 내부에서 벌어지는 일

InnoDB에서 DELETE 한 건이 실행되면:

[행 잠금]
해당 행에 X Lock이 걸린다.
인덱스가 여러 개면 인덱스마다 잠금이다.

[undo log]
삭제 전 데이터가 undo log에 기록된다.
롤백에 대비하기 위해서다.

[redo log]
변경 내용이 redo log에 기록된다.
크래시 복구에 대비하기 위해서다.

[binlog]
복제를 위해 binlog에도 기록된다.
한 건에 네 가지 부하.
1억을 곱하면 재앙이다.

### 복제 지연

대용량 DML의 가장 흔한 사고다.
소스에서 1억 건 DELETE가 30분 걸렸다면 리플리카에서도 30분이 걸린다.
MySQL 복제는 기본이 단일 스레드다. 그 30분 동안 다른 binlog 이벤트도 전부 뒤에서 기다린다.
리플리카 읽기가 30분 전 데이터를 보여준다. 결제 상태가 갱신 안 된다. 재고가 맞지 않는다. 서비스 장애다.

### undo log와 MVCC

InnoDB는 MVCC로 읽기 일관성을 유지한다.
현재 트랜잭션이 시작된 시점의 데이터를 undo log에서 재구성해 보여준다.
1억 건 DELETE 트랜잭션이 진행 중이면 그 1억 건의 이전 버전이 undo에 남아 있다.
purge 스레드가 이걸 정리하지 못한다.
InnoDB history list length가 치솟는다.
undo tablespace가 비대해진다.
극단적으로 디스크가 차면 DB가 멈춘다.
긴 트랜잭션이 undo를 잡아먹는다.
이건 DELETE뿐 아니라 오래 열려 있는 SELECT도 마찬가지다.

### 방법 1 — 청크 처리

가장 기본적이고 가장 많이 쓰는 방법이다.
한 번에 다 지우지 않고 조금씩 나눠 지운다.

```sql
DELETE FROM logs
WHERE created_at < '2025-01-01'
ORDER BY id
LIMIT 1000;
```

이걸 affected rows가 0이 될 때까지 반복한다.
각 청크는 독립된 트랜잭션이다.
락도 1000건만 잡고 놓는다.
undo도 1000건만 쌓이고 정리된다.
binlog도 1000건짜리 이벤트다.

### 청크 사이즈 튜닝

너무 작으면 오버헤드가 크다. 100건씩이면 100만 번 반복이다. 커넥션 비용만 해도 상당하다. 너무 크면 위험하다.
10만 건씩이면 락 보유 시간이 길어지고 복제 지연이 시작된다.

[적정 범위]
1,000~5,000건이 현실적인 스위트 스팟이다.

[슬립]
배치 사이에 0.5~1초의 슬립을 넣는다. 복제가 따라올 시간을 주는 것이다.
Seconds_Behind_Master를 보면서 조절한다.
서비스 트래픽이 적은 새벽에 돌리면
청크를 더 크게 잡을 수 있다.

### 방법 2 — pt-archiver

Percona Toolkit의 도구다. 대용량 DELETE/아카이빙을 안전하게 해준다.
내부적으로 청크 처리를 하지만 직접 스크립트를 짜지 않아도 된다.
복제 지연을 모니터링하면서 지연이 임계치를 넘으면 스스로 멈춘다. 지연이 줄면 다시 시작한다.
PK 기반으로 순차 접근하므로 테이블 스캔이 발생하지 않는다.
삭제와 동시에 다른 테이블에 아카이빙도 할 수 있다.
DBA가 밤에 걸어놓고 퇴근할 수 있는 도구다.

### 방법 3 — 파티션 DROP

테이블이 시간 기준으로 파티셔닝돼 있다면 이것이 가장 빠른 방법이다.

```sql
ALTER TABLE logs DROP PARTITION p202401;
```

행을 하나씩 지우는 게 아니다. 파티션 파일 자체를 삭제한다. 1억 건이든 10억 건이든 순식간이다.
undo log 없다. binlog 이벤트 한 줄이다. 복제 지연 없다.
단, 전제 조건이 있다.
테이블이 이미 파티셔닝돼 있어야 한다.
삭제 범위가 파티션 경계와 일치해야 한다.
사후에 파티셔닝을 추가하는 건 DDL이다.

### 대용량 UPDATE 패턴

DELETE만 위험한 게 아니다. UPDATE도 같은 문제를 일으킨다.

```sql
UPDATE users SET status = 'inactive'
WHERE last_login < '2024-01-01'
ORDER BY id
LIMIT 1000;
```

청크 처리 로직은 동일하다. 하지만 UPDATE에는 추가 주의점이 있다.

[인덱스 변경]
status에 인덱스가 있으면 값이 바뀔 때마다 인덱스도 갱신된다.
DELETE보다 인덱스 I/O가 더 크다.

[커버링 인덱스 무효화]
변경된 컬럼이 커버링 인덱스에 포함돼 있으면 해당 인덱스의 캐시 효율이 떨어진다.

### INSERT INTO SELECT — 뒤집어 생각하기

1억 건 중 9천만 건을 지워야 한다면? 지우는 것보다 남기는 게 빠르다.

```sql
CREATE TABLE logs_new LIKE logs;
INSERT INTO logs_new
SELECT * FROM logs
WHERE created_at >= '2025-01-01';
RENAME TABLE logs TO logs_old,
logs_new TO logs;
```

남길 1천만 건만 새 테이블에 넣고 테이블을 교체한다.
RENAME은 원자적이고 순간이다.
FK나 트리거가 있으면 복잡해진다. 자동 증가 값, 권한도 확인해야 한다.
하지만 90% 이상을 지울 때는 이 방법이 압도적으로 효율적이다.

### 대용량 DML 모니터링

실행 중에 봐야 할 지표가 있다.

[복제 지연]
Seconds_Behind_Master. 이게 올라가면 청크를 줄이거나 멈춘다.

[InnoDB history list length]
SHOW ENGINE INNODB STATUS에서 확인한다.
이 값이 수만을 넘으면 purge가 밀리고 있다.

[디스크 사용량]
undo tablespace와 binlog가 디스크를 먹는다.
특히 binlog 보관 기간이 길면 위험하다.

[활성 트랜잭션]
오래 열린 트랜잭션이 없는지 확인한다.
내 DELETE가 아니라 다른 세션의
잊힌 트랜잭션이 문제일 수 있다.

### PostgreSQL에서의 차이

PostgreSQL에는 undo log가 없다.
DELETE된 행은 즉시 사라지지 않고 dead tuple로 남는다. VACUUM이 이를 정리한다.
1억 건 DELETE 후 VACUUM을 안 하면 테이블이 부풀어 오른다(bloat).

```sql
DELETE FROM logs
WHERE ctid = ANY(
ARRAY(SELECT ctid FROM logs
WHERE created_at < '2025-01-01'
LIMIT 1000)
);
```

ctid 기반 배치 삭제가 PostgreSQL의 패턴이다.
삭제 후 VACUUM을 주기적으로 돌려야 한다.
autovacuum 설정이 맞는지 사전 확인이 중요하다.

### 청크 처리를 안 해도 되는 경우

모든 DELETE를 청크로 나눌 필요는 없다.

[데이터가 충분히 적을 때]
1만 건 이하면 그냥 한 번에 지워도 된다.
트랜잭션 시간이 수 초 이내라면 문제없다.

[점검 시간이 확보됐을 때]
서비스를 멈추고 작업할 수 있다면 청크의 이유가 사라진다.

[리플리카가 없을 때]
복제 지연 걱정이 없다면 제약이 크게 줄어든다.
위험을 정량적으로 판단하는 것이 모든 것을 청크로 나누는 것보다 낫다.

### DBA 관점에서의 정리

세 가지 방법을 언제 쓰는가.

1. 청크 처리: 범용적. 어떤 테이블에든 쓸 수 있다.
2. pt-archiver: 자동화가 필요할 때. 야간 배치에 적합하다.
3. 파티션 DROP: 가장 빠르다. 단, 사전 설계가 필요하다.

1000개 이상의 클러스터를 운영하면 매주 대용량 DML 요청이 온다.
매번 느끼는 건 같다. 위험한 건 SQL이 아니라 규모다.
같은 DELETE라도 1000건과 1억 건은 완전히 다른 작업이다.

### 마무리

대용량 DML은 기능의 문제가 아니다. 운영의 문제다.
SQL은 누구나 쓸 수 있다. 하지만 1억 건을 서비스 영향 없이 지우는 건 경험이 필요하다.
작게 나누고, 쉬어가면서, 지표를 보면서, 새벽에 돌리는 것.
화려하지 않지만 서비스가 멈추지 않는다.
그게 기술이다.

## 대용량 SELECT의 기술: 1억 건에서 원하는 데이터를 꺼내는 법

"조회 쿼리인데 왜 이렇게 느려요?"
서비스 초기에는 나오지 않던 질문이다.
테이블이 100만 행일 때는 어떤 쿼리를 날려도 빨랐다.
1천만을 넘기면서 느려지기 시작하고, 1억을 넘기면 단순한 SELECT도 무기가 된다.
읽기는 쓰기보다 안전하다고 믿지만, 대용량 SELECT는 DB를 죽일 수 있다.

### 왜 대용량 조회가 어려운가

SELECT는 락을 안 잡는다고 생각하지만 MVCC 스냅샷을 유지하는 동안 undo log를 정리하지 못한다.
수백만 행을 읽으면 그만큼의 메모리를 소비하고, 네트워크로 전송하고, buffer pool을 오염시킨다.
자주 쓰이는 핫 데이터가 밀려나고 한 번 쓸 콜드 데이터가 버퍼를 채운다. 이걸 buffer pool pollution이라 부른다.
대용량 SELECT는 자기만 느린 게 아니라 다른 쿼리까지 느리게 만든다.

### OFFSET 페이지네이션의 함정

가장 흔한 페이지네이션이다.

```sql
SELECT * FROM orders
ORDER BY id
LIMIT 20 OFFSET 1000000;
```

이 쿼리는 100만 행을 읽고 99만 9,980행을 버린다.
20행을 보여주기 위해 100만 행을 스캔하는 것이다.
페이지가 뒤로 갈수록 읽어야 하는 행이 선형으로 늘어난다.
1페이지는 0.001초, 50000페이지는 3초.
OFFSET은 건너뛰는 게 아니라 읽고 버리는 것이다.

### 커서 기반 페이지네이션

OFFSET의 대안이다.
마지막으로 본 행의 키를 기준으로 다음 페이지를 가져온다.

```sql
SELECT * FROM orders
WHERE id > 1000000
ORDER BY id
LIMIT 20;
```

id에 인덱스가 있으면 1000000번째 행으로 바로 점프한다.
앞의 100만 행을 읽지 않는다.
1페이지든 50000페이지든 실행 시간이 일정하다.
단점은 "3페이지로 바로 이동"이 안 된다는 것.
하지만 무한 스크롤, API 페이지네이션에는 이 방식이 압도적으로 유리하다.

### 복합 키 커서 페이지네이션

시간 순서로 정렬된 데이터는 id만으로 커서를 만들 수 없다.

```sql
SELECT * FROM events
WHERE (created_at, id) > ('2026-07-01', 99999)
ORDER BY created_at, id
LIMIT 100;
```

created_at이 같은 행이 여러 개일 때 id로 순서를 보장한다. 이걸 keyset pagination이라 부른다.
인덱스는 (created_at, id)로 잡는다.
정렬 순서와 인덱스 순서가 일치해야 filesort 없이 인덱스만으로 처리된다.
WHERE 절의 튜플 비교가 핵심이다. MySQL 8.0, PostgreSQL 모두 지원한다.

### 커버링 인덱스

쿼리가 필요로 하는 모든 컬럼이 인덱스에 포함돼 있으면 테이블 본체를 읽지 않는다.

```sql
-- 인덱스: (status, created_at, amount)
SELECT status, created_at, amount
FROM orders
WHERE status = 'done'
AND created_at > '2026-07-01';
```

EXPLAIN에 "Using index"가 뜨면 성공이다. 테이블 랜덤 I/O가 사라진다.
대용량 조회에서 가장 효과적인 최적화 중 하나다.
인덱스가 커지는 대신 조회가 극적으로 빨라진다.

### `SELECT *`는 비싸다

필요한 컬럼이 3개인데 테이블에 50개 컬럼이 있다.
`SELECT *`는 47개의 쓸모없는 컬럼을 함께 읽는다.
행 하나가 4KB면 100만 행은 4GB다.
필요한 3개 컬럼만 읽으면 200MB로 줄 수 있다.

[buffer pool 관점]
넓은 행은 버퍼 페이지를 많이 차지한다.
좁은 행은 같은 페이지에 더 많이 들어간다.
캐시 효율이 달라진다.

[네트워크 관점]
DB와 애플리케이션 사이 전송량이 20배 차이 날 수 있다.
`SELECT *`는 편하지만 대가가 크다.

### Read Replica 라우팅

무거운 조회를 Writer에서 돌리면 쓰기 트래픽에 영향을 준다.
Reader로 보내는 것이 원칙이다.

```text
Writer: INSERT, UPDATE, DELETE
Reader: SELECT (특히 대용량)
```

하지만 복제 지연(replication lag)이 있다.
Aurora는 보통 20ms 이내지만 부하가 높으면 수 초까지 벌어진다.

[주의할 쿼리]
방금 INSERT한 데이터를 바로 SELECT하는 패턴.
Writer에 쓰고 Reader에서 읽으면 아직 복제가 안 됐을 수 있다.
이런 read-after-write는 Writer에서 읽거나 복제 지연을 확인한 뒤 읽어야 한다.

### 파티셔닝으로 스캔 범위 줄이기

1억 행 테이블에서 최근 한 달 데이터만 조회한다면 나머지 11개월은 볼 필요가 없다.

```sql
CREATE TABLE logs (
id BIGINT,
created_at DATE,
message TEXT
) PARTITION BY RANGE (created_at);
```

`WHERE created_at >= '2026-07-01'`이면 7월 파티션만 스캔한다. 파티션 프루닝이다.
파티션 키가 WHERE 절에 없으면 모든 파티션을 뒤지므로 오히려 느려진다.
대용량 SELECT와 파티셔닝은 쿼리 패턴이 맞아떨어질 때만 궁합이 좋다.

### 비정규화와 사전 집계

주문 1억 행에서 매장별 월매출을 구한다고 하자.

```sql
SELECT store_id, SUM(amount) FROM orders
WHERE created_at BETWEEN '2026-06-01' AND '2026-07-01'
GROUP BY store_id;
```

매번 수천만 행을 집계하면 DB가 못 버틴다.
사전 집계 테이블을 만든다.

```sql
SELECT store_id, SUM(amount)
FROM daily_store_sales
WHERE sale_date BETWEEN '2026-06-01' AND '2026-07-01'
GROUP BY store_id;
```

1억 행 스캔이 3만 행 스캔으로 바뀐다.
실시간성을 약간 포기하고 속도를 얻는다.

### 스트리밍 조회

100만 행을 SELECT하면 애플리케이션은 메모리에 100만 행을 올릴까?
기본 JDBC는 그렇다. 전체 결과를 메모리에 올린 뒤 반환한다.
서버 사이드 커서를 쓰면 다르다.

```java
statement.setFetchSize(1000);
```

1000행씩 가져와서 처리한다.
메모리는 1000행분만 쓴다.

[MySQL 주의점]
MySQL JDBC는 fetchSize=Integer.MIN_VALUE로 설정해야 스트리밍 모드가 된다.
일반 숫자로는 동작하지 않는다.
대용량 데이터를 처리할 때 OOM의 원인은 쿼리가 아니라 결과를 한꺼번에 받는 클라이언트다.

### 대량 추출 패턴

1억 행을 파일로 내보내야 한다면 애플리케이션을 거치지 않는다.

```sql
-- MySQL
SELECT * INTO OUTFILE '/tmp/orders.csv'
FIELDS TERMINATED BY ','
FROM orders WHERE created_at > '2026-01-01';
-- PostgreSQL
COPY (SELECT * FROM orders
WHERE created_at > '2026-01-01')
TO '/tmp/orders.csv' WITH CSV;
```

DB가 직접 파일을 쓴다. 네트워크 전송도 행 변환 오버헤드도 없다.
애플리케이션에서 row-by-row로 처리하면 10~100배 느리다.
대량 추출은 DB 네이티브 도구가 답이다.

### 캐싱 전략

같은 쿼리가 초당 1000번 실행된다면 DB에 보내지 말고 캐시에서 꺼낸다.

```text
요청 → Redis 확인 → 있으면 반환
→ 없으면 DB 조회 → Redis 저장
```

[캐시 무효화]
데이터가 변경되면 캐시도 갱신해야 한다.
이게 가장 어려운 부분이다.
TTL 기반: 일정 시간 후 자동 만료.
이벤트 기반: 데이터 변경 시 캐시 삭제.
완벽한 정합성이 필요하면 캐시를 쓰지 않는다. "약간의 지연은 괜찮다"가 전제여야 한다.
핫 쿼리를 캐시로 빼면 DB의 대용량 조회 부담이 극적으로 줄어든다.

### 분석 DB로 넘어가야 할 때

"전체 사용자의 월별 구매 패턴을 뽑아주세요."
이런 쿼리를 운영 DB에서 돌리면 서비스가 멈출 수 있다.
OLTP DB는 행 단위 트랜잭션에 최적화돼 있다. 컬럼 단위 집계는 구조적으로 불리하다.

[언제 분석 DB로 가는가]
집계 대상이 수천만 행 이상.
쿼리에 GROUP BY, 윈도우 함수가 복잡하게 걸림.
실시간이 아니라 일/주/월 단위 분석.
Athena, BigQuery, ClickHouse 같은 컬럼 스토어 엔진은 같은 쿼리를 10~100배 빠르게 처리한다.
운영 DB와 분석 DB의 역할 분리. 이것이 대규모 서비스의 기본 구조다.

### DBA 관점에서의 정리

1000개 넘는 클러스터를 운영하면서 대용량 조회 문제를 수없이 봤다.
패턴은 대부분 같다.

[가장 흔한 실수]
`SELECT *`에 OFFSET 페이지네이션.
이 조합만 고쳐도 절반은 해결된다.

[가장 효과적인 최적화]
커버링 인덱스 + 커서 기반 페이지네이션.
인덱스 설계만으로 100배 차이가 난다.

[가장 자주 하는 조언]
"그 쿼리, 운영 DB에서 돌리지 마세요."
분석은 분석 DB에서.
대량 추출은 Reader에서.
실시간 조회는 캐시에서.
DB를 잘 쓴다는 건 DB에 보내지 않아도 될 쿼리를 보내지 않는 것이다.

### 마무리

1억 행은 특별한 숫자가 아니다.
조금만 성장한 서비스면 어디서든 마주치는 규모다.
문제는 데이터 양이 아니라 꺼내는 방식이다.
OFFSET 대신 커서를 쓰고, `SELECT *` 대신 필요한 컬럼만 고르고, Writer 대신 Reader로 보내고, DB 대신 캐시에서 응답하고, OLTP 대신 분석 DB에서 집계한다.
도구는 이미 다 있다. 대용량을 다루는 기술은 새로운 것을 배우는 게 아니라 기본을 정확히 지키는 것이다.

## 느린 쿼리를 쪼개는 기술: 하나보다 둘이 빠른 이유

가게별 통계 API가 느리다. 주문 테이블 2억 건. 파티셔닝도 했고 인덱스도 있다.
그런데 한 쿼리가 3초씩 걸린다.
쿼리를 열었다. 전체 주문 수, 전체 매출, 최근 3개월 주문 수, 최근 매출, 별점대별 카운트. CASE WHEN이 열 개. 한 번에 다 가져오고 있었다.
"한 번에 다 가져오는 게 효율적이잖아요."
두 개로 쪼갰다. 0.3초와 0.1초. 합쳐서 0.4초.
쿼리를 합치는 건 효율이 아니다. 쪼개는 게 효율인 순간이 있다.
성격이 다른 집계를 한 쿼리에 섞지 마라.
전체와 기간 한정은 반드시 분리하라.
분리하면 각 쿼리가 자기에게 맞는 최적화를 받는다.
애플리케이션에서 합치는 비용은 DB에서 합치는 비용보다 싸다.
쿼리가 느리면 인덱스 전에 분리를 먼저 의심하라.

### "한 방"의 유혹

개발자에게 쿼리 한 번은 본능이다.
네트워크 왕복 한 번. 커넥션 점유 한 번. 적을수록 좋다고 배웠다.
맞는 말이다. 단순한 쿼리에서는.
하지만 집계 범위가 갈리기 시작하면 한 쿼리 안에서 서로 다른 최적화가 충돌한다.
전체를 봐야 하는 집계와 최근만 보면 되는 집계를 한 WHERE에 넣으면 옵티마이저는 모두에게 차선인 계획을 고른다.
요구사항이 다른 계산을 한 실행 계획으로 처리하려는 게 문제다.

### 합쳐놓으면 이렇게 된다

```sql
SELECT id,
COUNT(*) AS total_cnt,
SUM(CASE
WHEN order_date >= '2026-02-01'
THEN 1 ELSE 0 END
) AS recent_cnt
FROM orders
WHERE id = 42
GROUP BY id
```

전체 카운트가 필요하니까 WHERE에 `order_date` 범위를 넣을 수 없다.
`order_date`가 파티션 키다. 파티션 키 조건이 없으니 60개 파티션 전부를 연다.
프루닝 실패.
최근 6개월치만 세면 되는 계산까지 5년치를 전부 뒤지고 있다.

### 쪼개면 각자 빨라진다

```sql
-- A: 전체 (단순 집계)
SELECT COUNT(*), SUM(amount)
FROM table WHERE id = 42
-- B: 최근 (파티션 프루닝 작동)
SELECT COUNT(*), SUM(amount)
FROM table
WHERE id = 42
AND date >= '2026-02-01'
```

A는 60개 파티션을 연다. 하지만 단순하다.
B는 6개 파티션만 연다. 복잡해도 된다.
합쳤을 때: `60개 파티션 × 복잡한 연산`.
나눴을 때: `(60 × 단순) + (6 × 복잡)`.
각 쿼리가 자기에게 맞는 실행 계획을 받는다.
이게 분리의 핵심이다.

### 어디서 자르는가

분리의 기준은 단순하다.
"이 집계에 필요한 최소 범위가 어디까지인가."

[전체 vs 기간 한정]
전체 카운트는 파티션 전체를 봐야 한다.
최근 카운트는 일부만 보면 된다.
범위가 다르면 나눈다.

[인덱스에 있는 컬럼 vs 없는 컬럼]
`COUNT, SUM(amount)`은 인덱스로 커버 가능하다.
`SUM(CASE WHEN image_count > 0 ...)`은 안 된다.
커버 가능 여부가 다르면 나눈다.

[자주 바뀌는 조건 vs 고정 조건]
전체 카운트는 캐싱하기 좋다.
최근 카운트는 매번 달라진다.
캐싱 전략이 다르면 나눈다.

### 커버링 인덱스가 살아난다

한 쿼리에 열 개 컬럼을 집계하면 인덱스에 없는 컬럼이 섞이기 마련이다.
인덱스에 없는 컬럼이 하나라도 있으면 매 행마다 데이터 페이지까지 가야 한다. 랜덤 I/O다.
쿼리를 나눠서 A에 인덱스 안의 컬럼만 남기면 인덱스만으로 응답할 수 있다. 커버링 인덱스다.
같은 60개 파티션을 열어도 인덱스 페이지만 훑는 것과 매번 데이터 페이지까지 찾아가는 건 전혀 다른 쿼리다.

### "두 번이면 느린 거 아닌가요"

가장 많이 듣는 반론이다.
쿼리 한 번의 오버헤드는 네트워크 왕복 + 파싱 + 실행 계획 수립. 같은 커넥션이면 왕복은 밀리초 단위다.
3초짜리 쿼리 하나를 0.3초 + 0.1초 두 개로 바꾸면 왕복이 한 번 늘어도 총 0.5초다.
빠른 쿼리 세 개가 느린 쿼리 한 개보다 항상 낫다.
오버헤드가 문제가 되는 건 쿼리가 수백 번 반복될 때다.
집계 쿼리 두세 번 분리는 오버헤드가 아니라 최적화다.

### 쪼개면 안 되는 경우

모든 쿼리를 쪼개라는 말이 아니다.

[정합성이 필요할 때]
A와 B 사이에 데이터가 바뀌면 결과가 어긋난다.
결제 잔액처럼 정확해야 하는 값은 한 트랜잭션 안에서 가져와야 한다.

[JOIN이 핵심일 때]
두 테이블의 관계를 보는 쿼리라면 나눌 수 없다.
애플리케이션 JOIN은 대부분 더 느리다.

[쿼리 자체가 단순할 때]
CASE WHEN 하나짜리 집계를 두 개로 나눌 이유는 없다.
분리의 이점은 집계 범위나 인덱스 조건이 갈릴 때 생긴다.

### DBA 관점에서의 정리

슬로우 쿼리를 받으면 대부분 인덱스부터 본다. 그 전에 할 질문이 있다.
"이 쿼리, 하나여야 하는 이유가 있는가?"
성격이 다른 집계를 한 쿼리에 섞지 마라.
"전체"와 "기간 한정"은 반드시 분리하라.
분리하면 각 쿼리가 자기에게 맞는 최적화를 받는다.
애플리케이션에서 합치는 비용은 DB에서 합치는 비용보다 싸다.
쿼리가 느리면 인덱스 전에 분리를 먼저 의심하라.
인덱스를 추가하고, 힌트를 주고, 파라미터를 튜닝하는 것. 전부 한 쿼리를 빠르게 만드는 방법이다.
가끔은 쿼리를 하나 더 만드는 게 답이다.
쿼리를 합치는 건 효율이 아니다. 쪼개는 게 효율인 순간이 있다.

## '다음 페이지'가 점점 느려지는 이유: OFFSET 없이 페이지 번호를 만드는 법

"커서 기반으로 바꾸면 빨라질 텐데요."
"안 됩니다. 저희는 페이지 번호가 있어서요."
관리자 페이지 성능 개선 논의에서 가장 자주 듣는 대화다.
OFFSET이 느린 건 안다. 커서 기반이 빠른 것도 안다.
하지만 페이지 번호가 있으니까 커서는 못 쓴다고 한다.
여기서 대화가 끝난다. 끝나면 안 된다.
페이지 번호는 UI의 모양이다. OFFSET은 데이터를 가져오는 방식이다.
둘은 같은 것이 아니다.
페이지 번호와 OFFSET을 같은 것으로 묶지 마라.
커서 값을 캐싱하면 페이지 번호 UI는 그대로 유지된다.
사용자의 실제 행동을 관찰하라. 5000페이지로 점프하는 사람은 없다.
OFFSET을 쓰더라도 Deferred Join으로 읽는 양을 줄여라.
필터 없이 수천만 건을 전체 조회하지 마라. 검색 범위를 먼저 좁혀라.

### OFFSET은 건너뛰는 게 아니다

```sql
SELECT * FROM orders
ORDER BY order_id
LIMIT 20 OFFSET 100000;
```

10만 행을 읽고 9만 9,980행을 버린다.
20행을 위해 10만 행을 스캔하는 것이다.
OFFSET 100000은 "10만 번째부터 보여줘"가 아니라 "처음부터 10만 개 읽고 버려. 거기서 20개 줘"다.
페이지가 뒤로 갈수록 읽고 버리는 양이 선형으로 늘어난다.

### 커서 기반의 본질

```sql
SELECT * FROM orders
WHERE order_id > 100000
ORDER BY order_id
LIMIT 20;
```

인덱스로 바로 점프한다. 앞의 10만 건을 읽지 않는다.
1페이지든 5000페이지든 실행 시간이 동일하다. OFFSET은 "읽고 버리기". 커서는 "바로 점프". 이 차이가 전부다.

### 오해의 구조

"커서 기반은 '다음 페이지'만 가능하다. 7페이지로 바로 가려면 7페이지의 시작 위치를 알아야 한다.
그걸 모르니까 OFFSET밖에 방법이 없다."
전제가 하나 틀렸다. "시작 위치를 모른다"는 부분이다.
기억해두면 된다. 사용자가 페이지를 넘길 때마다 그 위치를 저장해두면 된다.

### 커서 캐싱

핵심 아이디어다.

```text
1페이지 조회
→ 결과: id 10001~10020
→ 저장: { page2: 10020 }
2페이지 클릭
→ WHERE order_id > 10020 LIMIT 20
→ 결과: id 10021~10040
→ 저장: { page3: 10040 }
```

페이지를 넘길 때마다 다음 페이지의 시작점이 쌓인다.
UI에는 페이지 번호가 보인다. 내부에서는 WHERE로 점프한다.
사용자는 차이를 모른다.

### 이전 페이지도 된다

"3페이지에서 1페이지로 돌아가려면?"
캐시에 있다.

```text
캐시:
page1: start
page2: 10020
page3: 10040
page4: 10060
4페이지에서 2페이지 클릭
→ WHERE order_id > 10020 LIMIT 20
```

방문했던 페이지의 입구를 전부 기억하고 있으니까 OFFSET 없이 즉시 점프한다.

### 가보지 않은 페이지를 클릭하면

"3페이지까지만 봤는데 50페이지를 누르면?"
커서를 포기하는 가장 흔한 이유다. 50페이지의 커서가 캐시에 없으니까.
그런데 생각해보자. 관리자가 정말 50페이지로 점프하는가?
실제 사용 패턴을 보면 순차 이동이 대부분이다.
1→2→3, 또는 조건 바꿔서 다시 1페이지.
37페이지로 직접 점프하는 관리자는 거의 없다.
없는 문제를 해결하려고 전체 페이지에 OFFSET을 쓰고 있는 것이다.

### 점프를 지원하는 두 가지 방법

그래도 점프가 필요하다면.

[윈도우 방식]
Google 검색 결과처럼
현재 페이지 근처만 보여준다.

```text
3페이지: < 1 2 [3] 4 5 6 7 ... >
50페이지: < ... 48 49 [50] 51 52 ... >
```

보이는 모든 페이지의 커서가 캐시에 있다.
멀리 점프할 일 자체가 없어진다.

[하이브리드]
순차 이동은 커서. 먼 점프만 OFFSET.
95%는 빠르고 5%만 느리다. 전부 OFFSET인 것보다 훨씬 낫다.

### 정렬 기준이 id가 아닐 때

"주문일시 순 정렬인데 커서가 되나요?"
된다. 복합 키 커서를 쓴다.

```sql
SELECT * FROM orders
WHERE (created_at, order_id)
> ('2026-08-15 14:30:00', 10040)
ORDER BY created_at, order_id
LIMIT 20;
```

같은 시각에 주문이 여러 건이면 order_id로 순서를 보장한다.
인덱스를 (created_at, order_id)로 잡는다.
정렬 순서와 인덱스 순서가 일치해야 filesort 없이 처리된다.

### 전체 건수 문제

페이지 번호를 그리려면 전체 건수가 필요하다.
이건 OFFSET이든 커서든 동일한 문제다.

[정확한 수가 필요 없으면]
"약 3만 건" 수준의 추정치를 쓴다.

[정확한 수가 필요하면]
첫 조회 시 한 번 COUNT하고 캐싱한다.
30초 TTL이면 충분하다.

[과감하게]
"다음 페이지 있음"만 판별한다.
LIMIT 21로 조회해서 21번째가 있으면 다음 페이지 존재.
전체 건수 조회 자체를 없앤다.

### Deferred Join

커서 전환이 어렵다면 OFFSET이라도 빠르게 만들 수 있다.

```sql
SELECT o.* FROM orders o
INNER JOIN (
SELECT order_id FROM orders
WHERE created_at > '2026-01-01'
ORDER BY order_id
LIMIT 20 OFFSET 100000
) sub ON o.order_id = sub.order_id;
```

서브쿼리는 PK만 읽는다.
커버링 인덱스를 타면 읽고 버리는 대상이 전체 행이 아니라 인덱스 엔트리 몇 바이트다.
같은 OFFSET이라도 전체 행을 버리는 것과 PK만 버리는 것은 비용이 다르다.

### 관리자 페이지의 진짜 해법

3천만 건에 필터 20개. 인덱스를 몇 개 만들어야 할까.
답은 "인덱스로 풀지 않는다"다.
20개 필터 조합은 수십만 가지다. 전부 커버하는 건 불가능하다.

[기획을 바꾼다]
날짜 범위를 필수 필터로 만든다.
"최근 7일" 기본값. 최대 3개월. 3천만 건이 수만 건으로 줄어든다.
수만 건이면 LIKE '%keyword%'도 빠르다. 인덱스를 안 타도 버틴다.
가장 효과적인 DB 최적화는 쿼리를 고치는 게 아니라 3천만 건을 상대하지 않게 만드는 것이다.

### DBA 관점에서의 정리

"관리자 페이지가 느려요."
가장 많이 받는 문의 중 하나다. 열에 아홉은 같은 구조다.
필수 필터 없이 수천만 건을 OFFSET으로 뒤진다.
페이지 번호와 OFFSET을 같은 것으로 묶지 마라.
커서 값을 캐싱하면 페이지 번호 UI는 그대로 유지된다.
사용자의 실제 행동을 관찰하라. 5000페이지로 점프하는 사람은 없다.
OFFSET을 쓰더라도 Deferred Join으로 읽는 양을 줄여라.
필터 없이 수천만 건을 전체 조회하지 마라. 검색 범위를 먼저 좁혀라.
코드를 고치기 전에 기획자에게 가라.
"날짜 범위를 필수로 만들어주세요."
이 한마디가 인덱스 열 개보다 효과적이다.
"안 됩니다. 페이지 번호가 있어서요."
여기서 대화를 끝내지 마라. 페이지 번호는 UI의 모양이다.
OFFSET은 데이터를 가져오는 방식이다.
둘은 같은 것이 아니다.

## 락의 지형도: Row Lock, Gap Lock, Advisory Lock

"쿼리가 안 끝나요."
로그를 보면 쿼리 자체는 단순하다.
실행 시간도 0.001초면 될 쿼리인데 30초째 대기 중이다.
원인은 락이다. 누군가 같은 행을 잡고 있고, 그게 풀릴 때까지 기다리는 것이다.

### 왜 락이 필요한가

두 사람이 동시에 같은 계좌에서 돈을 인출한다고 생각하자.
잔액: 10,000원
A: 7,000원 인출
B: 5,000원 인출
락 없이 둘 다 잔액 10,000원을 읽고 각자 차감하면 둘 다 성공한다. 잔액은 -2,000원이 된다.
락은 이런 동시 접근을 직렬화한다. A가 끝날 때까지 B는 기다린다.
느려지지만 데이터는 정확하다.

### Shared Lock과 Exclusive Lock

모든 DB 락의 기본 분류다.

[Shared Lock (S Lock)]
"나 이거 읽고 있어."
다른 트랜잭션도 읽을 수 있다. 하지만 쓰기는 못 한다.
여러 트랜잭션이 동시에 S Lock을 잡을 수 있다.

[Exclusive Lock (X Lock)]
"나 이거 쓰고 있어."
다른 트랜잭션은 읽기도 쓰기도 못 한다. 하나의 트랜잭션만 잡을 수 있다.
S끼리는 호환, S-X는 충돌, X-X도 충돌. 이 규칙이 모든 락 동작의 기초다.

### MySQL InnoDB의 Row Lock

InnoDB는 인덱스 기반으로 행 잠금을 건다.
"이 인덱스 레코드를 잠근다"가 정확한 표현이다.
인덱스가 없으면?
테이블의 숨겨진 클러스터드 인덱스(PK)를 전부 스캔하면서 락을 건다. 사실상 테이블 락이 된다.
WHERE 절에 인덱스가 없는 UPDATE:

```sql
UPDATE orders SET status = 'done'
WHERE customer_name = 'dot';
-- customer_name에 인덱스 없으면 전체 행 락
```

인덱스 설계가 곧 락 범위 설계다.

### Gap Lock — InnoDB만의 독특한 락

Gap Lock은 "행과 행 사이의 빈 공간"을 잠근다.
존재하지 않는 행의 자리를 잠그는 것이다.
왜 필요한가? 팬텀 리드(Phantom Read)를 막기 위해서다.
id: 10, 20, 30이 있을 때 `WHERE id BETWEEN 15 AND 25`를 실행하면 id=20만 걸리지만, 이 사이 갭(10~20, 20~30)에도 락이 걸린다.
다른 트랜잭션이 id=15나 id=25를 INSERT 못 하게 막는 것이다.
REPEATABLE READ에서 자동으로 동작한다. READ COMMITTED로 내리면 Gap Lock이 사라진다.

### Next-Key Lock

Row Lock + Gap Lock의 조합이다. InnoDB의 기본 잠금 단위.
id: 10, 20, 30일 때
id=20에 Next-Key Lock이 걸리면:
`(10, 20]` 범위가 잠긴다. 앞의 갭 + 해당 레코드.
이 방식으로 InnoDB는 REPEATABLE READ에서도 팬텀 리드를 방지한다.
다른 DB들은 보통 SERIALIZABLE까지 올려야 팬텀 리드를 막는다.
InnoDB만의 독특한 트레이드오프다.

### PostgreSQL의 MVCC

PostgreSQL은 락 대신 MVCC(Multi-Version Concurrency Control)로 읽기/쓰기 충돌을 피한다.
행을 수정하면 이전 버전을 남겨둔다.
읽기는 이전 버전을, 쓰기는 새 버전을 쓴다.
읽기가 쓰기를 막지 않고, 쓰기가 읽기를 막지 않는다.
MySQL InnoDB도 MVCC를 쓰지만, PostgreSQL은 힙에 다중 버전을 직접 저장하고, InnoDB는 undo log에서 이전 버전을 재구성한다.
구현 방식이 다르다.

### PostgreSQL의 Explicit Locking

MVCC가 충돌을 피해주지만, 쓰기끼리는 여전히 락이 필요하다.

```sql
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;
```

이 행에 대해 X Lock을 명시적으로 잡는다.
다른 트랜잭션의 FOR UPDATE는 대기한다.

```text
FOR SHARE → S Lock
FOR UPDATE → X Lock
FOR NO KEY UPDATE → PK/Unique 외 컬럼 수정 시
FOR KEY SHARE → FK 참조 시
```

PostgreSQL은 락 모드가 세분화돼 있어서 불필요한 충돌을 줄일 수 있다.

### Advisory Lock

DB가 제공하는 "사용자 정의 락"이다.
테이블이나 행과 무관하게 임의의 정수 키로 락을 건다.

```sql
-- PostgreSQL
SELECT pg_advisory_lock(12345);
-- ... 작업 ...
SELECT pg_advisory_unlock(12345);
-- MySQL
SELECT GET_LOCK('my_lock', 10);
-- ... 작업 ...
SELECT RELEASE_LOCK('my_lock');
```

배치 중복 실행 방지, 분산 환경의 리더 선출, 외부 리소스 접근 제어에 쓴다.
테이블 락과 무관하므로 쿼리 성능에 영향을 주지 않는다.

### 데드락

A가 행 1을 잠그고 행 2를 기다린다.
B가 행 2를 잠그고 행 1을 기다린다.
서로를 기다리며 영원히 멈추는 상태. DB는 이걸 자동 감지한다.
MySQL은 InnoDB가 감지 즉시 하나의 트랜잭션을 롤백한다.
보통 작업량이 적은 쪽을 희생시킨다.
PostgreSQL도 deadlock_timeout (기본 1초) 이후 감지해서 하나를 취소한다.
데드락은 버그가 아니다. 동시성 환경에서 자연스럽게 발생한다.
중요한 건 애플리케이션이 재시도할 수 있게 설계하는 것이다.

### 데드락을 줄이는 방법

완전히 없앨 수는 없지만 빈도를 줄일 수는 있다.

[접근 순서 통일]
여러 행을 수정할 때 항상 PK 오름차순으로 접근한다.
A와 B가 같은 순서로 잠그면 데드락이 발생하지 않는다.

[트랜잭션을 짧게]
락 보유 시간을 줄인다.
트랜잭션 안에서 외부 API 호출 같은 느린 작업을 하지 않는다.

[적절한 인덱스]
인덱스가 없으면 락 범위가 넓어진다.
불필요한 행까지 잠그게 된다.

### 메타데이터 락 (MDL)

MySQL에서 DDL과 DML이 충돌할 때 걸리는 락.
누군가 SELECT를 하고 있으면 ALTER TABLE이 대기한다.
ALTER TABLE이 대기하면 그 이후의 모든 SELECT도 대기한다.
줄 서기 효과다.
DDL 하나가 전체 트래픽을 막는다.
DBA가 운영 중 DDL을 실행할 때 가장 조심하는 부분이다.
MySQL 8.0에서도 대부분의 ALTER TABLE은 MDL을 잡는다.
pt-online-schema-change나 gh-ost 같은 도구로 우회한다.

### 락 모니터링

문제가 생겼을 때 누가 누구를 막고 있는지 즉시 확인할 수 있어야 한다.
MySQL:

```sql
SELECT * FROM performance_schema.data_locks;
SELECT * FROM sys.innodb_lock_waits;
```

PostgreSQL:

```sql
SELECT * FROM pg_locks;
SELECT * FROM pg_stat_activity
WHERE wait_event_type = 'Lock';
```

DBA의 첫 번째 반응:
"어떤 세션이 잡고 있는가?"
두 번째:
"그 세션은 뭘 하고 있는가?"
세 번째:
"그 세션을 죽여도 되는가?"

### 낙관적 락 vs 비관적 락

DB 락이 아니라 애플리케이션 패턴이다.

[비관적 락]
"충돌이 날 거니까 미리 잠그자."
`SELECT ... FOR UPDATE`. DB 락을 직접 쓴다.

[낙관적 락]
"충돌은 드무니까 일단 진행하자."
version 컬럼을 두고, UPDATE 시 version 확인.

```sql
UPDATE orders SET status='done', version=2
WHERE id=1 AND version=1;
-- affected rows = 0이면 재시도
```

읽기가 많고 충돌이 드문 시스템은 낙관적, 금융처럼 충돌 비용이 큰 시스템은 비관적이 맞다.

### 마무리

락은 데이터를 지키는 장치이면서 성능을 떨어뜨리는 원인이기도 하다.
InnoDB의 Gap Lock은 다른 DB에 없는 독특한 존재다.
팬텀 리드를 막지만 예상치 못한 대기를 만들기도 한다.
PostgreSQL의 MVCC는 읽기/쓰기 충돌을 없애지만 VACUUM이라는 대가를 치른다.
락 문제를 풀 때 가장 중요한 건 "누가 잡고 있는가"를 빠르게 찾는 것이다.
쿼리가 느린 게 아니라 기다리고 있는 것일 수 있다.
트랜잭션은 짧게, 접근 순서는 일정하게, 인덱스는 정확하게.
이 세 가지가 락 문제의 대부분을 예방한다.

## 결제와 DB: 1원이 틀리면 안 되는 세계

"결제 데이터인데, 그냥 숫자 컬럼에 넣으면 안 되나요?"
금액을 저장하고 상태를 바꾸고 내역을 남긴다.
다른 서비스와 다를 게 없어 보인다.
그런데 1원이 틀리면 회계가 안 맞고 한 건이 중복되면 고객이 두 번 결제한다.
결제 DB는 빠를 필요는 없다. 대신 틀리면 안 된다. 한 건도, 1원도.

- 금액은 DECIMAL이다. float는 쓰지 마라.
- 상태 전이는 DB 제약으로 막아라.
- 중복 결제는 멱등 키로 차단하라.
- PG사 불일치는 대사 배치로 잡아라.
- 결제 데이터는 삭제할 수 없다.

### `0.1 + 0.2`는 0.3이 아니다

프로그래밍에서 float의 함정은 유명하다.
결제에서는 이게 사고가 된다.

```sql
SELECT 0.1 + 0.2
-- 0.30000000000000004
```

1000원짜리 상품에 10% 할인.
float로 계산하면 899.9999999원. 소수점을 버리면 899원. 반올림하면 900원.
1원 차이가 정산에서 수천 건 쌓이면 회계 감사에 걸린다.
금액은 DECIMAL이다. `DECIMAL(12,2)`면 소수점 둘째 자리까지 정확하다.
float는 빠르지만 돈에는 쓰면 안 된다.

### 결제 상태라는 상태 머신

결제에는 단계가 있다.
`대기 → 승인 → 완료`. 여기까지는 단순하다.
취소가 생기면 갈래가 생긴다.
`완료 → 취소 요청 → 취소 완료`. `부분 취소면 완료 → 부분 취소`.
환불이 들어오면 더 복잡해진다.
취소와 환불은 다르다. 취소는 결제를 되돌리는 것이고 환불은 이미 정산된 돈을 돌려주는 것이다.
상태 전이에는 규칙이 있다.
"대기"에서 "환불"로 직접 갈 수 없다.
DB에 CHECK 제약이나 트리거로 허용되지 않는 전이를 막아야 한다.
코드에서만 막으면 버그 한 줄로 뚫린다.

### 같은 요청이 두 번 오면

네트워크가 불안정하다.
사용자가 결제 버튼을 두 번 누른다. 혹은 타임아웃 후 재시도한다.
같은 주문에 대해 결제 요청이 두 번 온다. 두 번 다 처리하면 이중 결제다.
멱등성이 필요하다.
요청마다 고유한 idempotency_key를 발급하고 이미 처리된 key면 이전 결과를 그대로 반환한다.

```sql
INSERT INTO payments
(idempotency_key, amount, status)
VALUES
('ord-123-pay-1', 15000, 'pending')
ON DUPLICATE KEY UPDATE
idempotency_key = idempotency_key
```

유니크 제약이 두 번째 INSERT를 막는다.
멱등성은 DB 레벨에서 보장하는 것이 가장 확실하다.

### PG사 콜백과 트랜잭션의 타이밍

결제를 PG사에 요청한다. PG사가 승인한다. 콜백으로 결과를 보내준다.
그 사이에 우리 서버가 재시작됐다면?
PG사는 승인했는데 우리 DB에는 대기 상태 그대로다.
돈은 빠졌는데 주문은 실패다.
결제 요청 전에 "시도" 레코드를 먼저 만들고 콜백이 오면 상태를 갱신한다.
콜백이 안 오면 주기적으로 PG사에 조회한다. 이걸 reconciliation이라 한다.
DB에 "확인 안 된 결제" 목록이 항상 있어야 하고 배치가 주기적으로 정리해야 한다.

### 정산은 왜 실시간이 아닌가

오늘 판매한 금액을 실시간으로 보고 싶다.
SUM 하나면 될 것 같다.

```sql
SELECT SUM(amount) FROM payments
WHERE status = 'completed'
AND created_at >= '2026-08-01'
```

결제 건이 하루 100만 건이면 매번 100만 건을 집계한다. 인덱스를 타도 느리다.
그래서 정산은 배치다.
하루에 한 번, 일별 집계 테이블에 결과를 넣는다.
실시간 조회는 집계 테이블에서 읽는다.
원본과 집계 사이에 차이가 생기면?
그래서 정산 배치 후에 원본과 집계를 대조하는 검증 배치가 또 돈다.

### 부분 환불이 시작되면

주문 금액 30,000원. 상품 A 10,000원을 환불한다.
원래 결제 건과 환불 건은 어떻게 연결되는가.
환불 테이블이 따로 필요하다.
원결제 ID를 참조하고 환불 금액과 사유를 기록한다.
두 번째 부분 환불이 들어오면 총 환불 금액이 원결제를 초과하면 안 된다.

```sql
SELECT SUM(refund_amount) FROM refunds
WHERE original_payment_id = 101
```

이 `합계 + 신규 환불 ≤ 원결제 금액`. 이 검증을 코드에서만 하면 동시 요청에 뚫린다.
`SELECT FOR UPDATE`로 원결제 행을 잠가야 한다.

### 금융 감사와 데이터 보존

일반 서비스는 오래된 데이터를 지울 수 있다. 결제 데이터는 못 지운다.
전자금융거래법. 5년 보존 의무. 거래 기록, 접속 기록, 오류 기록.
5년치 결제 데이터가 하나의 테이블에 있으면 성능이 점점 나빠진다.
파티셔닝으로 연도별 분리하거나 아카이브 테이블로 이관하되 원본은 삭제하지 않는다.
삭제할 수 없다는 제약이 DB 설계를 처음부터 다르게 만든다.
결제 테이블은 커질 수밖에 없다는 전제로 시작해야 한다.

### DBA 관점에서의 정리

결제 DB는 특별하다.
빠르지 않아도 되지만 정확해야 한다.
금액은 DECIMAL이다. float는 쓰지 마라.
상태 전이는 DB 제약으로 막아라.
중복 결제는 멱등 키로 차단하라.
PG사 불일치는 대사 배치로 잡아라.
결제 데이터는 삭제할 수 없다.
다른 서비스는 장애가 나면 불편하다. 결제 장애는 돈이 사라진다.
결제 DB는 빠를 필요는 없다. 대신 틀리면 안 된다.
한 건도, 1원도.

## 검색 서비스와 DB: 검색은 DB의 일이 아니다

"검색창 하나 넣으려는데, LIKE 쓰면 되지 않나요?"
데이터가 적을 때는 된다. 1만 건이면 LIKE도 충분하다.
10만 건이 되면 느려지기 시작하고 100만 건이 되면 페이지가 멈춘다.
검색은 모든 서비스에 있지만 DB가 잘하는 일이 아니다.
DB는 정확한 조건으로 찾는 데 최적화돼 있다. "비슷한 것"을 찾는 건 다른 문제다.
LIKE는 데이터가 커지면 풀 스캔이다. Full-Text는 타협이지 해답이 아니다.
자동완성은 DB가 감당할 영역이 아니다. 검색 로그는 서비스 DB에서 분리하라.
한국어 검색은 결국 DB 밖으로 나가야 한다.

### LIKE의 한계

```sql
SELECT * FROM products
WHERE product_name LIKE '%반팔%'
```

데이터가 적으면 괜찮다. 많아지면 풀 테이블 스캔이다.
LIKE 앞에 %가 붙으면 인덱스를 탈 수 없다.
B-Tree 인덱스는 "시작이 같은 것"은 찾을 수 있지만 "중간에 포함된 것"은 찾을 수 없다.
100만 건의 상품명을 전부 읽고 한 글자씩 비교한다.
사용자가 검색할 때마다 DB가 책을 처음부터 끝까지 넘기는 셈이다.
목차가 없는 책에서 단어를 찾는 것과 같다.

### Full-Text Index라는 타협

MySQL의 Full-Text Index. PostgreSQL의 tsvector. 단어 단위로 역인덱스를 만든다.
"반팔"이 포함된 행의 ID 목록을 미리 만들어두는 것이다.
LIKE보다 훨씬 빠르다. 그런데 한계가 있다.
"반팔티"를 검색했는데 "반팔 티셔츠"가 안 나온다. 띄어쓰기가 다르면 다른 단어다.
"반팔"과 "반소매"는 같은 의미지만 Full-Text는 모른다.
오타 교정도 안 된다. 동의어 처리도 안 된다.
DB의 Full-Text는 "있으면 좋은 수준"이지 검색 엔진을 대체하지 못한다.

### 자동완성의 숨은 비용

검색창에 "반"을 치면 "반팔", "반바지", "반지"가 뜬다. 글자 하나 칠 때마다 쿼리가 날아간다.
빠르게 치면 초당 5~10번.

```sql
SELECT DISTINCT product_name
FROM products
WHERE product_name LIKE '반%'
ORDER BY popularity DESC
LIMIT 5
```

이 쿼리가 키 입력마다 실행된다.
사용자 1만 명이 동시에 검색하면 초당 수만에서 수십만 쿼리.
자동완성은 기능은 작지만 부하는 크다.
Redis에 인기 검색어를 캐시하거나 별도 자동완성 서비스를 두는 게 일반적이다.
DB가 감당할 영역이 아니다.

### 정렬 기준이 바뀌면 쿼리가 바뀐다

"관련도순" "최신순" "인기순" "가격순."
정렬 기준마다 다른 인덱스가 필요하다.
관련도순은 검색 엔진이 채점한 점수. 최신순은 created_at. 가격순은 price.
네 가지 정렬에 네 가지 인덱스. 인덱스가 늘면 쓰기가 느려진다.
관련도순은 DB가 할 수 없다.
DB는 "이 행이 검색어와 얼마나 관련 있는지" 점수를 매기는 구조가 아니다.
그래서 검색 결과의 정렬이 필요한 순간 DB 밖의 검색 엔진이 필요해진다.

### 검색 로그라는 또 다른 빅 테이블

사용자가 뭘 검색했는지 기록한다. 추천에도 쓰고 분석에도 쓴다.
검색 한 번에 로그 한 건. 하루 검색 100만 건이면 검색 로그 100만 건.
검색 결과를 클릭했는지까지 기록하면 로그가 두 배다.
이 테이블은 쓰기만 하고 실시간으로 읽을 일은 거의 없다.
서비스 DB에 넣으면 공간을 잡아먹는다. 별도 분석 DB나 데이터 웨어하우스로 빼는 게 맞다.
Kafka로 스트리밍하고 Athena나 BigQuery에서 분석하는 구조가 일반적이다.

### DB와 검색 엔진의 동기화

Elasticsearch를 도입했다. 상품 데이터는 DB에 있다. 검색은 Elasticsearch에서 한다.
상품이 등록되면 DB에 INSERT하고 Elasticsearch에도 인덱싱해야 한다.
이 사이에 시간 차가 있다. 상품을 등록한 직후 검색하면 안 나온다.
삭제는 더 위험하다. DB에서 지웠는데 검색 엔진에 남아 있으면 없는 상품이 검색된다.
동기화 실패 시 재시도 로직. 전체 재색인 배치.
DB와 검색 엔진 사이에는 항상 정합성 관리 비용이 따른다.

### 한국어 검색의 어려움

영어는 띄어쓰기로 단어가 나뉜다. 한국어는 그렇지 않다.
"아이폰케이스"와 "아이폰 케이스"는 같은 의미다.
"가방"을 검색했는데 "핸드백"은 안 나온다. "노트북"을 검색했는데 "랩탑"은 안 나온다.
형태소 분석기가 필요하다.
"먹었다"를 "먹다"로 변환해서 인덱싱한다. Nori(한국어 형태소 분석기)가 대표적이다.
DB의 Full-Text는 형태소 분석을 지원하지 않거나 지원해도 품질이 낮다.
한국어 검색을 제대로 하려면 결국 DB 밖으로 나가야 한다.

### DBA 관점에서의 정리

검색은 모든 서비스에 있다. 그리고 대부분 DB에서 시작한다.
LIKE는 데이터가 커지면 풀 스캔이다. Full-Text는 타협이지 해답이 아니다.
자동완성은 DB가 감당할 영역이 아니다.
검색 로그는 서비스 DB에서 분리하라.
한국어 검색은 결국 DB 밖으로 나가야 한다.
처음부터 검색 엔진을 둘 필요는 없다.
하지만 LIKE로 시작할 때 "이건 나중에 바뀔 거다"라는 인식은 있어야 한다.
검색은 DB가 잘하는 일이 아니다.
DB는 정확한 조건으로 찾는 데 최적화돼 있다. "비슷한 것"을 찾는 건 다른 문제다.

## Undo Log vs Redo Log: 되돌리는 기록과 다시 쓰는 기록

트랜잭션이 커밋되기 전에 DB가 죽으면 어떻게 될까.
커밋된 줄 알았는데 디스크엔 아직 안 쓰여 있다면?
이 두 가지 질문에 답하는 게 Undo Log와 Redo Log다.
Undo는 되돌린다. Redo는 다시 쓴다.
둘 다 없으면 트랜잭션은 성립하지 않는다.

### 왜 두 가지가 필요한가

트랜잭션에는 네 가지 속성이 있다. ACID. 이 중 A(Atomicity)와 D(Durability)가 핵심이다.
Atomicity.
트랜잭션은 전부 반영되거나 전부 취소된다.
반쯤 반영된 상태는 허용되지 않는다.
이걸 보장하는 게 Undo Log다.
Durability.
커밋된 트랜잭션은 절대 사라지지 않는다.
서버가 꺼져도, 디스크에 남아 있어야 한다.
이걸 보장하는 게 Redo Log다.

### Redo Log의 역할

InnoDB는 데이터를 변경할 때 디스크의 데이터 파일에 바로 쓰지 않는다.
먼저 Buffer Pool(메모리)에서 수정하고 Redo Log에 변경 내용을 기록한다.
이게 Write-Ahead Logging(WAL)이다. "쓰기 전에 먼저 로그를 기록한다."
커밋 시점에 Redo Log만 디스크에 flush하면 트랜잭션은 안전하다.
실제 데이터 페이지는 나중에 쓴다.
Redo Log는 순차 쓰기다. 데이터 파일은 랜덤 쓰기다.
순차 쓰기가 압도적으로 빠르다.

### Redo Log의 구조

InnoDB의 Redo Log는 순환 버퍼다. 파일 끝에 도달하면 처음으로 돌아가서 덮어쓴다.
MySQL 8.0.30 이전에는 ib_logfile0, ib_logfile1 두 파일이 기본이었다.
8.0.30부터는 #innodb_redo 디렉토리 아래 여러 파일로 자동 관리된다.
순환 구조에서 중요한 건 checkpoint다.
"여기까지는 데이터 파일에 반영 완료했다."
checkpoint 이전의 Redo는 덮어써도 안전하다.
checkpoint가 밀리면 Redo 공간이 부족해진다.

### Crash Recovery

서버가 갑자기 꺼졌다. 재시작하면 InnoDB는 이렇게 복구한다.

[Redo 단계]
Redo Log를 순서대로 읽는다.
커밋된 트랜잭션인데 데이터 파일에 없는 것. 다시 반영한다.

[Undo 단계]
커밋되지 않은 트랜잭션이 있다면 Undo Log를 사용해서 롤백한다.
Redo가 먼저, Undo가 나중이다. 먼저 앞으로 감고, 그다음 되감는다.

### Undo Log의 역할

Undo Log는 "변경 전 상태"를 저장한다.
`UPDATE users SET user_name='재환' WHERE user_id=1` 이 쿼리가 실행되면 Undo Log에는 변경 전 값이 기록된다.
`{user_id:1, user_name:'도트'}` 롤백이 발생하면 이 Undo 레코드를 읽어서 원래 상태로 되돌린다.
단순하다. 하지만 Undo의 진짜 역할은 따로 있다.

### MVCC와 Undo

InnoDB에서 SELECT는 락을 잡지 않는다. 읽기와 쓰기가 서로를 차단하지 않는다.
이게 가능한 이유가 MVCC(Multi-Version Concurrency Control)다. 여러 버전의 데이터를 동시에 유지하는 것이다.
트랜잭션 A가 행을 수정 중이어도 트랜잭션 B는 수정 전 버전을 읽을 수 있다.
그 "수정 전 버전"이 Undo Log에 있다. Undo Log는 버전의 체인이다.
현재 값 → 직전 값 → 그 전 값.
각 트랜잭션은 자기 시작 시점의 버전을 찾아 읽는다.

### Undo가 문제되는 순간

긴 트랜잭션이 Undo를 비대하게 만든다.
트랜잭션 A가 30분째 열려 있다. 그 사이 다른 트랜잭션들이 수만 건을 수정한다.
A가 시작 시점의 데이터를 읽으려면 그 수만 건의 Undo 레코드가 전부 살아 있어야 한다.
Undo purge가 멈춘다.
A가 끝나지 않으면 A 시점 이후의 모든 Undo를 정리할 수 없다.
History List Length가 치솟는다. 이 값이 수백만을 넘으면 체감이 시작된다.
SELECT가 느려진다. Undo 체인을 따라가는 비용이 커지기 때문이다.

### 실무에서 마주치는 Undo 사고

DBA라면 이런 상황을 한 번쯤 겪는다.
슬로우 쿼리가 갑자기 늘어났다. 실행 계획은 안 변했다. 인덱스도 정상이다.
그런데 같은 쿼리가 평소보다 10배 느리다.
History List Length를 확인한다. 수백만이다.
어딘가에 긴 트랜잭션이 열려 있다.
커넥션 풀에서 반환 안 된 세션. 개발 서버에서 열어놓은 BEGIN. 배치 잡이 실패했는데 롤백이 안 된 것.
범인을 찾아 끊으면 purge가 돌면서 Undo가 정리된다.
쿼리 속도가 원래대로 돌아온다.

### Redo가 문제되는 순간

대량 쓰기가 Redo를 병목으로 만든다.
수백만 건의 INSERT가 한꺼번에 들어온다.
모든 변경이 Redo Log에 기록된다.
커밋마다 Redo flush가 발생한다.
innodb_flush_log_at_trx_commit 값이 핵심이다.
1이면 매 커밋마다 flush. 가장 안전하지만 가장 느리다.
2이면 OS 버퍼까지만. 1초마다 flush.
0이면 InnoDB 버퍼에만. 가장 빠르지만 위험하다.
운영 환경에서는 1이 원칙이다.
하지만 대량 마이그레이션 중에는 잠시 0로 바꾸는 판단을 할 때가 있다.
그 판단의 무게를 아는 게 DBA다.

### Undo Tablespace

MySQL 5.6까지는 Undo Log가 시스템 테이블스페이스(ibdata1) 안에 있었다.
한번 커지면 줄어들지 않는 파일이다.
5.7부터 별도 Undo Tablespace로 분리가 가능해졌다. 8.0부터는 기본이다.
undo_001, undo_002 파일로 나뉜다. 8.0.14부터 Undo Tablespace truncation이 자동이다.
innodb_undo_log_truncate = ON이면 비활성화된 Undo Tablespace를 자동으로 축소한다.
"Undo가 커지면 ibdata1이 수십 GB"라는 고전적 사고가 이제는 발생하지 않는다.
다만 긴 트랜잭션의 위험은 여전하다.

### Aurora에서의 Redo

Amazon Aurora는 Redo Log의 위치를 바꿨다. 일반 MySQL에서 Redo는 로컬 디스크에 쓴다.
Aurora에서는 네트워크를 통해 분산 스토리지 레이어에 직접 쓴다.
"Log is the database." Aurora의 설계 철학이다.
DB 인스턴스는 Redo 레코드만 스토리지로 보낸다.
스토리지가 Redo를 받아서 데이터 페이지를 재구성한다.
데이터 페이지 자체를 네트워크로 보내지 않는다.
네트워크 I/O가 극적으로 줄어든다.
복제도 빨라진다.
Replica는 Redo 스트림만 받으면 된다.

### 마무리

Undo와 Redo는 동전의 양면이다.
Redo는 미래를 보장한다.
"커밋한 건 반드시 살린다." 이게 Durability다.
Undo는 과거를 보장한다.
"커밋 안 한 건 반드시 되돌린다." 이게 Atomicity다.
실무에서는 둘 다 "문제가 생겼을 때" 보인다.
History List Length가 올라가면 Undo를 의심한다.
쓰기 지연이 발생하면 Redo flush를 의심한다.
평소에는 존재감이 없다.
하지만 이 두 로그가 없으면 트랜잭션이라는 약속 자체가 성립하지 않는다.
조용히 일하는 것들이 가장 중요하다. Undo와 Redo가 딱 그렇다.
