# BEAR DBA

## 게시판에서 SNS로: 피드가 DB를 바꾸는 순간

"게시판은 만들어봤는데, 피드는 뭐가 다른가요?"
게시판은 목록이다. 전체 글을 최신순으로 보여주면 된다.
피드는 다르다. 내가 팔로우한 사람의 글만 보여줘야 한다. 시간순으로, 실시간으로.
게시판은 SELECT 하나로 되지만 피드는 관계를 따라가야 한다.
팔로우가 1000명이면 1000명의 글을 모아서 정렬해야 한다.
게시판이 커지면 페이징이 느려진다.
피드가 커지면 구조가 바뀌어야 한다.
피드는 Fan-out 전략을 정해야 한다.
유명인은 저장이 아니라 경로를 분리한다.
팔로우 관계는 양방향 인덱스가 필요하다.
좋아요는 카운터와 이력, 두 테이블이지만 실시간일 필요는 없다.
차단은 쿼리에서 빼는 것이고 빼는 것이 더 비싸다.
추천은 서비스 DB에서 돌리지 마라.

### 게시판은 되는데 피드는 왜 안 되나

게시판은 단순하다.

```sql
SELECT * FROM posts
ORDER BY created_at DESC
LIMIT 20
```

모든 사용자가 같은 목록을 본다. 인덱스 하나면 충분하다.
피드는 다르다. 사용자마다 다른 목록을 본다.
내가 팔로우한 사람의 글만 나와야 한다.

```sql
SELECT * FROM posts
WHERE author_id IN (1, 5, 23, 47, 102)
ORDER BY created_at DESC
LIMIT 20
```

팔로우가 500명이면 IN 절에 500개. 이 쿼리는 인덱스를 타도 무겁다.
사용자마다 팔로우가 달라서 쿼리 결과를 캐시하기도 어렵다.

### Fan-out: 쓸 때 복사할 것인가, 읽을 때 모을 것인가

피드를 만드는 방법은 두 가지다.

[Fan-out on Write]
글을 쓰면 팔로워 전원의 피드 테이블에 복사한다.
팔로워가 1만 명이면 INSERT 1만 건.
쓰기가 무겁지만 읽기는 가볍다.

[Fan-out on Read]
피드를 열 때 팔로우 목록을 가져와서 실시간으로 글을 모은다.
쓰기는 가볍지만 읽기가 무겁다. 정답은 없다.
팔로워가 많은 유명인은 Fan-out on Write가 비싸다.
글 하나에 수백만 건의 INSERT. 팔로워가 적은 일반인은 괜찮다.
그래서 대부분의 SNS는 둘을 섞는다.
일반인은 Write, 유명인은 Read.

### 유명인의 피드는 경로가 다르다

유명인의 테이블을 따로 두는 게 아니다.
유명인의 글을 피드 테이블에 안 넣는 것이다.
팔로워가 피드를 열면 피드 테이블의 일반인 글과 캐시에서 꺼낸 유명인 글을 합쳐서 정렬한다.
분리는 저장이 아니라 경로에서 일어난다.

### 팔로우 관계의 폭발

사용자 100만 명. 평균 팔로우 200명. 팔로우 테이블: 2억 건.
"내가 팔로우한 사람 목록." "나를 팔로우한 사람 목록." 두 방향의 쿼리가 모두 빨라야 한다.
인덱스가 두 개 필요하다.
`(follower_id, following_id)`, `(following_id, follower_id)`
"A가 B를 팔로우하는가?"를 확인하는 쿼리는 버튼 하나를 그릴 때마다 실행된다.
게시글 목록의 작성자마다 확인하면 글 20개에 쿼리 20번.
팔로우 관계는 단순한 테이블이지만 조회 패턴이 다양해서 인덱스 설계가 중요하다.

### 좋아요 카운터의 동시성

인기 게시글에 좋아요가 몰린다.
같은 행에 UPDATE가 집중된다.

```sql
UPDATE posts
SET like_count = like_count + 1
WHERE post_id = 999
```

조회수 카운터와 같은 문제다. row lock 경합. 인기 글일수록 심하다.
좋아요는 조회수보다 한 가지 더 어렵다.
"이 사용자가 이미 좋아요를 눌렀는가."
좋아요 테이블이 따로 필요하다.
(user_id, post_id)에 유니크 키. 좋아요를 누르면 두 테이블에 쓴다.
좋아요 이력 INSERT + 카운터 UPDATE. 취소하면 DELETE + UPDATE.
단순한 하트 버튼 하나에 두 테이블, 두 인덱스, 동시성 제어.

### 좋아요는 실시간이 아니다

하지만 좋아요 숫자는 실시간일 필요가 없다. 1만과 1만 47의 차이를 사용자는 모른다.
실시간을 포기하면 설계가 달라진다.
이력 테이블에 INSERT만 하고 카운터는 1분마다 배치로 갱신한다.
아니면 Redis에서 INCR로 세고 DB에는 모아서 flush한다.
row lock 경합이 사라진다.
정확해야 하는 것과 빨라야 하는 것을 구분하면 DB가 해야 할 일이 줄어든다.

### 해시태그와 다대다

글 하나에 태그 여러 개. 태그 하나에 글 여러 개. 전형적인 다대다 관계.
중간 테이블이 필요하다. `posts`, `tags`, `post_tags`.
여행 해시태그로 검색하면

```sql
SELECT p.* FROM posts p
JOIN post_tags pt
ON p.post_id = pt.post_id
JOIN tags t
ON pt.tag_id = t.tag_id
WHERE t.tag_name = '여행'
ORDER BY p.created_at DESC
LIMIT 20
```

조인이 두 번이다.
인기 태그에 글이 100만 건이면 정렬 비용이 크다.
태그별 최신 글은 별도 캐시로 관리하거나 역정규화로 post_tags에 created_at을 복사해서 조인을 줄이는 방법을 쓴다.

### 신고와 차단이 쿼리를 바꾼다

사용자 A가 사용자 B를 차단했다. A의 피드에 B의 글이 나오면 안 된다.
피드 쿼리에 조건이 하나 추가된다.

```sql
AND author_id NOT IN (
SELECT blocked_id FROM blocks
WHERE blocker_id = 42
)
```

차단한 사람이 10명이면 괜찮다. 100명이면 NOT IN이 무거워진다. 신고된 글도 숨겨야 한다.
관리자가 검토 중인 글도 제외해야 한다.
피드 쿼리에 예외 조건이 하나씩 붙을 때마다 실행 계획이 바뀌고 성능이 달라진다.
기능은 "안 보이게 하기"인데 DB는 "보이는 것만 골라내기"로 구현해야 한다.
빼는 것이 더하는 것보다 비싸다.

### 추천 알고리즘이 DB에 요구하는 것

시간순 피드를 넘어서 "당신이 좋아할 만한 글"을 보여주려면 사용자 행동 데이터가 필요하다.
어떤 글에 오래 머물렀는가. 어떤 태그를 자주 클릭하는가. 비슷한 취향의 사용자는 뭘 좋아하는가.
이 데이터는 이벤트 로그다.
서비스 DB에 넣으면 가장 큰 테이블이 된다.
추천은 OLTP가 아니라 OLAP의 영역이다.
서비스 DB에서 추천 쿼리를 돌리면 다른 기능이 전부 느려진다.
추천 데이터는 분석 DB로 분리하고 결과만 서비스 DB에 캐시하는 게 원칙이다.

### DBA 관점에서의 정리

게시판은 하나의 테이블로 시작한다.
피드가 되면 구조가 달라진다.
피드는 Fan-out 전략을 정해야 한다.
유명인은 저장이 아니라 경로를 분리한다.
팔로우 관계는 양방향 인덱스가 필요하다.
좋아요는 카운터와 이력, 두 테이블이지만 실시간일 필요는 없다.
차단은 쿼리에서 빼는 것이고 빼는 것이 더 비싸다.
추천은 서비스 DB에서 돌리지 마라.
게시판에서 SNS로 가는 길은 기능을 추가하는 것이 아니라 DB 구조를 다시 설계하는 것이다.
게시판이 커지면 페이징이 느려진다.
피드가 커지면 구조가 바뀌어야 한다.

## 쇼핑몰과 DB: 장바구니 하나가 이렇게 어려운 이유

"쇼핑몰 하나 만드는데 DB는 뭘 챙겨야 해요?"
상품 등록, 장바구니, 주문. 셋 다 CRUD다.
그런데 사용자가 늘면 가장 먼저 깨지는 게 재고다.
그 다음이 주문이고 마지막이 정산이다.
쉽다고 생각한 순간부터 한 줄짜리 UPDATE가 사고가 된다.
재고는 읽지 말고 바로 빼라.
장바구니는 수명을 정하라.
주문과 결제는 트랜잭션을 분리하라.
주문 내역은 스냅샷으로 남겨라.
정산은 처음부터 분리하라.

### 재고는 숫자 하나인데 왜 이렇게 어려운가

재고는 정수 컬럼 하나다. 10개 남았으면 10이다.
문제는 두 명이 동시에 사는 순간이다.
A가 SELECT해서 10을 봤다. B도 SELECT해서 10을 봤다.
A가 UPDATE로 9를 쓴다. B도 UPDATE로 9를 쓴다.
재고는 8이어야 하는데 9가 됐다.
하나를 공짜로 판 셈이다.
해법은 두 가지다.
`SELECT FOR UPDATE`로 잠그거나 `UPDATE stock SET qty = qty - 1 WHERE qty > 0`으로 애초에 읽지 않고 바로 빼거나.
읽고 나서 쓰면 늦다.

### 장바구니는 어디에 저장하는가

장바구니를 DB에 넣으면 영구적이다. 로그인하고 일주일 뒤에 와도 그대로 있다.
편하지만 테이블이 빠르게 커진다.
대부분의 장바구니는 버려진다. 담기만 하고 주문하지 않는다.
한 달 지난 장바구니 100만 건. DB에는 쓰레기다.
세션에 넣으면 가볍다. 대신 로그아웃하면 사라진다.
Redis에 넣으면 절충이 된다. TTL로 30일 뒤 자동 삭제.
로그인 상태에서는 유지.
어디에 넣느냐는 기능이 아니라 데이터 수명의 문제다.

### 주문 순간의 트랜잭션 경계

사용자가 "결제" 버튼을 누르면 일어나야 하는 일이 많다.
재고 차감. 주문 레코드 생성. 결제 요청. 포인트 차감. 쿠폰 사용 처리.
이걸 하나의 트랜잭션에 넣으면 결제 API 응답이 3초 걸릴 때 DB 커넥션도 3초 동안 잠긴다.
전부 롤백하면 깔끔하지만 결제는 이미 PG사에서 승인됐다.
DB만 롤백해도 돈은 빠져나갔다.
주문과 결제는 하나의 트랜잭션이 아니다. 분리하고 보상 트랜잭션으로 묶어야 한다.

### 트랜잭션 경계를 넘는 패턴들

주문과 결제를 분리하면 실패를 어떻게 되돌리는가.

[Saga 패턴]
각 단계가 독립 트랜잭션이다.
재고 차감 → 주문 생성 → 결제 요청.
결제가 실패하면 보상 트랜잭션으로 재고를 되돌린다.
이벤트로 연결하는 Choreography, 중앙에서 순서를 관리하는 Orchestration.

[Outbox 패턴]
주문 INSERT와 이벤트를 같은 트랜잭션에 넣는다.
outbox 테이블에 이벤트를 함께 INSERT하고 별도 프로세스가 폴링해서 Kafka로 발행한다.
DB 트랜잭션이 이벤트 전달을 보장한다. 2PC는 느리고 장애에 취약하다.
실무에서는 Saga + Outbox 조합이 현실적이다.

### 상품 옵션이라는 조합 폭발

티셔츠 하나. 색상 5개, 사이즈 4개. 옵션 조합 20개.
각 조합마다 재고가 다르고 가격이 다를 수도 있다.
상품 테이블 1건에 옵션 테이블 20건. 옵션마다 재고 테이블 20건.
상품이 1만 개면 옵션은 20만 건이다.
상품 목록 페이지에서 "재고 있는 것만 보기"를 누르면 옵션 테이블까지 조인해야 한다.
인덱스가 없으면 무너진다.

### 주문 내역은 정규화하면 안 된다

주문 당시 상품 이름은 "여름 반팔 티". 한 달 뒤 상품명이 "쿨링 반팔 티"로 바뀌었다.
주문 테이블이 상품 테이블을 FK로 참조하면 주문 내역에 바뀐 이름이 뜬다.
고객은 산 적 없는 상품이 보인다.
가격이 오르면 과거 주문 금액까지 바뀌고 할인율이 바뀌면 정산이 꼬인다.
복사해야 할 것: 상품명, 단가, 수량, 옵션, 할인, 배송비.
컬럼을 늘리거나 JSON 컬럼에 주문 시점의 스냅샷을 통째로 넣는다.
환불할 때도 이 스냅샷이 기준이다.
"그때 이 가격이 얼마였는가"의 답이 주문 레코드 안에 있어야 한다.
정규화 원칙에 어긋나지만 비즈니스가 요구하는 비정규화다.

### 판매자가 늘어나면

쇼핑몰 하나에 판매자 하나면 단순하다. 마켓플레이스가 되면 달라진다.
주문 하나에 판매자가 셋이면 배송도 셋이고 정산도 셋이다.
정산 테이블이 생긴다. 판매자별 수수료율이 다르다. 정산 주기도 다르다.
매월 1일에 정산 배치가 돌면 수백만 건의 주문을 집계한다.
Writer에서 돌리면 서비스가 멈춘다.
Reader에서 돌리면 replica lag이 터진다.
정산은 별도 DB를 만들거나 이벤트 기반으로 실시간 집계해야 한다.
나중에 분리하려면 비용이 열 배다.

### 이벤트 트래픽이라는 시한폭탄

평소 주문 100건/분. 타임세일이 시작되면 10,000건/분. 100배가 갑자기 온다.
재고 차감이 한 행에 몰린다.
row lock 대기열이 길어진다.
커넥션 풀이 바닥난다.
타임아웃이 터진다.
사용자는 결제 버튼을 다시 누른다.
중복 주문이 생긴다.
대기열(Queue)을 앞에 두고 주문 요청을 순서대로 처리하면 DB는 일정한 속도로 소화할 수 있다.
DB가 빨라지는 게 아니라 DB에 도달하는 속도를 조절하는 것이다.

### 소규모에서 대규모로

작을 때는 하나의 DB로 충분하다. MySQL 하나에 상품, 주문, 정산이 다 있어도 된다.
트래픽이 늘면 분리가 시작된다.

[소규모: 하나의 RDBMS]
MySQL 또는 PostgreSQL.
장바구니, 주문, 정산이 같은 스키마. JOIN 하나로 주문과 상품을 조회한다.

[중규모: 캐시와 읽기 분리]
장바구니는 Redis로. 검색은 Elasticsearch로. 읽기는 Read Replica로 분산한다.
DB 하나는 유지하되 부하를 나눈다.

[대규모: 도메인별 DB 분리]
주문 DB, 상품 DB, 정산 DB.
정산도 정합성이 필요하면 RDBMS이 답이다. 분석 워크로드만 Redshift나 BigQuery로 빼면 된다.
서비스 간 통신은 이벤트 기반.
나누는 타이밍을 놓치면 모놀리식 DB의 한 쿼리가 전체를 멈춘다.

### DBA 관점에서의 정리

쇼핑몰은 CRUD의 집합처럼 보인다. 실제로는 동시성과 정합성의 전쟁터다.
재고는 읽지 말고 바로 빼라.
장바구니는 수명을 정하라.
주문과 결제는 트랜잭션을 분리하라.
주문 내역은 스냅샷으로 남겨라.
정산은 처음부터 분리하라.
작은 쇼핑몰일 때는 아무것도 안 터진다.
커진 다음에는 전부 터진다.
쉽다고 생각한 순간부터 한 줄짜리 UPDATE가 사고가 된다.

## Collation의 실체: 같은 글자가 다르게 정렬되는 이유

collation은 보이지 않는 규칙이다.
보이지 않기 때문에 한 번 어긋나면 찾기도 어렵고 고치기도 비싸다.
인덱스는 정렬된 구조다.
B-Tree에 문자열이 들어갈 때 'A' 다음에 'B'가 오는 건 당연해 보인다.
그런데 'ß'는 어디에 놓이는가.
'á'와 'a'는 같은 자리인가. 'A'와 'a'는 같은 값인가, 다른 값인가.
이걸 결정하는 게 collation이다.
MySQL에서 자주 마주치는 세 가지가 있다.
utf8mb4_general_ci, utf8mb4_0900_ai_ci, 그리고 utf8mb4_bin.
같은 글자를 세 가지 방식으로 계산한다.

### 인덱스는 글자가 아니라 weight로 정렬된다

B-Tree에 문자열이 들어갈 때 원본 글자가 그대로 정렬되는 게 아니다.
각 글자를 weight라는 숫자로 변환하고 그 숫자 순서대로 트리에 꽂는다.
'A'와 'a'가 같은 위치에 들어가는 이유는 둘의 weight가 같기 때문이다.
collation은 이 weight를 계산하는 규칙이다.
규칙이 바뀌면 같은 데이터도 트리 안에서 다른 곳에 놓인다.
그런데 weight 변환 자체를 안 하는 놈도 있다. utf8mb4_bin이다.

### utf8mb4_general_ci: 한 글자에 weight 하나

MySQL이 자체적으로 만든 매핑 테이블이다.
단순하다. 글자 하나에 숫자 하나.

```text
'a' = 'A' = 'á' = 'ä' → 0x0041
'b' = 'B' → 0x0042
'ß' → 0x00DF
```

빠르다. 비교할 숫자가 하나뿐이니까.
대신 정확하지 않은 부분이 있다.
독일어 ß는 ss와 같은 글자인데 general_ci는 이걸 모른다.
각각 다른 weight를 갖는다.
Unicode 표준이 아니라 MySQL의 판단으로 만든 규칙이다.

### utf8mb4_0900_ai_ci: 세 겹의 weight

UCA 9.0.0이라는 Unicode 국제 표준을 따른다.
한 글자에 weight가 세 단계다.

```text
기본 악센트 대소문자
'a' → 1C47 0020 0002
'A' → 1C47 0020 0008
'á' → 1C47 0035 0002
'ß' → 1C47 + 1CA3 (= 'ss')
```

ai는 accent insensitive. 악센트를 무시한다.
ci는 case insensitive. 대소문자를 무시한다.
결국 기본 weight 하나로 비교한다.
단순 매핑이 아니라 국제 규칙이다.
ß가 ss와 같다는 것도 이 규칙이 정한다.

### utf8mb4_bin: weight 없이 바이트 그대로

weight 변환을 하지 않는다. 글자의 Unicode codepoint를 그대로 비교한다.
'A'는 0x41이고 'a'는 0x61이다. 다른 값이다. 다른 위치에 놓인다.
'café'와 'cafe'도 다르다. 'straße'와 'strasse'도 당연히 다르다.
가장 엄격하고 가장 빠르다.
변환할 게 없으니 비교 비용이 가장 낮다.
대소문자도 구분하고 악센트도 구분하고 바이트가 다르면 전부 다른 값이다.

### 같은 데이터, 세 가지 정렬

'strasse'로 WHERE 검색을 한다.
인덱스에 'straße'가 있을 때.
general_ci. ß와 ss는 다른 weight다. 못 찾는다.
0900_ai_ci. ß와 ss는 같은 weight다. 찾는다.
`_bin`. ß는 0xC39F이고 s는 0x73이다. 바이트가 다르니 당연히 못 찾는다.
'Strasse'와 'strasse'도 다른 값이다. 세 규칙이 같은 데이터를 다르게 판단한다.
어떤 collation을 고르느냐가 WHERE = 의 결과를 바꾼다.

### `_bin`을 써야 하는 순간

대부분의 서비스 테이블에는 ci를 쓴다. 대소문자 구분 없이 검색하는 게 자연스러우니까.
그런데 `_bin`이 맞는 경우가 있다.
비밀번호 해시. 'AbCdEf'와 'abcdef'는 달라야 한다.
API 토큰. Base64 인코딩은 대소문자가 의미를 갖는다.
파일 경로. Linux에서 File과 file은 다른 파일이다.
ci로 저장하면 다른 값이 같은 값으로 취급된다.
해시 충돌이 아닌데 충돌처럼 보인다.
정확한 바이트 일치가 필요하면 `_bin`. 사람이 읽는 텍스트면 ci.
이 기준이면 거의 틀리지 않는다.

### 악센트까지 같다고 보는 것

general_ci도 대소문자는 무시한다. 'Batch_User'와 'batch_user'는 같다.
0900_ai_ci는 여기에 악센트까지 무시한다. 'cafe'와 'café'도 같다.
`_bin`은 둘 다 구분한다. 'B'와 'b'도 다르고 'e'와 'é'도 다르다.
한국어 서비스에서는 체감이 적다. 한글에는 악센트가 없으니까.
그런데 글로벌 서비스를 만들면 달라진다.
사용자 이름에 José가 들어온다. jose로 검색해도 나와야 하는지.
이건 코드가 아니라 collation이 결정한다.

### 한글은 차이가 거의 없다

기본 한글 음절은 셋 다 Unicode codepoint 순서로 정렬된다.
가 나 다 순서. 차이가 없다.
차이가 나는 건 두 가지다.
한글 낱자. ㄱ, ㅏ 같은 자모. 0900이 Unicode 정규화를 더 정확히 처리한다.
이모지. general_ci는 4바이트 문자를 codepoint로만 비교한다.
0900은 UCA weight 기반이라 정렬이 더 정확하다.
`_bin`은 codepoint 그대로라 정렬은 되지만 유사 이모지를 묶지 못한다.
한국어 서비스에서 collation을 체감하는 순간은 이모지가 섞인 닉네임을 정렬할 때 정도다.

### UNIQUE 인덱스와 ORDER BY

collation은 "같다"의 기준을 바꾼다.
UNIQUE 인덱스에서 이게 직접적으로 드러난다.
ci에서는 'Admin'과 'admin'이 같은 값이다.
둘 중 하나만 들어간다. Duplicate key.
`_bin`에서는 다른 값이다. 둘 다 들어간다.
같은 UNIQUE 제약인데 collation에 따라 허용 범위가 달라진다.
ORDER BY도 마찬가지다.
ci는 'Apple'과 'apple'을 같은 순위로 본다.
`_bin`은 'Apple'이 먼저다. 대문자의 codepoint가 더 작으니까.
같은 쿼리, 같은 데이터. collation만 다르면 정렬 결과가 달라진다.

### CREATE TABLE의 함정

Aurora MySQL에서 테이블을 만든다.
CHARACTER SET utf8mb4만 지정하고 COLLATE는 안 넣었다.
MySQL 8.0 기본인 utf8mb4_0900_ai_ci가 붙는다. 지금은 맞다. 기본값이니까.
그런데 Aurora는 DB 레벨의 default collation을 나중에 바꿀 수 없다.
파라미터 그룹에서 collation_server를 바꿔도 이미 만들어진 DB에는 반영이 안 된다.
정책은 둘 중 하나여야 한다.
CHARACTER SET과 COLLATE를 항상 같이 명시하거나 둘 다 빼서 서버 기본값에 맡기거나.
charset만 넣고 collation을 빼는 게 가장 위험하다.
의도와 다른 collation이 묵시적으로 들어간다. 명시하거나 전부 맡기거나.
반만 지정하면 Default 값으로밖에 안들어간다.

### collation이 섞이면 생기는 일

MySQL 8.0으로 올리면 기본이 바뀐다.
새 테이블은 utf8mb4_0900_ai_ci로 생기고 기존 테이블은 utf8mb4_general_ci로 남는다.
아무도 모르는 사이에 섞인다.
이 두 테이블을 JOIN하면 MySQL은 한쪽 collation을 변환해야 한다.
변환되는 쪽은 인덱스를 탈 수 없다. 함수를 씌운 것과 같은 효과다.
양쪽 다 인덱스가 있어도 한쪽이 풀스캔으로 빠진다.
데이터가 적을 때는 모른다. 100만 건이 넘으면 쿼리가 갑자기 느려진다.
EXPLAIN을 보면 type이 ALL이다. 인덱스가 있는데 왜 안 타는지 한참 찾는다.
원인은 collation이다.

### Illegal mix of collations

JOIN만 문제가 아니다.
WHERE에서 서로 다른 collation 컬럼을 비교하면 MySQL이 에러를 던진다. "Illegal mix of collations"
UNION도 마찬가지다.
위쪽 SELECT는 general_ci인데 아래쪽이 0900_ai_ci면 에러다.
급할 때는 COLLATE 절로 강제한다.

```sql
ON A.user_name = B.user_name
COLLATE utf8mb4_0900_ai_ci
```

되긴 된다. 그런데 COLLATE를 붙인 쪽은 인덱스를 못 탄다.
급한 불은 끄지만 성능은 포기하는 것이다.
근본적인 해결은 하나다. collation을 통일하는 것이다.

### DBA 관점에서의 정리

하나의 DB에는 하나의 collation. 이게 원칙이다.
섞이는 순간 JOIN이 풀스캔으로 빠지고 UNION이 에러를 뱉고 UNIQUE의 중복 기준이 흔들리고 ORDER BY의 결과가 달라진다.
MySQL 8.0으로 올리면 자연스럽게 섞인다. Aurora에서는 DB 기본값을 나중에 못 바꾼다.
`ALTER TABLE CONVERT TO`는 인덱스 리빌드를 동반한다. 전부 나중에 고치기 비싼 것들이다.
처음에 정하고. 전부 맞추고. 건드리지 않는다.
CREATE TABLE마다 COLLATE를 명시하거나 서버 기본값을 믿고 전부 생략하거나.
collation은 보이지 않는 규칙이다.
보이지 않기 때문에 한 번 어긋나면 찾기도 어렵고 고치기도 비싸다.

## 홈페이지와 DB: 간단해 보이는 것이 복잡해지는 순간

"홈페이지 하나 만들건데 DB는 뭘 챙겨야 해요?"
게시판, 로그인, 검색. 셋 다 쉬워 보인다.
그런데 서비스가 커지면 가장 먼저 터지는 곳이 DB다.
쉽다고 생각한 순간부터 챙겨야 할 것들이 쌓이기 시작한다.
처음부터 챙겨야 할 건 정해져 있다.
읽기와 쓰기를 분리할 것.
검색은 DB 밖으로 뺄 것.
세션은 Redis에 둘 것.
커넥션 수를 계산할 것.
조회수 같은 고빈도 UPDATE는 버퍼를 둘 것.

### 읽기가 대부분이라는 착각

홈페이지는 읽기 위주라고 생각한다. 맞다. 대부분 SELECT다.
그런데 눈에 안 보이는 쓰기가 있다.
페이지를 열면 조회수가 올라간다. 로그인하면 세션이 저장된다. 검색하면 검색 로그가 쌓인다.
사용자 한 명이 한 번 방문할 때 읽기 3건, 쓰기 3건.
읽기 위주라는 말은 비율이다. 쓰기가 없다는 뜻이 아니다.
쓰기는 적어도 무거울 수 있다.

### 검색이 DB를 죽이는 순간

검색창을 넣는 건 쉽다. LIKE에 %를 붙이면 된다.
데이터가 1만 건이면 괜찮다. 100만 건이 되면 풀 테이블 스캔이다.
LIKE 앞에 %가 붙으면 인덱스를 탈 수 없다. 매번 전체를 뒤진다.
검색 한 번에 CPU가 치솟고 다른 쿼리가 밀린다.
사용자는 느려진 걸 느끼고 다시 검색을 누른다.
악순환이 시작된다.
검색은 기능이 아니라 설계 결정이다.
전문 검색 엔진을 따로 둘지, Full-Text Index를 쓸지, 처음부터 정해야 한다.

### 관리자 페이지의 무게

사용자 페이지는 신경을 쓴다. 인덱스도 타게 하고 페이징도 넣는다.
관리자 페이지는 안 그렇다.
"전체 주문 목록 조회."
"이번 달 가입자 통계."
"상품 전체 엑셀 다운로드."
건수 제한 없이 전체를 가져온다.
정렬도 넣고 필터도 넣고 조인도 세 개씩 걸린다.
관리자는 한 명인데 그 한 명의 쿼리가 사용자 천 명 분의 부하를 만든다.
관리자 페이지는 반드시 Reader에서 읽게 하거나 별도 커넥션으로 분리해야 한다.

### 세션을 DB에 넣으면 생기는 일

로그인 유지를 위해 세션을 DB에 저장하는 경우가 많다. 사용자가 1000명이면 문제없다.
10만 명이 되면 매 요청마다 세션 테이블을 SELECT한다.
세션은 짧다. 30분이면 만료된다.
그런데 만료된 세션을 안 지우면 테이블이 끝없이 커진다.
100만 건의 만료된 세션 사이에서 유효한 세션 하나를 찾는다.
인덱스가 없으면 재앙이다.
세션은 DB보다 Redis가 낫다.
TTL로 자동 만료되고 메모리 기반이라 빠르다.
DB에는 영구 보관할 데이터만 넣어야 한다.

### 조회수 카운터의 함정

게시글 조회수. 글을 열 때마다 +1.

```sql
UPDATE posts
SET view_count = view_count + 1
WHERE post_id = 12345
```

100명이 동시에 같은 글을 열면 같은 행에 UPDATE 100건이 몰린다.
row lock 경합이 시작된다. 인기 글일수록 심하다.
트래픽이 많은 글이 DB를 가장 괴롭힌다.
조회수는 실시간일 필요가 없다.
Redis에 먼저 쌓고 주기적으로 DB에 반영하면 100건이 1건으로 줄어든다.

### 파일은 밖에 있지만 메타는 안에 있다

이미지를 DB에 넣는 사람은 이제 거의 없다. S3에 올린다. 여기까진 맞다.
그런데 파일 이름, 크기, 업로드 시각, 썸네일 경로, 연결된 게시글 ID.
이 메타데이터는 전부 DB에 들어간다.
게시글은 삭제해도 이미지 메타데이터는 안 지우는 경우가 많다.
고아 레코드가 쌓인다.
몇 년 지나면 파일 테이블이 가장 큰 테이블이 된다.
업로드할 때 넣는 건 쉽다. 삭제할 때 같이 지우는 게 어렵다.
정기적으로 고아 레코드를 정리하는 배치가 필요하다.

### 커넥션, 얼마나 열 것인가

WAS를 띄우면 커넥션 풀이 생긴다. 기본값이 보통 10개에서 20개다.
WAS가 하나면 20개. 세 대면 60개. 오토스케일링으로 열 대가 되면 200개.
DB의 max_connections는 유한하다.
평소에는 여유롭다. 배포하거나 스케일링이 터지면 순간 폭발한다.
새 WAS가 뜨면서 풀을 한꺼번에 열고 이전 WAS가 꺼지면서 풀을 반환한다.
겹치는 구간이 위험하다.
커넥션 풀 크기는 WAS 최대 대수 곱하기 풀 크기가 DB 한계의 80%를 넘지 않게 잡아야 한다.

### 갑자기 트래픽이 늘 때

홈페이지는 예측 불가능하다.
기사 하나 나가면 트래픽이 10배 뛴다.
SNS에 공유되면 한 시간 만에 평소의 50배가 온다.
이때 DB가 버틸 수 있는지는 이미 결정돼 있다.
Reader가 없으면 Writer 하나가 전부 받는다.
캐시가 없으면 모든 요청이 DB까지 내려온다.
커넥션 풀이 작으면 대기열이 생기고 사용자는 빈 화면을 본다.
갑자기 늘어난 트래픽에 대비하는 방법은 하나다.
평소에 구조를 만들어두는 것이다.
Read Replica 하나. Redis 캐시 한 겹.
이 두 가지만 있어도 10배는 버틴다.

### DBA 관점에서의 정리

홈페이지는 모든 서비스의 시작이다. 단순해 보여서 DB를 대충 설계한다.
트래픽이 적을 때는 아무 문제 없다. 문제는 커진 다음에 터진다.
검색이 느려지고. 세션 테이블이 비대해지고. 관리자 한 명이 DB를 잡아먹고. 파일 메타데이터가 끝없이 쌓인다.
처음부터 챙겨야 할 건 정해져 있다.
읽기와 쓰기를 분리할 것.
검색은 DB 밖으로 뺄 것.
세션은 Redis에 둘 것.
커넥션 수를 계산할 것.
조회수 같은 고빈도 UPDATE는 버퍼를 둘 것.
나중에 고치려면 서비스를 멈춰야 한다.
처음에 챙기면 코드 몇 줄이다.
그 차이가 반년 뒤에 장애 보고서 한 장이 된다.

## 인덱스의 진짜 동작 원리: B-tree, 순서, 커버링의 실체

"인덱스 추가하면 되지 않나요?"
면접에서 이 말이 나오는 순간 후속 질문이 쏟아진다.
B-tree 구조가 뭔지, 왜 컬럼 순서가 중요한지, 커버링 인덱스가 왜 빠른지.
인덱스를 "안다"는 것과 인덱스를 "이해한다"는 것은 완전히 다른 영역이다.

### 면접에서 인덱스가 중요한 이유

"느린 쿼리를 어떻게 해결하셨나요?" DB 면접의 단골 질문이다.
대부분 "인덱스를 추가했습니다"라고 답한다. 여기서 끝나면 주니어다.
왜 그 인덱스가 효과가 있었는지, 어떤 구조로 동작하는지, 부작용은 없었는지.
이 세 가지를 설명할 수 있으면 시니어 레벨의 답이 된다.

### B-tree란

인덱스의 물리적 구조다.
Binary tree가 아니라 Balanced tree. 세 계층으로 이루어진다.

[Root]
트리의 꼭대기. 검색의 시작점.

[Branch]
중간 길잡이. 어느 리프로 가야 할지 안내한다.

[Leaf]
실제 키 값이 정렬된 채로 저장된다.
리프 페이지끼리는 양방향 링크드 리스트로 연결돼 있다.
도서관의 색인 카드와 같다.
카드가 정렬돼 있으니 원하는 책을 빠르게 찾는다.

### B-tree의 탐색 과정

1,000만 행 테이블에서 id=7777을 찾는다고 하자.
풀 스캔이면 최대 1,000만 번 비교한다.
B-tree는 다르다.
루트에서 시작해 브랜치를 거쳐 리프까지.
깊이가 3~4면 3~4번의 페이지 접근으로 끝난다.
O(N)이 O(log N)이 된다.
1,000만 행도 약 23번 비교면 충분하다. 이게 인덱스의 존재 이유다.
정렬된 구조가 검색을 압도적으로 빠르게 만든다.

### 복합 인덱스와 컬럼 순서

```sql
CREATE INDEX idx_name_age ON users(name, age);
```

이 인덱스는 name으로 먼저 정렬하고, 같은 name 안에서 age로 정렬한다.
전화번호부와 같다. 성이 같으면 이름순으로 정렬되는 것.

```sql
WHERE name = 'dot' AND age = 30 -- → 사용됨
WHERE name = 'dot' -- → 사용됨
WHERE age = 30 →--  사용 안 됨
```

이것이 최좌측 접두사(Leftmost Prefix) 규칙이다.
왼쪽부터 순서대로 매칭되지 않으면 인덱스를 탈 수 없다.

### 커버링 인덱스

인덱스만으로 쿼리가 완결되는 상태다.
테이블 본체를 전혀 읽지 않는다.

```sql
CREATE INDEX idx_cover ON orders(user_id, status);
SELECT user_id, status FROM orders
WHERE user_id = 100;
```

필요한 컬럼이 전부 인덱스 안에 있다. Extra 컬럼에 "Using index"가 뜬다.
이것이 Index Only Scan이다.
왜 빠른가?
인덱스는 테이블보다 훨씬 작고, 순서대로 정렬돼 있어 디스크 I/O가 최소화된다.
테이블 랜덤 접근이 사라지는 것이 핵심이다.

### 인덱스 선택도와 카디널리티

인덱스가 있어도 쓸모없을 때가 있다. 선택도(Selectivity)가 낮은 컬럼이다.
gender 컬럼에 M/F 두 값만 있다면 인덱스를 타도 전체 행의 50%를 읽는다.
옵티마이저는 이럴 때 풀 스캔을 선택한다. 인덱스 경유 랜덤 I/O보다 순차 스캔이 낫기 때문이다.
카디널리티 = 고유 값의 수. 높을수록 인덱스가 효과적이다.
email은 카디널리티가 높다. 인덱스에 적합하다.
is_active는 낮다. 단독 인덱스로는 낭비다.

### Clustered vs Non-Clustered

InnoDB에서 PK가 특별한 이유다.

[Clustered Index]
테이블 데이터 자체가 PK 순서로 저장된다.
PK 검색 = 데이터 직접 접근. 추가 단계 없음.
InnoDB는 테이블당 하나만 가능하다.

[Non-Clustered (Secondary Index)]
인덱스 리프에 PK 값이 들어 있다.
인덱스 검색 → PK 값 획득 → PK로 다시 검색.
이 두 번째 단계를 "테이블 룩업"이라 한다.
커버링 인덱스가 빠른 이유가 여기 있다. 테이블 룩업을 생략하기 때문이다.

### Index Scan vs Index Seek

같은 인덱스를 타도 성능 차이가 크다.

[Index Seek]
B-tree를 타고 내려가 정확한 위치를 찾는다.
`WHERE id = 100`. 핀포인트다.

[Index Range Scan]
시작점을 찾고 범위만큼 쭉 읽는다.
`WHERE id BETWEEN 1 AND 10000`.
범위가 넓으면 느려진다.

[Index Full Scan]
인덱스 전체를 순서대로 읽는다.
테이블 풀 스캔보다는 낫지만 인덱스를 제대로 활용하는 것은 아니다.
EXPLAIN의 type 컬럼에서 확인한다.
ref, eq_ref는 좋고, range는 범위 확인, ALL은 경고다.

### 인덱스의 쓰기 비용

인덱스는 읽기를 빠르게 하지만 쓰기를 느리게 한다.
INSERT: 테이블에 행 추가 + 모든 인덱스에 키 추가.
UPDATE: 변경된 컬럼의 인덱스를 갱신.
DELETE: 테이블 행 삭제 + 모든 인덱스에서 키 제거.
인덱스가 5개면 INSERT 한 번에 6번의 쓰기가 발생한다.
테이블 1회 + 인덱스 5회.
OLTP에서 초당 수천 건의 INSERT가 발생하는 테이블에 인덱스를 10개 걸어두면 쓰기 성능이 바닥을 친다.

### 인덱스 과다의 문제

인덱스가 많으면 세 가지가 나빠진다.

[저장 공간]
인덱스도 디스크를 차지한다. 테이블보다 인덱스 합계가 큰 경우도 흔하다.

[쓰기 증폭]
모든 DML이 모든 인덱스를 갱신한다. Write Amplification이 심해진다.

[옵티마이저 혼란]
인덱스가 너무 많으면 플래너가 잘못된 인덱스를 선택할 확률이 높아진다.
실행 계획이 불안정해진다.
"인덱스는 약이자 독이다."
DBA가 가장 자주 하는 말 중 하나다.

### Invisible Index와 미사용 인덱스 탐지

사용하지 않는 인덱스를 찾아 정리하는 것도 DBA의 일이다.
MySQL 8.0의 Invisible Index:

```sql
ALTER TABLE orders ALTER INDEX idx_old INVISIBLE;
```

인덱스를 삭제하지 않고 옵티마이저에서만 숨긴다.
문제 없으면 DROP. 문제 있으면 VISIBLE로 복구. 안전한 정리 방법이다.
PostgreSQL은 pg_stat_user_indexes로 확인한다.

```sql
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0;
```

idx_scan이 0인 인덱스는 한 번도 사용되지 않은 것이다.

### MySQL vs PostgreSQL 인덱스 차이

두 DB 모두 B-tree를 쓰지만 세부 동작이 다르다.

[InnoDB 세컨더리 인덱스]
리프에 PK를 저장한다.
PK가 크면 세컨더리 인덱스도 커진다. UUID PK가 위험한 이유다.

[PostgreSQL의 HOT Update]
인덱스 컬럼이 변경되지 않은 UPDATE는 힙 페이지 내에서만 처리한다.
인덱스를 건드리지 않으므로 빠르다.

[Partial Index — PostgreSQL 전용]

```sql
CREATE INDEX idx_active ON orders(user_id)
WHERE status = 'active';
```

조건을 만족하는 행만 인덱스에 넣는다. 크기와 쓰기 비용이 줄어든다.
MySQL에는 없는 기능이다.

### 면접에서 나오는 인덱스 질문들

실제로 받았거나 자주 등장하는 질문들이다.
"복합 인덱스 (a, b, c)에서 WHERE b = 1 AND c = 2는 인덱스를 타나요?"
→ 안 탄다. 최좌측 접두사 규칙 위반.
"PK를 UUID로 쓰면 어떤 문제가 있나요?"
→ 정렬 순서가 랜덤이라 페이지 분할이 잦고, 세컨더리 인덱스 크기가 커진다.
"인덱스를 추가했는데 오히려 느려진 경우가 있나요?"
→ 카디널리티가 낮아 풀 스캔보다 느리거나, 인덱스가 너무 많아 쓰기 성능이 떨어진 경우.
질문의 본질은 "왜"다. 구조를 알면 모든 파생 질문에 답할 수 있다.

### DBA 관점에서의 정리

DBA에게 인덱스는 매일 만지는 도구다. 슬로우 쿼리의 90%는 인덱스로 해결된다.
하지만 인덱스 과다의 30%는 인덱스를 줄여서 해결된다.
커버링 인덱스를 설계할 줄 아는 개발자는 드물다.
`SELECT *` 대신 필요한 컬럼만 조회하라는 말의 진짜 이유가 여기 있다.
인덱스를 추가하는 건 쉽다. 언제 추가하지 말아야 하는지 아는 게 어렵다.

### 마무리

인덱스는 정렬된 구조다.
B-tree가 그 구조를 구현하고, 리프 노드의 링크드 리스트가 범위 스캔을 가능하게 한다.
컬럼 순서가 중요한 이유는 정렬 순서 때문이고, 커버링 인덱스가 빠른 이유는 테이블 룩업을 없애기 때문이고, 카디널리티가 낮으면 인덱스가 무의미한 이유는 옵티마이저가 더 나은 방법을 알기 때문이다.
"인덱스 추가하면 되죠"에서 "이 인덱스는 이 구조로 동작하고, 이 쿼리 패턴에 이렇게 효과적입니다"로.
그 차이가 면접의 합격과 불합격을 가른다.

## 인덱스의 해부학: B-Tree에서 GIN까지, 그리고 안 타는 이유

"인덱스 걸어주세요." 개발자가 DBA에게 가장 많이 하는 요청이다.
그런데 인덱스가 실제로 어떻게 생겼는지, 왜 어떤 인덱스는 타고 어떤 건 안 타는지, 아는 사람은 많지 않다.

### 인덱스란

책 뒤에 붙은 색인을 생각하면 된다.
"트랜잭션"이라는 단어가 나오는 페이지를 전부 뒤지는 대신, 색인에서 페이지 번호만 찾으면 된다.
DB의 인덱스도 동일하다.
테이블 전체를 스캔하는 대신 원하는 행의 위치를 빠르게 찾아준다.
대신 대가가 있다.
INSERT, UPDATE, DELETE마다 인덱스도 함께 갱신해야 한다. 색인을 유지하는 비용이다.

### B-Tree — 거의 모든 인덱스의 기본

B-Tree는 "Balanced Tree"에서 왔다. 모든 리프 노드의 깊이가 같다.
1000만 행이 있어도 루트에서 리프까지 보통 3~4단계.
한 번의 탐색으로 수천만 행 중 원하는 행을 찾아낸다.
CREATE INDEX를 아무 옵션 없이 쓰면 MySQL이든 PostgreSQL이든 기본으로 B-Tree가 만들어진다.
`=, <, >, BETWEEN, ORDER BY`.
범위 검색과 정렬에 모두 쓸 수 있어서 만능에 가깝다.

### InnoDB의 Clustered Index

MySQL InnoDB에서는 테이블 자체가 인덱스다.
PK 순서대로 데이터가 물리적으로 정렬된다.
PK를 찾는 건 곧 데이터를 찾는 것이다.
세컨더리 인덱스(PK가 아닌 인덱스)는 리프 노드에 PK 값을 저장한다.
세컨더리 → PK 값 획득 → PK 인덱스로 다시 탐색. 이걸 "북마크 룩업"이라 부른다.
PK가 크면 세컨더리 인덱스도 커진다.
PK에 UUID를 쓰면 인덱스가 비대해지는 이유다.

### PostgreSQL의 Heap + Index

PostgreSQL은 다르다. 테이블(힙)과 인덱스가 분리돼 있다.
인덱스 리프 노드에는 행의 물리적 위치(ctid)가 들어간다.
인덱스 → ctid → 힙에서 직접 조회.
PK도 그냥 Unique Index + NOT NULL이다.
InnoDB처럼 "테이블 = PK 인덱스"가 아니다. 대신 VACUUM이 필요하다.
삭제된 행이 힙에 남아있고, 인덱스가 죽은 행을 가리킬 수 있다.
VACUUM이 이걸 정리한다.

### Hash Index

이름 그대로 해시 함수를 쓴다.
`=` 비교에만 쓸 수 있다. 범위 검색 불가, 정렬 불가.
MySQL 8.0 InnoDB에서는 Hash Index를 지원하지 않는다.
Adaptive Hash Index라는 내부 최적화가 자동으로 동작할 뿐이다.
(착각 할 수 있지만 Hash Join이 아니다 )

```sql
-- 이렇게 해도 InnoDB는 조용히 B-Tree로 만든다
CREATE INDEX idx USING HASH ON orders(user_id);
-- → 실제로는 BTREE로 생성됨
```

PostgreSQL은 Hash Index를 오래전부터 지원했지만 PG 9까지는 WAL에 기록되지 않아 공식 문서가 "discouraged"로 권고했다.
PG 10부터 WAL 기록이 추가되면서 비로소 프로덕션에서 쓸 수 있게 됐다.
정확히 딱 하나의 값을 찾는 경우 B-Tree보다 빠를 수 있다.
하지만 그 경우도 B-Tree가 충분히 빠르다.

### GIN — 배열과 전문 검색

GIN은 Generalized Inverted Index. "역인덱스"라고 생각하면 된다. PostgreSQL 전용.
일반 인덱스: 행 → 값
GIN: 값 → 해당 값을 가진 행들
JSONB 컬럼에서 특정 키를 검색하거나, 배열 컬럼에서 특정 원소를 찾거나, Full-Text Search에서 단어를 검색할 때 쓴다.
tsvector + GIN 조합이 PostgreSQL 전문 검색의 핵심이다.

### GiST — 공간과 범위

GiST는 Generalized Search Tree. PostgreSQL 전용.
지리 좌표, IP 범위, 날짜 범위 같은 "겹치는 영역"을 검색할 때 쓴다.
PostGIS의 공간 쿼리가 GiST 인덱스 위에서 동작한다.
"서울역 반경 1km 이내 음식점" 같은 쿼리가 가능해지는 이유다.
B-Tree로는 불가능한 영역이다. 정렬이 아니라 "포함/교차"를 판단해야 하기 때문이다.

### Covering Index

쿼리에 필요한 모든 컬럼이 인덱스 안에 들어있으면 테이블을 아예 안 읽어도 된다.
이걸 Index-Only Scan이라 한다.
(MySQL에서는 "커버링 인덱스")

```sql
CREATE INDEX idx_cover ON orders(user_id, status, amount);
SELECT status, amount FROM orders WHERE user_id = 42;
```

인덱스만 읽으면 답이 나온다. 디스크 I/O가 극적으로 줄어든다.
MySQL의 INCLUDE 절은 8.0에도 없다.
PostgreSQL은 11부터 지원한다:

```sql
CREATE INDEX idx ON orders(user_id) INCLUDE (status, amount);
```

PostgreSQL의 INCLUDE는 검색에 안 쓰는 컬럼을 B-Tree 내부 노드에서 제외해서 인덱스가 더 가볍다.
MySQL은 커버링 하려면 모든 컬럼을 인덱스 키에 넣어야 한다.

### Cardinality — 인덱스를 걸지 말지의 기준

카디널리티는 "컬럼의 고유 값 개수"다.
성별 컬럼: M/F 두 가지 → 카디널리티 2
주민번호 컬럼: 전부 다름 → 카디널리티 = 행 수
카디널리티가 낮으면 인덱스를 타도 결국 행의 절반을 읽는다.
인덱스를 거치면 랜덤 I/O가 발생하는데, 어차피 절반을 읽을 거면 순차 I/O로 쭉 읽는 Full Scan이 더 빠르다.
옵티마이저도 이걸 안다.
통계 정보에 카디널리티가 기록되어 있고, "인덱스 타봤자 소용없다"고 판단하면 인덱스를 무시한다.
"인덱스 걸었는데 안 타요." 카디널리티부터 확인해야 한다.

### Selectivity

셀렉티비티는 카디널리티의 비율 버전이다. 고유 값 수 / 전체 행 수.
1에 가까울수록 인덱스 효율이 높다.
0에 가까우면 인덱스가 의미 없다.

```text
PK: selectivity = 1.0 (완벽)
email: selectivity ≈ 0.99 (매우 좋음)
gender: selectivity ≈ 0.00005 (의미 없음)
```

DBA가 인덱스를 추천할 때 가장 먼저 보는 숫자다.

### 복합 인덱스의 순서

```sql
CREATE INDEX idx ON orders(user_id, created_at);
```

이 인덱스는

```sql
WHERE user_id = 42 AND created_at > '2026-01-01'
```

에는 효과적이다. 그런데

```sql
WHERE created_at > '2026-01-01'
```

에는 쓸 수 없다.
복합 인덱스는 왼쪽부터 순서대로 탄다.
전화번호부가 "성 → 이름" 순서로 정렬된 것과 같다. 이름만으로는 찾을 수 없다.
이걸 "Leftmost Prefix Rule"이라 부른다.
인덱스 설계에서 가장 자주 실수하는 부분이다.

### 인덱스가 안 타는 이유들

"인덱스 걸었는데 왜 느려요?" DBA가 가장 많이 받는 질문이다.

[함수 적용]

```sql
WHERE YEAR(created_at) = 2026
```

→ created_at 인덱스 사용 불가.
인덱스에 저장된 건 원본 값이지 YEAR() 결과가 아니다.

[묵시적 형변환]

```sql
WHERE phone = 01012345678
```

phone이 VARCHAR인데 숫자로 비교하면 MySQL이 전체 행을 형변환한다.

[LIKE 와일드카드]

```sql
WHERE name LIKE '%재환'
```

앞에 %가 오면 B-Tree 탐색 불가.

### Functional Index

함수 때문에 인덱스가 안 타는 문제, 해결 방법이 있다.
PostgreSQL은 오래전부터:

```sql
CREATE INDEX idx ON users (LOWER(email));
```

MySQL 8.0부터:

```sql
ALTER TABLE users ADD KEY idx ((LOWER(email)));
```

LOWER(email) 결과를 인덱스에 저장해둔다.

```sql
WHERE LOWER(email) = 'dot@example.com'
```

이 쿼리가 인덱스를 탈 수 있게 된다.
JSON 컬럼의 특정 키에도 쓸 수 있다.
함수 인덱스는 "인덱스가 안 타요"의 깔끔한 해결책이다.

### Invisible Index

MySQL 8.0에 추가된 기능.
인덱스를 삭제하지 않고 "안 보이게" 만들 수 있다.

```sql
ALTER TABLE orders ALTER INDEX idx_status INVISIBLE;
```

옵티마이저가 이 인덱스를 무시한다.
쿼리 성능이 나빠지는지 확인하고, 문제없으면 그때 삭제한다.
인덱스 삭제는 되돌리기 어렵다.
대형 테이블이면 재생성에 수 시간이 걸릴 수 있다.
INVISIBLE로 먼저 테스트하는 것이 DBA의 안전한 습관이다.

### 인덱스 파편화

INSERT/DELETE가 반복되면 인덱스 내부에 빈 공간이 생긴다.
페이지가 절반만 차있는 상태.
MySQL:
OPTIMIZE TABLE이나 `ALTER TABLE ... ENGINE=InnoDB`로 인덱스를 재구성할 수 있다.
Online DDL이라 서비스 중에도 가능하다.
PostgreSQL:
REINDEX 또는 pg_repack.
pg_repack은 락 없이 재구성한다.
운영 환경에서는 pg_repack이 표준이다.
파편화는 성능을 서서히 갉아먹는다.
눈에 안 보이기 때문에 더 위험하다.

### 인덱스가 쓰기를 느리게 만드는 구조

INSERT가 발생하면 테이블에 행을 넣고, 걸려있는 인덱스마다 B-Tree에도 삽입한다.
인덱스가 많을수록, 인덱스에 포함된 컬럼이 많을수록, 쓰기 한 건의 비용이 올라간다.
벤치마크에서는 인덱스 5개일 때 INSERT 처리량이 20% 이하로 떨어지기도 한다.
다만 컬럼 구성과 데이터 크기에 따라 차이가 크고 하지만 실제로는 인덱스 5개 이상으로 체감 할정도로 속도가 느려진 경험도 없다.
읽기가 많은 서비스라면 인덱스가 넉넉한 게 유리하다.
쓰기가 많은 서비스라면 꼭 필요한 것만 유지해야 한다.
DBA의 인덱스 설계는 이 트레이드오프를 서비스 특성에 맞추는 일이다.

### 마무리

인덱스는 CREATE INDEX 한 줄이지만 그 안에는 자료구조, 스토리지 레이아웃, 옵티마이저 판단이 모두 엮여 있다.
B-Tree 하나로 대부분 해결되지만, JSONB에는 GIN이, 공간 검색에는 GiST가, 정확 일치에는 Hash가 각자 자리를 가진다.
"인덱스 걸었는데 안 타요." 이 한마디 뒤에는 카디널리티, 함수 적용, 형변환, 복합 인덱스 순서 같은 원인이 숨어 있다.
인덱스는 마법이 아니다.
구조를 이해해야 제대로 쓸 수 있다.

## Wait Event로 읽는 Aurora MySQL: 느릴 때 진짜 원인을 찾는 법

Aurora MySQL이 느려졌다.
CPU는 여유 있고 메모리도 괜찮은데 쿼리가 끝나지 않는다.
이럴 때 봐야 하는 게 Wait Event다. DB가 지금 뭘 기다리고 있는지.
Performance Insights를 열면 상위 Wait가 나온다.
근데 이름만 봐서는 뭔 소린지 모른다.
증상별로 어떤 Wait Event가 뜨는지.
그걸 알면 원인과 대응이 동시에 보인다.

### Wait Event란

쿼리가 실행되는 동안 DB는 항상 뭔가를 기다린다.
디스크를 읽거나, 락을 잡거나, 네트워크로 결과를 보내거나.
그 "기다림"을 분류해서 이름을 붙인 게 Wait Event다.
Performance Schema가 수집하고 Performance Insights가 시각화한다.
CPU 사용률만 보면 병목의 절반을 놓친다.
Wait Event를 봐야 진짜 느린 이유가 보인다.

### io/socket/sql/client_connection

네트워크가 병목일 때 나타난다.
SELECT에 TEXT나 BLOB 컬럼이 포함되면 한 행이 수십 KB를 넘긴다. 1000건이면 수십 MB.
Aurora 인스턴스는 타입별로 네트워크 burst 한도가 있다.
큰 데이터를 한꺼번에 퍼올리면 burst를 소진하고 이 wait가 급등한다.
필요한 컬럼만 SELECT. BLOB은 별도 쿼리로 분리.
LIMIT은 습관이 아니라 생존이다.

### io/aurora_redo_log_flush

쓰기 레이턴시가 치솟을 때 나타난다.
INSERT, UPDATE, DELETE가 몰리면 Aurora는 redo log를 스토리지 레이어에 flush한다.
이 flush가 밀리면 모든 쓰기 쿼리가 대기한다.
대량 배치가 원인일 때가 많다.
1만 건 INSERT를 한 트랜잭션에 몰아넣으면 redo log가 한꺼번에 밀린다.
배치는 1000건 단위로 나눠 커밋. 쓰기를 시간대별로 분산. Writer 인스턴스 스펙 점검.

### io/table/sql/handler

디스크 읽기가 폭발할 때 나타난다. 인덱스를 안 타는 쿼리.
풀 테이블 스캔이 돌면 Aurora 스토리지에서 대량 페이지를 읽어야 한다.
EXPLAIN에서 type이 ALL이면 이 wait가 보일 가능성이 높다.
인덱스를 걸거나, 쿼리를 고치거나, 커버링 인덱스로 I/O를 줄이거나.
답은 항상 실행 계획에 있다.

### io/aurora_respond_to_client

쿼리 자체는 빠른데 응답이 늦을 때.
Aurora가 결과를 클라이언트에게 보내는 과정에서의 대기다.
client_connection과 비슷하지만 이쪽은 Aurora 내부에서 결과를 조립해서 내보내는 구간이다.
결과 행이 수만 건이거나 애플리케이션이 결과를 천천히 소비하면 나타난다.
fetchSize 조정이 의외로 효과 있다.
결과 셋 크기를 줄이는 게 근본이다.

### synch/cond/sql/MDL_context

ALTER TABLE이 끝나지 않고 뒤따르는 쿼리가 줄줄이 멈출 때. Metadata Lock.
DDL이 메타데이터 락을 잡으려는데 앞에서 긴 SELECT가 락을 쥐고 있다.
DDL은 대기하고, 뒤이어 들어오는 SELECT, INSERT도 전부 MDL 대기열에 갇힌다.
한 쿼리의 락이 전체 서비스를 멈추는 순간이다.
긴 트랜잭션을 먼저 정리. DDL은 트래픽 낮은 시간에. pt-online-schema-change를 고려.

### synch/mutex 계열: 버퍼풀과 트랜잭션 경합

CPU는 여유인데 TPS가 안 오를 때.

[buf_pool_mutex]
버퍼풀 접근이 직렬화되면서 생기는 대기.
동시 접근이 많은데 버퍼풀이 작으면 mutex 경합이 심해진다.
버퍼풀 인스턴스 수를 늘리거나 인스턴스를 스케일업.

[trx_mutex / lock_mutex]
같은 행을 여러 세션이 동시에 UPDATE.
InnoDB 내부의 트랜잭션 뮤텍스에서 대기.
핫 로우를 줄이는 설계가 근본 해결이다.
경합은 스펙을 올려도 안 풀린다. 설계를 바꿔야 한다.

### cpu

CPU 사용률이 높고 쿼리도 느릴 때. Wait Event 중에서 cpu는 특별하다.
"기다리는 시간"이 아니라 "일하는 시간"이다.
ORDER BY로 정렬, GROUP BY로 임시 테이블 생성, 복잡한 JOIN 연산.
CPU를 많이 쓴다는 건 쿼리가 무거운 연산을 하고 있다는 뜻이다.
인덱스로 정렬을 대체하거나, 서브쿼리를 풀거나, 불필요한 DISTINCT를 제거하거나.
CPU가 바쁜 건 쿼리가 비효율적이라는 신호다.

### 실전: Performance Insights에서 읽는 법

PI를 열면 상위 5개 Wait가 보인다. 이걸 읽는 순서가 있다.

[1단계: 지배적 Wait 확인]
전체의 50% 이상을 차지하는 Wait. 이게 지금 DB의 주요 병목이다.

[2단계: 시간대 상관관계]
Wait가 치솟는 시점과 슬로우 쿼리 발생 시점을 겹쳐본다.

[3단계: SQL 탭에서 범인 찾기]
해당 Wait를 가장 많이 유발하는 쿼리. 그 쿼리를 튜닝하면 Wait가 줄어든다.
Wait Event는 증상이다. SQL이 원인이다.

### DBA 관점에서의 정리

"DB가 느려요." 이 한 마디에서 시작하는 모든 대화.
CPU? 메모리? 디스크? 전부 정상인데 느리다고 한다. 그때 Wait Event를 연다.
client_connection이면 네트워크.
redo_log_flush면 쓰기 부하.
handler면 풀스캔.
MDL이면 긴 트랜잭션.
cpu면 쿼리를 뜯어본다.
DB는 항상 말하고 있다. 다만 Wait Event라는 언어로 말할 뿐이다.
그 언어를 읽을 줄 아는 사람이 DBA다.

## 백업과 복구의 실체: 풀백업은 쉬운데 복구는 왜 어려운가

"백업 있죠?" 장애 나면 가장 먼저 나오는 질문이다.
백업은 있다. 매일 자동으로 돌아간다. 알람도 없고 용량도 잘 쌓인다.
그런데 복구해본 적은 없다. 복구가 되는지 확인한 적도 없다.
백업은 쉽다. 복구가 어렵다.

### 논리 백업

데이터를 SQL 문으로 내보내는 방식이다.
MySQL: mysqldump. PostgreSQL: pg_dump

```bash
mysqldump --single-transaction mydb > backup.sql
pg_dump -Fc mydb > backup.dump
```

- 장점:
  - 사람이 읽을 수 있다.
  - 다른 버전, 다른 서버로 복원 가능.
  - 특정 테이블만 복원 가능.
- 단점:
  - 느리다. 10GB 넘으면 시간이 오래 걸린다.
  - 복원은 더 느리다.
  - INSERT 문을 하나씩 실행하니까.

### 물리 백업

데이터 파일을 통째로 복사하는 방식이다.
MySQL: Percona XtraBackup. PostgreSQL: pg_basebackup

```bash
xtrabackup --backup --target-dir=/backup/
pg_basebackup -D /backup/ -Ft -z
```

- 장점:
  - 빠르다. 파일 복사니까.
  - 복원도 빠르다. 파일을 제자리에 놓으면 된다.
- 단점:
  - 같은 버전, 같은 아키텍처에서만 복원 가능.
  - 특정 테이블만 꺼내기 어렵다.
  - 백업 중에도 서비스 가능하지만 I/O 부하가 증가한다.
  - 운영 환경에서는 물리 백업이 기본이다.
  - 논리 백업은 보조 수단으로 병행한다.

### 스냅샷 백업 — 클라우드 시대의 표준

AWS RDS를 쓰면 매일 자동으로 스냅샷이 찍힌다. 스냅샷은 EBS 볼륨의 포인트인타임 복사본이다.
실제로는 변경된 블록만 저장하므로 전체 크기보다 훨씬 적은 공간을 차지한다.
스냅샷 복원 시간은 데이터 크기가 아니라 I/O 패턴에 따라 달라진다.
"Lazy Loading" — 처음 읽는 블록은 스냅샷에서 실시간으로 가져온다.
복원 직후 성능이 느릴 수 있다. 워밍업이 필요한 이유다.

### PITR(Point-In-Time Recovery) — 시점 복구

"어제 14시 상태로 돌려주세요."
원리는 단순하다. 풀 백업 + 트랜잭션 로그 재실행.

[어제 02:00 풀 백업]
→ binlog/WAL 순서대로 재실행
→ [어제 14:00에 멈춤]

삭제 직전, 실수 직전으로 정확하게 되돌릴 수 있다.
AWS RDS는 자동으로 PITR을 지원한다.
백업 보존 기간(기본 7일) 내에서 1초 단위로 복원 가능하다.
새 인스턴스로 복원된다.

### PITR의 실제 소요 시간

"1초 단위로 복원 가능"이 "1초 만에 복원 가능"은 아니다.
AWS RDS PITR 절차:

1. 직전 스냅샷 선택 (자동)
2. 스냅샷에서 새 인스턴스 생성
3. 트랜잭션 로그를 목표 시점까지 적용

인스턴스 생성에 수십 분, 로그 적용에 수 분~수 시간.
DB 크기와 변경량에 따라 크게 달라진다.
트랜잭션 로그가 많을수록 (= 스냅샷과 목표 시점 사이 변경이 많을수록) 복원이 오래 걸린다.
장애 상황에서 "30분이면 되겠지"가 2시간이 되는 경우를 봤다.

### 복원 테스트를 안 하면

백업이 있어도 복원이 안 되는 경우:

[케이스 1]
mysqldump가 매일 성공하지만 실은 빈 파일이었다.
cron 로그만 보고 성공으로 간주.

[케이스 2]
물리 백업은 있지만 복원 후 바이너리 호환이 안 맞아 시작이 안 된다.
MySQL 마이너 버전 차이.

[케이스 3]
스냅샷 복원 했는데 보안 그룹이 다르게 설정돼서 애플리케이션이 접근을 못 한다.
복원 테스트를 주기적으로 하지 않으면 백업은 정신적 안정제일 뿐이다.

### 복원 순서가 중요하다

"이 테이블만 복원해주세요." 이 요청이 생각보다 까다롭다.
풀 백업에서 특정 테이블만 꺼내려면:
논리 백업(mysqldump): 단일 테이블 복원 가능하지만 느리다.
물리 백업(xtrabackup): InnoDB에서 특정 테이블 추출은 가능하나 exportable tablespace 옵션 필요.
스냅샷: 전체 인스턴스 복원만 가능. 특정 테이블만 꺼내려면 복원 인스턴스에서 mysqldump로 뽑아야 한다.
"테이블 하나" 복원이 "전체 DB 복원"보다 오래 걸리기도 한다.

### 대형 DB의 백업 전략

TB 급 DB의 백업은 그 자체로 도전이다.
mysqldump로 1TB를 뽑으면 수 시간. 복원은 그 이상.
실전 전략:

[계층 분리]
핫 데이터(최근 3개월)는 매일 백업.
콜드 데이터(이전)는 주 1회.
아카이브 데이터는 별도 스토리지.

[병렬 백업]
mydumper(MySQL) — 멀티 스레드 논리 백업.
pg_dump -j(PostgreSQL) — 병렬 dump.

[증분 백업]
xtrabackup의 incremental 모드.
변경된 페이지만 백업.
복원 시 전체 + 증분을 합쳐야 한다.

### 바이너리 로그 백업

풀 백업 사이의 변경은 트랜잭션 로그가 커버한다.
MySQL: mysqlbinlog로 binlog를 실시간 백업.

```bash
mysqlbinlog --read-from-remote-server --raw \
--host=db-server --result-file=/backup/binlog/
```

PostgreSQL: WAL 아카이빙.
archive_command로 WAL 파일을 S3나 별도 스토리지에 자동 복사.
이 로그가 없으면 마지막 풀 백업 이후의 변경이 전부 유실된다.
풀 백업만 있으면 RPO가 24시간. 로그 백업까지 있으면 RPO가 수 초~수 분.

### RPO와 RTO

장애 복구 계획의 두 축이다.

[RPO — Recovery Point Objective]
"최대 얼마만큼의 데이터를 잃어도 되는가"
RPO 1시간 = 최근 1시간 데이터 유실 허용.
RPO 0 = 데이터 유실 불가 → 동기 복제 필수.

[RTO — Recovery Time Objective]
"복구까지 최대 얼마나 걸려도 되는가"
RTO 30분 = 30분 안에 서비스 재개.
RTO 4시간 = 백업 복원으로 충분.

RPO를 줄이려면 로그 백업 주기를 짧게. RTO를 줄이려면 복원 절차를 자동화.
둘 다 0에 가깝게 하려면 비용이 급증한다.

### Delayed Replica

의도적으로 지연된 복제 서버.
"1시간 전 상태"를 항상 유지한다.
MySQL:

```sql
CHANGE REPLICATION SOURCE TO
SOURCE_DELAY = 3600; -- 1시간 지연
```

PostgreSQL:
`recovery_min_apply_delay = '1h'`
실수로 DROP TABLE을 했을 때 Delayed Replica에서 해당 테이블을 꺼내면 PITR보다 빠르게 복구할 수 있다.
풀 복원은 수 시간이지만 Replica에서 덤프는 수 분이다.
보험용 Replica다. 유지 비용은 들지만 장애 시 값어치를 한다.

### 삭제 사고 대응 플레이북

`DELETE FROM orders WHERE created_at < '2026-01-01'` 을 실수로 WHERE 없이 실행했다.

[즉시 대응]

1. 해당 세션 KILL (진행 중이라면)
2. 트래픽 차단 (추가 변경 방지)
3. binlog/WAL에서 삭제 시점 확인

[복구 경로 선택]

1. Delayed Replica 있으면 → 거기서 덤프
2. 없으면 → PITR로 새 인스턴스 복원
3. binlog로 역방향 SQL 생성 (MySQL)

[복구 후]

데이터 정합성 검증 (행 수, 체크섬)
원인 분석 + 재발 방지

시간이 생명이다.
이 절차를 미리 문서화해두지 않으면 장애 상황에서 판단이 느려진다.

### 마무리

백업은 보험이다. 들어놓고 안 쓰면 좋지만, 쓸 때 작동하지 않으면 의미가 없다.
풀백업은 버튼 하나로 된다. 하지만 복구는 다르다.
어떤 백업에서 복원할 것인가, 특정 테이블만 가능한가, 얼마나 걸리는가, 복원 후 정합성은 어떻게 확인하는가.
이 질문에 답할 수 있으려면 복원을 해봐야 한다.
"백업은 매일 한다"가 아니라 "복원을 마지막으로 테스트한 게 언제인가"가 DBA에게 더 중요한 질문이다.

## Physical vs Logical Backup: 백업이 빠르면 복구는 느리다

백업은 보험이다.
드는 건 꼬박꼬박 들면서 한 번도 써본 적 없는 보험.
문제는 써야 할 순간에 안 되는 보험이 있다는 거다.

### 최소 복구 체크리스트

먼저 이 다섯 가지부터 확인해봐라. AI가 만든 백업이든 손으로 짠 백업이든 똑같다.

- [ ] 백업 파일 크기가 0이 아닌가?
- [ ] 덤프 파일 끝에 Dump completed가 있는가?
- [ ] 빈 DB에 복원했을 때 에러 없이 끝나는가?
- [ ] 원본과 주요 테이블 row count가 일치하는가?
- [ ] 복구에 걸리는 시간을 기록했는가?
- [ ] 최근 30일 안에 이걸 해봤는가?

하나라도 No가 있으면 이 글을 끝까지 읽어라. 전부 Yes면 당신의 백업은 진짜 백업이다.
두 번째 항목이 가장 싸게 먹히는 검증이다.
mysqldump는 파일 끝에 `-- Dump completed`를, pg_dump는 `-- PostgreSQL database dump complete`를 남긴다.
이게 없으면 백업이 중간에 끊긴 거다. 매일 cron 돌린 뒤 tail 한 줄이면 잡을 수 있다.

### 백업의 두 갈래

DB 백업은 크게 두 가지로 나뉜다.

[논리 백업]
데이터를 SQL 문장으로 추출한다. mysqldump, pg_dump가 대표적이다.
결과물은 텍스트다.
`CREATE TABLE`과 `INSERT INTO`의 나열.

[물리 백업]
데이터 파일 자체를 복사한다. Percona XtraBackup, pg_basebackup이 대표적이다.
결과물은 바이너리 파일이다.
DB가 디스크에 쓰는 그대로를 가져온다.
같은 데이터를 담지만 속도, 크기, 복구 방식이 완전히 다르다.

### 논리 백업: mysqldump와 pg_dump

mysqldump는 MySQL DBA의 오래된 친구다.
테이블 구조를 CREATE TABLE로, 데이터를 INSERT로 뽑아낸다.

```sql
-- mysqldump 출력 예시
CREATE TABLE orders (
order_id BIGINT PRIMARY KEY,
user_name VARCHAR(100),
amount DECIMAL(10,2)
);
INSERT INTO orders VALUES (1,'dot',15000.00);
```

pg_dump도 마찬가지다.
텍스트라 사람이 읽을 수 있고 특정 테이블만 뽑거나 다른 DB 엔진으로 옮길 수도 있다.

### 논리 백업의 한계

100GB 데이터베이스를 mysqldump로 뽑는다. 몇 시간이 걸린다.
복구할 때도 INSERT를 한 줄씩 실행하므로 백업보다 복구가 더 오래 걸린다.
1TB라면? 하루가 걸릴 수도 있다.
장애 상황에서 하루를 기다릴 수 있는 서비스는 없다.
또 다른 문제.
mysqldump는 기본적으로 일관성을 위해 락을 잡는다.
`--single-transaction` 옵션이 있지만 InnoDB가 아닌 테이블이 섞여 있으면 `FLUSH TABLES WITH READ LOCK`이 걸린다.
백업이 서비스를 멈추는 역설이 발생한다.

### 물리 백업: XtraBackup과 pg_basebackup

Percona XtraBackup은 InnoDB 데이터 파일을 핫 카피한다. 서비스를 멈추지 않고 백업한다.
백업 중 변경된 데이터는 redo log로 추적해서 복구 시 apply한다.
pg_basebackup은 PostgreSQL의 데이터 디렉터리를 통째로 스트리밍 복사한다.
WAL 파일을 함께 아카이빙해서 특정 시점 복구(PITR)까지 지원한다.
두 도구 모두 바이너리 레벨 복사라 속도가 빠르다.
100GB를 30분 안에 끝낼 수 있다.

### 복구 속도의 차이

여기서 제목의 의미가 드러난다. "백업이 빠르면 복구는 느리다"는 논리 백업의 이야기다.
논리 백업은 백업은 쉬운데 복구가 느리다.
INSERT를 수십억 건 실행해야 하고 인덱스를 다시 빌드해야 한다.
물리 백업은 반대다.
백업 자체는 디스크 I/O에 의존하지만 복구는 파일을 제자리에 놓으면 끝이다.
XtraBackup이면 prepare 단계가 필요하고 pg_basebackup이면 WAL replay가 필요하지만 논리 복구보다 수십 배 빠르다.
장애 상황의 RTO(복구 목표 시간)는 물리 백업이 압도적으로 유리하다.

### 용량의 차이

논리 백업은 텍스트다.
숫자 1000000이 7바이트 문자열이 된다. 바이너리로는 4바이트면 될 값이다.
압축하면 줄어들지만 원본은 크다.
물리 백업은 디스크의 데이터 파일 크기와 같다.
인덱스, undo 영역까지 포함하므로 실제 데이터보다 클 수 있다.
결국 비슷하거나 물리 백업이 약간 더 크다.
하지만 압축 효율은 물리 백업이 좋다.
바이너리 데이터는 패턴이 반복되어 gzip으로도 높은 압축률을 얻는다.

### 유연성의 차이

논리 백업이 빛나는 순간이 있다.
"orders 테이블만 복구해주세요."
mysqldump로 테이블 단위 백업이 있으면 그 테이블만 복구할 수 있다.
"MySQL에서 PostgreSQL로 옮기고 싶어요."
논리 백업은 SQL이므로 약간의 변환으로 다른 엔진에 넣을 수 있다.
물리 백업은 이게 안 된다.
InnoDB 파일을 PostgreSQL에 넣을 수 없다. 테이블 하나만 꺼내는 것도 복잡하다.
전체를 복구한 뒤 필요한 것만 추출해야 한다.
유연성은 논리 백업의 유일하면서도 강력한 장점이다.

### PITR: 특정 시점 복구

장애 복구에서 가장 많이 쓰는 시나리오. "오늘 오후 2시 30분으로 되돌려주세요."
물리 백업 + binlog(MySQL) 또는 WAL(PostgreSQL) 조합으로 특정 시점까지 정확히 복구할 수 있다.
물리 백업을 복원하고 그 시점부터 원하는 시점까지 binlog/WAL을 재생한다. 분 단위, 초 단위 복구가 가능하다.
논리 백업만으로는 PITR이 어렵다. 마지막 덤프 시점으로만 돌아갈 수 있다.
그 사이의 데이터는 binlog가 따로 있어야 한다. 조합은 가능하지만 절차가 복잡하고 느리다.

### "AI한테 백업 스크립트 짜달라고 했어요"

바이브코딩 시대의 가장 흔한 함정이다. AI가 백업 스크립트를 짜줬다.
cron에 등록했다. 알림도 온다. 안심한다.
그런데 복구해 본 적은 있는가?
백업 파일이 0바이트일 수 있다.
SQL이 중간에 잘려 있을 수 있다.
권한 문제로 복원이 안 될 수 있다.
디스크 용량이 부족할 수 있다.
AI는 백업을 잘 짠다. 복구를 대신 검증해주진 않는다.
테스트 안 한 백업은 보험증서 없는 보험이다.

### 직접 해보기: mysqldump

먼저 덤프 파일이 온전한지 확인한다.

```bash
# 백업 완료 여부 확인
tail -1 backup.sql | grep -q "Dump completed" && echo "OK" || echo "BROKEN"
```

이게 OK면 복원을 해본다.

```bash
mysql -u root -e "CREATE DATABASE backup_test"
mysql -u root backup_test < backup.sql
mysql -u root -e "SELECT COUNT(*) FROM backup_test.orders"
```

에러 없이 끝나고 count가 원본과 같으면 합격.
끝나면 `DROP DATABASE backup_test`로 정리한다.

### 직접 해보기: pg_dump

Supabase나 PostgreSQL 사용자는 이쪽이다.
먼저 덤프 파일이 온전한지 확인한다.

```bash
tail -5 backup.sql | grep -q "dump complete" && echo "OK" || echo "BROKEN"
```

OK면 로컬 PG에 복원해본다.

```bash
createdb backup_test
psql backup_test < backup.sql
psql backup_test -c "SELECT COUNT(*) FROM orders"
```

에러 없이 끝나고 count가 원본과 같으면 합격.
끝나면 `dropdb backup_test`로 정리한다.

### crontab에 검증 걸기

백업만 cron에 걸고 검증은 안 거는 사람이 많다.
백업 끝난 직후에 tail 한 줄이면 된다.
매일 새벽 3시 백업 + 검증

```bash
0 3 \* \* \* mysqldump -u root --single-transaction mydb > /backup/mydb*$(date +\%Y\%m\%d).sql && tail -1 /backup/mydb_$(date +\%Y\%m\%d).sql | grep -q "Dump completed" || echo "BACKUP BROKEN: mydb" | mail -s "backup alert" you@email.com
```

한 줄이 길지만 하는 일은 단순하다. 덤프 뜨고, 마지막 줄 확인하고, 없으면 알림 보낸다.
pg_dump 사용자는 mysqldump를 `pg_dump -U postgres`로, `Dump completed`를 `dump complete`로 바꾸면 된다.
이것만 걸어도 0바이트 백업에 당하진 않는다.

### 직접 해보기: RDS 스냅샷

AWS 콘솔에서 세 단계면 된다.
자동 스냅샷 목록에서 최신 스냅샷을 고른다.
"스냅샷에서 복원"을 누른다.
인스턴스가 뜨면 접속해서 데이터를 확인한다.
CLI로 하면 이렇다.

```bash
aws rds restore-db-instance-from-db-snapshot \
--db-instance-identifier test-restore \
--db-snapshot-identifier my-snapshot
```

Available 상태가 되면 접속해서 count를 센다.
확인 끝나면 인스턴스 삭제. 비용은 분 단위다.

### 실전 전략: 물리 + 논리 병행

둘 중 하나만 쓰면 안 되는가? 안 되는 건 아니지만 위험하다.

[물리 백업]
매일 전체 백업. 빠른 복구를 위한 1차 방어선.
PITR 용도로 binlog/WAL 아카이빙 병행.

[논리 백업]
주 1회 또는 월 1회. 특정 테이블 복구, 크로스 엔진 마이그레이션, 데이터 감사용 아카이브로 활용.

물리 백업이 주력이고 논리 백업은 보조다.
보조가 없으면 물리 백업 파일이 깨졌을 때 할 수 있는 게 없다.

### DBA 관점에서의 정리

백업 전략을 세울 때 물어야 할 질문은 세 가지다.

1. 얼마나 빨리 복구해야 하는가? (RTO)
2. 어디까지 데이터를 잃어도 되는가? (RPO)
3. 복구를 실제로 해봤는가?

RTO가 짧으면 물리 백업이 필수다. RPO가 0에 가까워야 하면 PITR이 필수다.
복구 테스트를 안 했으면 둘 다 의미 없다.
AI에게 백업 스크립트를 시켰으면 복구 테스트 스크립트도 시켜라.
검증 코드까지 받아야 백업이 완성된다.
"백업 돌아가고 있습니다"는 답이 아니다. "지난주 복구 테스트 성공했습니다"가 답이다.

## DB 장애 대응의 기술: 탐지에서 회고까지, DBA는 무엇을 하는가

새벽 3시에 알람이 울린다. CPU 100%, 커넥션 풀 소진, 슬로우 쿼리 폭증.
이 순간 DBA가 하는 일은 원인을 찾는 게 아니다. 서비스를 살리는 것이다.
원인 분석은 그다음이다. 모니터링 보강은 그다다음이다. 회고는 맨 마지막이다.
순서가 중요하다. 순서를 틀리면 원인을 찾는 동안 서비스가 죽는다.
11년간 장애를 겪으며 체득한 대응의 순서를 정리한다.

### 장애 대응의 다섯 단계

장애 대응은 순서가 있다.
탐지 → 영향도 판단 → 긴급 조치 → 원인 분석 → 후속 조치

이 순서를 지키면 서비스 중단 시간이 줄어든다.
역순으로 가면 망한다.
원인을 먼저 찾으려 하면 분석하는 30분 동안 주문이 멈춘다.
면접에서 "장애 경험을 말해주세요"라고 물으면 이 다섯 단계를 따라 말하면 된다.
구조가 있는 답변은 신뢰를 준다.

### 1단계: 탐지 — 알람이 울리기 전에 아는가

장애 대응의 시작은 탐지다.
얼마나 빨리 알아채느냐가 서비스 영향 시간을 결정한다.

[좋은 탐지]
모니터링 알람이 1분 내 발생.
슬랙 채널에 자동 통보.
담당자가 즉시 인지.
임계치가 되서 서비스의 영향이 가기 전에 탐지

[나쁜 탐지]
고객이 CS로 전화해서 알게 됨.
개발자가 "뭔가 느려요" 하고 물어봄.
아침에 출근해서 로그를 보고 발견.
탐지 시간(Time to Detect)은 장애 보고서에 반드시 기록된다.
이 숫자가 5분이냐 30분이냐가 조직의 운영 성숙도를 보여준다.

### 2단계: 영향도 판단 — 뭐부터 할지 정한다

알람을 받았으면 다음은 영향 범위를 판단하는 것이다.

[Severity 1 — 서비스 전면 중단]
주문 불가, 결제 실패, 전체 사용자 영향.
모든 걸 내려놓고 이것만 한다. 에스컬레이션 즉시.

[Severity 2 — 부분 장애]
특정 기능 불가, 일부 사용자 영향.
긴급 조치 후 정상 프로세스 복귀.

[Severity 3 — 성능 저하]
느리지만 동작한다.
모니터링하면서 원인 분석 병행.

판단을 잘못하면 Sev3을 Sev1처럼 대응해서 오버하거나 Sev1을 Sev3처럼 대응해서 확산시킨다.

### 긴급 조치의 원칙: 원인보다 복구가 먼저

원인을 모르는 상태에서도 서비스를 살릴 수 있는 조치가 있다.

[커넥션 풀 소진]
원인 분석 전에 먼저 롱 쿼리를 kill한다.

```sql
-- 60초 이상 실행 중인 쿼리 확인
SELECT * FROM information_schema.processlist
WHERE TIME > 60 AND COMMAND != 'Sleep';
```

[CPU 100%]
슬로우 쿼리를 잡기 전에 먼저 읽기 트래픽을 레플리카로 전환하거나 읽기 트래픽이 폭주하면 리더를 추가한다.

[디스크 풀]
원인을 찾기 전에 바이너리 로그나 슬로우 로그를 정리한다.

공통점이 있다. 전부 "원인은 모르지만 숨통을 틔우는 것"이다.

### 긴급 조치 패턴 모음

현장에서 반복되는 패턴이 있다.

[패턴 1: Kill + 차단]
문제 쿼리를 kill하고 해당 쿼리가 재실행되지 않도록 앱 서버에 알려서 기능을 내린다.

[패턴 2: 페일오버]
마스터에 문제가 있으면 레플리카로 승격시킨다.
RDS는 Multi-AZ 페일오버를 수동 트리거할 수 있다.

[패턴 3: 스케일업/아웃]
리소스 부족이면 인스턴스를 키우거나 읽기 레플리카를 추가한다.

[패턴 4: 롤백]
배포 직후 장애면 이전 버전으로 롤백한다.
DB 변경이 동반됐으면 DDL 롤백이 가능한지 확인.
완벽한 조치가 아니어도 된다. 서비스가 살아나면 성공이다.

### 긴급 조치 중 하지 말아야 할 것

급하면 실수한다. 실수를 줄이려면 "하지 말 것"을 정해둬야 한다.
원인 분석을 위해 재현하려 하지 마라. 장애 상황에서 재현은 서비스를 한 번 더 죽이는 것이다.
로그를 정리하기 전에 보존하라. 증거를 날리면 원인 분석이 불가능해진다.
`cp`나 `tee`로 먼저 복사하고 정리한다. 혼자 판단하지 마라.
Sev1이면 에스컬레이션이 의무다. "내가 해결할 수 있을 것 같은데"가 가장 위험한 생각이다.
팀에 공유하고 빠르게 해야 할 일을 배분해야한다.

### 3단계: 원인 분석 — 서비스가 살아난 후에 한다

긴급 조치로 서비스가 복구됐다. 이제 원인을 찾는다.

[타임라인 구성]
장애 발생 전후의 이벤트를 시간순으로 나열한다.
배포, 트래픽 변화, 알람 발생, 조치 시점.
타임라인이 없으면 원인 분석이 추측이 된다.

[메트릭 대조]
CPU, 커넥션, 슬로우 쿼리, 레플리케이션 랙.
장애 시점에 어떤 지표가 먼저 튀었는가.
먼저가 중요하다.
결과가 아니라 원인을 찾아야 한다.

[로그 분석]
에러 로그, 슬로우 쿼리 로그, 감사 로그.
장애 시점 전후 5분을 정밀하게 본다.

### Five Whys: 근본 원인까지 파고들기

"왜?"를 다섯 번 묻는다.

```text
쿼리가 느려졌다.
→ 왜? 풀스캔이 발생했다.
→ 왜? 인덱스를 안 탔다.
→ 왜? 플래너가 잘못된 계획을 세웠다.
→ 왜? 통계가 갱신되지 않았다.
→ 왜? ANALYZE가 스케줄에 없었다.
```

위 예시에서 근본 원인은 "ANALYZE 미실행"이다.
쿼리를 고치는 것이 아니라 통계 갱신 자동화를 넣어야 재발을 막는다.
표면에서 멈추면 같은 장애가 반복된다.
다섯 번째 "왜"에 도달해야 액션 아이템이 근본적이 된다.

### Root Cause vs Impact Amplifier

원인 분석에서 흔한 실수가 있다. 전파 경로를 근본 원인으로 착각하는 것이다.
"커넥션 풀이 소진됐다"는 원인이 아니다. 결과다.
"슬로우 쿼리가 커넥션을 붙잡고 있었고 새 요청이 풀에서 커넥션을 받지 못했다"가 전파 경로다.
근본 원인은 "인덱스 없는 쿼리가 배포됐다"일 수 있다.

[Root Cause]
장애를 일으킨 최초 원인.

[Impact Amplifier]
장애가 확산된 경로.
커넥션 풀 소진, 캐스케이딩 타임아웃 등.

이 둘을 구분하지 않으면 확산 경로만 막고 근본 원인은 남겨두게 된다.

### 4단계: 후속 조치 — 모니터링을 추가한다

원인을 찾았으면 같은 장애가 다시 왔을 때 더 빨리 탐지할 수 있게 만든다.

[알람 추가]
이번에 놓친 지표에 알람을 건다.
슬로우 쿼리 수, 커넥션 대기 시간, 특정 에러 코드 발생 빈도.

[대시보드 보강]
장애 때 급하게 찾아본 지표를 한 화면에 모아둔다.
다음번에는 찾는 시간을 줄인다.

[런북 작성]
이번 긴급 조치를 절차서로 남긴다.
다음번에 내가 아닌 사람이 대응해도 같은 품질로 할 수 있게.
후속 조치의 핵심은 "다음번에는 더 빨리, 더 정확하게"다.

### 후속 조치의 세 가지 시간 축

액션 아이템은 시간 축으로 나눈다.

[Short-Term — 1주 내]
핫픽스 배포.
누락된 알람 추가.
임시 인덱스 생성.
즉시 할 수 있는 것.

[Mid-Term — 1개월 내]
쿼리 최적화.
아키텍처 보완.
자동화 스크립트 작성.
설계 변경이 필요한 것.

[Long-Term — 분기 내]
DB 버전 업그레이드.
샤딩/파티셔닝 도입.
모니터링 시스템 교체.
큰 투자가 필요한 것.

전부 Short-Term에 몰아넣으면 하나도 안 된다.
시간 축을 나눠야 실행된다.

### 5단계: 회고 — 배운 점을 남긴다

장애에서 가장 가치 있는 건 배운 점이다.

[What went well]
알람이 빨리 왔다.
에스컬레이션이 적절했다.
페일오버가 30초 만에 됐다.
잘한 것도 기록해야 다음에 반복한다.

[What didn't go well]
탐지가 10분 늦었다.
런북이 없어서 판단에 시간이 걸렸다.
로그를 실수로 삭제했다.

[Where did we get lucky]
트래픽이 적은 시간대였다.
마침 DBA가 깨어 있었다.
운이 좋았던 건 다음번에 없을 수 있다.
운에 의존한 부분을 시스템으로 바꿔야 한다.

### 면접에서 장애 경험을 말하는 법

"장애 경험을 말해주세요." 이 질문에 대부분은 기술적 원인만 말한다.
"인덱스가 빠져서 슬로우 쿼리가 터졌습니다." 면접관이 듣고 싶은 건 그게 아니다.

1. 상황: 어떤 장애였고, 영향 범위는
2. 판단: 왜 그 조치를 먼저 했는지
3. 행동: 실제로 한 긴급 조치
4. 결과: 복구 시간과 서비스 영향
5. 교훈: 뭘 배웠고 뭘 바꿨는지

이 순서로 말하면 기술력뿐 아니라 판단력과 성장을 보여준다.
면접관은 "이 사람과 새벽에 같이 대응할 수 있겠다"를 판단하고 있다.

### DBA 관점에서의 정리

장애 대응 능력은 경험으로만 쌓인다. 하지만 프레임워크는 배울 수 있다.

- 탐지: 알람을 5분 안에 받을 수 있는가
- 판단: 서비스 영향도를 30초 안에 분류할 수 있는가
- 조치: 원인 모르는 상태에서 서비스를 살릴 수 있는가
- 분석: Five Whys로 근본 원인까지 도달하는가
- 후속: 같은 장애를 두 번 겪지 않게 만드는가

이 다섯 줄이 장애 대응의 전부다. 순서를 지키는 게 핵심이다.
원인보다 복구가 먼저. 분석보다 서비스가 먼저. 완벽한 조치보다 빠른 조치가 먼저.

### 마무리

장애는 피할 수 없다.
1000대의 DB를 운영하면 자주 어딘가에서 무언가 터진다.
중요한 건 터지지 않게 하는 게 아니라 터졌을 때 얼마나 빨리 살리느냐다.
탐지 → 판단 → 조치 → 분석 → 후속. 이 순서를 몸에 익히면 새벽 3시에도 흔들리지 않는다.
그리고 회고를 남겨라. 장애에서 배우지 않으면 같은 새벽이 반복된다.
가장 좋은 장애 대응은 두 번째 장애가 없는 것이다.
