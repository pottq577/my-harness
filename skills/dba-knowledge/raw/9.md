# BEAR DBA

## 서브쿼리 vs JOIN: 같은 결과인데 속도가 다른 이유

같은 결과를 돌려주는 두 개의 쿼리가 있다.
하나는 서브쿼리로 썼고, 하나는 JOIN으로 썼다. 결과 집합은 동일하다.
그런데 하나는 0.1초, 하나는 30초.
옵티마이저가 둘을 같은 실행 계획으로 바꿔준다면 차이가 없을 것이다.
문제는 바꿔주지 못하는 경우가 있다는 것이다.

- 서브쿼리를 JOIN으로 변환할 수 있는지 먼저 확인하라.
- Correlated Subquery는 N+1 문제를 의심하라.
- Derived Table은 임시 테이블 생성 여부를 확인하라.
- MySQL 버전별 옵티마이저 차이를 인지하라.
- 반드시 EXPLAIN으로 실행 계획을 확인하라.

### 옵티마이저의 서브쿼리 변환

좋은 옵티마이저는 서브쿼리를 JOIN으로 변환한다.

```sql
-- 원본: 서브쿼리
SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users
);
-- 변환 후: Semi-JOIN
SELECT o.* FROM orders o
SEMI JOIN vip_users v
ON o.user_id = v.user_id;
```

이걸 "서브쿼리 플래트닝" 또는 "Semi-JOIN 변환"이라고 부른다.
MySQL 8.0, PostgreSQL, Oracle 모두 이 변환을 시도한다.
변환에 성공하면 서브쿼리와 JOIN의 성능 차이가 없다.
문제는 변환이 불가능한 경우다.
서브쿼리에 LIMIT이 있거나, UNION이 있거나, 집계 함수가 있거나, 상관(Correlated) 서브쿼리일 때 옵티마이저가 손을 놓는다.

### Correlated Subquery의 N+1 문제

상관 서브쿼리는 바깥 행마다 안쪽 쿼리를 실행한다.

```sql
SELECT o.order_id, o.amount,
(SELECT u.user_name
FROM users u
WHERE u.user_id = o.user_id)
FROM orders o;
```

orders가 100만 행이면 안쪽 SELECT가 100만 번 실행된다.
ORM의 N+1 문제와 같은 구조다.
바깥 루프가 안쪽 쿼리를 반복 호출한다.
users에 인덱스가 있으면 한 번의 조회는 빠르다.
하지만 100만 번이면 느리다.
JOIN으로 바꾸면 한 번에 끝난다.

```sql
SELECT o.order_id, o.amount, u.user_name
FROM orders o
LEFT JOIN users u ON o.user_id = u.user_id;
```

Hash Join이든 Nested Loop이든 한 번의 스캔으로 처리된다.

### Derived Table의 실체

FROM절에 서브쿼리를 쓰면 그걸 Derived Table(인라인 뷰)이라고 부른다.

```sql
SELECT d.user_id
FROM (
SELECT user_id, SUM(amount) AS total_amount
FROM orders
GROUP BY user_id
) d
WHERE d.total_amount > 100000;
```

이 서브쿼리의 결과가 어디에 저장되는가.
MySQL은 임시 테이블을 만든다.
디스크에 쓸 수도 있고 메모리에 둘 수도 있다.
MySQL 8.0부터는 Derived Table Merge가 가능하다.
옵티마이저가 서브쿼리를 바깥 쿼리에 합쳐서 임시 테이블 없이 처리한다.
하지만 GROUP BY, DISTINCT, LIMIT, UNION이 있으면 Merge가 불가능하다.
위 예시도 GROUP BY 때문에 임시 테이블이 생긴다.
결과가 크면 디스크에 쓴다.
그 순간 속도가 급격히 떨어진다.

### MySQL 5.6 이전의 서브쿼리 비극

MySQL 5.5까지는 서브쿼리 최적화가 처참했다.

```sql
SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users
);
```

이 쿼리를 5.5는 이렇게 실행했다.
orders의 모든 행에 대해 vip_users를 매번 풀스캔.
IN 서브쿼리를 상관 서브쿼리로 변환해버린 것이다.
orders 100만 행, vip_users 1만 행이면 1만 행 풀스캔을 100만 번. 사실상 100억 행 스캔.
5.6에서 Materialization이 도입되면서 서브쿼리 결과를 임시 테이블에 한 번만 만들고 재사용하게 됐다.
5.7에서 Semi-JOIN 변환이 개선됐고 8.0에서 Hash Join이 추가되면서 서브쿼리와 JOIN의 성능 차이가 크게 줄었다.
하지만 오래된 코드베이스에는 5.5 시절의 "서브쿼리 피하기" 습관이 아직도 남아 있다.

### 실행 계획으로 확인하는 법

서브쿼리가 어떻게 처리되는지는 EXPLAIN으로만 확인할 수 있다.

```sql
EXPLAIN SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users);
```

봐야 할 것들이 있다.

- select_type이 SUBQUERY면 별도 실행.
- DEPENDENT SUBQUERY면 상관 서브쿼리.

이 둘이 보이면 위험하다.
MATERIALIZED면 임시 테이블로 한 번 만든 것.
SIMPLE이면 JOIN으로 변환된 것.
이 둘은 괜찮다.
PostgreSQL에서는 EXPLAIN ANALYZE로 실제 실행 시간까지 확인한다.
loops 값이 1이면 좋고 10만이면 N+1이다.

### DBA 관점에서의 정리

"서브쿼리는 느리고 JOIN은 빠르다"는 반만 맞는 말이다.
옵티마이저가 변환해주면 둘은 같다.
변환하지 못하면 서브쿼리가 느리다.
문제는 변환 여부를 쿼리를 보는 것만으로는 알 수 없다는 것이다.
DB 버전, 통계 정보, 데이터 분포에 따라 같은 쿼리도 다른 계획이 나온다.

- 서브쿼리를 JOIN으로 변환할 수 있는지 먼저 확인하라.
- Correlated Subquery는 N+1 문제를 의심하라.
- Derived Table은 임시 테이블 생성 여부를 확인하라.
- MySQL 버전별 옵티마이저 차이를 인지하라.
- 반드시 EXPLAIN으로 실행 계획을 확인하라.

쿼리를 쓰는 사람은 결과가 맞는지 본다.
DBA는 실행 계획이 맞는지 본다.
같은 결과를 내는 수많은 길 중에서 가장 싸게 도착하는 길을 고르는 것.
그게 쿼리 튜닝의 본질이다.

## Discord는 왜 DB를 두 번 바꿨나: MongoDB에서 ScyllaDB까지

Discord는 DB를 두 번 바꿨다. MongoDB에서 Cassandra로. Cassandra에서 ScyllaDB로.
두 번 다 "안 되겠다"는 판단이 있었고, 두 번 다 도메인의 요구가 바뀐 게 아니라 규모가 바뀐 것이었다.
메시지를 저장하고 꺼내는 일.
본질은 같은데 수천만 명이 쓰기 시작하면 모든 게 달라진다.

### 시작 --- MongoDB

Discord의 초기 선택은 MongoDB였다.
2015년, 서비스 초기 단계에서 유연한 스키마와 빠른 개발 속도가 매력적이었다.
메시지는 문서(Document) 구조와 잘 맞는다.
사용자, 채널, 메시지 본문, 첨부파일, 리액션. JSON으로 담기 자연스러운 데이터다.
작은 규모에서는 문제가 없었다.
하지만 데이터가 쌓이면서 MongoDB의 한계가 드러나기 시작했다.
메시지는 시간 순서로 쌓이고, 오래된 메시지도 조회 대상이다.
"3개월 전 대화 내용"을 뒤지는 사용자가 많다.
데이터가 RAM을 넘어서면서 디스크 I/O가 급증했고, 읽기 성능이 떨어지기 시작했다.

### 첫 번째 이동 --- Cassandra

Discord는 Cassandra를 선택했다. 이유는 분명했다.
쓰기가 빠르고, 수평 확장이 쉽고, 노드를 추가하면 선형으로 성능이 느는 구조.
메시지 저장에 이상적으로 보였다.
채널 ID + 타임스탬프를 파티션 키로 잡으면 시간 순서 조회가 자연스럽다. 그리고 실제로 잘 동작했다.
수년간 Cassandra는 Discord의 메시지를 저장했다.

### 수조 건 --- 문제가 시작되다

2022년 초, Discord의 Cassandra 클러스터는 177대의 노드에 수조 건의 메시지를 저장하고 있었다.
Discord의 공식 블로그에서 이 클러스터를 "high-toil system"이라고 표현했다.
운영 부담이 높고, 지연이 예측 불가능한 시스템.
문제는 크게 두 가지였다.

### 문제 1 --- GC pause

Cassandra는 Java로 작성됐다.
JVM 위에서 동작한다. JVM에는 가비지 컬렉션이 있다.
더 이상 사용하지 않는 메모리를 자동으로 회수하는 메커니즘.
편리하지만 대가가 있다.
GC가 동작할 때 모든 애플리케이션 스레드가 멈춘다. Stop-the-world.
이 멈춤이 수십 밀리초에서 수백 밀리초까지 걸릴 수 있다.
평소에 5ms에 응답하던 노드가 GC가 돌면 200ms가 걸린다.
클라이언트 입장에서는 "갑자기 멈췄다"가 된다.
Discord는 GC 튜닝에 상당한 시간을 투자했다고 밝혔다.
JVM의 힙 크기, GC 알고리즘, 옵션 조합.
하지만 근본적 한계가 있다. Java인 한 GC는 피할 수 없다.

### 문제 2 --- hot partition

Cassandra는 데이터를 파티션 단위로 분산한다.
특정 채널에 사용자가 몰리면 그 채널의 파티션이 있는 노드에 부하가 집중된다.
Discord에서 이런 일은 흔하다.
게임 출시 이벤트, 스트리머의 라이브 채팅, 수만 명이 동시에 같은 채널에서 대화하는 순간.
hot partition이 발생하면 해당 노드의 지연이 급증하고, 그 영향이 다른 요청까지 번진다.
Cassandra의 아키텍처에서 이 문제를 깔끔하게 해결하기 어려웠다.

### gossip dance

Discord 엔지니어들은 "gossip dance"라는 운영 패턴을 만들었다.
노드를 클러스터에서 빼고, 트래픽 없이 compaction을 돌리고, 다시 넣어서 밀린 데이터를 받고, 또 빼서 compaction을 돌리고.
이걸 반복하는 것이다. 수작업으로.
177대 노드에서 이걸 하고 있었다.
자동화된 시스템이 아니라 엔지니어가 수동으로 관리해야 하는 절차였다.
이건 운영이 아니라 생존이다.

### 두 번째 이동 --- ScyllaDB

Discord는 ScyllaDB를 선택했다. ScyllaDB는 Cassandra와 API 호환이다.
CQL(Cassandra Query Language)을 그대로 쓸 수 있다. 데이터 모델도 같다.
하지만 근본적인 차이가 있다.
C++로 작성됐다. JVM이 없다. GC가 없다.
GC가 없으면 stop-the-world가 없다.
지연 스파이크의 가장 큰 원인이 사라진다.
ScyllaDB는 shard-per-core 아키텍처를 쓴다.
각 CPU 코어가 독립적으로 데이터를 관리한다.
코어 간 잠금(lock) 경합이 없다.
이것도 tail latency를 줄이는 핵심이다.

### 마이그레이션 --- Rust로 9일

수조 건의 메시지를 옮기는 일이 남았다.
기존 도구를 쓰면 마이그레이션에 약 3개월이 걸릴 것으로 예상됐다.
실시간 서비스에서 3개월은 너무 길다.
Discord는 Rust로 마이그레이션 도구를 직접 만들었다.
결과적으로 9일 만에 마이그레이션을 완료했다.
Discord 공식 블로그에서 이 과정을 상세히 공개했다.

### 결과

Discord 공식 블로그의 수치다.

- 과거 메시지 조회: p99 지연이 40~125ms에서 15ms로 떨어졌다.
- 메시지 저장: p99 지연이 5~70ms에서 안정적으로 5ms를 유지한다.
- 노드 수: Cassandra 177대에서 ScyllaDB 72대로 줄었다.

"70ms에서 5ms"라는 숫자보다 "5~70ms에서 안정적 5ms"라는 표현이 핵심이다.
변동폭이 사라졌다.
GC pause가 만들던 지연 스파이크가 없어진 것이다.

### DBA 관점에서의 정리

Discord의 여정에서 배울 점은 "어떤 DB가 최고인가"가 아니다.
규모가 바뀌면 답이 바뀐다는 것이다.
MongoDB는 초기에 맞았다.
Cassandra는 성장기에 맞았다.
ScyllaDB는 수조 건 규모에 맞았다.
매번 "나쁜 선택"을 한 게 아니다.
규모가 선택을 넘어선 것이다.
결정적 순간에 선택을 가른 건 기능이 아니라 런타임 특성이었다.
Cassandra와 ScyllaDB는 데이터 모델이 같고 쿼리 언어가 같다.
다른 건 딱 하나. JVM 위에서 도는가, 아닌가.
GC pause 하나가 177대와 72대의 차이를 만들었고, p99 125ms와 15ms의 차이를 만들었다.
때로는 가장 기초적인 선택이 모든 것을 결정한다.

## WiredTiger: MongoDB의 심장을 열어본다

MongoDB 3.2부터 기본 스토리지 엔진은 WiredTiger다.
그 전의 MMAPv1은 역사 속으로 사라졌다.
대부분의 MongoDB 사용자는 WiredTiger를 의식하지 않는다.
Document를 넣으면 저장되고 읽으면 나온다.
그 사이에서 무슨 일이 벌어지는지는 모른다.

- MVCC의 동작 원리를 이해하라.
- 캐시와 디스크의 경계를 파악하라.
- 체크포인트와 저널의 역할을 구분하라.
- 압축 옵션을 워크로드에 맞게 선택하라.
- Dirty ratio를 모니터링하라.

스토리지 엔진은 보이지 않는 곳에서 모든 걸 결정한다.

### MVCC: 읽기와 쓰기가 서로를 막지 않는 이유

WiredTiger는 MVCC를 쓴다. Multi-Version Concurrency Control.
하나의 Document에 대해 여러 버전을 유지한다.
읽기는 자기 시점의 스냅샷을 본다. 쓰기는 새 버전을 만든다.
읽기와 쓰기가 동시에 일어나도 블로킹이 없다.
InnoDB의 MVCC와 원리는 같다.
undo log 대신 WiredTiger는 인메모리 버전 체인을 쓴다.
오래된 스냅샷이 살아 있으면 이전 버전을 지울 수 없다.
긴 트랜잭션이 위험한 이유가 여기 있다.
버전 체인이 길어지면 메모리가 증가하고 캐시 pressure가 올라간다.

### Document-level Locking

MMAPv1은 Collection-level Lock이었다.
하나의 Document를 쓰면 Collection 전체가 잠겼다.
WiredTiger는 Document-level이다.
서로 다른 Document는 동시에 쓸 수 있다.
다만 "lock"이라는 표현이 약간 오해를 준다.
WiredTiger의 내부는 optimistic concurrency에 가깝다.
쓰기 충돌이 발생하면 한쪽이 retry한다.
같은 Document를 동시에 쓰면?
한쪽이 WriteConflict를 받고 재시도한다.
MongoDB 드라이버가 자동으로 처리하지만 핫 Document에 쓰기가 몰리면 retry 비용이 쌓인다.

### 캐시: WiredTiger Internal Cache

WiredTiger는 자체 캐시를 가지고 있다.
기본값은 `(RAM - 1GB) * 50%`.
8GB 서버라면 3.5GB.
이 캐시에 인덱스와 Document가 올라간다.
압축 해제된 상태로 올라간다.
디스크에서는 압축돼 있지만 캐시에서는 풀려 있다.
그래서 디스크 사용량이 10GB인데 캐시가 10GB 필요한 건 아니다.
압축률에 따라 캐시에서 2~4배 더 차지할 수 있다.
캐시가 부족하면 eviction이 발생한다.
자주 안 쓰는 페이지를 디스크로 내보낸다.
이때 dirty page면 디스크에 써야 하니까 I/O가 발생한다.

### Dirty Ratio

캐시 안의 데이터 중 디스크에 아직 반영되지 않은 비율이 dirty ratio다.
WiredTiger는 두 개의 eviction 임계값을 가지고 있다.

[eviction_target]
캐시 사용률이 이 값을 넘으면 백그라운드 eviction 시작.
기본값 80%.

[eviction_dirty_target]
dirty page 비율이 이 값을 넘으면 dirty eviction 시작.
기본값 5%.

dirty ratio가 치솟으면 쓰기 요청이 eviction을 기다리게 된다.
쓰기 레이턴시가 갑자기 튀는 원인 중 하나다.
`serverStatus()`의 `wiredTiger.cache."tracked dirty bytes in the cache"`로 확인한다.

### 체크포인트

WiredTiger는 60초마다 체크포인트를 만든다.
그 시점까지의 모든 변경을 디스크에 쓴다.
체크포인트가 완료되면 그 이전의 저널(journal)은 더 이상 필요 없다.
복구 시 마지막 체크포인트부터 시작하면 되니까.
체크포인트 중에는 디스크 I/O가 증가한다.
대량의 dirty page를 한꺼번에 flush하기 때문이다.
60초 간격은 조절 가능하지만 짧게 하면 I/O가 자주, 길게 하면 복구 시간이 길어진다.
체크포인트 동안 쓰기가 느려지면 I/O 대역폭이 부족한 것이다.
Atlas에서는 IOPS provisioning을 늘리는 것으로 대응하고 Self-managed에서는 스토리지 성능을 점검한다.

### 저널(Journal)

체크포인트 사이의 변경을 보호하는 것이 저널이다.
Write-Ahead Log. WAL.
쓰기 요청이 들어오면 먼저 저널에 기록하고 그 다음 캐시에 반영한다.
서버가 체크포인트 사이에 죽으면 마지막 체크포인트 + 저널로 복구한다.
저널의 sync 간격은 기본 100ms.
100ms마다 저널을 디스크에 flush한다.
Write Concern에서 `j: true`를 쓰면 해당 쓰기가 저널에 sync될 때까지 기다린다.
성능은 떨어지지만 데이터 유실 가능성이 줄어든다.
InnoDB의 redo log와 같은 역할이다.
개념은 같고 구현이 다를 뿐이다.

### 압축

WiredTiger는 디스크에 데이터를 압축해서 저장한다.
세 가지 옵션이 있다.

[snappy] (기본값)
압축률은 보통이지만 속도가 빠르다.
대부분의 워크로드에 적합하다.
CPU 부담이 적다.

[zlib]
압축률이 높다.
디스크 공간을 아껴야 할 때.
CPU를 더 쓴다. 읽기/쓰기 레이턴시가 올라갈 수 있다.

[zstd] (MongoDB 4.2+)
snappy의 속도에 zlib의 압축률.
두 장점을 모두 취한다.

신규 배포라면 zstd가 가장 좋은 선택이다.
인덱스는 기본적으로 prefix compression을 사용한다.
별도 설정이 가능하지만 대부분 기본값으로 충분하다.

### InnoDB와의 비교

RDB DBA가 WiredTiger를 이해하는 가장 빠른 길은 InnoDB와 비교하는 것이다.

[캐시]
InnoDB Buffer Pool ↔ WiredTiger Internal Cache.
둘 다 디스크 I/O를 줄이기 위한 메모리 영역이다.
다만 WiredTiger는 압축 해제된 상태로 캐시에 올린다.

[WAL]
InnoDB redo log ↔ WiredTiger journal.
둘 다 crash recovery를 위한 선행 기록 로그다.

[MVCC]
둘 다 MVCC를 쓴다.
InnoDB는 undo log에 이전 버전을 저장한다.
WiredTiger는 인메모리 버전 체인을 쓴다.

[잠금]
InnoDB는 row-level lock.
WiredTiger는 document-level.
크기만 다르고 원리는 같다.

## MongoDB 트랜잭션: 쓸 수 있다와 써야 한다는 다르다

MongoDB 4.0에서 Multi-document Transaction이 들어왔다.
"드디어 트랜잭션!"이라고 환호했지만 정작 잘 쓰는 곳은 많지 않다.
RDB에서는 모든 쓰기가 트랜잭션 안에 있다. 당연한 것이다.
MongoDB에서는 트랜잭션 없이도 하나의 Document 안에서는 원자성이 보장된다.

- Document 설계로 트랜잭션 필요를 줄여라.
- 단일 Document 원자성을 먼저 활용하라.
- Multi-document Transaction의 제약을 파악하라.
- 60초 타임아웃을 인지하라.
- Write Concern과 Read Concern의 조합을 이해하라.

트랜잭션이 있다고 RDB처럼 쓰면 MongoDB의 장점이 사라진다.

### 단일 Document 원자성

MongoDB에서 하나의 Document에 대한 쓰기는 원자적이다. 별도 트랜잭션 없이.
주문 Document 안에 items 배열이 있다면 items를 수정하는 updateOne은 원자적이다.
다른 연산이 중간에 끼어들 수 없다.

```json
db.orders.updateOne(
    { _id: ObjectId("...") },
    { $push: { items: { product: "피자", qty: 1 } },
    $inc: { total: 15000 } }
)
```

items에 추가하고 total을 올리는 게 한 번에 일어난다.
실패하면 둘 다 안 일어난다.
이게 Embed 설계의 힘이다.
관련 데이터가 하나의 Document에 있으면 트랜잭션 없이도 일관성이 보장된다.

### Multi-document Transaction

서로 다른 Document를 묶어야 할 때가 있다.
계좌 이체. A에서 빼고 B에 넣는다.

```javascript
const session = client.startSession();
session.startTransaction();
try {
  db.accounts.updateOne(
    { _id: "A" },
    { $inc: { balance: -10000 } },
    { session },
  );
  db.accounts.updateOne(
    { _id: "B" },
    { $inc: { balance: 10000 } },
    { session },
  );
  session.commitTransaction();
} catch (e) {
  session.abortTransaction();
}
```

세션을 열고 트랜잭션을 시작하고 커밋하거나 롤백한다.
RDB의 `BEGIN - COMMIT - ROLLBACK`과 같다.

### 제약과 비용

Multi-document Transaction은 공짜가 아니다.

[60초 타임아웃]
기본값이 60초다.
60초 안에 커밋하지 않으면 자동 abort된다.
대량 데이터를 트랜잭션으로 처리하려 하면 걸린다.

[WiredTiger 캐시 압박]
트랜잭션 중에는 스냅샷을 유지해야 한다.
오래된 버전을 지울 수 없다.
긴 트랜잭션이 캐시 eviction을 방해한다.

[성능 오버헤드]
트랜잭션 밖의 쓰기보다 느리다.
잠금 대기, 스냅샷 유지, 커밋 프로토콜.
모든 쓰기를 트랜잭션으로 감싸면 처리량이 떨어진다.

[Sharding 환경]
여러 Shard에 걸친 트랜잭션은 2-phase commit이 필요하다.
더 느리고 더 복잡하다.

### Read Concern과 트랜잭션

트랜잭션 안에서의 Read Concern은 트랜잭션 밖과 다르게 동작한다.

[snapshot]
트랜잭션의 기본 Read Concern.
트랜잭션 시작 시점의 일관된 스냅샷을 읽는다.
트랜잭션 안에서 다른 쓰기가 들어와도 보이지 않는다.
RDB의 REPEATABLE READ와 비슷하다.
같은 쿼리를 두 번 실행해도 같은 결과가 나온다.

[majority]
트랜잭션 시작 전에 majority로 커밋된 데이터만 읽는다.
`Write Concern majority + Read Concern snapshot`.
이 조합이 트랜잭션에서 가장 안전한 설정이다.

### Causal Consistency

트랜잭션 없이도 인과 관계를 보장할 수 있다.
Causal Consistency Session이다.
A가 데이터를 쓰고 B에게 "다 됐다"고 알린다.
B가 읽었는데 아직 안 보인다.
Secondary에서 읽었기 때문이다.
Causal Consistency를 켜면 B의 읽기가 A의 쓰기 이후 시점을 보장한다.

```javascript
const session = client.startSession({
  causalConsistency: true,
});
```

세션 안의 모든 연산이 인과 순서를 지킨다.
Secondary에서 읽어도 "내가 쓴 건 반드시 보인다."
트랜잭션보다 가볍고 eventual consistency보다 강하다.
많은 경우 이것으로 충분하다.

### Retryable Writes

네트워크 오류로 쓰기 응답을 못 받았다.
성공한 건가 실패한 건가. 다시 보내면 중복되는 건 아닌가.
Retryable Writes는 이 문제를 해결한다.
MongoDB 3.6부터 기본으로 켜져 있다.
드라이버가 쓰기에 고유 ID를 붙인다.
서버가 같은 ID의 쓰기를 다시 받으면 실행하지 않고 이전 결과를 반환한다.
멱등성이 보장된다.
모든 쓰기가 지원되는 건 아니다. 단일 Document 연산만 해당된다.
Multi-document 쓰기는 트랜잭션 안에서 처리해야 한다.

### 트랜잭션을 줄이는 설계

RDB에서 왔다면 모든 걸 트랜잭션으로 감싸고 싶다.
MongoDB에서는 반대로 생각해야 한다.
"트랜잭션이 필요 없게 설계할 수 있는가?"

[패턴 1: 관련 데이터를 Embed]
주문과 아이템을 다른 Collection에 두면 트랜잭션이 필요하다.
하나의 Document에 Embed하면 필요 없다.

[패턴 2: 상태 머신]
pending → processing → completed.
상태 전이를 하나의 updateOne으로 처리한다.
findOneAndUpdate의 원자적 조건 검사로 동시성도 해결한다.

[패턴 3: 보상 트랜잭션]
실패 시 반대 연산을 수행한다.
트랜잭션 대신 eventual consistency를 받아들인다.
MSA에서 흔히 쓰는 Saga 패턴이다.

### DBA 관점에서의 정리

- Document 설계로 트랜잭션 필요를 줄여라.
- 단일 Document 원자성을 먼저 활용하라.
- Multi-document Transaction의 제약을 파악하라.
- 60초 타임아웃을 인지하라.
- Write Concern과 Read Concern의 조합을 이해하라.

RDB DBA에게 트랜잭션은 공기처럼 당연한 것이다.

```sql
BEGIN;
UPDATE;
UPDATE;
COMMIT
```

이게 없는 세계는 상상하기 어렵다.
MongoDB에서 트랜잭션은 공기가 아니라 산소통이다.
필요할 때 꺼내 쓰는 것이지 항상 등에 메고 다니는 게 아니다.
Document 모델의 핵심은 "관련 데이터를 함께 두면 트랜잭션이 필요 없다"는 것이다.
트랜잭션을 줄이는 설계가 MongoDB를 MongoDB답게 쓰는 것이다.
트랜잭션이 있다고 RDB처럼 쓰면 MongoDB의 장점이 사라진다.

## MongoDB 인덱싱: 쿼리가 빠른 건 우연이 아니다

느린 쿼리를 만나면 대부분 인덱스를 추가한다.
빨라지면 넘어간다. 왜 빨라졌는지는 안 본다.
그러다 인덱스가 20개가 된다. 쓰기가 느려진다.
어떤 인덱스가 쓰이는지도 모른다.

- Compound Index의 필드 순서를 근거로 정하라.
- ESR 룰을 외우지 말고 이해하라.
- Covered Query를 설계의 목표로 삼아라.
- 인덱스가 메모리에 있는지 확인하라.
- 쓰이지 않는 인덱스는 삭제하라.

인덱스는 추가하는 게 아니라 설계하는 것이다.

### B-Tree가 아니라 B+ Tree다

MongoDB의 WiredTiger 엔진은 인덱스를 B+ Tree로 관리한다.
B-Tree는 모든 노드에 데이터가 있다.
B+ Tree는 리프 노드에만 데이터가 있고 리프끼리 링크드 리스트로 연결돼 있다.
이 차이가 범위 검색에서 갈린다.
B-Tree는 트리를 다시 타야 하고 B+ Tree는 리프를 따라 스캔하면 된다.
COLLSCAN은 모든 Document를 읽는다.
IXSCAN은 인덱스의 리프를 따라간다.
이 차이는 Collection이 커질수록 극적으로 벌어진다.

### Single Field Index

가장 단순한 인덱스다. 하나의 필드에 건다.

```json
db.orders.createIndex({ "status": 1 })
```

`1`은 오름차순, `-1`은 내림차순.
Single Field에서는 방향이 크게 상관없다. MongoDB가 양방향으로 탐색할 수 있기 때문이다.
다만 이것만으로는 실무에서 부족하다.
"status가 pending인 주문을 날짜순으로"라는 쿼리에는 status 하나만으로는 정렬을 커버하지 못한다.
Single Field Index는 출발점이지 도착점이 아니다.

### Compound Index와 필드 순서

두 개 이상의 필드를 묶은 인덱스다. 필드 순서가 성능을 결정한다.

```json
db.orders.createIndex({ "status": 1, "created_at": -1 })
```

이 인덱스는 status 먼저 정렬하고 같은 status 안에서 created_at으로 정렬한다.
전화번호부와 같다. 성 먼저, 이름 다음.
status로만 검색하면 이 인덱스를 쓸 수 있다. created_at으로만 검색하면 쓸 수 없다.
왼쪽 prefix가 일치해야 한다.
이걸 Prefix Rule이라 한다.
순서를 바꾸면 다른 인덱스다.
`{ created_at: -1, status: 1 }` 은 완전히 다르게 동작한다.

### ESR 룰

Compound Index의 필드 순서를 정하는 실전 원칙이다.

[E - Equality]
등호 조건. `status = "pending"`.
가장 먼저 배치한다.
정확히 일치하는 값으로 범위를 좁히기 때문이다.

[S - Sort]
정렬 조건. `ORDER BY created_at DESC`.
Equality 다음에 배치한다.
인덱스 순서가 정렬 순서와 맞으면 별도 sort 단계가 사라진다.

[R - Range]
범위 조건. `created_at > "2026-08-01"`.
가장 마지막에 배치한다.
범위 조건 뒤의 필드는 인덱스 효율이 떨어지기 때문이다.

```text
{ status: 1, created_at: -1, amount: 1 }
E(status) → S(created_at) → R(amount)
```

### Covered Query

쿼리가 필요한 모든 필드가 인덱스 안에 있으면 Document 자체를 읽지 않아도 된다.

```json
db.orders.createIndex(
    { "status": 1, "created_at": -1, "total": 1 }
)
db.orders.find(
    { status: "pending" },
    { created_at: 1, total: 1, _id: 0 }
)
```

`explain()`에서 `totalDocsExamined`가 0이면 성공이다.
인덱스만으로 결과를 반환한 것이다.
주의할 점은 `_id`를 projection에서 빼야 한다는 것이다.
`_id`는 별도 인덱스에 있어서 포함되면 Document를 다시 읽어야 한다.
디스크 I/O가 0에 가까워지는 가장 확실한 방법이다.

### Partial Index

조건에 맞는 Document만 인덱싱한다.
인덱스 크기가 줄고 쓰기 부담이 줄어든다.

```json
db.orders.createIndex(
    { "created_at": -1 },
    { partialFilterExpression: { "status": "pending" } }
)
```

이 인덱스는 status가 pending인 Document만 포함한다.
완료된 주문 수백만 건은 인덱스에 없다.

주의: 쿼리의 필터가 partialFilterExpression을 반드시 포함해야 이 인덱스를 탄다.
status 조건 없이 created_at만 검색하면 COLLSCAN이 된다.
Sparse Index는 비슷하지만 다르다.
필드가 존재하는 Document만 인덱싱한다.
Partial이 더 세밀한 조건을 걸 수 있어서 대부분 Partial을 쓴다.

### TTL Index

일정 시간이 지나면 Document를 자동 삭제한다.
세션, 임시 토큰, 로그에 유용하다.

```json
db.sessions.createIndex(
    { "created_at": 1 },
    { expireAfterSeconds: 3600 }
)
```

created_at 기준으로 1시간이 지나면 삭제된다.
백그라운드 스레드가 60초마다 돌면서 만료된 Document를 지운다.
주의할 점이 있다. 삭제가 즉각적이지 않다. 최대 60초 지연.
대량 만료가 동시에 발생하면 삭제 부하가 생긴다.
TTL 필드는 반드시 Date 타입이어야 한다.
문자열이면 만료되지 않는다. 에러도 없이.

### Wildcard Index

스키마가 유동적인 필드에 건다.
어떤 필드가 올지 모를 때.

```json
db.products.createIndex({ "attributes.$**": 1 })
```

attributes 아래 어떤 키가 와도 인덱싱된다.
`{"attributes": {"color": "red"}}`도 되고, `{"attributes": {"weight": 1.5}}`도 된다.
만능처럼 보이지만 제약이 있다.
Compound Index와 결합할 수 없다.
배열 안의 배열은 지원하지 않는다.
Equality 쿼리에서만 효율적이고 범위 쿼리에서는 약하다.
"어떤 필드가 올지 모르지만 검색은 해야 한다"는 아주 특수한 상황에서만 쓴다.

### Text Index와 Atlas Search

Text Index는 MongoDB 내장 전문 검색이다.
단어 단위 토큰화, 스테밍, 가중치를 지원한다.

```json
db.articles.createIndex(
    { "title": "text", "body": "text" },
    { weights: { title: 10, body: 1 } }
)
```

간단한 키워드 검색에는 충분하다.
하지만 한국어 형태소 분석, 자동완성, 퍼지 검색은 못 한다.
Atlas Search는 Lucene 기반이다.
Elasticsearch와 동급의 전문 검색을 제공한다.
별도 클러스터 없이 MongoDB 안에서 돌아간다.
Aggregation Pipeline의 $search 스테이지로 호출한다.
인덱스 동기화도 자동이다.
Elasticsearch를 따로 운영하는 부담이 사라진다.

### 인덱스와 메모리

인덱스는 메모리에 있어야 빠르다.
디스크에서 읽으면 B+ Tree 탐색마다 I/O가 발생한다.
WiredTiger 캐시에 인덱스가 올라가 있는지 확인하는 방법은 `serverStatus()`의 `wiredTiger.cache` 섹션이다.
인덱스 전체 크기는 이렇게 본다.

```json
db.orders.stats().totalIndexSize
```

이 값이 WiredTiger 캐시보다 크면 인덱스 일부가 디스크에서 읽힌다.
쿼리 레이턴시가 불규칙해진다.
불필요한 인덱스는 메모리를 낭비한다.
사용되지 않는 인덱스는 `$indexStats`로 확인한다.
0 ops인 인덱스는 삭제 후보다.

### `explain()` 읽는 법

쿼리가 인덱스를 타는지 확인하는 유일한 방법이다.

```json
db.orders.find({status: "pending"}).explain("executionStats")
```

봐야 할 숫자 세 개.

[nReturned]
실제 반환된 Document 수.

[totalKeysExamined]
인덱스에서 스캔한 키 수.

[totalDocsExamined]
Document를 실제로 읽은 수.

이상적인 상태는 세 숫자가 같거나 `totalDocsExamined`가 0(Covered Query)인 것이다.
`nReturned`가 10인데 `totalDocsExamined`가 100,000이면 인덱스가 없거나 잘못 타고 있는 것이다.
`winningPlan`의 stage를 보면 COLLSCAN인지 IXSCAN인지 나온다.

### DBA 관점에서의 정리

- Compound Index의 필드 순서를 근거로 정하라.
- ESR 룰을 외우지 말고 이해하라.
- Covered Query를 설계의 목표로 삼아라.
- 인덱스가 메모리에 있는지 확인하라.
- 쓰이지 않는 인덱스는 삭제하라.

인덱스를 많이 거는 건 쉽다. 인덱스를 적게 거는 게 어렵다.
모든 인덱스는 쓰기 비용을 올린다.
insert마다 모든 인덱스의 B+ Tree를 갱신해야 한다.
인덱스 5개면 쓰기 비용이 5배가 아니지만 확실히 늘어난다.
읽기를 위해 인덱스를 추가하고 쓰기를 위해 인덱스를 삭제한다.
이 균형을 잡는 게 인덱싱이다.
인덱스는 추가하는 게 아니라 설계하는 것이다.

## MongoDB 안티패턴: 되는데 하면 안 되는 것들

MongoDB는 자유롭다.
스키마를 강제하지 않고 배열에 뭐든 넣을 수 있고 Document 안에 Document를 넣을 수 있다.
그래서 위험하다.
"된다"와 "해도 된다"는 다르다.

RDB에서는 잘못된 구조를 만들면 DB가 거부한다.
외래키 위반, 타입 불일치, NOT NULL 제약.
MongoDB에서는 잘못된 구조를 만들면 DB가 받아준다.
그리고 서비스가 커진 뒤에야 대가를 치른다.

- 무한히 자라는 배열을 만들지 마라.
- 테이블을 Collection으로 그대로 옮기지 마라.
- `$lookup`으로 RDB의 JOIN을 재현하지 마라.
- Write Concern을 이해 없이 기본값으로 두지 마라.
- Projection 없이 Document 전체를 읽지 마라.

안티패턴은 처음엔 동작한다. 그게 함정이다.

### 무한 성장 배열

가장 흔하고 가장 치명적인 안티패턴이다.
게시글에 댓글을 배열로 Embed한다.
처음엔 문제없다. 댓글이 5개, 10개.

```json
{
  "title": "오늘의 메뉴",
  "comments": [
    { "user": "A", "text": "맛있겠다", "date": "..." },
    { "user": "B", "text": "어디서 파나요", "date": "..." }
  ]
}
```

1년이 지났다. 댓글이 50,000개다.
Document 크기가 12MB다.
댓글 하나를 추가할 때마다 12MB Document 전체가 재할당된다.

### 무한 성장 배열: 왜 재할당이 문제인가

WiredTiger는 Document를 수정할 때 기존 공간에서 in-place update를 시도한다.
Document가 커져서 기존 공간에 안 맞으면 새 위치에 통째로 복사한다.
`$push`로 배열에 하나를 추가하면 Document 전체 크기가 증가한다.
재할당 빈도가 올라간다.
디스크 단편화가 생긴다.
WiredTiger 캐시에서 dirty page가 늘어난다.
증상은 서서히 나타난다.
쓰기 레이턴시가 조금씩 올라간다.
어느 날 16MB를 넘는 Document가 생기면 insert가 실패한다. 에러도 갑작스럽다.

[해결]
댓글은 별도 Collection으로 분리한다.
게시글에는 comment_count만 Computed Pattern으로 유지한다.
최신 댓글 3개만 Subset Pattern으로 Embed한다.

### 깊은 중첩

Document 안에 Document 안에 Document.
5단계, 7단계까지 들어간다.

```json
{
  "company": {
    "dept": {
      "team": {
        "member": {
          "address": { "city": "서울" }
        }
      }
    }
  }
}
```

[쿼리가 길어진다]
`company.dept.team.member.address.city`
오타 하나면 결과가 빈 배열이다. 에러도 안 난다.

[인덱싱이 어렵다]
중첩이 깊으면 인덱스 키도 길어진다.

[업데이트가 위험하다]
`$set` 경로가 길어질수록 실수 확률이 올라간다.
잘못된 경로에 $set하면 새 필드가 생겨버린다.

[해결]
2~3단계 이내로 유지한다.
깊어지면 별도 Collection으로 분리하거나 flatten한다.

### RDB를 그대로 옮기기

MySQL 테이블 10개를 MongoDB Collection 10개로 1:1 변환한다.
가장 자연스러워 보이지만 가장 나쁜 시작이다.
users, orders, order_items, products, payments...
테이블 하나가 Collection 하나. 결과는 이렇다.
주문 상세 페이지를 그리려면 `orders`, `order_items`, `products`, `users`, `delivery`.
`$lookup` 다섯 번. RDB에서는 하나의 SQL JOIN으로 했다.
`$lookup` 다섯 번은 JOIN 하나보다 훨씬 비싸다.
JOIN이 없는 DB에서 JOIN을 하고 있는 것이다.

[해결]
마이그레이션 전에 Access Pattern을 먼저 정리한다.
"이 화면에서 무엇을 읽는가."
테이블이 아니라 화면이 Document의 구조를 결정한다.

### 모든 걸 하나에 Embed

RDB 이식의 반대쪽 극단이다.
"MongoDB는 Embed하라고 했잖아." 그래서 전부 넣는다.
사용자 Document에 주문 전체를 Embed한다.
주문 안에 아이템을 Embed한다.
아이템 안에 상품 상세를 Embed한다.
상품 안에 리뷰를 Embed한다.
하나의 Document가 5MB다.
사용자 프로필만 보려고 해도 5MB를 읽는다.
이름과 이메일만 필요한데 주문 1000건이 딸려온다.
쓰기는 더 심각하다.
리뷰 하나가 추가될 때마다 사용자 Document 전체가 갱신된다.

[해결]
Embed의 기준은 "함께 읽히는가"이지 "관계가 있는가"가 아니다.
관계가 있어도 따로 읽히면 Reference다.

### `$lookup` 남용

`$lookup`은 MongoDB의 JOIN이다.
쓸 수 있다. 하지만 비용을 알고 써야 한다. `$lookup` 하나가 실행될 때 벌어지는 일.
메인 Collection에서 Document를 하나 읽고 from Collection에서 일치하는 Document를 찾는다.
from Collection에 인덱스가 없으면?
메인 Document 하나마다 COLLSCAN한다.
메인이 10,000건이면 COLLSCAN이 10,000번이다.
`$lookup`을 세 번 체이닝하면?
각 스테이지가 앞 스테이지의 결과만큼 반복된다.
비용이 곱셈으로 증가한다.

[해결]
`$lookup`은 분석용이지 서비스 쿼리용이 아니다.
서비스에서 필요하면 Extended Reference Pattern으로 자주 쓰는 필드만 미리 복사해 둔다.
`$lookup`을 쓸 때는 from Collection에 반드시 인덱스를 건다.

### Projection 없이 전체 읽기

`find()`에 projection을 안 주면 Document의 모든 필드가 반환된다.

```json
// 이름만 필요한데 전체를 읽는다
db.users.find({ status: "active" })

// Projection으로 필요한 것만
db.users.find(
    { status: "active" },
    { name: 1, email: 1, _id: 0 }
)
```

Document가 작으면 차이가 미미하다.
하지만 Document에 큰 배열이나 긴 텍스트가 있으면 네트워크 전송량과 드라이버의 역직렬화 비용이 크게 달라진다.
특히 목록 화면에서 심각하다.
사용자 100명의 이름만 보여주는데 100명의 전체 프로필(주소, 설정, 활동 로그)이 딸려오면 불필요한 데이터가 필요한 데이터의 수십 배가 된다.
Projection을 쓰면 Covered Query의 기회도 생긴다.
안 쓰면 그 기회가 원천 차단된다.

### Write Concern을 기본값으로 방치

기본값은 `w: 1`이다. Primary에 쓰여지면 성공.
Secondary에 복제됐는지는 모른다.
이게 왜 안티패턴인가.
Primary가 갑자기 죽으면 복제 안 된 쓰기가 사라진다.
"서버가 잘 죽나요?" 죽는다.
하드웨어 장애, OOM, 네트워크 파티션.
AWS에서 인스턴스가 사라지는 건 일상이다.

[잃어도 되는 데이터]
조회 로그, 임시 세션, 캐시성 데이터.
`w: 1`로 충분하다.

[잃으면 안 되는 데이터]
결제, 주문, 사용자 정보.
`w: "majority"`를 써야 한다.
`j: true`까지 쓰면 저널에 기록될 때까지 기다린다.
안티패턴은 "기본값이니까 괜찮겠지"라고 생각하는 것이다.
기본값이 최선이 아닌 경우가 많다.

### Secondary에서 정합성 필요한 데이터 읽기

Read Preference를 secondary로 설정하면 읽기 부하가 분산된다.
하지만 Secondary는 Primary보다 뒤처져 있다.
보통 밀리초지만 부하가 높으면 초 단위까지 벌어진다.
"방금 결제했는데 주문 내역에 안 보여요."
쓰기는 Primary에 갔고 읽기는 Secondary에서 왔다.
아직 복제가 안 된 것이다.

[안티패턴이 되는 경우]
쓰기 직후 읽기가 필요한 화면.
결제 → 결제 확인. 글 작성 → 내 글 목록.

[해결]
이런 경로에서는 Read Preference를 primary로 둔다.
또는 Causal Consistency Session을 사용한다.
"내가 쓴 건 반드시 읽힌다"를 보장하는 세션이다.
통계, 대시보드처럼 지연이 허용되는 읽기만 secondary로 보낸다.

### MongoDB를 큐로 쓰기

"처리 대기 목록"을 Collection에 넣고 워커가 `findOneAndUpdate`로 하나씩 꺼내 간다.
status를 "pending"에서 "processing"으로 바꾸면서.
소규모에서는 동작한다. 하지만 이건 큐가 아니다.

[문제 1: 폴링]
워커가 주기적으로 "pending 있나?" 쿼리를 날린다.
데이터가 없어도 쿼리는 실행된다.
워커가 10개면 빈 쿼리가 초당 수십 번 날아간다.

[문제 2: 순서 보장 없음]
`findOneAndUpdate`는 순서를 보장하지 않는다.
먼저 들어온 게 먼저 처리되리라는 보장이 없다.

[문제 3: 재처리]
워커가 "processing" 상태에서 죽으면 그 Document는 영원히 processing 상태에 갇힌다.
타임아웃 로직을 직접 구현해야 한다.

[해결]
큐가 필요하면 큐를 쓴다. RabbitMQ, SQS, Kafka.
MongoDB Change Streams + 외부 큐 조합도 방법이다.

### 큰 바이너리를 Document에 저장

이미지, PDF, 동영상을 Document의 필드에 Binary로 넣는다.

```json
{
    "filename": "photo.jpg",
    "data": BinData(0, "base64로 인코딩된 5MB...")
}
```

16MB 제한에 빠르게 도달한다.
그리고 이 Document를 읽을 때마다 5MB를 메모리에 올린다.
WiredTiger 캐시를 한 장의 사진이 차지한다.

[해결: GridFS]
MongoDB의 공식 대용량 파일 저장 방식이다.
파일을 255KB 청크로 쪼개서 저장한다.
`fs.files`(메타데이터)와 `fs.chunks`(데이터) 두 Collection을 쓴다.

[더 나은 해결: 오브젝트 스토리지]
S3, GCS 같은 오브젝트 스토리지에 파일을 저장하고 MongoDB에는 URL만 저장한다.
대부분의 경우 이게 정답이다.
MongoDB는 메타데이터를 관리하고 파일 서빙은 CDN이 하는 것이 맞다.

### 인덱스 없는 Collection

"일단 개발하고 나중에 인덱스를 걸자." 이 나중은 보통 안 온다.
데이터가 수백만 건이 될 때까지.
`_id`에는 자동으로 인덱스가 걸린다.
하지만 `_id`가 아닌 필드로 검색하면 인덱스가 없으면 COLLSCAN이다.
소규모에서는 느린 줄도 모른다.
10,000건 COLLSCAN은 밀리초다.
1,000만 건 COLLSCAN은 수 초에서 수십 초다.

[증상]
서비스 초기에는 빠르다.
데이터가 쌓이면서 점점 느려진다.
어느 날 갑자기 타임아웃이 터진다.
"아무것도 안 바꿨는데 느려졌어요."
데이터가 바뀐 것이다.

[해결]
설계 시점에 Access Pattern을 정의하고 그에 맞는 인덱스를 미리 건다.
프로덕션 배포 전에 `explain()`으로 확인한다.

### 인덱스를 너무 많이 거는 것

반대쪽 극단이다.
느린 쿼리가 나올 때마다 인덱스를 추가한다.
Collection에 인덱스가 15개, 20개가 된다.
인덱스 하나가 추가될 때마다 모든 쓰기 연산이 느려진다.
insert 한 번에 20개의 B+ Tree를 갱신해야 한다.
인덱스는 메모리를 차지한다.
20개 인덱스의 총 크기가 WiredTiger 캐시보다 크면 데이터가 캐시에서 밀려난다.
읽기도 느려진다.

[해결]
`$indexStats`로 사용 빈도를 확인한다.

```json
db.orders.aggregate([{ $indexStats: {} }])
```

ops가 0인 인덱스는 삭제 후보다.
Compound Index 하나가 Single Index 여러 개를 대체할 수 있다.

`{ status: 1, created_at: -1 }`는 `{ status: 1 }`의 역할도 한다. Prefix Rule.

### ObjectId를 비즈니스 키로 의존

`_id`의 기본값인 ObjectId는 편리하다. 자동 생성, 유니크, 시간순.
하지만 비즈니스 로직에서 ObjectId를 직접 쓰면 문제가 생긴다.

[URL에 노출]
`/orders/507f1f77bcf86cd799439011`
ObjectId는 생성 시간을 포함한다.
앞 4바이트가 UNIX timestamp다.
생성 시각이 외부에 노출된다.

[외부 시스템 연동]
REST API로 주문 ID를 주고받을 때 ObjectId 문자열 24자를 쓰면
상대 시스템이 파싱하기 번거롭다.

[Sharding 시]
ObjectId는 시간순 단조 증가한다.
Ranged Sharding에서 핫스팟을 만든다.
최신 데이터가 항상 마지막 Shard에 몰린다.

[해결]
비즈니스 키는 별도 필드로 관리한다.
`{ order_code: "ORD-20260826-001" }`
`_id`는 내부 식별자로만 쓰고 외부에는 비즈니스 키를 노출한다.

### 갱신 안 되는 계산값

Computed Pattern의 잘못된 적용이다.
상품 Document에 `avg_rating`을 미리 계산해 뒀다.
리뷰가 추가될 때 `avg_rating`을 갱신한다.
그런데 리뷰가 삭제될 때는? 리뷰가 수정될 때는? 관리자가 리뷰를 숨김 처리할 때는?
모든 변경 경로에서 `avg_rating`을 다시 계산해야 한다.
하나라도 빠지면 값이 틀어진다.
그리고 빠진다. 반드시 빠진다.

[증상]
"별점 4.3인데 리뷰를 보면 다 5점이에요."
삭제된 1점짜리 리뷰가 avg에 반영된 채로 남아 있다.

[해결]
갱신 경로가 단순하면 Computed Pattern을 쓴다.
추가만 있고 삭제/수정이 없는 카운터 같은 경우.
갱신 경로가 복잡하면 주기적으로 재계산한다.
Aggregation Pipeline을 배치로 돌려서 정확한 값을 덮어쓰는 방식이다.
실시간성은 떨어지지만 정합성이 보장된다.

### 스키마 없이 프로덕션 운영

MongoDB는 아무 구조나 받아준다.
한 Collection에 이런 Document가 공존할 수 있다.

```json
{"name": "김철수", "age": 30}
{"name": 12345, "age": "서른"}
{"nm": "이영희"}
```

name이 문자열이기도 하고 숫자이기도 하다.
필드명이 name이기도 하고 nm이기도 하다.
age가 숫자이기도 하고 문자열이기도 하다.
애플리케이션이 이걸 다 처리해야 한다.
처리 못 하면 런타임에 터진다.

[해결]
Schema Validation을 건다.
필수 필드, 타입, 값 범위를 정의한다.
프로덕션에서는 strict 모드.
마이그레이션 중에는 moderate 모드.
"MongoDB는 스키마가 없으니까 자유롭게"는 개발 단계에서만 유효한 말이다.
프로덕션은 자유가 아니라 규율이다.

### 대용량 `$in` 쿼리

`$in`에 수천, 수만 개의 값을 넣는다.

```json
db.orders.find({
    user_iid: { $in: [id1, id2, id3, ... id50000] }
})
```

인덱스가 있어도 느리다. `$in`의 각 값마다 인덱스를 탐색한다.
50,000개면 50,000번의 인덱스 탐색이다.
BSON Document 크기 제한에도 걸릴 수 있다.
쿼리 자체가 하나의 Document이기 때문이다.
16MB를 넘는 쿼리는 실행되지 않는다.

[해결]
`$in`의 값이 수십 개까지는 괜찮다.
수백 개를 넘어가면 설계를 재검토한다.
배치로 나눠서 실행하거나 애초에 `$in`이 필요 없는 구조로 설계한다.
사용자 그룹이 필요하면 group_iid 필드를 Document에 추가해서 `$in` 대신 단일 값 쿼리로 바꾼다.

### DBA 관점에서의 정리

- 무한히 자라는 배열을 만들지 마라.
- 테이블을 Collection으로 그대로 옮기지 마라.
- `$lookup`으로 RDB의 JOIN을 재현하지 마라.
- Write Concern을 이해 없이 기본값으로 두지 마라.
- Projection 없이 Document 전체를 읽지 마라.

안티패턴의 공통점이 있다. 전부 처음엔 동작한다.
데이터가 적을 때는 빠르고 문제가 없다.
데이터가 100배 되면 무한 배열은 터지고 COLLSCAN은 타임아웃을 내고 `$lookup` 체인은 서버를 멈추고 `w: 1`은 데이터를 잃는다.
MongoDB의 자유도는 양날의 검이다.
RDB는 잘못하면 거부당하고 MongoDB는 잘못하면 받아들여진다.
거부당하는 게 차라리 안전하다.
안티패턴을 아는 것은 패턴을 아는 것만큼 중요하다.
뭘 해야 하는지보다 뭘 하면 안 되는지를 먼저 알아야 실수가 서비스에 들어가기 전에 잡힌다.
안티패턴은 처음엔 동작한다. 그게 함정이다.

## MongoDB 성능 튜닝: 느리다는 말의 안쪽

"MongoDB가 느려요."
이 한 마디에 원인은 열 가지다.
인덱스가 없는 건지. 캐시가 부족한 건지. 커넥션이 모자란 건지. 잠금 대기가 긴 건지. 디스크가 느린 건지.
"느리다"를 "어디가 왜 느리다"로 바꾸는 게 튜닝의 시작이다.

- Profiler로 느린 쿼리를 잡아라.
- explain()으로 실행 계획을 읽어라.
- serverStatus()의 핵심 지표를 파악하라.
- Connection Pool을 적절히 설정하라.
- WiredTiger 캐시 상태를 모니터링하라.

숫자 없는 튜닝은 감이다. 감은 틀린다.

### Database Profiler

느린 쿼리를 잡는 첫 번째 도구다.

```json
db.setProfilingLevel(1, { slowms: 100 })
```

- Level 0: 꺼짐.
- Level 1: slowms보다 느린 쿼리만 기록.
- Level 2: 모든 쿼리 기록.

프로덕션에서는 Level 1, 100ms가 적당하다.
Level 2는 모든 쿼리를 기록하니까 부하가 생긴다.
기록은 system.profile Collection에 저장된다.
capped collection이라 오래된 건 자동으로 사라진다.

```json
db.system.profile.find().sort({ ts: -1 }).limit(5)
```

어떤 쿼리가 얼마나 걸렸는지. 몇 개의 Document를 스캔했는지. 인덱스를 탔는지. 전부 여기 있다.

### `explain()` 실전

쿼리가 어떻게 실행되는지 보여주는 도구다.
세 가지 모드가 있다.

[queryPlanner]
실행 계획만 보여준다. 실제로 실행하지 않는다.

[executionStats]
실제로 실행하고 통계를 보여준다.
nReturned, totalKeysExamined, totalDocsExamined.

[allPlansExecution]
후보 계획 전부의 실행 통계를 보여준다.
executionStats를 가장 많이 쓴다.

핵심 숫자 세 개.

- nReturned: 10.
- totalDocsExamined: 100,000.
- executionTimeMillis: 3200.

10개를 찾기 위해 10만 개를 뒤졌고 3.2초 걸렸다.
인덱스가 없다는 의미다.

### `currentOp()`

지금 이 순간 실행 중인 연산을 보여준다.

```json
db.currentOp({ "active": true, "secs_running": { "$gt": 5 } })
```

5초 이상 실행 중인 연산만 필터링.
어떤 쿼리가, 어떤 컬렉션에서, 얼마나 걸리고 있는지. 잠금을 잡고 있는 연산도 보인다.
waitingForLock이 true인 연산이 쌓이고 있으면 누군가가 잠금을 오래 들고 있다는 뜻이다.
긴급 상황에서는 `killOp()`으로 연산을 죽일 수 있다.

```json
db.killOp(opId)
```

다만 killOp은 즉각적이지 않을 수 있다.
연산이 다음 중단점에 도달해야 실제로 멈춘다.

### `serverStatus()`

MongoDB 서버의 전반적인 상태를 보여주는 명령이다.
Prometheus나 Datadog으로 수집하는 지표의 원본이다.
가장 먼저 볼 지표 다섯 가지.

[connections.current]
현재 연결 수. 급증하면 커넥션 풀 문제.

[opcounters]
insert, query, update, delete, command의 초당 횟수.
패턴 변화를 감지한다.

[wiredTiger.cache]
캐시 사용률과 dirty ratio.
eviction이 과도하면 캐시가 부족하다.

[globalLock.currentQueue]
잠금 대기 큐. 쌓이면 병목.

[repl.apply.batches.totalMillis]
Secondary의 복제 지연. 커지면 stale read 위험.

### Connection Pool

애플리케이션은 MongoDB에 커넥션 풀을 유지한다.
요청마다 커넥션을 열고 닫는 게 아니라 미리 만들어둔 커넥션을 재사용한다.
기본 풀 사이즈는 드라이버마다 다르다.
Java는 100, Python은 100, Node.js는 100이 기본.
너무 적으면 대기가 발생한다.
너무 많으면 MongoDB 서버의 커넥션 제한에 걸린다.
maxConnections 기본값은 65536이지만 실제로는 메모리가 한계를 정한다.
커넥션 하나당 약 1MB의 메모리를 쓴다. 1000개 커넥션이면 1GB.
마이크로서비스 10개가 각각 100개씩 열면 1000개다.
maxPoolSize를 워크로드에 맞게 조절하고 minPoolSize로 최소 커넥션을 유지한다.

### 느린 쿼리 해결 프로세스

증상을 발견하고 원인을 찾고 해결하는 순서다.

[1단계: 발견]
Profiler에서 slowms 이상 쿼리를 찾는다.
또는 모니터링 대시보드에서 레이턴시 스파이크를 감지한다.

[2단계: 분석]
`explain()`으로 실행 계획을 확인한다.
COLLSCAN이면 인덱스가 없다.
IXSCAN인데 느리면 인덱스가 최적이 아니다.

[3단계: 해결]
인덱스 추가 또는 변경.
쿼리 패턴 수정.
Schema 재설계.

[4단계: 검증]
다시 `explain()`으로 개선을 확인한다.
`totalDocsExamined`가 줄었는지.
`executionTimeMillis`가 줄었는지.

이 루프를 돌리는 것이 튜닝이다.

### mongotop과 mongostat

두 가지 CLI 모니터링 도구다.

[mongotop]
컬렉션별로 읽기/쓰기에 소비한 시간을 보여준다.
어떤 컬렉션이 가장 바쁜지 한눈에 보인다.
top 명령처럼 실시간으로 갱신된다.
특정 컬렉션의 읽기가 비정상적으로 높다면 해당 컬렉션의 인덱스나 쿼리 패턴을 점검해야 한다.

[mongostat]
서버 전체의 초당 통계를 보여준다.
insert, query, update, delete 횟수. 사용 중인 커넥션 수. 큐에 대기 중인 읽기/쓰기 수.
둘 다 가벼워서 프로덕션에서도 부담 없이 쓸 수 있다.
Atlas를 쓴다면 Atlas의 Real-Time Performance Panel이 같은 역할을 한다.

### 메모리와 Working Set

Working Set은 자주 접근하는 데이터의 크기다.
이게 WiredTiger 캐시 안에 들어가야 빠르다.
전체 데이터가 100GB인데 실제로 자주 읽히는 건 최근 1달 10GB라면 Working Set은 10GB다.
캐시가 8GB라면 Working Set이 캐시를 넘는다.
일부 데이터가 디스크에서 읽힌다.
레이턴시가 불규칙해진다.

[확인 방법]
`serverStatus()`의 `wiredTiger.cache` 섹션에서 `"bytes read into cache"`가 지속적으로 높다면 캐시가 부족한 것이다.
해결은 두 가지.
메모리를 늘리거나 Working Set을 줄이거나(아카이빙, TTL).

### Atlas Performance Advisor

Atlas를 쓴다면 Performance Advisor가 있다.
느린 쿼리를 자동으로 분석해서 인덱스를 추천한다.
추천 인덱스를 한 클릭으로 생성할 수 있다.
편하지만 맹목적으로 따르면 안 된다.
추천은 읽기 최적화 관점이다. 쓰기 비용은 고려하지 않는다.
이미 비슷한 인덱스가 있는지도 확인해야 한다.
Real-Time Performance Panel에서는 현재 실행 중인 쿼리의 레이턴시 분포를 볼 수 있다.
p50, p95, p99. p99가 튀는 시점을 찾으면 원인도 따라온다.
Self-managed라면 PMM(Percona Monitoring and Management)이나 Datadog MongoDB Integration이 같은 역할을 한다.

### DBA 관점에서의 정리

- Profiler로 느린 쿼리를 잡아라.
- `explain()`으로 실행 계획을 읽어라.
- `serverStatus()`의 핵심 지표를 파악하라.
- Connection Pool을 적절히 설정하라.
- WiredTiger 캐시 상태를 모니터링하라.

MySQL에서 slow_query_log와 EXPLAIN을 쓰듯이 MongoDB에서 Profiler와 `explain()`을 쓴다.
도구 이름만 다르고 하는 일은 같다.
다른 점이 있다면 MongoDB는 스토리지 엔진 레벨의 지표가 더 중요하다는 것이다.
WiredTiger 캐시, dirty ratio, eviction.
이 숫자들이 쿼리 레이턴시를 직접 좌우한다.
숫자를 보고 판단하는 것. 그게 감이 아니라 근거다.
숫자 없는 튜닝은 감이다. 감은 틀린다.

## Aggregation Pipeline: `find()`를 넘어서

`find()`로 검색하고 `sort()`로 정렬하고 `limit()`로 자른다.
여기까지는 쉽다.
"지난 한 달 간 카테고리별 매출 합계를 구해줘." `find()`로는 안 된다.
이게 Aggregation Pipeline의 영역이다.
Pipeline은 데이터를 단계별로 변환하는 컨베이어 벨트다.
`$match`로 거르고, `$group`으로 묶고, `$sort`로 정렬한다.
각 스테이지의 출력이 다음 스테이지의 입력이 된다.

- `$match`를 파이프라인 앞에 둬라.
- `$project`로 필요한 필드만 남겨라.
- `$lookup`의 비용을 과소평가하지 마라.
- `allowDiskUse`의 의미를 이해하라.

인덱스를 타는 스테이지와 못 타는 스테이지를 구분하라.
SQL의 GROUP BY가 할 수 있는 건 Pipeline도 할 수 있다.
Pipeline이 할 수 있는 건 GROUP BY로는 못 하는 것도 있다.

### 파이프라인의 구조

Aggregation은 스테이지의 배열이다.
앞에서부터 순서대로 실행된다.

```json
db.orders.aggregate([
    { $match: { status: "completed" } },
    { $group: {
        _id: "$category",
        total: { $sum: "$amount" }
    }},
    { $sort: { total: -1 } }
])
```

`$match`가 완료된 주문만 거른다.
`$group`이 카테고리별로 금액을 합산한다.
`$sort`가 합계 내림차순으로 정렬한다.

각 스테이지는 Document 스트림을 받아서 변환된 Document 스트림을 내보낸다.
Unix의 파이프와 같은 개념이다.

### `$match`: 가장 먼저, 가장 많이 거르기

`$match`는 파이프라인의 필터다. `find()`의 쿼리와 같은 문법을 쓴다.
`$match`를 파이프라인 맨 앞에 두면 인덱스를 탈 수 있다.
뒤에 두면 앞 스테이지가 모든 Document를 처리한 뒤에야 거른다.

```json
[
    { $match: { created_at: { $gte: ISODate("2026-08-01") } } },
    { $group: { _id: "$category", count: { $sum: 1 } } }
]
```

`$match`가 앞에 있으면 8월 이후 데이터만 `$group`으로 넘어간다.
뒤에 있으면 전체를 `$group`한 뒤 8월 이후만 걸러낸다.
결과는 같지만 비용이 완전히 다르다.

### `$group`: 집계의 핵심

`_id` 필드로 그룹핑 기준을 정하고 accumulator로 계산한다.
`$sum`, `$avg`, `$min`, `$max`, `$push`, `$addToSet`.

```json
{
  "$group": {
    "_id": {
      "year": { "$year": "$created_at" },
      "month": { "$month": "$created_at" }
    },
    "total_amount": { "$sum": "$amount" },
    "order_count": { "$sum": 1 },
    "unique_users": { "$addToSet": "$user_iid" }
  }
}
```

`_id`에 표현식을 넣으면 복합 그룹핑이 된다.
년-월별로 매출 합계, 주문 건수, 유니크 사용자를 한 번에 구한다.
`$push`는 그룹 안의 모든 값을 배열로 모은다.
그룹이 크면 이 배열이 거대해질 수 있다.
메모리 제한(100MB)에 걸린다.

### `$project`와 `$addFields`

`$project`는 필드를 선택하거나 새로 만든다.
불필요한 필드를 제거해서 다음 스테이지의 부담을 줄인다.

```json
{
  "$project": {
    "order_iid": 1,
    "total": 1,
    "discount_rate": {
      "$divide": ["$discount", "$total"]
    },
    "_id": 0
  }
}
```

`$addFields`는 기존 필드를 유지하면서 새 필드만 추가한다.
`$project`로 하면 명시하지 않은 필드가 사라지지만 `$addFields`는 나머지를 그대로 둔다.
파이프라인 중간에 `$project`를 넣으면 이후 스테이지가 처리할 데이터 양이 줄어든다.
특히 큰 배열이나 텍스트 필드가 있을 때 효과적이다.

### `$lookup`: MongoDB의 JOIN

다른 Collection에서 데이터를 가져온다.
SQL의 LEFT OUTER JOIN과 비슷하다.

```json
{
  "$lookup": {
    "from": "products",
    "localField": "product_iid",
    "foreignField": "_id",
    "as": "product_info"
  }
}
```

결과는 배열로 들어온다. 일치하는 Document가 없으면 빈 배열.
`$lookup`은 강력하지만 비용이 크다.
from Collection의 foreignField에 인덱스가 없으면 매 Document마다 COLLSCAN이 발생한다.
또한 `$lookup`은 Sharded Collection에서 제약이 있다.
from Collection이 같은 DB에 있어야 하고 Sharding 환경에서는 성능이 크게 떨어질 수 있다.
필요할 때만, 인덱스를 확인하고 쓴다.

### `$unwind`

배열을 풀어서 각 요소를 별도 Document로 만든다.

```json
// 원본: { items: ["치킨", "피자", "콜라"] }
{ "$unwind": "$items" }

// 결과:
// { items: "치킨" }
// { items: "피자" }
// { items: "콜라" }
```

배열 안의 요소별로 집계할 때 쓴다.
"주문 아이템별 매출"을 구하려면 items를 먼저 풀어야 한다.

주의: 배열이 크면 Document 수가 폭증한다.
100개짜리 배열을 `$unwind`하면 100배가 된다.
`100만 Document * 100 = 1억 Document`.
preserveNullAndEmptyArrays 옵션을 쓰면 빈 배열이나 필드 없는 Document도 유지된다.
LEFT JOIN처럼 동작하고 싶을 때 필요하다.

### `$facet`: 하나의 쿼리로 여러 집계를

하나의 입력 데이터셋에 대해 여러 파이프라인을 동시에 실행한다.

```json
{
  "$facet": {
    "by_category": [
      { "$group": { "_id": "$category", "count": { "$sum": 1 } } }
    ],
    "by_month": [
      {
        "$group": {
          "_id": { "$month": "$created_at" },
          "total": { "$sum": "$amount" }
        }
      }
    ],
    "total_count": [{ "$count": "count" }]
  }
}
```

대시보드를 만들 때 유용하다.
카테고리별 건수, 월별 매출, 전체 건수를 한 번의 쿼리로 전부 구한다.
각 facet은 독립적으로 실행된다.
다만 전체 결과가 16MB를 넘으면 실패한다.

### allowDiskUse

Aggregation은 기본적으로 메모리에서 실행된다.
각 스테이지의 메모리 제한은 100MB. 초과하면 에러가 발생한다.

```json
db.orders.aggregate([...], { allowDiskUse: true })
```

이 옵션을 켜면 100MB를 넘는 스테이지가 임시 파일을 디스크에 쓸 수 있다.
느려지지만 실패하지는 않는다.
대량 데이터 집계에서는 사실상 필수다.
다만 이게 켜져야 한다는 건 데이터가 너무 많다는 신호이기도 하다.
`$match`를 앞에 둬서 데이터를 줄이거나 `$project`로 불필요한 필드를 제거하는 게 먼저다.
디스크를 쓰기 전에 파이프라인을 최적화하라.

### 파이프라인 최적화

MongoDB는 내부적으로 파이프라인을 최적화한다.
하지만 한계가 있다. 직접 최적화하는 것이 낫다.

[`$match` + `$match` 병합]
연속된 $match는 하나로 합쳐진다. 자동.

[`$match`를 `$project` 앞으로]

`$project` 뒤의 `$match`가 `$project`의 필드만 쓴다면
MongoDB가 순서를 바꿔준다. 자동.

[수동으로 해야 하는 것]
`$lookup` 전에 `$match`로 줄이기.
`$unwind` 전에 불필요한 필드 제거하기.
`$group`의 `_id`를 단순하게 유지하기.
`explain()`을 쓰면 최적화된 파이프라인을 볼 수 있다.

```json
db.orders.explain().aggregate([...])
```

queryPlanner의 optimizedPipeline에서 확인한다.

### DBA 관점에서의 정리

- `$match`를 파이프라인 앞에 둬라.
- `$project`로 필요한 필드만 남겨라.
- `$lookup`의 비용을 과소평가하지 마라.
- allowDiskUse의 의미를 이해하라.
- 인덱스를 타는 스테이지와 못 타는 스테이지를 구분하라.

Aggregation Pipeline은 SQL의 대체재가 아니다.
SQL은 "무엇을 원하는가"를 선언하고 Pipeline은 "어떻게 변환할 것인가"를 서술한다.
선언적 사고와 절차적 사고의 차이다.
RDB에서 복잡한 서브쿼리를 짜던 경험이 Pipeline의 스테이지 설계에 그대로 쓰인다.
다만 파이프라인은 순서가 곧 성능이다.
같은 결과를 내는 두 파이프라인의 비용이 100배 차이 날 수 있다.
SQL의 GROUP BY가 할 수 있는 건 Pipeline도 할 수 있다.
Pipeline이 할 수 있는 건 GROUP BY로는 못 하는 것도 있다.

## MongoDB 운영: 보안, 백업, 그리고 Atlas

설계가 끝나면 운영이 시작된다. 운영은 화려하지 않다.
백업이 돌아가는지, 인증이 켜져 있는지, 디스크가 차지 않았는지.
사고가 나기 전에는 아무도 관심 없다.
사고가 나면 전부 운영의 책임이다.

- 인증 없이 MongoDB를 노출하지 마라.
- Role 기반 접근 제어를 설계하라.
- 백업은 복구 테스트까지가 백업이다.
- Change Streams의 활용 범위를 파악하라.
- Atlas와 Self-managed의 트레이드오프를 이해하라.

운영은 평소에 보이지 않는다. 사고가 나면 전부가 된다.

### 인증(Authentication)

MongoDB는 기본 설치 시 인증이 꺼져 있다.
아무나 접속해서 아무 데이터나 볼 수 있다.
2017년에 인증 없는 MongoDB가 대량으로 랜섬웨어에 당했다.
인터넷에 노출된 MongoDB를 봇이 찾아서 데이터를 삭제하고 "비트코인을 보내라"는 메시지를 남겼다.
인증을 켜는 건 기본이다.

[SCRAM]
기본 인증 메커니즘.
username/password 기반.
SCRAM-SHA-256이 현재 표준이다.

[x.509]
인증서 기반 인증.
TLS와 함께 사용한다.
서비스 간 통신에서 비밀번호 없이 인증할 때.

[LDAP]
기업 디렉토리 서비스와 연동.
Active Directory와 통합할 때.

### 인가(Authorization)와 RBAC

인증은 "누구인가"를 확인하는 것이다. 인가는 "무엇을 할 수 있는가"를 결정하는 것이다.
MongoDB는 Role-Based Access Control을 쓴다.

[Built-in Roles]
read: 읽기만.
readWrite: 읽기 + 쓰기.
dbAdmin: 인덱스 관리, 통계 확인.
userAdmin: 사용자/롤 관리.
clusterAdmin: 클러스터 관리.

[Custom Roles]
세밀한 권한이 필요하면 직접 만든다.
특정 Collection에만 읽기 권한을 주거나
특정 액션만 허용할 수 있다.
원칙은 최소 권한이다.
애플리케이션에 root 권한을 주지 않는다.
readWrite만 주고 dbAdmin은 DBA만 가진다.

### 암호화

[전송 중 암호화 (In-Transit)]
TLS/SSL로 클라이언트-서버 간 통신을 암호화한다.
Replica Set 멤버 간 통신도.
프로덕션에서는 필수다.

[저장 시 암호화 (At-Rest)]
디스크에 저장된 데이터를 암호화한다.
WiredTiger가 지원한다.
AES-256-CBC.
서버가 물리적으로 탈취돼도 데이터를 읽을 수 없다.

[Client-Side Field Level Encryption]
특정 필드만 클라이언트에서 암호화해서 저장한다.
주민번호, 카드번호 같은 민감 데이터.
서버에서도 복호화할 수 없다.
키를 가진 클라이언트만 읽을 수 있다.

Atlas에서는 이 세 가지가 모두 기본 또는 한 클릭이다.
Self-managed에서는 직접 구성해야 한다.

### Audit Log

누가 언제 무엇을 했는지 기록하는 것이다.
보안 사고가 났을 때 추적의 근거가 된다.
Enterprise 버전에서만 지원된다. Atlas에서는 기본 제공.
기록할 수 있는 이벤트. 인증 성공/실패. CRUD 연산. 사용자/롤 변경. DDL(Collection 생성/삭제).
모든 걸 기록하면 로그가 폭발한다.
필요한 이벤트만 필터링해서 기록하는 게 실무다.
금융, 의료 등 컴플라이언스가 필요한 도메인에서는 Audit Log가 선택이 아니라 필수다.

### 백업: mongodump

가장 간단한 백업 도구다. 논리적 백업. BSON 형태로 export한다.
장점은 단순함이다. Collection 단위, DB 단위, 전체 백업 가능.
복원도 mongorestore로 간단하다.
단점은 느리다는 것이다.
대량 데이터에서는 시간이 오래 걸린다.
백업 중 일관성이 보장되지 않을 수 있다.
`--oplog` 옵션을 써야 point-in-time 복원이 가능하다.
수 GB 이하의 소규모 DB에 적합하다. 수 TB 규모에서는 다른 방법을 써야 한다.

### 백업: Filesystem Snapshot

스토리지 레벨에서 스냅샷을 찍는다. EBS Snapshot, LVM Snapshot, ZFS Snapshot.
물리적 백업이라 빠르다.
데이터 크기에 관계없이 스냅샷 생성 자체는 순간적이다. (COW 방식이라 실제 복사는 이후에 일어난다.)

[주의사항]
저널링이 켜져 있어야 한다. (WiredTiger 기본 ON)
스냅샷 시점의 저널이 포함돼야 일관된 복원이 가능하다.

대규모 프로덕션에서는 이 방법이 표준이다.
Atlas는 내부적으로 이 방식을 쓴다.
복원은 스냅샷에서 볼륨을 만들고 MongoDB를 시작하면 된다.
WiredTiger가 저널로 자동 복구한다.

### Point-in-Time Recovery

"오늘 오후 2시 상태로 돌려주세요." 이게 Point-in-Time Recovery(PITR)다.
스냅샷 백업 + Oplog의 조합으로 가능하다.
마지막 스냅샷으로 복원하고 스냅샷 이후의 Oplog를 원하는 시점까지 재생한다.
mongorestore의 `--oplogReplay` 옵션.
또는 Ops Manager/Atlas의 PITR 기능.
Atlas에서는 Continuous Backup이 이걸 자동으로 해준다.
최근 N일 이내의 아무 시점으로 복원 가능하다.
Self-managed에서는 직접 구성해야 한다.
Oplog의 크기가 충분히 커야 한다.
Oplog가 덮어쓰여지면 그 이전 시점으로는 돌아갈 수 없다.

### Change Streams

Collection이나 DB의 변경 사항을 실시간으로 구독한다.
CDC(Change Data Capture)다.

```json
const changeStream = db .orders .watch();
changeStream.on("change", (change) => {
    console.log(change.operationType);
    console.log(change.fullDocument);
});
```

insert, update, delete, replace 이벤트를 받는다.

[활용 사례]
실시간 알림. 주문이 생기면 푸시.
캐시 무효화. 데이터가 바뀌면 Redis 갱신.
동기화. MongoDB 변경을 Elasticsearch에 반영.
이벤트 소싱. 변경 이력을 다른 시스템으로 전달.
Oplog 기반이라 Replica Set이 필수다.
resume token으로 끊긴 지점부터 이어서 받을 수 있다.

### Atlas vs Self-managed

[Atlas]
MongoDB가 직접 운영하는 클라우드 서비스다.
배포, 스케일링, 백업, 모니터링이 자동이다.
Atlas Search, Data Federation, Charts 등 부가 기능.
운영 부담이 거의 없다. 하지만 비용이 비싸다.
그리고 세밀한 설정에 제약이 있다.

[Self-managed]
직접 설치하고 운영한다. 모든 설정을 제어할 수 있다.
비용은 인프라 비용만.
하지만 운영 인력이 필요하다.

[판단 기준]
팀에 MongoDB 운영 경험이 있는가.
SLA 요구 수준은 어느 정도인가.
비용 대비 운영 부담을 감당할 수 있는가.

Atlas가 비싸 보여도 DBA 인건비를 포함하면 Atlas가 싸다는 계산이 나오기도 한다.

### 버전 업그레이드

MongoDB는 메이저 버전 간 직접 업그레이드를 지원하지 않는다.
4.4 → 5.0 → 6.0 → 7.0. 한 단계씩만 올릴 수 있다.

[업그레이드 전 반드시 확인할 것]
Feature Compatibility Version(FCV)을 현재 버전으로 설정했는지.
deprecated된 기능을 쓰고 있는지.
드라이버가 새 버전을 지원하는지.

Replica Set에서는 Rolling Upgrade가 가능하다.
Secondary부터 하나씩 올리고 마지막에 Primary를 stepdown 시키고 올린다.
다운타임 없이 업그레이드할 수 있다.
Sharded Cluster는 더 복잡하다.
Config Server → Shard → mongos 순서를 지켜야 한다.

### DBA 관점에서의 정리

- 인증 없이 MongoDB를 노출하지 마라.
- Role 기반 접근 제어를 설계하라.
- 백업은 복구 테스트까지가 백업이다.
- Change Streams의 활용 범위를 파악하라.
- Atlas와 Self-managed의 트레이드오프를 이해하라.

운영은 개발보다 지루하다.
같은 모니터링을 매일 보고 같은 백업이 매일 돌고 같은 알림이 매일 울린다.
하지만 백업이 실패한 날 사고가 난다.
인증을 안 건 서버가 뚫린다.
디스크가 찬 서버가 새벽에 죽는다.
지루한 일을 빠짐없이 하는 것. 그게 운영이다.
운영은 평소에 보이지 않는다. 사고가 나면 전부가 된다.

## 지도 서비스와 DB: 내 주변 1km가 풀스캔이 되는 이유

"내 주변 음식점 찾기." 사용자에게는 버튼 하나다.
DB에게는 수학 문제다. 위도와 경도.
두 개의 숫자로 지구 위의 한 점을 표현한다.
"내 주변 1km"는 이 점에서 반경 1km 안에 있는 모든 행을 찾으라는 뜻이다.
일반 인덱스는 한 축으로만 정렬한다.
위도 순서로 정렬하면 경도를 모르고 경도 순서로 정렬하면 위도를 모른다.
2차원 공간을 1차원 인덱스로 검색하는 것. 그래서 풀스캔이 된다.

- 위도/경도를 일반 컬럼에 넣고 BETWEEN으로 찾지 마라.
- 공간 인덱스가 필요하면 처음부터 설계에 넣어라.
- Geohash는 읽기 캐시와 근접 검색에 유리하다.
- 거리 계산은 DB보다 애플리케이션에서 하라.

공간 쿼리의 성능은 인덱스가 아니라 후보군 크기가 결정한다.

### BETWEEN의 함정

가장 직관적인 방법이다.
내 위치에서 위도/경도 범위를 잡고 BETWEEN으로 검색한다.

```sql
SELECT * FROM restaurants
WHERE latitude BETWEEN 37.49 AND 37.51
AND longitude BETWEEN 127.02 AND 127.04
```

인덱스가 latitude에 걸려 있다면 위도 범위는 인덱스를 탄다.
그런데 경도는?
복합 인덱스 `(latitude, longitude)`를 만들어도 range 조건이 첫 컬럼에 걸리면 두 번째 컬럼은 인덱스를 활용하지 못한다.
위도가 37.49~37.51인 행을 전부 읽고 그 안에서 경도를 필터링한다.
서울 전체의 음식점이 수십만 개면 위도 범위만으로 수만 건이 걸려온다.

### 공간 인덱스가 필요한 이유

B-Tree는 1차원이다. 숫자를 정렬해서 범위를 찾는다.
공간 데이터는 2차원이다. 위도와 경도가 동시에 가까운 것을 찾아야 한다.
R-Tree가 이 문제를 푼다.
2차원 공간을 겹치는 사각형으로 나누고 사각형 단위로 인덱스를 만든다.
검색할 때는 "이 범위와 겹치는 사각형"을 찾고 그 안의 점들만 확인한다.
전체를 스캔하지 않는다.
MySQL의 SPATIAL INDEX가 R-Tree 기반이다.
PostgreSQL의 GiST도 비슷한 구조다.
일반 인덱스로는 절대 풀 수 없는 문제를 공간 인덱스가 효율적으로 풀어준다.

### MySQL SPATIAL INDEX

MySQL 5.7부터 InnoDB에서 SPATIAL INDEX를 지원한다.

```sql
CREATE TABLE restaurants (
    restaurant_id BIGINT PRIMARY KEY,
    location POINT NOT NULL SRID 4326,
    SPATIAL INDEX (location)
);
```

검색은 ST_Contains나 ST_Within으로 한다.
SPATIAL INDEX를 타면 범위 안의 후보만 빠르게 추려낸다.
다만 MySQL의 공간 함수는 기능이 제한적이다.
복잡한 공간 연산이 필요하면 PostgreSQL의 PostGIS가 더 적합하다.

### PostGIS라는 선택지

PostgreSQL에 PostGIS를 얹으면 본격적인 공간 DB가 된다.
GiST 인덱스가 R-Tree 역할을 한다.
함수가 풍부하다.

```sql
SELECT * FROM restaurants
WHERE ST_DWithin(
    location,
    ST_SetSRID(ST_MakePoint(127.03, 37.50), 4326),
    1000
)
```

ST_DWithin은 "이 점에서 1000m 이내"를 의미한다.
인덱스를 타고 효율적으로 검색한다.
도로를 따른 거리 계산, 다각형 안에 포함된 점 찾기, 교차 영역 계산.
지도 서비스를 본격적으로 만든다면 PostGIS는 사실상 표준이다.

### Geohash로 공간을 문자열로

Geohash는 2차원 좌표를 하나의 문자열로 변환하는 기법이다.
서울 강남역 부근이면 "wydm9q" 정도다.
같은 접두사를 공유하면 가까운 위치다.
이게 왜 유용한가.
문자열이면 B-Tree 인덱스를 탈 수 있다.
공간 인덱스가 없는 시스템에서도 `LIKE 'wydm9%'`로 근접 검색이 가능하다.
Redis의 GEO 명령도 내부적으로 Geohash를 쓴다.
DynamoDB처럼 공간 인덱스가 없는 DB에서도 Geohash를 파티션 키로 쓰면 범위 검색이 된다.
다만 Geohash 격자의 경계에서 가까운 점이 다른 해시에 속하는 문제가 있다.
인접 격자도 함께 검색해야 정확하다.

### 배달 앱에서 "내 주변 음식점"이 DB를 치는 방식

배달 앱을 열면 현재 위치 기준으로 음식점 목록이 뜬다.
이 요청이 어떻게 처리될까.

[1단계. 내 위치에서 반경 3km 안의 음식점을 찾는다]
공간 인덱스나 Geohash로 후보를 추린다.

[2단계. 후보 중 영업 중인 곳을 필터링한다]
영업 시간, 휴무일, 배달 가능 여부.
여기서 JOIN이 발생한다.

[3단계. 정렬한다]
거리순, 평점순, 주문 많은 순.
정렬 기준마다 다른 연산이 필요하다.

지도를 드래그할 때마다 이 쿼리가 다시 날아간다.
사용자가 지도를 조금만 움직여도 새로운 범위의 음식점을 다시 검색한다.
캐시 없이 DB에 직접 때리면 사용자 수에 비례해서 쿼리가 쏟아진다.

### 거리 계산을 어디서 할 것인가

"이 음식점까지 1.2km"라는 표시. 이 거리를 DB에서 계산할까, 앱에서 계산할까.
DB에서 하면 정확하지만 느리다.
모든 후보에 대해 삼각함수 연산을 해야 한다.
후보가 1000개면 1000번의 수학 연산이 DB에서 돌아간다.
실무에서는 2단계로 나눈다.
DB는 사각형 범위로 후보를 빠르게 추린다.
정확한 원형 거리 계산은 애플리케이션에서 한다.
DB가 1000개를 추리고 앱이 그중 반경 안의 800개를 골라낸다.
DB에는 가벼운 범위 쿼리만 남긴다.
공간 쿼리의 성능은 인덱스의 종류보다 후보군의 크기가 결정한다.
후보를 줄이는 것이 핵심이다.

### DBA 관점에서의 정리

지도 서비스는 쉬워 보인다.
좌표 두 개를 저장하고 가까운 걸 찾으면 된다.
그런데 "가까운 것을 찾는다"는 연산이 DB에게는 전혀 자연스럽지 않다.
DB는 정렬된 데이터에서 범위를 찾는 데 최적화돼 있다.
2차원 근접 검색은 그 구조에 맞지 않는다.

- 위도/경도를 일반 컬럼에 넣고 BETWEEN으로 찾지 마라.
- 공간 인덱스가 필요하면 처음부터 설계에 넣어라.
- Geohash는 읽기 캐시와 근접 검색에 유리하다.
- 거리 계산은 DB보다 애플리케이션에서 하라.
- 공간 쿼리의 성능은 인덱스가 아니라 후보군 크기가 결정한다.

배달 앱을 열 때마다 사용자는 지도를 보고 있지만 DB는 수학 시험을 치르고 있다.
공간 데이터를 다루려면 인덱스 전략부터 달라야 한다.
일반 B-Tree의 세계에서 한 발 벗어나야 한다.

## DynamoDB vs MongoDB: 서버리스 NoSQL의 두 철학

NoSQL을 쓰겠다고 결정한 다음에 가장 먼저 만나는 갈림길이 있다.
DynamoDB로 갈 것인가. MongoDB로 갈 것인가.
둘 다 도큐먼트를 저장한다.
둘 다 매니지드로 운영할 수 있다.
둘 다 수평 확장을 지원한다.
그런데 설계 철학이 완전히 다르다.
DynamoDB는 접근 패턴을 먼저 정한다.
MongoDB는 데이터를 먼저 넣고 나중에 질문한다.

- 과금 모델이 쿼리 설계를 바꾼다는 걸 이해하라.
- DynamoDB의 단일 테이블 설계를 두려워하지 마라.
- MongoDB의 유연함이 공짜가 아님을 기억하라.
- 인덱스 전략이 비용과 성능을 결정한다.
- 워크로드 패턴을 먼저 분석하고 선택하라.

과금 방식이 다르면 설계가 달라진다. 설계가 다르면 운영이 달라진다.

### DynamoDB의 철학

DynamoDB는 AWS가 만든 Key-Value 스토어다. 정확히는 Key-Value + 도큐먼트 하이브리드다.
모든 접근은 파티션 키로 시작한다. 파티션 키 없이는 아무것도 할 수 없다.
풀 스캔은 가능하지만 과금 폭탄이다.
테이블을 설계하기 전에 "어떤 쿼리를 할 것인가"를 먼저 정해야 한다.
접근 패턴이 곧 스키마다.
서버가 없다. 프로비저닝할 인스턴스가 없다.
용량 모드만 선택하면 AWS가 알아서 확장한다.
이 단순함이 DynamoDB의 강점이다.
운영할 것이 거의 없다.

### MongoDB의 철학

MongoDB는 도큐먼트 모델의 대표다. JSON 같은 구조를 그대로 저장한다.
스키마가 유연하다. 같은 컬렉션 안에서 문서마다 필드가 달라도 된다.
쿼리가 자유롭다. 어떤 필드로든 검색할 수 있다.
집계 파이프라인으로 복잡한 분석도 가능하다.
정규표현식, 지리공간 쿼리, 텍스트 검색까지 지원한다.
Atlas를 쓰면 매니지드로 운영할 수 있다.
DocumentDB는 MongoDB 호환 API를 제공하지만 내부 엔진이 다르다.
"일단 넣고 나중에 질문한다." 이 접근이 MongoDB의 출발점이다.

### 과금 모델이 설계를 바꾸는 이유

DynamoDB의 과금은 읽기/쓰기 용량 단위다. RCU(Read Capacity Unit)와 WCU(Write Capacity Unit).
4KB 이하의 strongly consistent read가 1 RCU. 1KB 이하의 write가 1 WCU.
이게 의미하는 건 큰 아이템을 자주 읽으면 비싸다는 것이다.
그래서 DynamoDB 설계의 핵심은 읽기를 줄이는 것이다.
한 번의 쿼리로 필요한 데이터를 전부 가져온다.
조인이 없으니 관련 데이터를 같은 아이템에 넣는다.
MongoDB는 인스턴스 기반 과금이다.
Atlas는 클러스터 티어별 시간당 요금.
쿼리를 많이 하든 적게 하든 비용이 같다.
대신 인스턴스 스펙이 부족하면 느려진다.
과금 구조가 다르니 최적화 방향도 다르다.

### 단일 테이블 설계 vs 자유로운 컬렉션

DynamoDB의 단일 테이블 설계는 악명이 높다.
사용자, 주문, 상품을 한 테이블에 넣는다.
파티션 키에 `USER#123`, `ORDER#456`을 쓴다.
정렬 키로 관계를 표현한다.

```text
PK=USER#123, SK=PROFILE -> 사용자 정보
PK=USER#123, SK=ORDER#001 -> 주문 1
PK=USER#123, SK=ORDER#002 -> 주문 2
```

한 번의 Query로 사용자와 주문을 함께 가져온다. RCU를 아끼는 설계다.
MongoDB라면 users와 orders를 분리한다.
`$lookup`으로 조인하거나 필요하면 임베딩으로 넣는다. 직관적이다.
DynamoDB는 효율적이지만 진입 장벽이 높다.
MongoDB는 직관적이지만 대규모에서 비용이 커진다.

### 쿼리 유연성의 차이

MongoDB는 어떤 필드든 쿼리할 수 있다.
인덱스가 없어도 일단 동작한다.
느리지만 결과는 나온다.
DynamoDB는 파티션 키 없이 쿼리할 수 없다.
GSI(Global Secondary Index)를 만들어야 한다.
GSI도 별도의 RCU/WCU를 소모한다.
"이 사용자의 최근 주문 3건" 같은 패턴은 DynamoDB가 강하다.
파티션 키 + 정렬 키로 즉시 응답한다.
"지난달 취소된 주문 중 금액이 10만 원 이상인 것"은 DynamoDB가 약하다.
필터 표현식은 스캔 후 거르는 것이지 스캔 자체를 줄이지 않는다.
MongoDB에서는 복합 인덱스 하나면 된다.
이 차이가 워크로드 선택의 핵심이다.

### 언제 DynamoDB를 써야 하는가

접근 패턴이 명확할 때.
"이 키로 이 데이터를 가져온다"가 확정돼 있을 때.
트래픽이 예측 불가할 때.
서버리스 아키텍처에서 Lambda와 함께 쓸 때.
Auto scaling이 매끄럽다.
밀리초 단위 응답이 필수일 때.
DAX(인메모리 캐시)를 붙이면 마이크로초까지 간다.
운영 부담을 극한까지 줄이고 싶을 때.
서버도 없고, 패치도 없고, 백업도 자동이다.
세션 스토어, 사용자 프로필, IoT 이벤트, 게임 리더보드, 장바구니.
키 기반 접근이 지배적인 도메인이 후보다.

### 언제 MongoDB를 써야 하는가

스키마가 자주 바뀔 때.
초기 스타트업에서 기능이 매주 추가될 때.
필드를 추가하는 데 ALTER TABLE이 필요 없다.
쿼리 패턴이 유동적일 때.
분석 요건이 수시로 바뀌는 환경.
"이번 달은 이 기준으로 집계해주세요"가 잦을 때.
도큐먼트 구조가 복잡할 때.
중첩된 배열, 가변 필드, 다형성 데이터.
RDBMS로 표현하면 조인이 5개 이상 필요한 구조.
콘텐츠 관리, 제품 카탈로그, 사용자 생성 데이터, 로그 집계, 실시간 분석.
구조가 유연해야 하는 도메인이 후보다.

### DBA 관점에서의 정리

- 과금 모델이 쿼리 설계를 바꾼다는 걸 이해하라.
- DynamoDB의 단일 테이블 설계를 두려워하지 마라.
- MongoDB의 유연함이 공짜가 아님을 기억하라.
- 인덱스 전략이 비용과 성능을 결정한다.
- 워크로드 패턴을 먼저 분석하고 선택하라.

DynamoDB는 제약이 많은 대신 그 제약 안에서는 예측 가능한 성능을 보장한다.
MongoDB는 자유가 많은 대신 그 자유가 성능 문제로 돌아올 수 있다.
"NoSQL 쓰겠습니다"는 시작이 아니다. "어떤 NoSQL을 왜 쓰겠습니다"가 시작이다.
과금 방식이 다르면 설계가 달라진다.
설계가 다르면 운영이 달라진다.
