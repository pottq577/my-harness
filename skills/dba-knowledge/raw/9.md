# BEAR DBA

## 서브쿼리 vs JOIN: 같은 결과인데 속도가 다른 이유

같은 결과를 돌려주는 두 개의 쿼리가 있다.
하나는 서브쿼리로 썼고, 하나는 JOIN으로 썼다. 결과 집합은 동일하다.
그런데 하나는 0.1초, 하나는 30초.
옵티마이저가 둘을 같은 실행 계획으로 바꿔준다면 차이가 없을 것이다.
문제는 바꿔주지 못하는 경우가 있다는 것이다.

- 서브쿼리를 JOIN으로 변환할 수 있는지 먼저 확인하라.
- Correlated Subquery는 N+1 문제를 의심하라.
- Derived Table은 임시 테이블 생성 여부를 확인하라.
- MySQL 버전별 옵티마이저 차이를 인지하라.
- 반드시 EXPLAIN으로 실행 계획을 확인하라.

### 옵티마이저의 서브쿼리 변환

좋은 옵티마이저는 서브쿼리를 JOIN으로 변환한다.

```sql
-- 원본: 서브쿼리
SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users
);
-- 변환 후: Semi-JOIN
SELECT o.* FROM orders o
SEMI JOIN vip_users v
ON o.user_id = v.user_id;
```

이걸 "서브쿼리 플래트닝" 또는 "Semi-JOIN 변환"이라고 부른다.
MySQL 8.0, PostgreSQL, Oracle 모두 이 변환을 시도한다.
변환에 성공하면 서브쿼리와 JOIN의 성능 차이가 없다.
문제는 변환이 불가능한 경우다.
서브쿼리에 LIMIT이 있거나, UNION이 있거나, 집계 함수가 있거나, 상관(Correlated) 서브쿼리일 때 옵티마이저가 손을 놓는다.

### Correlated Subquery의 N+1 문제

상관 서브쿼리는 바깥 행마다 안쪽 쿼리를 실행한다.

```sql
SELECT o.order_id, o.amount,
(SELECT u.user_name
FROM users u
WHERE u.user_id = o.user_id)
FROM orders o;
```

orders가 100만 행이면 안쪽 SELECT가 100만 번 실행된다.
ORM의 N+1 문제와 같은 구조다.
바깥 루프가 안쪽 쿼리를 반복 호출한다.
users에 인덱스가 있으면 한 번의 조회는 빠르다.
하지만 100만 번이면 느리다.
JOIN으로 바꾸면 한 번에 끝난다.

```sql
SELECT o.order_id, o.amount, u.user_name
FROM orders o
LEFT JOIN users u ON o.user_id = u.user_id;
```

Hash Join이든 Nested Loop이든 한 번의 스캔으로 처리된다.

### Derived Table의 실체

FROM절에 서브쿼리를 쓰면 그걸 Derived Table(인라인 뷰)이라고 부른다.

```sql
SELECT d.user_id
FROM (
SELECT user_id, SUM(amount) AS total_amount
FROM orders
GROUP BY user_id
) d
WHERE d.total_amount > 100000;
```

이 서브쿼리의 결과가 어디에 저장되는가.
MySQL은 임시 테이블을 만든다.
디스크에 쓸 수도 있고 메모리에 둘 수도 있다.
MySQL 8.0부터는 Derived Table Merge가 가능하다.
옵티마이저가 서브쿼리를 바깥 쿼리에 합쳐서 임시 테이블 없이 처리한다.
하지만 GROUP BY, DISTINCT, LIMIT, UNION이 있으면 Merge가 불가능하다.
위 예시도 GROUP BY 때문에 임시 테이블이 생긴다.
결과가 크면 디스크에 쓴다.
그 순간 속도가 급격히 떨어진다.

### MySQL 5.6 이전의 서브쿼리 비극

MySQL 5.5까지는 서브쿼리 최적화가 처참했다.

```sql
SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users
);
```

이 쿼리를 5.5는 이렇게 실행했다.
orders의 모든 행에 대해 vip_users를 매번 풀스캔.
IN 서브쿼리를 상관 서브쿼리로 변환해버린 것이다.
orders 100만 행, vip_users 1만 행이면 1만 행 풀스캔을 100만 번. 사실상 100억 행 스캔.
5.6에서 Materialization이 도입되면서 서브쿼리 결과를 임시 테이블에 한 번만 만들고 재사용하게 됐다.
5.7에서 Semi-JOIN 변환이 개선됐고 8.0에서 Hash Join이 추가되면서 서브쿼리와 JOIN의 성능 차이가 크게 줄었다.
하지만 오래된 코드베이스에는 5.5 시절의 "서브쿼리 피하기" 습관이 아직도 남아 있다.

### 실행 계획으로 확인하는 법

서브쿼리가 어떻게 처리되는지는 EXPLAIN으로만 확인할 수 있다.

```sql
EXPLAIN SELECT * FROM orders
WHERE user_id IN (
SELECT user_id FROM vip_users);
```

봐야 할 것들이 있다.

- select_type이 SUBQUERY면 별도 실행.
- DEPENDENT SUBQUERY면 상관 서브쿼리.

이 둘이 보이면 위험하다.
MATERIALIZED면 임시 테이블로 한 번 만든 것.
SIMPLE이면 JOIN으로 변환된 것.
이 둘은 괜찮다.
PostgreSQL에서는 EXPLAIN ANALYZE로 실제 실행 시간까지 확인한다.
loops 값이 1이면 좋고 10만이면 N+1이다.

### DBA 관점에서의 정리

"서브쿼리는 느리고 JOIN은 빠르다"는 반만 맞는 말이다.
옵티마이저가 변환해주면 둘은 같다.
변환하지 못하면 서브쿼리가 느리다.
문제는 변환 여부를 쿼리를 보는 것만으로는 알 수 없다는 것이다.
DB 버전, 통계 정보, 데이터 분포에 따라 같은 쿼리도 다른 계획이 나온다.

- 서브쿼리를 JOIN으로 변환할 수 있는지 먼저 확인하라.
- Correlated Subquery는 N+1 문제를 의심하라.
- Derived Table은 임시 테이블 생성 여부를 확인하라.
- MySQL 버전별 옵티마이저 차이를 인지하라.
- 반드시 EXPLAIN으로 실행 계획을 확인하라.

쿼리를 쓰는 사람은 결과가 맞는지 본다.
DBA는 실행 계획이 맞는지 본다.
같은 결과를 내는 수많은 길 중에서 가장 싸게 도착하는 길을 고르는 것.
그게 쿼리 튜닝의 본질이다.
