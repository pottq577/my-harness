# BEAR DBA

## 푸시 알림이 DB에 주는 영향: 1000만 명에게 쿠폰을 보내면 생기는 일

마케팅 팀에서 말한다. "오늘 저녁 6시에 전체 푸시 나갑니다."
개발팀은 서버를 늘리고 DBA는 모니터링을 띄운다.
1000만 명에게 알림이 간다. 10%만 열어도 100만 명이다.
그 100만 명이 3초 안에 같은 페이지를 연다.
크롤러는 밖에서 오는 트래픽이었다. 푸시는 우리가 스스로 만든 트래픽이다.
더 무섭다.

### Thundering Herd

양 떼가 동시에 몰려가는 현상.
분산 시스템에서는 이걸 Thundering Herd라 부른다.
푸시 알림은 모든 사용자에게 거의 동시에 도착한다.
평소 하루에 걸쳐 분산되던 요청이 몇 초 안에 쏟아진다.
트래픽이 많은 것과 한 번에 몰리는 것은 DB 입장에서 완전히 다른 문제다.
점심시간 트래픽은 30분에 걸쳐 올라간다. DB는 적응할 수 있다.
푸시 트래픽은 절벽처럼 솟는다. 적응할 시간이 없다.

### 어떤 쿼리가 폭발하는가

푸시의 종류에 따라 DB에 닿는 쿼리가 다르다.

[쿠폰 발급형]
사용자가 쿠폰을 수령한다.
재고를 차감하는 UPDATE 하나에 모든 요청이 몰린다.
같은 행, 같은 컬럼. Hot Row 경합.

[이벤트 페이지형]
랜딩 페이지를 연다.
상품 목록과 가격을 읽는 SELECT가 폭발한다.
Reader에 읽기 부하가 집중된다.

[주문 유도형]
할인 쿠폰으로 주문이 밀린다.
주문 INSERT + 재고 UPDATE + 결제 INSERT.
Writer에 쓰기가 몰린다.

### Hot Row: 가장 위험한 패턴

쿠폰 재고가 1만 개다. 1000만 명에게 푸시를 보냈다. 모든 요청이 같은 행을 갱신한다.

```sql
UPDATE coupon
SET stock = stock - 1
WHERE coupon_id = 12345
AND stock > 0
```

빠른 쿼리다. 인덱스도 타고 한 행만 건드린다.
그런데 동시에 수천 명이 실행하면 한 행에 row lock이 걸린다.
한 명이 커밋해야 다음 한 명이 들어간다. 나머지는 전부 줄을 선다.
큐가 아니라 전쟁이다.

### 커넥션 풀이 먼저 죽는다

DB가 느려지는 게 아니다. DB 앞의 커넥션 풀이 먼저 고갈된다.
평소에는 쿼리가 빨리 끝나고 커넥션이 즉시 반환된다. 풀이 넉넉하다.
그런데 Hot Row로 lock wait가 걸리면 한 쿼리가 수백 ms를 점유한다. 커넥션이 돌아오지 않는다.
풀이 차면 대기 큐에 쌓이고 타임아웃이 터지고 사용자는 에러를 본다.
CPU도 정상, 메모리도 정상. 커넥션만 0이다.
장애 원인을 DB에서 찾으면 아무것도 안 보인다.

### Cache Stampede

캐시가 있으면 괜찮을까. 평소에는 괜찮다.
이벤트 페이지를 캐시에 올려두면 대부분의 요청은 캐시에서 끝난다.
그런데 캐시에도 TTL이 있다. TTL이 만료되는 순간 수십만 명의 요청이 동시에 캐시 미스를 맞는다.
전부 DB로 간다. 이걸 Cache Stampede라 한다.
한 명만 DB에 다녀와서 캐시를 채우면 되는데 만 명이 동시에 간다.
캐시가 있어도 캐시가 없어지는 순간이 문제다.

### 실제 사례: 선착순 쿠폰

선착순 1000장. 푸시가 나가고 30초.
쿠폰 테이블의 한 행에 UPDATE가 쏟아진다.
대기 시간이 길어질수록 lock wait timeout에 걸려 롤백된다.
실패한 요청이 재시도를 한다. 사용자도 "쿠폰 받기"를 다시 누른다.
프론트에서 버튼을 비활성화해도 새로고침으로 우회한다. 트래픽이 줄지 않고 오히려 늘어난다.
실패가 재시도를 부르고 재시도가 부하를 키운다.
1000장짜리 쿠폰이 DB에 10만 건의 UPDATE를 만든다.

### 실제 사례: 타임세일 랜딩

오후 5시 타임세일. 4시 55분에 푸시가 나간다.
사용자는 페이지를 열어놓고 기다린다. 5시 정각에 새로고침을 누른다. 동시에.
타임세일 상품은 방금 가격이 바뀌었다. 캐시가 무효화된 상태다.
수십만 명의 요청이 전부 DB까지 내려온다. Reader가 순간적으로 CPU 한계에 닿는다.
평소와 같은 쿼리다. 바뀐 건 동시 실행 수뿐이다.
DB는 쿼리가 아니라 동시성에 죽는다.

### 방어: 앱과 인프라에서

DB까지 오기 전에 끊어야 한다.

[푸시 분산 발송]
1000만 건을 한 번에 보내지 않는다. 5분에 걸쳐 나눠 보낸다.
이것만으로 피크가 크게 떨어질 수 있다.

[큐 기반 처리]
쿠폰 발급을 동기로 처리하지 않는다. 요청을 큐에 넣고 순차 처리한다.
사용자에게는 "발급 중"을 보여준다.

[캐시 워밍]
이벤트 시작 전에 캐시를 미리 채운다. TTL도 이벤트 시간에 맞춰 조정한다.
Cache Stampede를 원천 차단한다.

[Rate Limiting]
동일 사용자의 반복 요청을 제한한다.
버튼 연타와 새로고침을 앞단에서 끊는다.

### 방어: DB 레벨에서

앞단을 뚫고 들어오면 DB에서도 버텨야 한다.

[Reader 스케일 아웃]
이벤트 전에 Reader를 미리 늘려둔다. 끝나면 다시 줄인다.
읽기 부하에는 이게 가장 직접적이다.

[커넥션 풀 분리]
이벤트용 엔드포인트의 풀을 따로 잡는다.
이벤트 트래픽이 일반 트래픽의 커넥션을 먹지 않게.

[Hot Row 분산]
쿠폰 재고를 한 행에 두지 않는다. 여러 행으로 나눠서 분산 차감한다.
UPDATE가 여러 행에 흩어지면 lock 경합이 그만큼 줄어든다.

### 스케일링으로 안 풀리는 것

"서버를 늘리면 되지 않나?"
읽기는 된다. Reader를 늘리면 SELECT는 분산된다.
쓰기는 안 된다. Writer는 하나다. Hot Row도 하나다.
서버를 아무리 늘려도 한 행에 대한 UPDATE는 직렬 처리다.
이게 푸시 트래픽의 핵심이다. 수평 확장으로 풀리지 않는 병목이 있다.
인프라가 아니라 설계로 풀어야 한다. 큐, 재고 분산, 비동기 처리.
이건 서버의 문제가 아니라 코드의 문제다.

### DBA 관점에서의 정리

크롤링은 밖에서 왔다. 푸시 트래픽은 우리가 만든다.
마케팅이 푸시를 보내겠다고 하면 DBA는 물어야 한다. 몇 시에, 몇 명에게, 어떤 종류인지.
쿠폰이면 Hot Row를 대비하고 타임세일이면 캐시 워밍을 확인하고 Reader를 미리 늘려둔다.
푸시 한 방은 마케팅의 무기다. 그런데 그 무기의 반동은 DB가 맞는다.
사전에 알면 대비할 수 있다. 사후에 알면 장애 보고서를 쓴다.
그 차이가 DBA의 존재 이유다.

## 크롤링이 DB에 주는 영향: 검색엔진이 서비스를 죽이는 순간

새벽 3시에 알람이 울렸다. CPU가 치솟고 커넥션이 가득 찼다.
배포도 없었고 이벤트도 없었다. 범인은 크롤러였다.
Googlebot도 아니고 정체불명의 봇이 상품 목록 페이지를 초당 수백 건씩 긁고 있었다.
크롤링은 외부에서 들어오는 트래픽이다. 우리가 통제할 수 없는 트래픽.
그런데 그 트래픽이 결국 DB까지 닿는다.

### 크롤러는 사람이 아니다

사람은 페이지를 읽고 생각하고 다음을 누른다. 크롤러는 안 그런다.
한 페이지를 받자마자 다음 요청을 보낸다. Think time이 0이다.
사람 100명이 동시에 보는 트래픽과 크롤러 하나가 만드는 트래픽은 DB 입장에서 성격이 다르다.
사람은 한 페이지에 머무는 동안 DB 커넥션이 반환된다.
크롤러는 쉬지 않으니 커넥션을 계속 점유한다.
초당 요청 수로 보면 크지 않아도 커넥션 점유 패턴이 다르다.

### 어떤 쿼리가 문제가 되는가

크롤러가 좋아하는 페이지가 있다.

[상품 목록 / 카테고리 페이지]
페이지네이션을 따라가며 전체 목록을 훑는다.
OFFSET이 깊어질수록 쿼리가 무거워진다.
OFFSET 10000이면 10000건을 읽고 버린다.

[검색 결과 페이지]
쿼리 파라미터를 조합해서 존재하지 않는 검색어까지 시도한다.
캐시를 우회하는 cold query가 쏟아진다.

[상품 상세 페이지]
크롤러가 상품 ID를 순차 탐색하면 삭제된 상품, 비공개 상품까지 조회한다.
없는 데이터를 찾는 쿼리는 인덱스를 끝까지 탄다.

### DB에 나타나는 증상들

크롤링 부하가 심해지면 DB 모니터링에 특징적인 패턴이 나타난다.

[커넥션 포화]
동시 커넥션이 평소의 2~3배까지 올라간다.
max_connections에 도달하면 정상 사용자의 요청도 거부된다.

[Read IOPS 급등]
캐시에 없는 데이터를 계속 요청하니 버퍼풀 히트율이 떨어지고 스토리지 읽기가 폭발한다.

[CPU 사용률 상승]
정렬, 그루핑, 임시 테이블 생성.
목록 페이지 쿼리는 대부분 이걸 동반한다.

[Replication Lag]
Reader에 크롤링 트래픽이 몰리면 Reader의 apply가 밀리면서 lag이 발생하기도 한다.

### 실제 사례: 가격 비교 크롤러

가격 비교 사이트가 있다.
이 사이트의 봇이 상품 가격을 수집하려고 카테고리별 목록을 전수 크롤링한다.
새벽 시간대에 집중적으로 돌린다. 배치 스케줄이겠지.
문제는 이 시간대가 DB 백업이 도는 시간이기도 하다는 것이다.
백업 + 크롤링이 겹치면 Reader 인스턴스의 IOPS가 한계에 닿는다.
백업이 느려지고 크롤링 응답도 느려지고 새벽 배치까지 밀린다.
한 크롤러가 세 가지를 동시에 망가뜨린다.

### 실제 사례: SEO 봇의 무한 크롤링

잘 만든 사이트는 SEO를 신경 쓴다. 그런데 SEO를 잘하면 봇이 더 많이 온다.
sitemap을 제공하면 봇은 sitemap에 있는 URL을 전부 방문한다.
상품이 100만 개면 100만 페이지. URL에 필터 파라미터가 붙으면 더 심하다.
`?sort=price&page=1`, `?sort=date&page=1`, `?sort=price&page=2` 조합이 폭발한다.
봇은 이걸 전부 다른 페이지로 인식한다.
같은 데이터를 다른 파라미터로 반복 조회.
DB 입장에서는 캐시 효율이 바닥으로 떨어진다.

### 실제 사례: 악의적 스크래핑

경쟁사가 가격 정보를 빼간다. 이건 크롤링이 아니라 스크래핑이다.
User-Agent를 위장하고 IP를 로테이션하면서 상품 가격과 재고를 실시간으로 긁는다.
이 트래픽은 rate limiting을 우회한다. 정상 사용자처럼 보이니까.
DB 레벨에서 보면 특정 쿼리 패턴의 실행 횟수가 비정상적으로 높다.
슬로우 쿼리는 아닌데 같은 쿼리가 분당 수천 번 실행된다. QPS는 높은데 unique 쿼리 수는 적다.
이 불균형이 스크래핑의 시그널이다.

### 캐시가 만능이 아닌 이유

"캐시를 두면 되지 않나?"
맞는 말이긴 하다. 그런데 크롤러는 캐시를 무력화하는 데 재능이 있다.
크롤러는 URL 전체를 순회한다.
캐시 키가 URL 기반이면 방문하는 URL마다 캐시 미스가 난다.
long tail 페이지는 평소에 아무도 안 본다. 캐시에 없다.
크롤러가 방문하면 DB까지 직행한다. 캐시 용량에도 한계가 있다.
크롤러가 전수 탐색을 하면 hot data가 캐시에서 밀려나고 정상 사용자의 캐시 히트율까지 떨어진다.
이걸 cache pollution이라고 한다.

### 방어는 DB 밖에서 해야 한다

DB에서 할 수 있는 건 한계가 있다. 방어선은 앞단에 쳐야 한다.

[robots.txt]
기본이지만 선의의 봇만 지킨다.
Googlebot은 존중하지만 스크래퍼는 무시한다.

[Rate Limiting]
IP 기반, User-Agent 기반. WAF나 API Gateway에서 처리.
크롤러의 요청 패턴을 식별해서 제한.

[CDN / 정적 캐시]
목록 페이지를 CDN에 캐시하면 DB까지 요청이 안 내려간다.
TTL을 짧게 잡아도 효과가 크다.

[렌더링 분리]
SSR 대신 ISR이나 정적 생성.
크롤러에게는 미리 만든 HTML을 준다. DB 쿼리 자체를 안 태운다.

### 개발자가 막는 법

크롤러가 DB까지 닿기 전에 코드에서 먼저 끊을 수 있다.

[페이지네이션 방식 전환]
OFFSET 기반은 크롤러의 먹이다.
커서 기반으로 바꾸면 깊은 페이지를 요청해도 성능이 일정하고 페이지 번호를 찍어보는 탐색도 막힌다.

[최대 페이지 제한]
100페이지 이후는 404를 돌려준다.
사람은 100페이지까지 안 간다. 거기까지 가는 건 봇뿐이다.

[파라미터 조합 정규화]
sort, filter, page의 조합이 각각 다른 캐시 키를 만들지 않게 정규화된 순서로 정렬한다.

### DB 레벨에서 할 수 있는 것

앞단 방어가 뚫리면 DB에서도 최소한의 보호가 필요하다.

[Reader 분리]
크롤링 트래픽을 전용 Reader로 보낸다.
이 Reader가 과부하로 죽어도 Writer와 서비스용 Reader는 살아있다.

[커넥션 풀 분리]
크롤링용 커넥션 풀을 따로 둔다.
전체 커넥션의 10%만 할당하면 나머지 90%는 정상 트래픽에 보장된다.

[쿼리 타임아웃]
OFFSET이 남아있다면 max_execution_time으로 끊는다.
깊은 OFFSET 쿼리는 어차피 의미 없다.
크롤러 때문에 서비스가 죽는 건 DB가 착하기 때문이다.
들어오는 건 다 처리하려고 하니까.

### DBA 관점에서의 정리

크롤링은 외부 트래픽이다. DBA가 직접 막을 수는 없다.
하지만 크롤링이 DB를 죽이는 건 DBA가 알아야 한다.
새벽에 IOPS가 튀면 배치만 의심하지 말고 access log를 봐라.
커넥션이 갑자기 차면 배포 이력만 보지 말고 봇을 의심해라.
크롤러는 우리 시스템의 사용자가 아니다. 그런데 DB는 구분을 못 한다.
모든 쿼리를 성실하게 처리한다. 그 성실함이 서비스를 죽인다.
방어는 앞단에서. 감지는 DB에서.
그 사이를 연결하는 게 DBA의 일이다.

## 트랜잭션 격리 수준의 실체: Read Committed에서 Serializable까지

"트랜잭션 격리 수준 네 가지 설명해보세요." 면접에서 이 질문이 나온다.
Read Uncommitted, Read Committed, Repeatable Read, Serializable. 이름을 나열하는 건 누구나 한다.
하지만 "DB가 알아서 해주는 거 아닌가요?"라고 되물으면 대부분 멈춘다.
격리 수준은 DB가 동시성 문제를 어디까지 막아줄지 결정하는 계약이다.
그 계약의 실체를 들여다본다.

### 네 가지 격리 수준

SQL 표준이 정의한 네 단계다.

[Read Uncommitted]
다른 트랜잭션이 아직 커밋하지 않은 데이터도 읽는다. 가장 느슨하다.

[Read Committed]
커밋된 데이터만 읽는다. PostgreSQL의 기본값.

[Repeatable Read]
같은 트랜잭션 안에서 같은 쿼리는 같은 결과를 보장한다. MySQL InnoDB의 기본값.

[Serializable]
트랜잭션이 순서대로 실행된 것처럼 동작한다. 가장 엄격하고, 가장 느리다.
위로 갈수록 빠르고 위험하다. 아래로 갈수록 안전하고 느리다.

### Dirty Read — 커밋되지 않은 것을 읽다

A가 계좌 잔액을 10,000원에서 3,000원으로 UPDATE했다. 아직 COMMIT하지 않았다.
B가 잔액을 조회한다. 3,000원이 보인다. A가 ROLLBACK한다. 잔액은 다시 10,000원이다.
하지만 B는 3,000원을 기준으로 이미 로직을 수행했다.
존재한 적 없는 데이터를 읽은 것이다. 이것이 Dirty Read다.
Read Uncommitted에서만 발생한다. 실무에서 이 수준을 쓰는 경우는 거의 없다.

### Non-Repeatable Read — 같은 쿼리, 다른 결과

트랜잭션 A가 잔액을 조회한다. 10,000원.
트랜잭션 B가 잔액을 5,000원으로 바꾸고 COMMIT한다.
트랜잭션 A가 다시 조회한다. 5,000원.
같은 트랜잭션 안에서 같은 SELECT가 다른 값을 돌려줬다.
이것이 Non-Repeatable Read다. Read Committed에서 발생한다.
"내가 읽은 값이 변하지 않을 거라"는 보장이 없다는 뜻이다.

### Phantom Read — 없던 행이 나타나다

트랜잭션 A가 주문 건수를 센다.

```sql
SELECT COUNT(*) FROM orders
WHERE status = 'PENDING';
-- 결과: 5
```

트랜잭션 B가 새 주문을 INSERT하고 COMMIT한다.
트랜잭션 A가 다시 센다. 결과: 6.
기존 행의 값이 바뀐 게 아니다. 없던 행이 새로 나타난 것이다.
이것이 Phantom Read다. Repeatable Read에서도 발생할 수 있다.
단, MySQL InnoDB는 예외다.

### 격리 수준별 이상 현상 정리

SQL 표준이 정의한 매핑이다.

| 격리 수준        | Dirty Read | Non-Repeatable | Phantom |
| ---------------- | ---------- | -------------- | ------- |
| Read Uncommitted | O          | O              | O       |
| Read Committed   | X          | O              | O       |
| Repeatable Read  | X          | X              | O       |
| Serializable     | X          | X              | X       |

위에서 아래로 갈수록 막아주는 이상 현상이 늘어난다. 대신 락이나 검증 비용이 커진다.
이 표를 외우는 건 쉽다. 문제는 실제 DB 구현이 이 표대로 동작하지 않는다는 것이다.

### MVCC — DB가 격리를 구현하는 방법

락으로 모든 충돌을 막으면 동시성이 바닥을 친다.
읽기가 쓰기를 막고, 쓰기가 읽기를 막는다.
MVCC는 이 문제를 풀었다.
행을 수정할 때 이전 버전을 보존한다.
읽기는 자기 트랜잭션 시점의 스냅샷을 본다.
쓰기는 새 버전을 만든다.
읽기와 쓰기가 서로를 막지 않는다.
현대 DB의 동시성은 MVCC 위에 서 있다.
MySQL은 undo log에서 이전 버전을 재구성한다.
PostgreSQL은 힙에 다중 버전을 직접 저장한다.

### MySQL의 기본: Repeatable Read

InnoDB의 기본 격리 수준이다.
트랜잭션 시작 시점의 스냅샷을 찍고 그 스냅샷을 끝까지 읽는다.
같은 SELECT를 두 번 해도 결과가 같다.
Non-Repeatable Read가 없다.
Phantom Read는? SQL 표준에서는 발생한다고 한다.
하지만 InnoDB는 Gap Lock으로 막는다.
인덱스 레코드 사이의 빈 공간을 잠가서 다른 트랜잭션의 INSERT를 차단한다.
덕분에 Serializable까지 안 올려도 Phantom Read가 방지된다.
대가는 있다. Gap Lock이 예상치 못한 대기를 만든다.

### PostgreSQL의 기본: Read Committed

PostgreSQL은 Read Committed가 기본이다. MySQL보다 한 단계 느슨하다.
매 SQL문마다 새로운 스냅샷을 찍는다.
트랜잭션 시작 시점이 아니라 각 쿼리 실행 시점의 커밋된 데이터를 본다.
같은 트랜잭션 안에서 같은 SELECT가 다른 결과를 줄 수 있다. Non-Repeatable Read가 발생한다.
왜 이걸 기본으로 선택했을까?
Gap Lock 같은 암묵적 락 범위를 줄이고 동시성을 극대화하겠다는 설계 철학이다.
대부분의 OLTP 워크로드에서는 이 수준으로 충분하다는 판단이다.

### 같은 이름, 다른 동작

MySQL의 Repeatable Read와 PostgreSQL의 Repeatable Read는 같은 이름이지만 동작이 다르다.

[MySQL Repeatable Read]
Gap Lock으로 Phantom Read까지 방지한다.
사실상 Serializable에 가깝다. 하지만 Write Skew는 막지 못한다.

[PostgreSQL Repeatable Read]
SSI의 전 단계.
스냅샷 기반으로 Phantom Read를 방지하되 충돌 시 트랜잭션을 abort한다.
락이 아니라 검증 기반이다.

면접에서 "둘 다 Repeatable Read인데 뭐가 다릅니까?"라는 질문이 나오면 락 기반 vs 검증 기반의 차이를 설명해야 한다.

### Serializable — 언제 필요한가

가장 강한 격리 수준이다. 모든 트랜잭션이 순서대로 실행된 것처럼 동작한다.
MySQL에서는 모든 SELECT가 자동으로 `SELECT ... LOCK IN SHARE MODE`가 된다.
읽기에도 공유 락이 걸린다. 동시성이 크게 떨어진다.
PostgreSQL에서는 SSI(Serializable Snapshot Isolation)를 쓴다.
락 대신 트랜잭션 간 의존성을 추적하고 위반 시 abort + 재시도를 강제한다.
언제 필요한가?
금융 정산, 좌석 예약, 재고 차감처럼 "절대 틀리면 안 되는" 로직에서.
하지만 대부분은 애플리케이션 레벨 락으로 대체한다.

### Lost Update와 Write Skew

격리 수준 표에 없는 이상 현상이 있다.

[Lost Update]
A가 잔액 10,000을 읽고 +3,000을 계산한다.
B도 10,000을 읽고 +5,000을 계산한다.
A가 13,000을 쓴다.
B가 15,000을 쓴다.
A의 +3,000이 사라졌다.

[Write Skew]
당직 의사가 2명일 때 각각 "다른 사람이 있으니 나는 빠져도 되겠지"
두 명 다 빠진다.
각 트랜잭션은 규칙을 지켰지만 결과는 위반이다.

Repeatable Read로도 이 둘을 완전히 막지 못한다.
Serializable이나 명시적 FOR UPDATE가 필요하다.

### 서비스별 격리 수준 선택

모든 서비스에 같은 수준을 쓸 필요는 없다.

[결제/정산]
정합성이 생명이다. `Repeatable Read + FOR UPDATE`.
성능보다 정확성이 우선이다.

[일반 서비스 (주문, 상품)]
Read Committed로 충분한 경우가 대부분이다.
필요한 곳만 SELECT FOR UPDATE로 보호한다.

[로그/분석]
Read Uncommitted도 괜찮다. 다만 서비스로 연관된다면 격리수준을 높여야한다.
근사치만 있으면 되는 집계에 락 비용을 치를 이유가 없다.
격리 수준은 전역 설정이 아니라 트랜잭션 단위로 조절하는 것이다.

### DBA 관점에서의 정리

격리 수준은 성능과 정합성의 트레이드오프다.
MySQL DBA는 Repeatable Read가 기본이므로 Gap Lock으로 인한 대기를 항상 의식해야 한다.
Read Committed로 내리면 Gap Lock이 사라지지만 Phantom Read가 열린다.
PostgreSQL DBA는 Read Committed가 기본이므로 Non-Repeatable Read를 감수하고 있다는 걸 알아야 한다.
Repeatable Read로 올리면 abort 재시도 로직이 필수다.
공통으로 중요한 건 "우리 서비스의 기본 격리 수준이 무엇이고, 그 수준에서 어떤 이상 현상이 발생 가능한가"를 정확히 아는 것이다.

### 마무리

격리 수준은 네 줄짜리 표가 아니다.
같은 이름이 DB마다 다르게 동작하고, 표준에 없는 이상 현상이 실무에서 터진다.
"DB가 알아서 해준다"는 말은 "내가 어디까지 맡겼는지 안다"는 뜻이어야 한다.
Dirty Read는 왜 위험한지, Gap Lock은 왜 존재하는지, Serializable은 왜 느린지.
이걸 설명할 수 있으면 면접에서 "격리 수준"은 끝난 것이다.
하지만 진짜 실력은 운영 중인 서비스의 격리 수준이 뭔지 알고, 그 수준에서 무엇이 깨질 수 있는지 미리 대비하는 데 있다.

## 프로시저는 아직도 쓸 만한가: DB에 로직을 넣는다는 것

10년 전만 해도 비즈니스 로직의 절반은 DB 안에 있었다.
프로시저에 IF문을 넣고 커서를 돌리고 트리거로 후처리를 걸었다.
요즘은 "프로시저 쓰지 마세요"가 정설처럼 통한다.
마이크로서비스, CI/CD, 코드 리뷰. 전부 프로시저와 안 맞는다.
그런데 정말 안 쓰는가. 금융권은 아직도 프로시저 위에서 돌아간다.
배치 처리에서 프로시저를 빼면 느려지는 시스템도 있다.
"쓰지 마"가 아니라 "언제 쓰고 언제 피하는가"가 맞는 질문이다.

### 프로시저의 전성기

1990년대부터 2000년대 중반까지. SI 프로젝트의 표준 아키텍처였다.
애플리케이션은 화면을 그리고 DB가 로직을 처리했다.
프로시저 하나에 수백 줄. 조건 분기, 반복, 예외 처리까지 전부 PL/SQL이나 T-SQL로 작성했다.
이유가 있었다. 앱 서버 성능이 나빴고 네트워크는 느렸다. DB에서 한 번에 처리하는 게 빨랐다.
그리고 Oracle이 그 시대의 왕이었다. Oracle의 PL/SQL은 강력했고 모든 것을 DB 안에서 해결하는 게 자연스러웠다.

### 프로시저가 하는 일

저장 프로시저는 DB 서버에 저장된 함수다.
SQL과 제어 구문을 묶어서 하나의 이름으로 호출한다.

```sql
CALL calculate_monthly_fee(2026, 7);
```

이 한 줄이 내부에서 하는 일은 이렇다.
해당 월의 거래 내역을 조회하고, 등급별 수수료율을 적용하고, 결과를 정산 테이블에 INSERT하고, 처리 건수를 로그 테이블에 기록한다.
네트워크 왕복 한 번. DB 안에서 모든 게 끝난다.

### 장점 1: 네트워크 왕복 최소화

앱에서 같은 일을 하려면 이렇다.

```text
앱 → DB: SELECT 거래 내역 (왕복 1)
앱 → DB: SELECT 수수료율 (왕복 2)
앱에서 계산
앱 → DB: INSERT 정산 결과 (왕복 3)
앱 → DB: INSERT 로그 (왕복 4)
```

왕복 네 번. 프로시저는 왕복 한 번이다.
레코드가 10건이면 차이가 안 난다. 10만 건이면 체감이 된다. 100만 건이면 프로시저 없이는 답이 안 나올 수 있다.
대량 배치에서 프로시저가 살아남는 이유다.

### 장점 2: 원자적 실행

프로시저 안의 모든 SQL은 하나의 트랜잭션으로 묶을 수 있다. 중간에 에러가 나면 전체를 롤백한다.
앱에서 여러 쿼리를 보내면서 트랜잭션 경계를 관리하는 것보다 DB 안에서 한 덩어리로 처리하는 게 확실하다.
특히 금융 시스템에서 중요하다.
정산 금액을 넣고 로그를 남기는 사이에 앱이 죽으면 어떻게 되는가.
프로시저 안이면 DB가 알아서 롤백한다.

### 장점 3: 권한 분리

프로시저에 EXECUTE 권한만 주면 된다.
테이블에 직접 SELECT, INSERT 권한을 안 줘도 프로시저를 통해서만 데이터에 접근하게 할 수 있다.
앱이 직접 테이블을 건드리지 못하게 하는 것이다. 보안 관점에서 강력하다. 은행 시스템에서 이걸 많이 쓴다.
계좌 테이블에 직접 UPDATE를 날리는 건 금지. 반드시 `sp_transfer_funds` 프로시저를 통해서만 이체.
프로시저 안에서 잔액 검증, 한도 체크, 로그 기록까지 한다.

### 단점 1: 버전 관리가 안 된다

프로시저는 DB에 저장된다. Git에 없다.
누가 언제 무엇을 바꿨는지 추적이 안 된다.
"이 프로시저 마지막에 수정한 사람이 누구야?"
DB 카탈로그를 뒤져야 한다. 수정 이력은 없다.
물론 프로시저 DDL을 Git에 넣을 수 있다.
그런데 실제 DB에 배포된 버전과 Git의 버전이 다른 경우가 허다하다.
누군가 급하게 DB에 직접 ALTER PROCEDURE를 날렸기 때문이다.
Git과 DB 사이의 정합성. 이걸 유지하는 비용이 생각보다 크다.

### 단점 2: 테스트가 어렵다

앱 코드는 단위 테스트를 작성한다.
Mock을 쓰고, 의존성을 주입하고, CI에서 자동으로 돌린다.
프로시저는 어떻게 테스트하는가.
실제 DB가 있어야 한다.
테스트 데이터를 넣어야 한다.
실행하고 결과를 확인해야 한다.
롤백해야 한다.
Mock이 안 된다.
DB에 의존적이다.
CI 파이프라인에 넣기 어렵다.

테스트를 안 하는 게 아니라 하기가 너무 어려운 것이다.

### 단점 3: 배포 파이프라인 밖에 있다

앱 코드는 PR을 열고 리뷰하고 merge한다. CI가 빌드하고 테스트하고 배포한다.
프로시저는 이 흐름 밖에 있다.
DBA가 SQL 파일을 받아서 수동으로 DB에 실행하는 경우가 많다. 배포 자동화가 안 돼 있다.
Liquibase나 Flyway로 마이그레이션 스크립트에 프로시저를 포함할 수 있다.
하지만 프로시저가 복잡해지면 마이그레이션 스크립트도 복잡해진다.
의존성 순서, 권한 설정, 에러 핸들링.

### 단점 4: 디버깅의 고통

앱 코드에서 `NullPointerException`이 나면 스택 트레이스가 줄 번호까지 알려준다. IDE에서 브레이크포인트를 걸고 변수를 본다.
프로시저에서 에러가 나면? "Error Code 1644, line 47"이 전부다. line 47이 어디인지 에디터에서 세야 한다.
변수 값을 보려면 SELECT로 중간 결과를 출력해야 한다.
프로시저가 프로시저를 호출하면 더 심하다. 콜 스택을 추적하는 도구가 빈약하다. print 디버깅의 세계로 돌아간다.

### 현대 시스템에서 프로시저가 어울리는 곳

전면 폐기할 필요는 없다. 적합한 자리가 있다.

[대량 배치 처리]
100만 건의 정산을 앱에서 row by row로 처리하면 네트워크 왕복만으로 시간이 소모된다.
DB 안에서 SET 기반으로 한 번에 처리하는 게 빠르다.

[데이터 정합성 보장이 절대적인 곳]
은행 이체, 포인트 차감.
앱 장애와 무관하게 DB 안에서 원자적으로 끝내야 할 때.

[레거시 시스템 유지보수]
이미 프로시저로 돌아가는 시스템이 있다.
전부 앱으로 옮기는 비용이 새로 만드는 것보다 클 때.

### 현대 시스템에서 프로시저를 피해야 하는 곳

[비즈니스 로직]
IF문과 분기가 복잡한 도메인 로직은 앱 코드에 있어야 한다.
테스트 가능하고 버전 관리가 되고 리뷰가 된다.

[마이크로서비스]
서비스마다 DB가 분리된 구조에서 프로시저에 로직을 넣으면 서비스 경계가 무너진다.
DB가 로직의 중심이 되면 서비스 분리의 의미가 없어진다.

[빠른 배포 주기]
하루에 여러 번 배포하는 팀이라면 프로시저 배포 파이프라인까지 관리하는 건 부담이다.

### 마무리

프로시저가 나쁜 기술은 아니다. 시대가 바뀌었을 뿐이다.
앱 서버가 비쌌던 시절에는 DB에 로직을 넣는 게 합리적이었다.
지금은 앱 서버가 싸고 수평 확장이 쉽다.
DB는 여전히 수직 확장이 기본이다.
DB에 로직을 넣으면 DB가 병목이 될 때 빼기가 어렵다.
앱에 로직을 두면 앱 서버를 늘리면 된다.
DBA로서 프로시저를 많이 봤다. 성능은 좋은데 유지보수가 지옥인 코드.
아무도 건드리지 못하는 3,000줄짜리 프로시저. 원작자가 퇴사하고 주석도 없는 프로시저.
도구는 잘못이 없다. 언제 쓰고 언제 안 쓰는지를 판단하는 게 기술이다.
그 판단의 기준은 단순하다. "이 로직이 DB 안에 있어야 할 이유가 있는가?"
이유가 있으면 쓴다. 없으면 밖으로 뺀다.

## Kafka vs RabbitMQ: 메시지를 보내는 것과 로그를 남기는 것의 차이

"우리도 카프카 써야 하나요?"
개발팀에서 가장 많이 듣는 질문 중 하나다. 대답하기 전에 먼저 물어봐야 한다.
메시지를 보내고 싶은 건가, 이벤트를 기록하고 싶은 건가.
RabbitMQ는 메시지를 전달한다.
받는 쪽이 처리하면 메시지는 사라진다. 편지를 보내는 것과 같다.
Kafka는 이벤트를 기록한다.
Consumer가 읽어도 로그는 남아 있다. 일기장에 쓰는 것과 같다.
이 차이를 모르면 아무리 비교해도 결론이 안 난다.

### 근본적인 구조 차이

RabbitMQ는 메시지 브로커다.
Producer가 메시지를 보내면 브로커가 큐에 넣고 Consumer가 꺼내 간다. 처리가 끝나면 큐에서 삭제된다.
Kafka는 분산 로그다.
Producer가 이벤트를 보내면 브로커가 파티션에 append한다. Consumer가 읽어도 로그는 그대로 남는다. retention 기간이 지나야 삭제된다.

"메시지가 처리되면 사라지는가?"
이 질문 하나로 둘의 철학이 갈린다.

### RabbitMQ의 세계

AMQP 프로토콜 기반이다.
Exchange가 메시지를 받아서 라우팅 키에 따라 큐로 분배한다.

[Direct Exchange]
정확히 일치하는 큐로 보낸다.
주문 큐에는 주문만, 결제 큐에는 결제만.

[Topic Exchange]
패턴 매칭으로 보낸다.
`order.*` 라우팅 키로 주문 관련 큐 전부에 전달.

[Fanout Exchange]
바인딩된 모든 큐에 복사한다.
브로드캐스트다. 라우팅이 유연하다.
메시지를 "어디로 보낼 것인가"에 초점이 맞춰져 있다.

### Kafka의 세계

토픽과 파티션이 핵심이다.
토픽은 이벤트의 카테고리. 파티션은 토픽 안의 물리적 로그 파일.
Producer가 이벤트를 보내면 파티션 끝에 순서대로 붙는다. append-only 로그다.
Consumer는 offset으로 읽는다. "나는 여기까지 읽었다"는 위치를 기억한다. 같은 이벤트를 다시 읽을 수 있다.
Kafka의 초점은 "무슨 일이 일어났는가"를 기록하는 것이다.

### 순서 보장

[RabbitMQ]
단일 큐 안에서는 순서가 보장된다.
하지만 여러 Consumer가 동시에 꺼내 가면 처리 순서는 보장되지 않는다.
Consumer A가 메시지 1을 처리하는 동안 Consumer B가 메시지 2를 먼저 끝낼 수 있다.

[Kafka]
파티션 안에서 순서가 보장된다.
같은 파티션에 들어간 이벤트는 반드시 쓴 순서대로 읽힌다.
키 기반 파티셔닝으로 같은 주문의 이벤트를 같은 파티션에 모은다.
순서가 중요한 도메인이라면 Kafka의 파티션 모델이 더 자연스럽다.

### 재처리

여기서 결정적 차이가 난다.

[RabbitMQ]
Consumer가 ACK를 보내면 메시지는 큐에서 사라진다.
"어제 들어온 주문 이벤트를 다시 처리해줘." 불가능하다. 이미 없다.
Dead Letter Queue에 실패 메시지를 보관할 수는 있지만 전체 재처리와는 다르다.

[Kafka]
Consumer가 읽어도 로그는 남아 있다. offset을 되돌리면 처음부터 다시 읽을 수 있다.
"어제 들어온 이벤트 전부 재처리." 가능하다. offset만 리셋하면 된다.
버그 수정 후 재처리, 새 Consumer 추가 후 과거 이벤트 소급. Kafka에서는 일상이고 RabbitMQ에서는 불가능하다.

### 처리량

[RabbitMQ]
단일 노드에서 초당 수만 메시지를 처리한다. 대부분의 서비스에는 충분하다.
하지만 수십만 이상으로 올라가면 클러스터링과 샤딩이 필요하고 복잡도가 급격히 올라간다.

[Kafka]
파티션을 늘리면 처리량이 선형으로 증가한다. 파티션 10개면 Consumer 10대가 병렬로 읽는다.
초당 수백만 이벤트도 처리 가능하다. LinkedIn에서 태어난 이유가 이것이다.
소규모 서비스에서는 RabbitMQ로 충분하다. 대규모 이벤트 스트림이라면 Kafka가 맞다.

### 운영 복잡도

[RabbitMQ]
설치가 쉽다.
Erlang 기반이라 클러스터링도 내장이다.
관리 UI가 기본 제공된다.
큐 상태, Consumer 수, 메시지 적체를 한눈에 본다.
소규모 팀이 운영하기 좋다.

[Kafka]
ZooKeeper 의존성이 있었다.
KRaft 모드로 벗어나는 중이지만 아직 과도기다.
브로커, 파티션, 리플리카, ISR, 리밸런싱. 알아야 할 개념이 많다.
Kafka는 강력하지만 운영 비용도 강력하다.
전담 인력 없이 Kafka를 운영하는 건 보험 없이 스포츠카를 모는 것과 같다.

### Consumer 모델

[RabbitMQ]
push 모델이다.
브로커가 Consumer에게 메시지를 밀어준다.
prefetch count로 한 번에 받을 양을 조절한다.
Consumer가 느리면 메시지가 큐에 쌓인다.

[Kafka]
pull 모델이다.
Consumer가 브로커에서 직접 가져간다.
자기 속도에 맞춰 읽는다.
느린 Consumer는 느리게 읽을 뿐이다.
다른 Consumer에 영향을 주지 않는다.
pull 모델이 Consumer 장애에 더 강하다.
한 Consumer가 죽어도 다른 Consumer는 영향 없다.

### DB 이벤트 발행 관점

DBA 입장에서 가장 중요한 맥락이다. DB 변경을 외부에 알려야 할 때 어느 쪽을 쓰는가.

[CDC + Kafka]
Debezium이 binlog를 읽어서 Kafka 토픽으로 보낸다.
이벤트가 로그로 남으니 재처리가 가능하다.
새 Consumer를 붙이면 과거 변경분까지 소급한다.
CDC의 자연스러운 파트너다.

[Outbox + RabbitMQ]
outbox 테이블을 폴링해서 RabbitMQ로 보낸다.
단순하고 즉시 전달된다.
하지만 재처리가 필요하면 outbox 테이블을 다시 읽어야 한다.

이벤트를 "한 번 보내면 끝"이면 RabbitMQ.
"기록으로 남기고 여러 번 소비"하면 Kafka.

### "우리도 카프카 써야 하나요?"

이 질문에 대한 현실적 답변.

[RabbitMQ가 맞는 경우]
작업 큐가 필요하다.
이메일 발송, 이미지 변환, 비동기 처리.
메시지를 보내고 처리하면 끝이다.
재처리 요구사항이 없다.
팀 규모가 작다.

[Kafka가 맞는 경우]
이벤트 스트림이 필요하다.
주문 흐름, 결제 흐름, 사용자 행동 추적.
여러 Consumer가 같은 이벤트를 독립적으로 소비한다.
재처리가 필수다.
처리량이 많다.

"카프카가 좋다더라"는 이유가 아니다.
"우리에게 로그가 필요한가"가 기준이다.

### 둘 다 쓰는 현실

대규모 시스템에서는 둘 다 쓴다.
Kafka는 이벤트 백본. 주문 생성, 결제 완료, 배송 상태 변경.
모든 도메인 이벤트가 Kafka를 통해 흐른다.
RabbitMQ는 작업 큐. 알림 발송, PDF 생성, 배치 트리거.
처리하면 끝나는 일에는 RabbitMQ가 가볍다.
양자택일이 아니다. 역할이 다른 도구를 적재적소에 쓰는 것이다.
망치와 드라이버 중 뭐가 좋으냐고 묻는 건 질문 자체가 틀린 것이다.

### DBA 관점에서의 정리

Kafka든 RabbitMQ든 결국 데이터의 출발점은 DB다.
CDC는 DB 로그를 읽고, Outbox는 DB 테이블에 쓰고, 어떤 메시지 시스템을 쓰든 DB의 트랜잭션 안에서 이벤트가 태어난다.
DBA가 신경 쓸 건 Kafka의 파티션 수가 아니다.
binlog가 얼마나 빠르게 소비되는지, outbox 테이블이 얼마나 빠르게 커지는지, CDC 커넥터가 복제 지연을 만들고 있지는 않은지.
메시지 시스템은 전달할 뿐이다. 원본은 언제나 DB에 있고, 그 원본을 지키는 건 DBA의 일이다.

## Redis vs Memcached: 캐시만 할 거면 Memcached가 맞다

"캐시 쓸 건데 Redis 올려주세요."
이 요청을 받으면 하나 물어본다.
"혹시 캐시만 할 건가요?"
캐시만 할 거라면 Memcached가 더 나은 선택일 수 있다.
"Redis가 Memcached 상위호환 아닌가요?"
아니다. 그 오해를 풀어보자.

### 태생이 다르다

Memcached는 2003년에 나왔다. LiveJournal의 브래드 피츠패트릭이 만들었다.
목적이 명확했다. "DB 앞에 메모리 캐시를 두자."
Redis는 2009년에 나왔다. 살바토레 산필리포가 만들었다.
처음부터 "데이터 구조 서버"를 지향했다.
캐시는 Redis가 할 수 있는 일 중 하나일 뿐이다.
Memcached는 캐시를 위해 태어났다. Redis는 캐시도 할 수 있게 태어났다.
이 차이가 설계 전체에 반영돼 있다.

### 데이터 구조 차이

Memcached의 데이터 모델은 단순하다. key-value.
value는 바이트 배열이다.
문자열이든 직렬화된 객체든 Memcached는 신경 안 쓴다. 그냥 저장하고 돌려줄 뿐이다.
Redis는 다르다.
String, Hash, List, Set, Sorted Set, Stream, HyperLogLog, Bitmap, Geospatial.
서버 사이드에서 데이터 구조를 조작할 수 있다.
Sorted Set에서 랭킹을 계산하고, List에서 큐를 구현하고, Hash에서 필드 단위로 읽고 쓴다.
캐시만 할 거면 이 기능이 전부 필요 없다.
GET, SET, DELETE. Memcached로 충분하다.

### 스레딩 모델

이게 가장 과소평가되는 차이다.
Redis는 싱글 스레드다. 명령어를 하나씩 순서대로 처리한다.
이 설계 덕분에 락 없이 원자적 연산이 가능하다. 하지만 CPU 코어 하나만 쓴다.
Memcached는 멀티스레드다. 여러 코어를 동시에 활용한다.
단순 GET/SET 연산을 여러 스레드가 병렬로 처리한다.
vCPU 4코어 인스턴스에서 단순 캐시 룩업만 한다면 Memcached가 Redis보다 처리량이 높다.
Redis 7.0부터 I/O 스레딩이 추가됐지만 명령어 처리 자체는 여전히 싱글 스레드다.

### 메모리 효율

Memcached는 slab allocator를 쓴다.
메모리를 미리 slab 단위로 나눠놓고 비슷한 크기의 아이템을 같은 slab에 넣는다.
메모리 단편화가 적다. 예측 가능한 메모리 사용.
Redis는 jemalloc을 쓴다.
다양한 데이터 구조를 지원하다 보니 오버헤드가 더 크다.
같은 key-value 1,000만 건을 저장하면 Memcached가 Redis보다 메모리를 적게 쓴다. 각 키에 붙는 메타데이터가 더 작기 때문이다.
순수 캐시 워크로드에서 같은 메모리로 더 많은 데이터를 넣을 수 있다는 건 노드 수를 줄일 수 있다는 뜻이다.
비용 차이가 생긴다.

### 영속성

Redis는 RDB 스냅샷과 AOF 로그를 지원한다. 재시작해도 데이터가 살아 있다.
이 기능 덕분에 Redis를 1차 저장소처럼 쓰는 서비스도 있다.
Memcached는 영속성이 없다. 재시작하면 전부 사라진다. 캐시니까 사라져도 된다는 전제.
영속성은 공짜가 아니다.
Redis의 AOF는 디스크 I/O를 유발한다.
fsync 정책에 따라 쓰기 성능에 영향을 준다.
RDB 포크는 메모리를 일시적으로 2배 쓸 수 있다.
캐시 용도로만 쓴다면 이 오버헤드가 전부 불필요하다.
Memcached는 이 비용을 처음부터 지지 않는다.

### 클러스터링

[Memcached]
클라이언트 사이드 샤딩.
클라이언트가 키를 해시해서 적절한 노드를 직접 선택한다.
서버끼리는 서로를 모른다.
단순하고 예측 가능하다.

[Redis Cluster]
서버 사이드 샤딩.
16,384개 해시 슬롯을 노드에 분배한다.
노드 간 gossip 프로토콜로 상태를 공유한다.
자동 페일오버, 리샤딩이 가능하다.
Redis Cluster는 강력하지만 복잡하다.
MULTI/EXEC가 같은 슬롯 안에서만 동작하고, 클라이언트가 MOVED/ASK 리다이렉션을 처리해야 한다.
ElastiCache Memcached는 Auto Discovery로 노드 추가/제거를 클라이언트가 자동 감지한다.
구성이 단순하다.

### "Redis가 무조건 상위호환"이라는 오해

이 오해가 널리 퍼져 있다.
Redis가 Memcached의 기능을 전부 포함하니까 Redis만 쓰면 된다는 논리.
틀렸다. Memcached가 Redis보다 나은 지점이 있다.

- 멀티스레드로 코어를 전부 활용한다.
- 메모리 오버헤드가 작다.
- 영속성 비용이 없다.
- 구조가 단순해서 예측 가능하다.

"캐시만 할 거면 Memcached"는 성능과 효율의 관점에서 합리적인 선택이다.
Redis는 캐시 이상의 일을 할 때 빛난다. 캐시만 할 때는 불필요한 복잡성이 딸려온다.

### Redis가 빛나는 순간

캐시를 넘어서는 요구사항이 있을 때.

[세션 스토어]
사용자 세션을 Hash로 저장하고 TTL로 자동 만료.
필드 단위 읽기/쓰기가 가능하다.

[실시간 랭킹]
Sorted Set 하나로 수백만 명의 실시간 순위를 관리한다.
ZADD, ZRANK, ZRANGE.

[메시지 큐]
List의 LPUSH/BRPOP으로 간단한 큐.
Stream으로 본격적인 이벤트 스트리밍.

[분산 락]
SET NX EX 로 분산 환경 락을 구현한다.
Redlock 알고리즘까지 지원.

[Pub/Sub]
실시간 알림, 이벤트 브로드캐스트.

이 중 하나라도 필요하면 Redis다. Memcached로는 할 수 없다.

### Memcached가 더 나은 경우

구체적으로 이런 상황이다.

[순수 캐시]
DB 쿼리 결과를 key-value로 캐시.
GET으로 읽고, 없으면 DB에서 가져와서 SET.
이 패턴만 반복하는 서비스.

[높은 처리량 요구]
초당 수십만 건의 단순 GET/SET.
멀티스레드의 이점이 극대화된다.

[메모리 효율이 중요]
같은 예산으로 더 많은 데이터를 캐시해야 할 때.
노드당 캐시 용량이 Memcached가 더 크다.

[운영 단순성]
캐시 노드가 죽으면 다시 워밍업하면 된다.
페일오버 복잡성이 필요 없다.
상태가 없으니 교체가 쉽다.

Facebook이 Memcached를 선택한 이유가 정확히 이것이다.
수십억 건의 단순 캐시 룩업.

### ElastiCache에서의 선택

AWS 관리형 서비스 기준으로 보면.

[ElastiCache for Redis]
클러스터 모드, 자동 페일오버, 백업/복원.
기능이 풍부하고 관리 포인트가 많다.

[ElastiCache for Memcached]
Auto Discovery, 멀티스레드.
백업 없음, 페일오버 없음.

노드가 죽으면 새 노드가 빈 상태로 올라온다. 비용도 다르다.
같은 인스턴스 타입이라도 Redis가 Memcached보다 비싸다.
Redis의 복제, 백업, 클러스터 관리 비용이 반영돼 있다.
캐시 미스 시 원본 DB로 가면 되는 구조라면 Memcached의 "상태 없음"이 오히려 장점이다. 복구가 단순해진다.

### 실무 판단 기준

팀에서 "캐시 도입하겠습니다"라고 할 때 DBA가 물어야 하는 질문이 있다.
"캐시 외에 Redis의 데이터 구조를 쓸 건가요?"
쓴다면 Redis. 안 쓴다면 Memcached를 먼저 고려.
"캐시 데이터가 유실되면 서비스에 영향이 있나요?"
있다면 Redis(영속성). 없다면 Memcached.
"단일 키 조회가 대부분인가요, 서버 사이드 연산이 필요한가요?"
전자면 Memcached. 후자면 Redis.
세 질문 모두 첫 번째 답이면 Memcached가 맞는 선택이다.

### DBA 관점에서의 정리

Redis는 만능이 아니다.
만능에 가깝지만 만능에는 비용이 따른다.

- 싱글 스레드의 처리량 한계.
- 다양한 데이터 구조에 따른 메모리 오버헤드.
- 영속성 유지 비용.
- 클러스터 운영의 복잡성.

캐시만 할 거면 이 비용을 다 치를 필요가 없다.
Memcached는 캐시라는 한 가지 일을 30년 가까이 해온 도구다.
Redis를 써야 하는 이유가 명확할 때 Redis를 쓰고, "그냥 Redis가 좋다더라"로 선택하지 않는 것.
도구는 용도에 맞게 쓸 때 빛난다.
Redis는 데이터 구조 서버로 빛나고,
Memcached는 캐시로 빛난다.

## 옵티마이저가 보는 세상: 쿼리가 느린 건 DB가 다르게 생각하기 때문이다

같은 쿼리가 어제는 0.01초, 오늘은 30초가 걸린다.
데이터도 안 바뀌었고, 인덱스도 그대로인데. 원인은 옵티마이저다.
DB가 쿼리를 실행하는 방법을 "다르게 선택"한 것이다.

### 옵티마이저란

SQL은 "무엇을 원하는지"만 말한다. "어떻게 가져올지"는 말하지 않는다.

```sql
SELECT * FROM orders WHERE user_id = 42;
```

이 쿼리를 실행하는 방법은 여러 가지다:
테이블 전체를 스캔하거나, user_id 인덱스를 쓰거나, 커버링 인덱스로 테이블 접근 없이 끝내거나.
이 선택지 중 가장 빠른 것을 고르는 게 옵티마이저의 역할이다.

### 비용 기반 최적화 (CBO)

현대 DB는 전부 비용 기반(Cost-Based) 옵티마이저다.
각 실행 계획의 "비용"을 추정하고 가장 비용이 낮은 계획을 고른다.
비용이란 대략적인 I/O + CPU 연산량이다. 실제 실행 시간이 아니라 추정치다.
이 추정이 정확하면 좋은 계획을 고르고, 부정확하면 나쁜 계획을 고른다.
추정의 핵심 재료가 "통계 정보"다. 통계가 오래되면 판단이 틀어진다.

### 통계 정보

옵티마이저가 참고하는 데이터 요약본이다.
테이블 행 수, 컬럼별 고유 값 수(카디널리티), 값의 분포(히스토그램), NULL 비율, 인덱스의 선택도.

MySQL:

```sql
ANALYZE TABLE orders;
-- mysql.innodb_table_stats, innodb_index_stats 갱신
```

PostgreSQL:

```sql
ANALYZE orders;
-- pg_statistic 갱신
```

통계가 실제와 다르면 옵티마이저가 "이 인덱스는 소용없다"고 잘못 판단할 수 있다.
그렇다고 운영에 analyze를 막 날리면 안된다

### 히스토그램

카디널리티만으로는 부족할 때가 있다.
status 컬럼에 'active'가 99%, 'inactive'가 1%라면?
카디널리티는 2지만 'inactive' 검색은 인덱스가 효과적이고 'active' 검색은 풀스캔이 낫다.
히스토그램은 이런 값의 분포를 저장한다.

MySQL 8.0:

```sql
ANALYZE TABLE orders UPDATE HISTOGRAM ON status;
```

PostgreSQL은 ANALYZE 시 자동으로 히스토그램을 수집한다.
`default_statistics_target`으로 정밀도를 조절할 수 있다.

### 실행 계획 읽기

EXPLAIN은 옵티마이저의 생각을 보여준다.

MySQL:

```sql
EXPLAIN SELECT * FROM orders WHERE user_id = 42;
```

type, key, rows, Extra 컬럼이 핵심이다.
type 순서 (좋은 → 나쁜): const → eq_ref → ref → range → index → ALL
ALL이 나오면 풀 테이블 스캔이다.
rows가 실제보다 크게 잡혀 있으면 통계가 부정확한 것이다.
`EXPLAIN ANALYZE (MySQL 8.0.18+)`는 예상이 아니라 실제 실행 결과를 보여준다.
추정 vs 실제를 비교할 수 있다.

### PostgreSQL의 EXPLAIN

PostgreSQL은 EXPLAIN이 더 상세하다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42;
```

Seq Scan, Index Scan, Bitmap Scan, Nested Loop, Hash Join, Merge Join
같은 노드가 트리 구조로 표시된다. 각 노드에 예상 비용과 실제 시간이 같이 나온다.
`actual time vs estimated cost`.
Buffers 옵션을 켜면 shared hit(캐시) / read(디스크)도 보인다.
느린 원인이 I/O인지 CPU인지 구분할 수 있다.

### 조인 전략

옵티마이저가 가장 고민하는 부분이다.

[Nested Loop]
한 테이블의 각 행마다 다른 테이블을 탐색한다.
인덱스가 있으면 매우 빠르다.
소량 데이터 조인에 적합.

[Hash Join]
한 테이블을 해시 테이블로 만들고 다른 테이블을 순회하며 매칭한다.
인덱스 없이도 효율적.
대용량 조인에 적합.

[Merge Join]
양쪽을 정렬한 뒤 병합한다.
이미 정렬돼 있으면 매우 빠르다.
PostgreSQL이 자주 선택한다.

### MySQL vs PostgreSQL 옵티마이저 성격

두 DB의 옵티마이저는 성격이 다르다.

- MySQL (InnoDB):
  - Nested Loop Join만 지원했다.
  - 8.0.18부터 Hash Join 추가.
  - 옵티마이저가 상대적으로 단순하다.
- PostgreSQL:
  - 세 가지 조인 전부 지원.
  - 서브쿼리 최적화도 공격적이다.
  - 통계 기반 판단이 더 정교하다.
  - 대신 ANALYZE를 꼬박꼬박 해줘야 한다.

MySQL은 "단순하지만 예측 가능", PostgreSQL은 "똑똑하지만 가끔 변덕".

### 실행 계획이 갑자기 바뀌는 이유

"어제까지 잘 되던 쿼리가 오늘 느려요." DBA가 가장 자주 듣는 말이다.
원인들:

[통계 갱신]
ANALYZE가 돌면서 통계가 바뀌었다. 옵티마이저가 다른 계획을 선택했다.

[데이터 분포 변경]
특정 값이 급증해서 인덱스 효율이 떨어졌다.

[테이블 크기 변화]
소규모일 때는 풀스캔이 빨랐는데 커지면서 역전됐다. 또는 그 반대.

[MySQL 버전 업그레이드]
옵티마이저 코드가 바뀌었다.
같은 통계로도 다른 판단을 한다.

### 힌트

옵티마이저의 판단을 강제로 바꾸는 도구다.

MySQL:

```sql
SELECT /*+ INDEX(orders idx_user) */ *
FROM orders WHERE user_id = 42;
```

PostgreSQL:
공식 힌트가 없다. `pg_hint_plan` 확장을 설치해야 한다.

```sql
/*+ IndexScan(orders idx_user) */
SELECT * FROM orders WHERE user_id = 42;
```

힌트는 최후의 수단이다.
데이터가 바뀌면 힌트가 오히려 독이 된다.
통계 갱신이나 인덱스 재설계가 우선이다.

### 쿼리 리라이팅

같은 결과를 내는 다른 SQL이 완전히 다른 실행 계획을 만들 수 있다.

```sql
-- 서브쿼리 (느릴 수 있음)
SELECT * FROM orders
WHERE user_id IN (SELECT id FROM users WHERE grade='vip');
-- JOIN으로 변환 (보통 빠름)
SELECT o.* FROM orders o
JOIN users u ON o.user_id = u.i(d)
WHERE u.grade = 'vip';
```

MySQL 옵티마이저는 서브쿼리 최적화가 약하다.
IN 서브쿼리를 조인으로 바꾸면 극적으로 빨라지는 경우가 많다.
PostgreSQL은 대부분 자동으로 서브쿼리를 조인으로 변환한다.

### Adaptive Query Optimization

최근 DB들은 실행 중에 계획을 수정하는 기능을 도입하고 있다.

Oracle 12c: Adaptive Plan — 실행 중에 Nested Loop ↔ Hash Join을 전환한다.
PostgreSQL: 아직 adaptive plan은 없지만, JIT 컴파일(PG 11+)로 실행 중 CPU 최적화를 한다.
MySQL 8.0: Hash Join 추가가 사실상 가장 큰 옵티마이저 개선이었다. adaptive 기능은 아직 없다.
미래의 옵티마이저는 "한 번 정하고 끝"이 아니라 "실행하면서 조정"하는 방향으로 간다.

### 슬로우 쿼리 분석 순서

DBA가 느린 쿼리를 받았을 때 실제로 하는 일:

1. EXPLAIN (ANALYZE) 확인
   1. 어떤 계획을 썼는지
2. 예상 행 수 vs 실제 행 수 비교
   1. 차이가 크면 통계 문제
3. ANALYZE TABLE/ANALYZE 실행
   1. 통계 갱신 후 재확인
4. 인덱스 확인
   1. 적절한 인덱스가 있는지
5. 쿼리 리라이팅
   1. 같은 결과, 다른 경로
6. 마지막 수단으로 힌트
   1. 임시 처방, 근본 해결 아님

이 순서를 거치면 대부분의 슬로우 쿼리는 해결된다.

### 마무리

옵티마이저는 DB 안의 의사결정자다.
우리가 "무엇을"만 말하면 옵티마이저가 "어떻게"를 결정한다. 그 결정의 근거는 통계 정보다.
통계가 부정확하면 판단이 틀어지고, 쿼리가 갑자기 느려진다.
EXPLAIN을 읽을 수 있으면 옵티마이저의 생각을 이해할 수 있다. 이해하면 고칠 수 있다.
힌트로 강제하기 전에 통계를 먼저 의심하고, 인덱스를 점검하고, 쿼리를 바꿔보는 것.
DB는 틀린 게 아니라 다르게 생각한 것이다.
그 생각을 읽는 게 DBA의 일이다.

## 커넥션 풀의 안쪽: 왜 DB가 멀쩡한데 연결이 안 되는가

새벽 3시에 알람이 울린다. "DB 커넥션을 맺을 수 없습니다."
DB 서버 CPU는 5%. 메모리도 여유롭다. 쿼리도 안 느리다.
그런데 연결이 안 된다.
원인은 DB가 아니라 커넥션 풀에 있는 경우가 대부분이다.

### DB 커넥션의 실제 비용

애플리케이션이 DB에 연결할 때 실제로 일어나는 일은 생각보다 많다.

1. TCP 3-way handshake
2. TLS 핸드셰이크(SSL 사용 시)
3. 인증(사용자/비밀번호 검증)
4. 세션 초기화(타임존, 문자셋, 변수 설정)

MySQL 기준으로 커넥션 하나 맺는 데 수 ms.
TLS까지 더하면 수십 ms가 될 수도 있다.
요청마다 새로 맺으면 초당 1000 요청 = 초당 1000번의 핸드셰이크.
DB가 연결 맺느라 정작 쿼리를 못 처리한다.

### 커넥션 풀이란

미리 커넥션을 여러 개 만들어놓고 요청이 오면 꺼내쓰고 돌려놓는 구조다.
핸드셰이크를 한 번만 하고 이후 요청은 이미 열린 커넥션을 재사용한다.
모든 현대 애플리케이션은 커넥션 풀을 쓴다.
직접 맺고 끊는 코드를 쓰면 성능이 수 배 이상 떨어질 수 있다.
커넥션 풀의 핵심 설정은 세 가지:
최소 유지 수(min),
최대 허용 수(max),
대기 타임아웃(timeout).

### HikariCP — Java 생태계의 표준

Spring Boot 2.0부터 기본 커넥션 풀이다. 이전의 Tomcat DBCP, C3P0을 대체했다.
빠른 이유는 단순하다. 락을 최소화하고, 바이트코드 레벨에서 최적화했다.
핵심 설정:
maximumPoolSize: 최대 커넥션 수 (기본 10)
minimumIdle: 최소 유휴 커넥션 (기본 = max)
connectionTimeout: 풀에서 대기 최대 시간 (기본 30초)
idleTimeout: 유휴 커넥션 폐기까지 시간
HikariCP는 공식적으로 minimumIdle = maximumPoolSize를 권장한다.
"필요할 때 만들겠다"는 전략보다 "항상 준비해두겠다"가 낫다는 철학이다.

### pgBouncer — PostgreSQL의 경량 프록시

PostgreSQL은 커넥션당 프로세스를 fork한다. 커넥션 100개 = 프로세스 100개.
MySQL은 스레드 기반이라 가볍지만, PostgreSQL은 프로세스 기반이라 커넥션이 많아지면 메모리가 빠르게 찬다.
pgBouncer는 이 문제를 해결한다. 앱 ↔ pgBouncer ↔ PostgreSQL.
앱은 pgBouncer에 1000개 연결해도 pgBouncer가 실제 PostgreSQL에는 50개만 연결하고 돌려쓴다.

### pgBouncer 풀링 모드 3가지

[Session]
커넥션을 앱 세션 동안 점유한다.
사실상 풀링 효과가 거의 없다.
Prepared Statement 사용 가능.

[Transaction]
트랜잭션 단위로 커넥션을 할당한다.
트랜잭션 끝나면 다른 클라이언트에게 넘긴다.
가장 많이 쓰는 모드.
단, Prepared Statement 사용 불가.
PG 14부터 protocol-level로 해결됐다.

[Statement]
쿼리 하나 단위로 커넥션을 할당한다.
멀티 스테이트먼트 트랜잭션 불가.
극단적 환경에서만 쓴다.

### ProxySQL — MySQL의 만능 프록시

MySQL 생태계의 pgBouncer에 해당하지만 기능이 훨씬 많다.
커넥션 풀링은 기본이고, 쿼리 라우팅(읽기는 Replica로), 쿼리 캐싱, 쿼리 리라이팅, 쿼리 차단까지 가능하다.
관리 인터페이스가 MySQL 프로토콜이라 mysql 클라이언트로 접속해서 설정한다.

```sql
-- ProxySQL 관리 콘솔에서
SELECT * FROM stats_mysql_connection_pool;
```

DBA가 애플리케이션 코드 수정 없이 쿼리를 제어할 수 있는 도구다.

### max_connections의 함정

MySQL의 max_connections 기본값은 151. PostgreSQL은 100.
"동시 접속이 많으니까 늘리자." 이 판단이 틀린 경우가 많다.
커넥션이 1000개 열려 있어도 실제로 쿼리를 실행 중인 건 10~20개다.
나머지는 유휴 상태로 메모리만 잡아먹는다.
MySQL: 커넥션당 수 MB
PostgreSQL: 프로세스당 수~십수 MB
1000개 열면 수 GB가 커넥션 유지에만 소비된다.
정작 쿼리 실행에 쓸 메모리가 부족해진다.

### 적절한 풀 사이즈

HikariCP 공식 문서의 공식: connections = (CPU 코어 수 × 2) + 디스크 수
4코어 서버라면 약 10개.
직관과 다를 수 있지만 벤치마크에서 반복 검증된 수치다.
커넥션을 늘리면 컨텍스트 스위칭이 늘어난다.
CPU가 쿼리 실행 대신 스레드 전환에 시간을 쓴다.
"풀 사이즈를 20에서 200으로 올렸더니 오히려 느려졌다."
DBA가 자주 목격하는 현상이다.

### wait_timeout과 유휴 커넥션

MySQL의 wait_timeout 기본값은 28800초. 8시간이다.
아무 쿼리도 안 보내는 커넥션을 8시간 동안 끊지 않는다는 뜻이다.
배포 후 커넥션 풀이 재생성되면 이전 커넥션들이 좀비처럼 남는다.
풀은 새 커넥션을 맺고, DB에는 좀비가 쌓인다.

해결:
wait_timeout을 300~600초로 줄이고, 커넥션 풀의 idleTimeout도 맞춘다.
DB의 타임아웃 < 풀의 타임아웃이면 풀이 이미 끊긴 커넥션을 꺼내준다.
"Connection is closed" 에러의 흔한 원인이다.

### JDBC URL에서 놓치기 쉬운 옵션들

`connectTimeout=5000`
TCP 연결 타임아웃(ms). 기본 0 = 무제한 대기.
DB가 응답 불가 상태면 앱이 영원히 멈춘다.
`socketTimeout=30000`
쿼리 응답 대기 타임아웃(ms). 기본 0.
슬로우 쿼리가 커넥션을 무한 점유하는 걸 막는다.
`tcpKeepAlive=true`
유휴 커넥션의 생존을 OS 레벨에서 감지한다.
`autoReconnect=true`
쓰지 말 것. MySQL 공식 문서도 권장하지 않는다.
트랜잭션 도중 재연결되면 세션 상태가 유실된다.
재연결은 커넥션 풀이 검증 단계에서 처리한다.
앱이 직접 리커넥트 로직을 짤 필요는 없다.
트랜잭션 자체가 실패하면 앱에서 트랜잭션 단위로 재시도하는 것이 올바른 방식이다.

### 커넥션 누수

커넥션을 풀에서 빌려놓고 반납하지 않는 버그.
시간이 지나면 풀이 고갈된다.

```java
Connection conn = dataSource.getConnection();
// ... 쿼리 실행
// conn.close() 호출 안 함 → 누수
```

try-with-resources 안 쓰면 예외 발생 시 반납이 빠진다.
풀이 한 개씩 줄어들다가 결국 timeout 에러가 터진다.
HikariCP의 leakDetectionThreshold를 켜면 반납 안 된 커넥션을 경고로 잡아준다.
기본은 꺼져있다.

### 커넥션 검증

풀에 들어있는 커넥션이 실제로 살아있는지 어떻게 아는가.

[MySQL]
예전에는 SELECT 1 쿼리를 보냈다.
MySQL Connector/J 5.1.12부터 ping 패킷으로 대체됐다.
네트워크 왕복 1회로 확인 가능.

[PostgreSQL]
libpq 레벨에서 PQstatus() 함수로 확인한다.
HikariCP는 커넥션을 꺼낼 때마다 자동으로 유효성 검증을 한다.
connectionTestQuery 설정은 이제 거의 필요 없다.

### 멀티 AZ와 커넥션

AWS RDS 멀티 AZ 환경에서 페일오버가 발생하면 기존 커넥션이 전부 끊긴다.
DNS가 새 인스턴스로 바뀌지만, 커넥션 풀은 이전 IP를 캐싱하고 있다.
해결:
커넥션 풀의 maxLifetime을 짧게 설정한다.
HikariCP 기본값은 30분.
주기적으로 커넥션을 교체하면 DNS 변경이 자연스럽게 반영된다.
페일오버 직후 순간적으로 모든 앱이 동시에 재연결을 시도한다.
이 순간이 DB에 가장 위험하다. 커넥션 풀에 retry + backoff가 필요한 이유다.

### Too many connections

MySQL이 max_connections에 도달하면 새 연결을 거부한다.
`ERROR 1040 (HY000): Too many connections`
이 에러가 나면 DBA도 접속이 안 된다. 그래서 MySQL에는 숨겨진 비상구가 있다.
SUPER 유저는 max_connections + 1개까지 접속할 수 있다.
MySQL 8.0.14부터는 admin_port로 별도 포트를 열 수도 있다.
이걸 모르면 장애 때 서버에 SSH 접속해서 mysql 소켓 연결을 해야 한다.

### 커넥션 폭증 시나리오

실제로 겪는 패턴들:

[슬로우 쿼리 연쇄]
쿼리 하나가 느려지면 커넥션을 오래 점유한다.
풀이 비고, 다른 요청이 대기하고, 대기가 쌓여서 전체 응답이 느려진다.

[배포 직후]
이전 인스턴스와 새 인스턴스가 동시에 풀을 연다.
순간적으로 커넥션 수가 두 배.

[스케일 아웃]
서버를 10대에서 50대로 늘렸는데 풀 사이즈를 안 줄였다.
50대 × 20개 = 1000개. DB가 감당 못 한다.

### 마무리

커넥션 풀은 애플리케이션과 DB 사이의 보이지 않는 중간 계층이다.
DB가 멀쩡한데 연결이 안 될 때, 원인은 거의 여기에 있다.
풀 사이즈는 작게 시작하고, 타임아웃은 DB와 풀을 맞추고, 누수 탐지는 반드시 켜야 한다.
커넥션은 공유 자원이다. 잘 만들어진 커넥션 풀은 수백 대의 서버가 수십 개의 커넥션으로 동작하게 해준다.
문제는 대부분 커넥션이 모자란 게 아니라 있는 커넥션을 제대로 쓰지 않는 것이다.

## DB가 이벤트를 발행해야 할 때: 트랜잭션과 메시지 사이의 설계

주문이 들어오면 DB에 저장하고, Kafka에 이벤트를 보내고, 검색 엔진을 갱신하고, 알림을 발송해야 한다.
"저장하고 알린다." 한 문장이지만 이 안에 분산 시스템의 가장 오래된 문제가 숨어 있다.
DB에 쓰면서 동시에 외부에 알리는 것.
이 문제를 풀기 위해 CDC, Outbox, Event Sourcing이라는 세 가지 설계가 등장했다.
어떤 건 DB 로그를 훔쳐보고, 어떤 건 이벤트를 DB에 같이 심고, 어떤 건 아예 이벤트만 저장한다.
복잡도도, 해결 범위도, 대가도 다르다.

### 듀얼 라이트

가장 직관적인 방법. DB에 쓰고, Kafka에도 쓴다.

```python
db.sav.e(order)
kafka.send(order_event)
```

코드 두 줄이면 끝.
하지만 이건 두 개의 독립된 시스템에 각각 쓰기를 하는 것이다.
하나의 트랜잭션으로 묶을 수 없다.
DB 트랜잭션은 Kafka를 모르고, Kafka는 DB 트랜잭션을 모른다.

### 듀얼 라이트가 깨지는 순간

DB 성공, Kafka 실패.
→ 주문은 저장됐는데 이벤트가 안 나간다.
→ 검색엔진에 주문이 안 뜬다.
DB 실패, Kafka 성공.
→ 주문은 없는데 이벤트는 나갔다.
→ 존재하지 않는 주문의 알림이 간다.
어느 쪽이든 데이터 불일치.
그리고 이건 "가끔" 일어나는 게 아니라 시간 문제다.
네트워크는 실패하게 돼 있다.

### 세 가지 선택지

듀얼 라이트를 피하는 방법은 크게 세 가지다.
하나, DB 로그를 읽어서 전달한다. CDC.
둘, 이벤트를 DB 트랜잭션에 함께 넣는다. Outbox 패턴.
셋, 이벤트 자체를 데이터 모델로 삼는다. Event Sourcing.
복잡도가 올라가는 순서다. 해결하는 범위도 달라진다.

### 선택지 1 --- CDC

DB에는 트랜잭션 로그가 있다. binlog, WAL, redo log.
어차피 기록되는 로그를 Debezium 같은 커넥터가 읽어서 Kafka로 전달한다.
애플리케이션 코드를 안 건드린다. DB에 쓰기만 하면 된다.
비침투적이고 도입 비용이 가장 낮다.

### CDC의 한계

CDC가 전달하는 건 "행이 바뀌었다"는 물리적 사실이다.
"주문이 확정됐다"가 아니라 "status 컬럼이 PENDING에서 CONFIRMED로 바뀌었다".
비즈니스 의미는 Consumer가 직접 해석해야 한다.
그리고 테이블 스키마가 바뀌면 모든 Consumer가 영향을 받는다.
DB의 내부 구현이 외부 계약이 되어버리는 것이다.

### 선택지 2 --- Outbox 패턴

이벤트를 비즈니스 언어로 직접 설계하고 싶다면. outbox 테이블을 하나 만든다.
같은 트랜잭션 안에서:

1. orders 테이블 UPDATE
2. outbox 테이블에 이벤트 INSERT

같은 DB 트랜잭션이니까 둘 다 성공하거나 둘 다 실패한다.
원자성이 보장된다.
Debezium이 outbox 테이블의 변경을 읽어서 Kafka로 전달한다.

### Outbox가 주는 것

이벤트 페이로드를 개발자가 직접 정의할 수 있다.

```json
{
  "type": "OrderConfirmed",
  "orderId": "20260715-001",
  "amount": 15000
}
```

DB 스키마와 이벤트 스키마가 분리된다.
테이블 컬럼을 바꿔도 이벤트 구조는 그대로 유지할 수 있다.
CDC의 "내부 구현이 외부 계약" 문제를 Outbox가 해결한다.

### Outbox의 운영 비용

outbox 테이블은 계속 커진다.
이벤트가 Kafka로 전달된 뒤에도 행은 DB에 남아 있다. 주기적으로 삭제해야 한다.
대량 DELETE는 DB에 부하를 준다.
파티셔닝으로 DROP PARTITION하는 게 깔끔하지만 처음부터 설계하는 팀은 드물다.
그리고 모든 쓰기 트랜잭션에 outbox INSERT가 하나씩 추가된다.
TPS가 높은 시스템에서는 무시 못 할 비용이다.

### 선택지 3 --- Event Sourcing

발상을 뒤집는다.
보통 DB에는 "현재 상태"를 저장한다. 주문의 현재 상태는 CONFIRMED.
Event Sourcing은 다르다. "일어난 일"을 저장한다.
OrderCreated → OrderPaid → OrderConfirmed
현재 상태는 이벤트를 순서대로 재생해서 계산한다.
이벤트가 곧 데이터다. 별도로 이벤트를 "발행"할 필요가 없다.
저장 자체가 발행이다.

### 왜 상태만으로는 부족한가

```sql
SELECT status FROM orders WHERE id = 1;
-- → CANCELLED
```

취소됐다는 건 안다. 그런데 왜 취소됐는가? 고객이 취소한 건가, 재고 부족으로 시스템이 취소한 건가, 결제 실패로 자동 취소된 건가.
상태만 저장하면 "지금 어떤가"는 알 수 있지만 "어떻게 여기까지 왔는가"는 알 수 없다.
UPDATE는 이전 값을 덮어쓴다. 덮어쓴 순간 과거는 사라진다.

### Event Sourcing이 빛나는 도메인

[금융/결제]
계좌 잔액이 -50,000원이 됐다. "왜?"가 답변 가능해야 한다.
입금 3건, 출금 5건, 수수료 2건. 이벤트 시퀀스가 곧 장부다.
규제 기관은 현재 잔액이 아니라 거래 내역 전체를 요구한다.

[물류/배송]
주문이 "배송중"인데 고객은 못 받았다. 어디서 멈췄는가.
접수 → 출고 → 허브 도착 → 배송 출발.
각 단계가 이벤트로 남아 있어야 병목 지점을 찾을 수 있다.

[게임/포인트]
포인트 잔액 조작 의심 문의. 적립, 사용, 만료, 보상.
이벤트 로그가 없으면 "정상입니다"라고 답할 근거가 없다.

### Event Sourcing이 주는 것

모든 변경 이력이 남는다. "왜 이 상태가 됐는지"를 이벤트 시퀀스로 추적할 수 있다.
시간 여행이 가능하다. 어제 15시 기준 주문 상태를 그 시점까지만 재생하면 알 수 있다.
감사 추적이 자연스럽다. 금융, 결제, 의료처럼 "누가 언제 무엇을 했는가"가 규제 요구사항인 도메인에서 강력하다.

### Event Sourcing의 대가

읽기가 어려워진다.
"현재 주문 상태를 보여줘"에 이벤트를 처음부터 재생해야 한다.
주문 하나에 이벤트가 50개면 50번 재생해서 현재 상태를 구성한다.
스냅샷으로 완화할 수 있지만 복잡도가 올라간다.
그리고 이벤트 스키마는 한 번 정하면 바꾸기 어렵다.
과거 이벤트는 이미 저장돼 있다.
버전 관리가 필수다.

### CQRS --- Event Sourcing의 동반자

읽기 문제를 해결하는 패턴. 쓰기와 읽기를 완전히 분리한다.
쓰기: 이벤트 스토어에 append.
읽기: 이벤트를 구독해서
미리 만들어둔 읽기 뷰를 갱신.
주문 목록 조회? 이벤트를 재생하지 않는다. 읽기 전용 뷰를 바로 조회한다.
강력하지만 시스템이 두 배로 늘어난다.
쓰기 모델, 읽기 모델, 동기화 파이프라인. 세 가지를 전부 관리해야 한다.

### 언제 무엇을 선택하는가

[CDC]
기존 시스템에 이벤트 발행을 얹을 때.
코드를 안 건드리고 싶을 때.
이벤트 구조에 대한 요구가 느슨할 때.

[Outbox]
이벤트 스키마를 직접 설계해야 할 때.
DB 스키마와 이벤트를 분리해야 할 때.
대부분의 서비스에서 가장 현실적인 선택.

[Event Sourcing]
모든 변경 이력이 비즈니스 요구일 때.
감사 추적이 규제 요건일 때.
복잡도를 감당할 팀 역량이 있을 때.

### DBA 관점에서의 정리

세 가지 선택지의 공통점이 있다. 전부 DB를 경유한다는 것이다.
CDC는 DB 로그를 읽고, Outbox는 DB 테이블에 쓰고, Event Sourcing은 DB 자체가 이벤트 스토어다.
"이벤트를 발행한다"는 말이 개발자에게는 Kafka 토픽 설계지만 DBA에게는 디스크 용량이고, 복제 지연이고, 트랜잭션 크기다.
결국 이벤트 아키텍처의 신뢰성은 Kafka가 아니라 그 아래 있는 DB가 결정한다.
메시지 브로커는 전달할 뿐이다. 진실은 언제나 DB에 있다.

## 왜 분석 쿼리는 RDBMS에서 느린가: Athena, Snowflake, BigQuery의 구조

10억 행 테이블에서

```sql
SELECT AVG(amount) FROM orders WHERE created_at >= '2026-01-01'
```

을 실행한다.
MySQL에서 돌리면 수십 분이 걸린다.
BigQuery에서 돌리면 수 초에 끝난다. 같은 SQL인데 왜 이렇게 다를까.
답은 "DB가 좋아서"가 아니다. 데이터를 저장하는 방식이 근본적으로 다르기 때문이다.

### 행 저장이라는 기본값

모든 건 저장 방식에서 시작한다.
MySQL, PostgreSQL 같은 RDBMS는 행 단위(row-oriented)로 데이터를 저장한다.
하나의 행이 디스크에 연속으로 놓인다.

```text
[id=1, name="김철수", amount=50000, created_at="2026-01-15"]
[id=2, name="이영희", amount=30000, created_at="2026-02-20"]
[id=3, name="박민수", amount=70000, created_at="2026-01-08"]
```

한 사람의 정보를 전부 읽으려면 한 번의 디스크 읽기로 충분하다.

```sql
SELECT * FROM users WHERE id = 1
```

에 최적화된 구조다.

### 열 저장이라는 발상의 전환

BigQuery, Snowflake, Athena는 열 단위(column-oriented)로 저장한다.

```text
[id]: 1, 2, 3, ...
[name]: "김철수", "이영희", "박민수", ...
[amount]: 50000, 30000, 70000, ...
[created_at]: "2026-01-15", "2026-02-20", "2026-01-08", ...
```

같은 컬럼의 값들이 디스크에 연속으로 놓인다.
100개 컬럼 중 2개만 필요한 분석 쿼리라면 98개 컬럼은 아예 읽지 않는다.
이 차이가 모든 성능 격차의 출발점이다.

### 왜 열 저장이 분석에 유리한가

분석 쿼리의 특성을 보자.

```sql
SELECT AVG(amount) FROM orders WHERE created_at >= '2026-01-01'
```

이 쿼리가 필요한 컬럼은 딱 두 개다. amount와 created_at.
100개 컬럼이 있는 테이블이라도 98개 컬럼은 읽을 필요가 없다.
행 저장에서는?
amount를 읽으려면 그 행의 모든 컬럼을 디스크에서 읽어야 한다.
`id, name, email, address, phone...` 필요 없는 98개 컬럼까지 전부.
10억 행이면 10억 행의 모든 컬럼을 읽는다.
열 저장에서는?
amount 컬럼만 읽는다. created_at 컬럼만 읽는다. 나머지 98개 컬럼은 아예 디스크에서 읽지 않는다.
I/O 양이 50분의 1로 줄어든다. 100개 컬럼 중 2개만 읽으니까.
이게 "10배 빠르다"가 아니라 "100배 빠르다"가 가능한 이유다.

### 압축이라는 두 번째 무기

열 저장의 두 번째 장점은 압축이다.
같은 컬럼의 값은 같은 타입이다. amount에는 숫자만, created_at에는 날짜만, status에는 몇 가지 값만 반복된다.
같은 타입의 데이터가 연속으로 놓여 있으면 압축률이 극적으로 올라간다.

[Run-Length Encoding]
status에 'active'가 100만 번 반복되면 ('active', 1000000)으로 저장한다.
100만 개를 하나로 줄이는 셈이다.

[Dictionary Encoding]
값이 'active', 'inactive', 'pending' 세 가지면 사전을 만든다. 0, 1, 2.
문자열을 숫자로 바꾸는 것만으로 공간이 줄어든다.

### Delta Encoding과 Capacitor

[Delta Encoding]
created_at이 시간 순서로 정렬돼 있으면 값 자체 대신 이전 값과의 차이만 저장한다.
차이값은 원래 값보다 훨씬 작다.
BigQuery의 Capacitor 포맷은 이런 인코딩 기법들을 조합하고, 행의 순서까지 재배치(record reordering)해서 압축률을 극대화한다.
압축된 데이터는 디스크에서 더 적게 읽힌다. 네트워크를 덜 탄다. 메모리에 더 많이 올라간다.
모든 단계에서 빨라진다.

### BigQuery --- Google의 10년

BigQuery의 뿌리는 Dremel이다.
2010년 Google이 발표한 논문에서 시작된, 수십 페타바이트를 대화형으로 분석하기 위한 시스템이다.
Dremel 쿼리 엔진이 쿼리를 실행 트리로 분해한다.
리프 노드(slot)가 데이터를 읽고, 브랜치 노드(mixer)가 결과를 집계한다.
수천 대의 머신이 동시에 읽고, 집계하고, 합친다.
스토리지는 Colossus, 네트워크는 Jupiter, 컴퓨팅은 Borg. 이 세 인프라가 분리돼 있다.
스토리지와 컴퓨팅의 분리. 쿼리를 보내면 컴퓨팅 리소스가 동적으로 할당되고, 끝나면 반납된다.
서버를 프로비저닝할 필요가 없다. Serverless.

### Snowflake --- 3층 아키텍처

Snowflake는 스토리지와 컴퓨팅의 분리를 상용 제품으로 구현한 첫 클라우드 데이터 웨어하우스다.

[Storage Layer]
데이터는 Micro-Partition(50MB~500MB) 단위로 열 저장된다.
파티셔닝은 자동이다. 스키마 정의가 필요 없다.

[Compute Layer]
가상 웨어하우스가 쿼리를 실행한다. 웨어하우스는 독립적이다.
분석팀과 대시보드 서비스가 같은 데이터를 읽지만 서로의 성능에 영향을 주지 않는다.

[Cloud Services Layer]
인증, 메타데이터 관리, 쿼리 최적화, 접근 제어.
컴퓨팅과 분리된 독립 레이어에서 동작한다.

### Athena --- S3 위의 쿼리 엔진

Athena는 자체 스토리지가 없다. S3에 있는 데이터를 직접 쿼리하는 서비스다.
데이터를 "로드"하지 않는다.
S3에 Parquet 파일을 올려놓고, 스키마를 정의하고, SQL을 던진다.
쿼리 엔진은 Trino 기반이다.
코디네이터가 계획을 세우고, 워커 노드가 S3에서 데이터를 읽어 처리한다.
모든 처리가 인메모리 파이프라인이다.
강점은 "있는 데이터를 그대로 쿼리한다"는 것이다.
로그, 이벤트, JSON, CSV, Parquet. ETL 없이 바로 분석할 수 있다.
단, 성능은 포맷에 좌우된다. CSV 10TB는 느리고, Parquet로 변환하면 열 단위 접근 + 압축의 이점을 그대로 얻는다.

### 자원 경합과 수평 확장의 벽

RDBMS가 분석에 약한 진짜 이유는 단순히 "행 저장이니까"가 전부가 아니다.

[자원 경합]
RDBMS는 OLTP를 위해 설계됐다.
INSERT, UPDATE, DELETE가 초당 수천 건 들어오는 환경.
분석 쿼리가 10억 행을 풀스캔하면 Buffer Pool과 I/O 대역폭을 독점하고, 서비스 쿼리가 밀린다.
BigQuery, Snowflake, Athena는 분석 전용이다.
서비스 DB와 물리적으로 분리돼 있어서 아무리 무거운 쿼리를 돌려도 서비스에 영향이 없다.

[수평 확장]
RDBMS의 분석 쿼리는 하나의 인스턴스에서 실행된다.
그 서버의 물리적 한계가 쿼리의 한계다.
분석 엔진은 분산 실행한다.
10억 행을 1대가 읽으면 10분.
1000대가 나눠 읽으면 0.6초.

### 비용 모델의 전환

RDBMS는 서버가 항상 켜져 있다. 분석을 안 해도 비용이 나간다.
BigQuery는 스캔한 데이터 양에 비례해서 과금된다. 쿼리를 안 돌리면 스토리지 비용만 나간다.
Snowflake는 웨어하우스 실행 시간당 과금이다. 안 쓸 때는 자동으로 꺼진다.
Athena도 스캔한 데이터 양에 비례한다.
Parquet로 저장하면 스캔량이 줄어서 비용도 줄어든다.
"쓴 만큼만 낸다"는 모델이 대용량 분석에 훨씬 합리적이다.

### 세 서비스의 차이

같은 "분석용 DB"지만 세 서비스의 포지션은 다르다.

[BigQuery]
Google 인프라 위의 완전 서버리스.
Capacitor 포맷 + Dremel 엔진으로 자동 분산 실행.
적합: 페타바이트 스케일 분석, ML 파이프라인.

[Snowflake]
멀티 클라우드(AWS, GCP, Azure).
워크로드 격리와 데이터 거버넌스가 강점.
적합: 여러 팀이 같은 데이터를 다른 용도로 쓰는 환경.

[Athena]
자체 스토리지 없이 S3 직접 쿼리. Trino 기반.
적합: 이미 S3에 데이터가 있는 AWS 환경, 애드혹 분석.

### Parquet이라는 공통 언어

세 서비스 모두 Apache Parquet을 지원한다.
BigQuery는 자체 Capacitor 포맷이 기본이지만 Parquet 읽기를 지원한다.
Parquet은 열 단위 저장 포맷의 사실상 표준이다.
Parquet으로 데이터를 저장하면:

- 열 단위 접근 → 필요한 컬럼만 읽기
- 내장 압축 → Snappy, Zstd 등
- 중첩 구조 지원 → JSON 같은 데이터도 가능
- Row Group 단위 → 병렬 읽기에 적합

CSV 10TB를 Parquet으로 변환하면 1~2TB로 줄어드는 경우가 흔하다.
Athena에서 CSV를 쿼리하면 10TB를 스캔해서 비용이 50달러.
같은 데이터를 Parquet으로 바꾸면 200GB만 스캔해서 비용이 1달러.
포맷을 바꾸는 것만으로 성능과 비용이 동시에 개선된다.

### DBA 관점에서의 정리

"분석 쿼리가 느려요." 이 말을 들었을 때 RDBMS에서 인덱스를 추가하거나 쿼리를 튜닝하는 건 근본적 해결이 아닐 수 있다.
10억 행에서 GROUP BY + AVG를 하는 건 행 저장 기반 DB가 구조적으로 느린 작업이다.
아무리 튜닝해도 열 저장 + 분산 실행을 이길 수 없다.
올바른 질문은 이것이다. "이 쿼리는 OLTP인가, OLAP인가?"
OLTP면 RDBMS.
`WHERE id = 1`로 한 행을 빠르게 찾는 일.
INSERT, UPDATE가 초당 수천 건 들어오는 일.
OLAP면 분석 엔진.
수억 행에서 집계하는 일.
여러 차원으로 그룹핑하고 비교하는 일.

여기서는 BigQuery, Snowflake, Athena가 맞다.
"MySQL이 느린 게 아니다. MySQL에게 시킬 일이 아닌 걸 시킨 것이다."
망치에게 나사를 박으라고 하면 못 박는 게 아니라 나사가 부러진다.
도구를 탓하기 전에 쓰임새를 먼저 확인해야 한다.
