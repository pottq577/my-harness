# BEAR DBA

## 레플리케이션과 페일오버: 복제는 쉬운데 전환은 왜 어려운가

레플리카를 붙이는 건 어렵지 않다. 콘솔에서 버튼 하나면 된다.
읽기 트래픽이 분산되고, 장애 나면 승격하면 된다고 생각한다.
그런데 막상 장애가 터지면, "어떤 레플리카를 올릴 것인가"부터 막힌다.
복제는 쉽다. 전환이 어렵다.

### 레플리케이션이 필요한 이유

한 대짜리 DB는 위험하다. 죽으면 끝이다.
레플리케이션은 세 가지를 동시에 해결한다.

[읽기 분산]
쓰기는 마스터로, 읽기는 레플리카로.
읽기가 80%인 서비스라면 마스터 부하가 극적으로 줄어든다.

[고가용성]
마스터가 죽으면 레플리카를 승격한다.
백업에서 복원하는 것보다 훨씬 빠르다.

[재해 복구]
다른 리전에 레플리카를 두면 데이터센터가 통째로 날아가도 살아남는다.

### 비동기 복제

가장 기본적인 방식이다. 마스터가 쓰고, 레플리카가 뒤따라간다.
마스터는 트랜잭션을 커밋하고 바이너리 로그(binlog)나 WAL을 보낸다.
레플리카가 받아서 재실행한다.
마스터는 레플리카를 기다리지 않는다. 그래서 빠르다.
대신 마스터가 죽는 순간, 아직 전달 안 된 트랜잭션이 있을 수 있다.
데이터가 유실된다. 커밋은 성공했지만 복제는 안 된 영역.
이 틈이 비동기 복제의 근본적 한계다.

### 반동기 복제

MySQL의 `semi-synchronous replication`.
마스터가 커밋할 때 최소 한 대의 레플리카가 로그를 받았다는 확인(ACK)을 기다린다.

```sql
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_wait_point = 'AFTER_SYNC';
```

ACK가 오면 클라이언트에 응답을 돌려준다.
레플리카가 "적용"까지 한 건 아니다. "받았다"까지만 보장한다.
타임아웃 안에 ACK가 안 오면 비동기 모드로 자동 전환된다.
완전한 보장은 아니지만 비동기보다는 안전하다.
쓰기 지연은 네트워크 RTT만큼 늘어난다.

### 동기 복제

PostgreSQL의 synchronous_commit.
레플리카가 WAL을 디스크에 기록할 때까지 마스터가 기다린다.

```sql
ALTER SYSTEM SET synchronous_standby_names = 'replica1';
ALTER SYSTEM SET synchronous_commit = 'remote_apply';
```

`remote_apply`까지 설정하면 레플리카가 "적용 완료"할 때까지 기다린다.
데이터 유실 가능성이 사실상 0이다.
대가는 분명하다. 쓰기 지연이 네트워크 왕복 + 디스크 I/O만큼 늘어난다.
레플리카가 죽으면 마스터도 멈춘다.
금융처럼 한 건도 잃으면 안 되는 곳에서 쓴다.
그 외에는 반동기가 현실적 선택이다.

### 레플리케이션 랙

레플리카가 마스터를 뒤쫓아가는 지연이다.
0이면 완벽하지만, 현실에서 0인 적은 거의 없다.
랙이 커지는 원인:

[긴 트랜잭션]
마스터에서 100만 행을 UPDATE하면 레플리카도 100만 행을 재실행해야 한다.
마스터는 병렬이지만 레플리카는 직렬일 수 있다.

[대량 쓰기]
배치 작업, 대량 INSERT, DDL.
마스터의 쓰기 속도가 레플리카의 적용 속도를 초과한다.

[레플리카 스펙 부족]
마스터보다 낮은 스펙의 레플리카는 따라잡을 체력이 부족하다.

### 랙 모니터링

모르면 대응할 수 없다. 랙은 반드시 실시간으로 감시해야 한다.

MySQL:

```sql
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source
```

이 값은 "마지막으로 적용한 이벤트의 타임스탬프와 현재 시간의 차이"다.
정확하지 않다. 추정치다.
I/O 스레드가 멈추면 0으로 보이기도 한다.

PostgreSQL:

```sql
SELECT now() - pg_last_xact_replay_timestamp()
AS replication_lag;
```

pg_stat_replication 뷰로 바이트 단위 랙도 볼 수 있다.
알람 기준은 서비스마다 다르지만, 5초를 넘기면 문제가 생기기 시작한다.

### Read-after-Write 정합성 문제

마스터에 쓰고 레플리카에서 읽으면 방금 쓴 데이터가 안 보일 수 있다.
사용자가 글을 작성하고 새로고침했는데 글이 없다.
"저장 안 됐나?" 다시 쓴다. 중복 데이터가 생긴다.

해결 방법:

[쓴 직후에는 마스터에서 읽기]
쓰기 후 수 초간은 마스터 읽기로 라우팅.
단순하지만 효과적이다.

[세션 기반 일관성]
세션 내에서 자기가 쓴 데이터는 반드시 마스터에서 읽도록 보장.

[GTID 기반 대기]
MySQL의 `WAIT_FOR_EXECUTED_GTID_SET`.
레플리카가 특정 트랜잭션까지 따라잡을 때까지 기다린다.

### 페일오버 — 진짜 어려운 부분

마스터가 죽었다. 레플리카를 새 마스터로 승격해야 한다.
이 과정이 왜 어려운가.

[어떤 레플리카를 올릴 것인가]
가장 최신 데이터를 가진 레플리카가 후보다.
하지만 비동기 복제라면 어느 레플리카도 마스터와 100% 같지 않다.

[나머지 레플리카의 재연결]
새 마스터를 바라보도록 변경해야 한다.
GTID가 있으면 자동화할 수 있지만, 없으면 binlog 포지션을 수동으로 맞춰야 한다.

[애플리케이션의 연결 전환]
DNS를 바꾸든, VIP를 옮기든, 애플리케이션이 새 마스터를 알아야 한다.
이 전환 시간이 다운타임이다.

### 스플릿 브레인

페일오버에서 가장 무서운 시나리오다.
마스터가 죽은 줄 알고 레플리카를 승격했는데, 원래 마스터가 살아돌아왔다.
두 대가 동시에 쓰기를 받는다.
A에는 주문 1001이 '배달 중'이고 B에는 주문 1001이 '취소됨'이다.
누가 맞는가? 합칠 수 있는가? 어느 쪽을 버릴 것인가?
스플릿 브레인을 막으려면 옛 마스터를 확실히 차단해야 한다.
네트워크 펜싱, STONITH.
"의심스러우면 죽여라"가 원칙이다.

### RDS Multi-AZ와 Aurora 페일오버

AWS가 이 복잡함을 대신 처리해준다.

[RDS Multi-AZ]
동기 복제로 스탠바이를 유지한다.
장애 시 DNS를 스탠바이로 전환한다.
보통 60~120초.
DNS TTL과 커넥션 풀 갱신이 필요하다.

[Aurora]
스토리지 레이어가 분리돼 있다.
6개 복사본이 3개 AZ에 분산된다.
레플리카 승격은 스토리지를 복사하지 않는다.
보통 30초 이내.
Aurora는 Reader Endpoint도 제공한다.
읽기 부하 분산이 자동이다.
다만 DNS 기반이라 캐시 문제는 여전하다.

### Orchestrator, Patroni, repmgr

수동 페일오버는 새벽 3시에 하기 싫다.
자동화 도구가 필요하다.

[Orchestrator]
MySQL용. 토폴로지를 시각화하고 장애 감지 시 자동 승격한다.
GitHub가 만들었다.

[Patroni]
PostgreSQL용. etcd/ZooKeeper를 리더 선출에 쓴다.
분산 합의 기반이라 스플릿 브레인에 강하다.
Zalando가 만들어 오픈소스로 공개했다.

[repmgr]
PostgreSQL용. 설정이 단순하다.
소규모 클러스터에 적합하다.
분산 합의가 없어 스플릿 브레인 위험은 있다.
도구가 있어도 "정말 자동으로 전환할 것인가"는 팀의 판단이다.

### 캐스케이딩 레플리케이션

레플리카가 또 다른 레플리카의 소스가 되는 구조다.
`마스터 → 레플리카A → 레플리카B`
`마스터 → 레플리카A → 레플리카C`
마스터의 복제 부하를 줄일 수 있다.
레플리카가 5대, 10대로 늘어날 때 마스터가 모든 레플리카에 직접 보내면 네트워크와 CPU 부하가 크다.
대신 단점도 있다. 레플리케이션 랙이 누적된다.
A가 1초 늦으면 B는 2초 늦을 수 있다.
페일오버 시 토폴로지 재구성이 복잡해진다.
A가 죽으면 B, C를 어디에 붙일 것인가.

### DBA 관점에서의 정리

레플리케이션은 운영의 기본이다. 하지만 "붙여놨으니 안전하다"는 착각이다.
비동기면 데이터 유실 가능성을 수용하는 것이고, 동기면 쓰기 성능 저하를 감수하는 것이다.
공짜 점심은 없다.
랙 모니터링은 서비스 품질과 직결된다.
랙을 안 보고 운영하는 건 속도계 없이 운전하는 것과 같다.
페일오버 도구를 두더라도 정기적으로 전환 테스트를 해야 한다.
쓰지 않은 도구는 작동한다고 보장할 수 없다.

### 마무리

레플리카를 만드는 건 쉽다. 문제는 그 다음이다.
랙은 얼마나 허용할 것인가, 비동기와 동기 사이 어디에 설 것인가, 장애 시 자동 전환할 것인가 수동으로 할 것인가, 스플릿 브레인은 어떻게 막을 것인가.
이 질문들에 답할 수 있어야 레플리케이션을 "운영하고 있다"고 말할 수 있다.
복제는 설정이다. 하지만 전환은 판단이다.
그 판단의 무게가 DBA라는 직업의 본질이다.

## 주문 테이블 설계: orders 하나로 시작하면 첫 환불에서 깨진다

"주문 테이블 하나 만들어주세요."
`orders`에 `user_id`, `product_id`, `qty`, `price`. 컬럼 넷이면 끝난 것 같다.
그런데 상품 두 개를 한 번에 사면?
한 달 뒤 상품명이 바뀌면?
둘 중 하나만 취소하면?
쿠폰과 포인트를 같이 쓰면?
질문 하나마다 컬럼이 하나씩 늘고 어느 순간 ALTER TABLE로는 못 고치는 구조가 된다.
주문 헤더와 주문 상품을 분리하라.
주문 시점의 값은 참조하지 말고 복사하라.
상태는 덮어쓰지 말고 이력으로 쌓아라.
금액은 계산하지 말고 저장하고 검증하라.
PK와 주문번호를 분리하라.
주문 테이블은 CRUD가 아니라 장부다.
장부는 고쳐 쓰지 않고 덧붙여 쓴다.

### orders 하나로 시작하면

가장 흔한 첫 설계.

```sql
-- MySQL
CREATE TABLE orders (
order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id BIGINT NOT NULL,
product_id BIGINT NOT NULL,
qty INT NOT NULL,
price DECIMAL(12,2) NOT NULL
);
```

상품 하나만 사는 세계에서는 완벽하다.
두 개를 담는 순간 깨진다.
주문 한 건이 행 두 개가 되고 "주문 총액"을 어디에 둘지부터 막힌다.
주문은 헤더와 라인으로 나뉜다.
헤더는 "누가 언제 얼마를"이고 라인은 "무엇을 몇 개"다.

### 헤더와 라인

```sql
-- MySQL
CREATE TABLE orders (
order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id BIGINT NOT NULL,
status VARCHAR(20) NOT NULL
);
CREATE TABLE order_items (
order_item_id BIGINT PRIMARY KEY,
order_id BIGINT NOT NULL,
product_id BIGINT NOT NULL,
qty INT NOT NULL
);
```

주문 하나에 라인 N개. 이 1:N이 주문 설계의 뼈대다.
그런데 라인에 함정이 남아 있다.
product_id만 있다.

### 참조하지 말고 복사하라

라인에 product_id만 있으면 상품명과 가격은 JOIN으로 가져온다.
한 달 뒤 상품명이 바뀌고 가격이 오른다.
고객 주문 내역에 산 적 없는 이름이 뜨고 환불 금액도 지금 가격으로 계산된다.

```sql
-- MySQL
ALTER TABLE order_items
ADD product_name VARCHAR(200) NOT NULL,
ADD unit_price DECIMAL(12,2) NOT NULL,
ADD option_snapshot JSON NULL;
```

주문 시점의 값을 라인에 복사한다.
product_id는 추적용으로만 남긴다.
정규화 위반이 아니라 장부의 기본이다.

### PK와 주문번호는 다르다

`order_id`는 1, 2, 3으로 올라간다.
이걸 URL과 영수증에 그대로 노출하면 경쟁사가 하루 주문량을 셀 수 있고 번호 하나 바꿔서 남의 주문을 열어볼 수도 있다.

```sql
-- PostgreSQL
CREATE TABLE orders (
order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
order_no VARCHAR(32) NOT NULL UNIQUE,
-- ...
);
```

내부 PK는 JOIN용이다. 짧고 순차적이어야 인덱스가 좋다.
외부 주문번호는 사람용이다. 날짜가 들어가고 추측이 안 되어야 한다.
둘을 하나로 쓰면 어느 한쪽을 포기하게 된다.

### 금액은 네 개다

총액 하나면 될 것 같다.
환불할 때 상품 금액, 할인, 배송비를 각각 묻게 된다.

```sql
-- PostgreSQL
ALTER TABLE orders
ADD item_amount NUMERIC(12,2),
ADD discount_amount NUMERIC(12,2),
ADD shipping_fee NUMERIC(12,2),
ADD total_amount NUMERIC(12,2),
ADD CHECK (total_amount = item_amount
- discount_amount + shipping_fee);
```

계산하면 되지 않나.
정산 배치가 매일 수백만 라인을 다시 더한다.
파생값이라도 장부에는 적는다.
틀리는 길은 CHECK로 막는다.

### 상태는 덮어쓰지 않는다

`status` 하나를 `PAID`, `SHIPPED`로 `UPDATE`한다. 편하다.
그런데 CS에서 묻는다. "이 주문 언제 출고됐어요?"
답이 없다. 덮어썼으니까.

```sql
-- MySQL
CREATE TABLE order_status_history (
history_id BIGINT AUTO_INCREMENT PRIMARY KEY,
order_id BIGINT NOT NULL,
from_status VARCHAR(20) NULL,
to_status VARCHAR(20) NOT NULL,
changed_at DATETIME(6) NOT NULL
);
```

헤더의 status는 "지금 상태" 캐시다.
진실은 이력 테이블에 있다.

### 취소는 라인 단위로 온다

티셔츠와 바지를 한 주문에 샀다.
바지만 취소한다.
헤더 status에 CANCELLED를 넣으면 티셔츠까지 취소된 셈이 된다.
`PARTIALLY_CANCELLED`를 추가해도 "어느 것이" 취소됐는지는 없다.

```sql
-- PostgreSQL
ALTER TABLE order_items
ADD status VARCHAR(20) NOT NULL DEFAULT 'ORDERED',
ADD cancelled_qty INT NOT NULL DEFAULT 0
CHECK (cancelled_qty <= qty);
```

취소, 반품, 교환은 전부 라인에서 일어난다.
헤더 상태는 라인 상태들의 요약일 뿐이다.
방향은 항상 라인에서 헤더로다.

### 할인은 주문에 어떻게 붙는가

헤더에 coupon_id 컬럼을 하나 둔다.
쿠폰 한 장만 쓰면 문제없다.
쿠폰과 포인트를 같이 쓰면?
컬럼이 coupon_id_2, point_amount로 번식한다.

```sql
-- MySQL
CREATE TABLE order_discounts (
discount_id BIGINT PRIMARY KEY,
order_id BIGINT NOT NULL,
order_item_id BIGINT NULL,
discount_type VARCHAR(20) NOT NULL,
amount DECIMAL(12,2) NOT NULL
);
```

할인도 라인이다.
order_item_id가 NULL이면 주문 할인, 있으면 상품 할인.

### 인덱스는 조회 패턴이 정한다

주문 테이블을 읽는 사람은 둘이다.

[고객]
"내 주문 목록" 최신순.
user_id로 찾고 created_at으로 정렬한다.

[운영 배치]
"결제 후 3일 지난 미출고 건".
status로 찾고 created_at으로 자른다.

```sql
CREATE INDEX ix_orders_user ON orders (user_id, created_at DESC);
CREATE INDEX ix_orders_status ON orders (status, created_at);
```

status 단독 인덱스는 거의 쓸모가 없다.
DELIVERED가 전체의 대부분이라 옵티마이저가 인덱스를 버리기도 한다.
created_at을 뒤에 붙여야 범위가 잘린다.

### 최종 구조 한눈에

```text
orders 누가, 언제, 얼마를 (헤더)
├── order_items 무엇을 몇 개, 그때 가격으로 (스냅샷)
│ └── order_discounts 상품 단위 할인
├── order_discounts 주문 단위 할인 (order_item_id NULL)
└── order_status_history 언제 어떤 상태로 바뀌었나
```

테이블 넷.
처음의 orders 하나보다 복잡해 보인다.
하지만 이 넷은 첫 환불, 첫 상품명 변경, 첫 쿠폰 중복 사용에서 `ALTER TABLE` 없이 버틴다.

### DBA 관점에서의 정리

주문 테이블은 설계 시점에 가장 단순하고 운영 3년 차에 가장 복잡해지는 테이블이다.
주문 헤더와 주문 상품을 분리하라.
주문 시점의 값은 참조하지 말고 복사하라.
상태는 덮어쓰지 말고 이력으로 쌓아라.
금액은 계산하지 말고 저장하고 검증하라.
PK와 주문번호를 분리하라.
DBA가 이 테이블을 만나는 건 대개 수억 건이 쌓인 뒤다.
그때 라인을 분리하고 스냅샷 컬럼을 채워 넣는 마이그레이션은 처음 설계의 수십 배 비용이 되기도 한다.
주문 테이블은 CRUD가 아니라 장부다.
장부는 고쳐 쓰지 않고 덧붙여 쓴다.

## 로그인이 DB에 주는 영향: 출근 시간에 서버가 느려지는 이유

매일 오전 9시. 수만 명이 동시에 로그인한다.
대시보드가 느려지고, API 응답이 밀린다.
느린 건 비즈니스 로직이 아니다. 로그인이다.
로그인 한 번에 DB로 가는 쿼리는 생각보다 많다.
사용자 조회, 세션 생성, 마지막 접속 갱신, 권한 로딩.
하나하나는 가벼워도 수만 명이 동시에 치면 무겁다.

1. 세션 테이블은 INSERT와 DELETE가 교차하는 핫 테이블로 설계하라.
2. JWT를 쓰더라도 블랙리스트와 refresh token의 DB 비용을 계산하라.
3. 소셜 로그인의 upsert 패턴이 만드는 락을 인지하라.
4. 로그인 스파이크 시간대에 맞춰 커넥션 풀 여유를 확보하라.
5. 세션 스토어를 DB에서 분리하는 시점을 판단하라.

로그인은 매일 반복되는 부하다. 피크가 예측 가능하다는 게 오히려 함정이다.

### 세션 테이블에 무슨 일이 벌어지는가

전통적인 세션 기반 인증에서 로그인 한 번은 DB에 이런 흔적을 남긴다.

```text
SELECT: 사용자 아이디와 비밀번호 조회.
INSERT: 세션 테이블에 세션 ID, 만료시간, 사용자 정보 저장.
UPDATE: 사용자 테이블의 last_login_at 갱신.
```

로그아웃하면 DELETE. 세션이 만료되면 배치로 DELETE.
하나의 테이블에 INSERT, SELECT, DELETE가 끊임없이 교차한다.
이런 테이블은 인덱스 단편화가 빠르게 진행된다.
auto_increment PK가 계속 올라가면서 페이지 스플릿이 반복된다.
세션 테이블은 로그 테이블이 아니다. 살아 있는 데이터와 죽는 데이터가 동시에 존재하는 핫 테이블이다.

### JWT로 전환하면 DB 부하가 사라지는가

JWT는 서버에 상태를 저장하지 않는다.
토큰 자체에 사용자 정보가 들어 있으니 세션 테이블이 필요 없다.
그러면 DB 부하가 0이 되는가. 아니다.

[블랙리스트]
로그아웃한 토큰을 무효화해야 한다.
토큰이 만료될 때까지 블랙리스트에 보관해야 한다.
이 블랙리스트를 어딘가에 저장해야 한다.

[Refresh Token]
access token은 짧게, refresh token은 길게.
refresh token은 DB에 저장하는 경우가 많다.
탈취 대응을 위해 rotation을 하면 UPDATE가 추가된다.

[권한 변경 반영]
JWT 안에 담긴 권한 정보는 발급 시점 기준이다.
권한이 바뀌면 기존 토큰의 정보는 틀리다.
실시간 반영이 필요하면 매 요청마다 DB를 조회해야 한다.
세션 테이블 하나는 사라지지만 다른 형태의 DB 부하가 생긴다.

### 소셜 로그인이 만드는 추가 쿼리

카카오, 네이버, 구글 로그인. OAuth 콜백이 오면 DB에서 벌어지는 일이다.
먼저 provider + provider_user_iid 조합으로 기존 계정을 찾는다.
없으면 새 계정을 만든다. 있으면 토큰 정보를 갱신한다.
이것이 upsert다.

```sql
INSERT INTO social_accounts (provider, provider_user_iid, user_iid)
VALUES ('kakao', '12345', 42)
ON DUPLICATE KEY UPDATE updated_at = NOW();
```

MySQL에서 ON DUPLICATE KEY UPDATE는 내부적으로 exclusive lock을 잡는다.
동시에 같은 사용자가 여러 기기에서 로그인하면 같은 행에 락이 경합한다.
소셜 로그인은 편하지만 DB에는 일반 로그인보다 쿼리가 많다.
provider별 테이블 분리, 유니크 인덱스 설계가 성능을 좌우한다.

### 출근 시간 스파이크 패턴

B2B SaaS, 사내 시스템, 그룹웨어.
이런 서비스의 트래픽 그래프에는 뾰족한 봉우리가 두 개 있다.
오전 9시와 오후 1시. 출근 직후와 점심 직후. 수만 명이 거의 동시에 로그인한다.
이 스파이크는 선착순 이벤트와 다르다.
선착순은 예고된 1회성이지만 출근 스파이크는 매일 반복된다.
매일 반복된다는 건 DB가 매일 이 부하를 견뎌야 한다는 뜻이다.
인덱스 단편화도 매일 쌓이고 세션 만료 DELETE도 매일 돌아야 한다.
피크가 예측 가능하니까 대비도 가능하다고 생각하기 쉽다.
하지만 예측 가능한 피크를 매일 방치하면 그게 만성 장애의 씨앗이 된다.

### 세션 스토어를 Redis로 옮기면 해결되는가

세션을 DB 대신 Redis에 저장하면 INSERT/SELECT/DELETE가 전부 Redis로 간다.
DB 부하가 확실히 줄어든다.
하지만 새로운 질문이 생긴다.
Redis가 죽으면 전원이 로그아웃된다.
영속성을 원하면 AOF나 RDB 스냅샷을 켜야 한다.
그러면 Redis의 장점인 속도가 줄어든다.
세션 데이터 크기도 문제다.
세션에 장바구니, 최근 본 상품 같은 데이터를 넣으면 키 하나가 수 KB가 된다.
동시 접속 10만이면 메모리가 수 GB다.
Redis로 옮기는 건 해결이 아니라 전환이다. 문제의 장소가 바뀌는 것이다.
Redis의 메모리 정책, 복제, 장애 대응까지 설계해야 옮긴 의미가 있다.

### 실전 최적화 패턴

[last_login_at 갱신 분리]
로그인할 때마다 사용자 테이블을 UPDATE하면 사용자 테이블에 쓰기 경합이 생긴다.
비동기로 분리하거나 별도 테이블로 빼는 것이 낫다.

[세션 만료 배치]
expired된 세션을 실시간으로 DELETE하지 않는다.
새벽 시간대에 배치로 정리한다.
DELETE가 많으면 파티셔닝을 걸어 DROP PARTITION으로 처리한다.

[인증 캐시]
같은 사용자가 5분 안에 다시 로그인하면 DB 조회 없이 캐시에서 인증 정보를 반환한다.
브라우저 새로고침 폭풍을 막는 패턴이다.
작은 최적화들이 모여 스파이크를 흡수한다.

### DBA 관점에서의 정리

로그인은 기능적으로는 단순하다.
아이디 확인하고, 세션 만들고, 끝.
그런데 DB 입장에서는 가장 부하가 집중되는 시간대를 만드는 주범이다.
DBA가 모니터링 대시보드를 볼 때 매일 9시에 CPU가 치솟으면 가장 먼저 의심하는 게 로그인이다.
SHOW PROCESSLIST를 찍으면 세션 테이블 쿼리가 줄줄이 나온다.

1. 세션 테이블은 INSERT와 DELETE가 교차하는 핫 테이블로 설계하라.
2. JWT를 쓰더라도 블랙리스트와 refresh token의 DB 비용을 계산하라.
3. 소셜 로그인의 upsert 패턴이 만드는 락을 인지하라.
4. 로그인 스파이크 시간대에 맞춰 커넥션 풀 여유를 확보하라.
5. 세션 스토어를 DB에서 분리하는 시점을 판단하라.

로그인은 매일 반복되는 부하다. 피크가 예측 가능하다는 게 오히려 함정이다.

## 배포가 DB에 주는 영향: Rolling Update 중에 스키마가 달라지면 생기는 일

배포는 애플리케이션의 일이고 DB는 가만히 있는다고 생각하기 쉽다. 그렇지 않다.
Rolling Update 중에는 v1 서버와 v2 서버가 동시에 떠 있다. 둘 다 같은 DB를 바라본다.
v2가 새 컬럼을 기대하는데 아직 없으면 에러가 난다.
v1이 삭제된 컬럼을 읽으려 하면 에러가 난다.
코드는 두 버전인데 DB는 하나다. 이 간극이 장애를 만든다.

1. 컬럼 추가는 코드 배포 전에 먼저 하라.
2. 컬럼 삭제는 코드 배포 후에 나중에 하라.
3. 컬럼 이름 변경은 하지 마라. 새 컬럼 추가로 대체하라.
4. NOT NULL 제약은 DEFAULT 없이 추가하지 마라.
5. 스키마 버전과 앱 버전을 분리해서 관리하라.

DB 스키마는 앱보다 먼저 준비되고, 앱보다 늦게 정리되어야 한다.

### v1과 v2가 동시에 DB를 바라보는 순간

Rolling Update는 서버를 한 대씩 교체한다.
10대 중 3대가 v2로 올라갔고 7대는 아직 v1이다.
이 순간 DB에는 v1의 쿼리와 v2의 쿼리가 섞여 들어온다.
v2가 새 컬럼 memo를 INSERT한다.
v1은 memo 컬럼을 모른다.
v1의 INSERT에는 memo가 없다.
memo에 NOT NULL 제약이 걸려 있으면 v1의 INSERT가 실패한다.
배포 자체는 성공했는데 v1 서버에서 500 에러가 쏟아진다.
롤백해도 이미 v2가 쓴 데이터에 memo 값이 들어가 있다.
코드 배포와 스키마 변경이 동시에 일어나면 이런 창이 반드시 생긴다.

### 컬럼 추가는 안전한데 컬럼 삭제는 왜 위험한가

컬럼을 추가하는 건 비교적 안전하다.
v1은 새 컬럼을 모르지만 무시하면 된다.
`SELECT *`를 쓰지 않는 한 영향이 없다.
INSERT 시 새 컬럼에 DEFAULT가 있으면 문제없다.
컬럼 삭제는 다르다. v1이 아직 그 컬럼을 읽고 있다.
`SELECT old_column FROM users` 라는 쿼리가 돌고 있다.
컬럼을 지우는 순간 v1의 쿼리가 전부 실패한다.
컬럼 이름 변경도 마찬가지다.
old_name을 new_name으로 바꾸면 old_name을 참조하는 모든 코드가 깨진다.
이름 변경은 사실상 삭제 후 추가와 같다.
핵심 원칙은 간단하다.
추가는 코드보다 먼저. 삭제는 코드보다 나중에.

### Expand-Contract 패턴

스키마 변경의 표준 패턴이다.
확장하고, 마이그레이션하고, 수축한다.

[Expand]
새 컬럼을 추가한다. 기존 컬럼은 그대로 둔다.
v1과 v2 모두 정상 동작한다.

[Migrate]
v2를 전체 배포한다.
새 컬럼에 데이터를 채운다.
기존 컬럼의 데이터를 새 컬럼으로 옮긴다.

[Contract]
v1이 완전히 사라진 뒤에 기존 컬럼을 삭제한다.

세 단계가 각각 별도의 배포다.
한 번에 하려는 유혹을 참아야 한다.
급할수록 Expand-Contract가 빠르다.
한 번에 하면 롤백이 불가능하기 때문이다.

### Blue-Green 배포에서 DB가 병목이 되는 이유

Blue-Green은 두 환경을 통째로 준비한다.
Green이 준비되면 트래픽을 한 번에 전환한다.
Rolling Update의 혼재 문제가 없다.
애플리케이션은 그렇다. DB는 아니다.
Blue와 Green이 같은 DB를 쓰면 결국 두 버전이 같은 DB를 바라보는 것이다.
Rolling Update와 같은 문제가 생긴다.
DB도 분리하면 해결되지 않을까.
그러면 Blue DB의 데이터를 Green DB로 동기화해야 한다.
실시간 동기화는 복제 래그 문제가 있고 전환 순간의 데이터 정합성을 보장하기 어렵다.
결국 DB는 하나를 공유할 수밖에 없고 스키마 호환성은 애플리케이션이 책임져야 한다.
배포 전략이 뭐든 DB 호환성 문제는 피할 수 없다.

### 스키마 버전과 앱 버전을 분리해서 관리하는 법

앱 버전이 v2.3.1이고 DB 스키마가 migration_047이다.
이 둘은 독립적으로 관리해야 한다.
Flyway나 Liquibase 같은 마이그레이션 도구를 쓰면 스키마 변경에 고유 번호가 붙는다.
어떤 앱 버전이 어떤 스키마 버전을 필요로 하는지 명시한다.
중요한 규칙이 있다. 마이그레이션은 항상 전진만 한다.
롤백 마이그레이션은 만들지 않는다.
삭제가 필요하면 새 마이그레이션으로 삭제를 명시한다.
v2.3.1은 migration_045 이상이면 동작한다.
v2.4.0은 migration_047 이상이면 동작한다.
이런 식으로 호환 범위를 정의해두면 배포 순서를 자유롭게 조절할 수 있다.

### 실전에서 흔한 실수들

[NOT NULL 함정]
새 컬럼을 NOT NULL로 추가하면서 DEFAULT를 안 준다.
기존 행에 값이 없으니 마이그레이션이 실패한다.
반드시 DEFAULT를 함께 지정하거나 NULL 허용으로 시작한다.

[ENUM 추가]
MySQL의 ENUM에 값을 추가하는 건 DDL이다.
v2가 새 ENUM 값을 쓰는데 스키마에 아직 없으면 INSERT가 실패한다.
ENUM 추가는 코드 배포 전에 먼저 해야 한다.

[ORM의 자동 마이그레이션]
Django의 migrate, Rails의 db:migrate.
개발 환경에서는 편하지만 운영에서 자동 실행하면 위험하다.
ALTER TABLE이 언제 어떤 락을 잡는지 ORM은 신경 쓰지 않는다.

### DBA 관점에서의 정리

DBA에게 배포일은 긴장의 날이다.
슬로우 쿼리 알람이 울리면 가장 먼저 확인하는 게 "오늘 배포 있었나"다.
스키마 변경이 포함된 배포는 반드시 DBA와 사전 협의한다.
DDL이 어떤 락을 잡는지, 얼마나 걸리는지 DBA가 판단해야 한다.

1. 컬럼 추가는 코드 배포 전에 먼저 하라.
2. 컬럼 삭제는 코드 배포 후에 나중에 하라.
3. 컬럼 이름 변경은 하지 마라. 새 컬럼 추가로 대체하라.
4. NOT NULL 제약은 DEFAULT 없이 추가하지 마라.
5. 스키마 버전과 앱 버전을 분리해서 관리하라.
6. DB 스키마는 앱보다 먼저 준비되고, 앱보다 늦게 정리되어야 한다.
