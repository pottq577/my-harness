# BEAR DBA

## 레플리케이션과 페일오버: 복제는 쉬운데 전환은 왜 어려운가

레플리카를 붙이는 건 어렵지 않다. 콘솔에서 버튼 하나면 된다.
읽기 트래픽이 분산되고, 장애 나면 승격하면 된다고 생각한다.
그런데 막상 장애가 터지면, "어떤 레플리카를 올릴 것인가"부터 막힌다.
복제는 쉽다. 전환이 어렵다.

### 레플리케이션이 필요한 이유

한 대짜리 DB는 위험하다. 죽으면 끝이다.
레플리케이션은 세 가지를 동시에 해결한다.

[읽기 분산]
쓰기는 마스터로, 읽기는 레플리카로.
읽기가 80%인 서비스라면 마스터 부하가 극적으로 줄어든다.

[고가용성]
마스터가 죽으면 레플리카를 승격한다.
백업에서 복원하는 것보다 훨씬 빠르다.

[재해 복구]
다른 리전에 레플리카를 두면 데이터센터가 통째로 날아가도 살아남는다.

### 비동기 복제

가장 기본적인 방식이다. 마스터가 쓰고, 레플리카가 뒤따라간다.
마스터는 트랜잭션을 커밋하고 바이너리 로그(binlog)나 WAL을 보낸다.
레플리카가 받아서 재실행한다.
마스터는 레플리카를 기다리지 않는다. 그래서 빠르다.
대신 마스터가 죽는 순간, 아직 전달 안 된 트랜잭션이 있을 수 있다.
데이터가 유실된다. 커밋은 성공했지만 복제는 안 된 영역.
이 틈이 비동기 복제의 근본적 한계다.

### 반동기 복제

MySQL의 `semi-synchronous replication`.
마스터가 커밋할 때 최소 한 대의 레플리카가 로그를 받았다는 확인(ACK)을 기다린다.

```sql
SET GLOBAL rpl_semi_sync_master_enabled = 1;
SET GLOBAL rpl_semi_sync_master_wait_point = 'AFTER_SYNC';
```

ACK가 오면 클라이언트에 응답을 돌려준다.
레플리카가 "적용"까지 한 건 아니다. "받았다"까지만 보장한다.
타임아웃 안에 ACK가 안 오면 비동기 모드로 자동 전환된다.
완전한 보장은 아니지만 비동기보다는 안전하다.
쓰기 지연은 네트워크 RTT만큼 늘어난다.

### 동기 복제

PostgreSQL의 synchronous_commit.
레플리카가 WAL을 디스크에 기록할 때까지 마스터가 기다린다.

```sql
ALTER SYSTEM SET synchronous_standby_names = 'replica1';
ALTER SYSTEM SET synchronous_commit = 'remote_apply';
```

`remote_apply`까지 설정하면 레플리카가 "적용 완료"할 때까지 기다린다.
데이터 유실 가능성이 사실상 0이다.
대가는 분명하다. 쓰기 지연이 네트워크 왕복 + 디스크 I/O만큼 늘어난다.
레플리카가 죽으면 마스터도 멈춘다.
금융처럼 한 건도 잃으면 안 되는 곳에서 쓴다.
그 외에는 반동기가 현실적 선택이다.

### 레플리케이션 랙

레플리카가 마스터를 뒤쫓아가는 지연이다.
0이면 완벽하지만, 현실에서 0인 적은 거의 없다.
랙이 커지는 원인:

[긴 트랜잭션]
마스터에서 100만 행을 UPDATE하면 레플리카도 100만 행을 재실행해야 한다.
마스터는 병렬이지만 레플리카는 직렬일 수 있다.

[대량 쓰기]
배치 작업, 대량 INSERT, DDL.
마스터의 쓰기 속도가 레플리카의 적용 속도를 초과한다.

[레플리카 스펙 부족]
마스터보다 낮은 스펙의 레플리카는 따라잡을 체력이 부족하다.

### 랙 모니터링

모르면 대응할 수 없다. 랙은 반드시 실시간으로 감시해야 한다.

MySQL:

```sql
SHOW REPLICA STATUS\G
-- Seconds_Behind_Source
```

이 값은 "마지막으로 적용한 이벤트의 타임스탬프와 현재 시간의 차이"다.
정확하지 않다. 추정치다.
I/O 스레드가 멈추면 0으로 보이기도 한다.

PostgreSQL:

```sql
SELECT now() - pg_last_xact_replay_timestamp()
AS replication_lag;
```

pg_stat_replication 뷰로 바이트 단위 랙도 볼 수 있다.
알람 기준은 서비스마다 다르지만, 5초를 넘기면 문제가 생기기 시작한다.

### Read-after-Write 정합성 문제

마스터에 쓰고 레플리카에서 읽으면 방금 쓴 데이터가 안 보일 수 있다.
사용자가 글을 작성하고 새로고침했는데 글이 없다.
"저장 안 됐나?" 다시 쓴다. 중복 데이터가 생긴다.

해결 방법:

[쓴 직후에는 마스터에서 읽기]
쓰기 후 수 초간은 마스터 읽기로 라우팅.
단순하지만 효과적이다.

[세션 기반 일관성]
세션 내에서 자기가 쓴 데이터는 반드시 마스터에서 읽도록 보장.

[GTID 기반 대기]
MySQL의 `WAIT_FOR_EXECUTED_GTID_SET`.
레플리카가 특정 트랜잭션까지 따라잡을 때까지 기다린다.

### 페일오버 — 진짜 어려운 부분

마스터가 죽었다. 레플리카를 새 마스터로 승격해야 한다.
이 과정이 왜 어려운가.

[어떤 레플리카를 올릴 것인가]
가장 최신 데이터를 가진 레플리카가 후보다.
하지만 비동기 복제라면 어느 레플리카도 마스터와 100% 같지 않다.

[나머지 레플리카의 재연결]
새 마스터를 바라보도록 변경해야 한다.
GTID가 있으면 자동화할 수 있지만, 없으면 binlog 포지션을 수동으로 맞춰야 한다.

[애플리케이션의 연결 전환]
DNS를 바꾸든, VIP를 옮기든, 애플리케이션이 새 마스터를 알아야 한다.
이 전환 시간이 다운타임이다.

### 스플릿 브레인

페일오버에서 가장 무서운 시나리오다.
마스터가 죽은 줄 알고 레플리카를 승격했는데, 원래 마스터가 살아돌아왔다.
두 대가 동시에 쓰기를 받는다.
A에는 주문 1001이 '배달 중'이고 B에는 주문 1001이 '취소됨'이다.
누가 맞는가? 합칠 수 있는가? 어느 쪽을 버릴 것인가?
스플릿 브레인을 막으려면 옛 마스터를 확실히 차단해야 한다.
네트워크 펜싱, STONITH.
"의심스러우면 죽여라"가 원칙이다.

### RDS Multi-AZ와 Aurora 페일오버

AWS가 이 복잡함을 대신 처리해준다.

[RDS Multi-AZ]
동기 복제로 스탠바이를 유지한다.
장애 시 DNS를 스탠바이로 전환한다.
보통 60~120초.
DNS TTL과 커넥션 풀 갱신이 필요하다.

[Aurora]
스토리지 레이어가 분리돼 있다.
6개 복사본이 3개 AZ에 분산된다.
레플리카 승격은 스토리지를 복사하지 않는다.
보통 30초 이내.
Aurora는 Reader Endpoint도 제공한다.
읽기 부하 분산이 자동이다.
다만 DNS 기반이라 캐시 문제는 여전하다.

### Orchestrator, Patroni, repmgr

수동 페일오버는 새벽 3시에 하기 싫다.
자동화 도구가 필요하다.

[Orchestrator]
MySQL용. 토폴로지를 시각화하고 장애 감지 시 자동 승격한다.
GitHub가 만들었다.

[Patroni]
PostgreSQL용. etcd/ZooKeeper를 리더 선출에 쓴다.
분산 합의 기반이라 스플릿 브레인에 강하다.
Zalando가 만들어 오픈소스로 공개했다.

[repmgr]
PostgreSQL용. 설정이 단순하다.
소규모 클러스터에 적합하다.
분산 합의가 없어 스플릿 브레인 위험은 있다.
도구가 있어도 "정말 자동으로 전환할 것인가"는 팀의 판단이다.

### 캐스케이딩 레플리케이션

레플리카가 또 다른 레플리카의 소스가 되는 구조다.
`마스터 → 레플리카A → 레플리카B`
`마스터 → 레플리카A → 레플리카C`
마스터의 복제 부하를 줄일 수 있다.
레플리카가 5대, 10대로 늘어날 때 마스터가 모든 레플리카에 직접 보내면 네트워크와 CPU 부하가 크다.
대신 단점도 있다. 레플리케이션 랙이 누적된다.
A가 1초 늦으면 B는 2초 늦을 수 있다.
페일오버 시 토폴로지 재구성이 복잡해진다.
A가 죽으면 B, C를 어디에 붙일 것인가.

### DBA 관점에서의 정리

레플리케이션은 운영의 기본이다. 하지만 "붙여놨으니 안전하다"는 착각이다.
비동기면 데이터 유실 가능성을 수용하는 것이고, 동기면 쓰기 성능 저하를 감수하는 것이다.
공짜 점심은 없다.
랙 모니터링은 서비스 품질과 직결된다.
랙을 안 보고 운영하는 건 속도계 없이 운전하는 것과 같다.
페일오버 도구를 두더라도 정기적으로 전환 테스트를 해야 한다.
쓰지 않은 도구는 작동한다고 보장할 수 없다.

### 마무리

레플리카를 만드는 건 쉽다. 문제는 그 다음이다.
랙은 얼마나 허용할 것인가, 비동기와 동기 사이 어디에 설 것인가, 장애 시 자동 전환할 것인가 수동으로 할 것인가, 스플릿 브레인은 어떻게 막을 것인가.
이 질문들에 답할 수 있어야 레플리케이션을 "운영하고 있다"고 말할 수 있다.
복제는 설정이다. 하지만 전환은 판단이다.
그 판단의 무게가 DBA라는 직업의 본질이다.

## 주문 테이블 설계: orders 하나로 시작하면 첫 환불에서 깨진다

"주문 테이블 하나 만들어주세요."
`orders`에 `user_id`, `product_id`, `qty`, `price`. 컬럼 넷이면 끝난 것 같다.
그런데 상품 두 개를 한 번에 사면?
한 달 뒤 상품명이 바뀌면?
둘 중 하나만 취소하면?
쿠폰과 포인트를 같이 쓰면?
질문 하나마다 컬럼이 하나씩 늘고 어느 순간 ALTER TABLE로는 못 고치는 구조가 된다.
주문 헤더와 주문 상품을 분리하라.
주문 시점의 값은 참조하지 말고 복사하라.
상태는 덮어쓰지 말고 이력으로 쌓아라.
금액은 계산하지 말고 저장하고 검증하라.
PK와 주문번호를 분리하라.
주문 테이블은 CRUD가 아니라 장부다.
장부는 고쳐 쓰지 않고 덧붙여 쓴다.

### orders 하나로 시작하면

가장 흔한 첫 설계.

```sql
-- MySQL
CREATE TABLE orders (
order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id BIGINT NOT NULL,
product_id BIGINT NOT NULL,
qty INT NOT NULL,
price DECIMAL(12,2) NOT NULL
);
```

상품 하나만 사는 세계에서는 완벽하다.
두 개를 담는 순간 깨진다.
주문 한 건이 행 두 개가 되고 "주문 총액"을 어디에 둘지부터 막힌다.
주문은 헤더와 라인으로 나뉜다.
헤더는 "누가 언제 얼마를"이고 라인은 "무엇을 몇 개"다.

### 헤더와 라인

```sql
-- MySQL
CREATE TABLE orders (
order_id BIGINT AUTO_INCREMENT PRIMARY KEY,
user_id BIGINT NOT NULL,
status VARCHAR(20) NOT NULL
);
CREATE TABLE order_items (
order_item_id BIGINT PRIMARY KEY,
order_id BIGINT NOT NULL,
product_id BIGINT NOT NULL,
qty INT NOT NULL
);
```

주문 하나에 라인 N개. 이 1:N이 주문 설계의 뼈대다.
그런데 라인에 함정이 남아 있다.
product_id만 있다.

### 참조하지 말고 복사하라

라인에 product_id만 있으면 상품명과 가격은 JOIN으로 가져온다.
한 달 뒤 상품명이 바뀌고 가격이 오른다.
고객 주문 내역에 산 적 없는 이름이 뜨고 환불 금액도 지금 가격으로 계산된다.

```sql
-- MySQL
ALTER TABLE order_items
ADD product_name VARCHAR(200) NOT NULL,
ADD unit_price DECIMAL(12,2) NOT NULL,
ADD option_snapshot JSON NULL;
```

주문 시점의 값을 라인에 복사한다.
product_id는 추적용으로만 남긴다.
정규화 위반이 아니라 장부의 기본이다.

### PK와 주문번호는 다르다

`order_id`는 1, 2, 3으로 올라간다.
이걸 URL과 영수증에 그대로 노출하면 경쟁사가 하루 주문량을 셀 수 있고 번호 하나 바꿔서 남의 주문을 열어볼 수도 있다.

```sql
-- PostgreSQL
CREATE TABLE orders (
order_id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
order_no VARCHAR(32) NOT NULL UNIQUE,
-- ...
);
```

내부 PK는 JOIN용이다. 짧고 순차적이어야 인덱스가 좋다.
외부 주문번호는 사람용이다. 날짜가 들어가고 추측이 안 되어야 한다.
둘을 하나로 쓰면 어느 한쪽을 포기하게 된다.

### 금액은 네 개다

총액 하나면 될 것 같다.
환불할 때 상품 금액, 할인, 배송비를 각각 묻게 된다.

```sql
-- PostgreSQL
ALTER TABLE orders
ADD item_amount NUMERIC(12,2),
ADD discount_amount NUMERIC(12,2),
ADD shipping_fee NUMERIC(12,2),
ADD total_amount NUMERIC(12,2),
ADD CHECK (total_amount = item_amount
- discount_amount + shipping_fee);
```

계산하면 되지 않나.
정산 배치가 매일 수백만 라인을 다시 더한다.
파생값이라도 장부에는 적는다.
틀리는 길은 CHECK로 막는다.

### 상태는 덮어쓰지 않는다

`status` 하나를 `PAID`, `SHIPPED`로 `UPDATE`한다. 편하다.
그런데 CS에서 묻는다. "이 주문 언제 출고됐어요?"
답이 없다. 덮어썼으니까.

```sql
-- MySQL
CREATE TABLE order_status_history (
history_id BIGINT AUTO_INCREMENT PRIMARY KEY,
order_id BIGINT NOT NULL,
from_status VARCHAR(20) NULL,
to_status VARCHAR(20) NOT NULL,
changed_at DATETIME(6) NOT NULL
);
```

헤더의 status는 "지금 상태" 캐시다.
진실은 이력 테이블에 있다.

### 취소는 라인 단위로 온다

티셔츠와 바지를 한 주문에 샀다.
바지만 취소한다.
헤더 status에 CANCELLED를 넣으면 티셔츠까지 취소된 셈이 된다.
`PARTIALLY_CANCELLED`를 추가해도 "어느 것이" 취소됐는지는 없다.

```sql
-- PostgreSQL
ALTER TABLE order_items
ADD status VARCHAR(20) NOT NULL DEFAULT 'ORDERED',
ADD cancelled_qty INT NOT NULL DEFAULT 0
CHECK (cancelled_qty <= qty);
```

취소, 반품, 교환은 전부 라인에서 일어난다.
헤더 상태는 라인 상태들의 요약일 뿐이다.
방향은 항상 라인에서 헤더로다.

### 할인은 주문에 어떻게 붙는가

헤더에 coupon_id 컬럼을 하나 둔다.
쿠폰 한 장만 쓰면 문제없다.
쿠폰과 포인트를 같이 쓰면?
컬럼이 coupon_id_2, point_amount로 번식한다.

```sql
-- MySQL
CREATE TABLE order_discounts (
discount_id BIGINT PRIMARY KEY,
order_id BIGINT NOT NULL,
order_item_id BIGINT NULL,
discount_type VARCHAR(20) NOT NULL,
amount DECIMAL(12,2) NOT NULL
);
```

할인도 라인이다.
order_item_id가 NULL이면 주문 할인, 있으면 상품 할인.

### 인덱스는 조회 패턴이 정한다

주문 테이블을 읽는 사람은 둘이다.

[고객]
"내 주문 목록" 최신순.
user_id로 찾고 created_at으로 정렬한다.

[운영 배치]
"결제 후 3일 지난 미출고 건".
status로 찾고 created_at으로 자른다.

```sql
CREATE INDEX ix_orders_user ON orders (user_id, created_at DESC);
CREATE INDEX ix_orders_status ON orders (status, created_at);
```

status 단독 인덱스는 거의 쓸모가 없다.
DELIVERED가 전체의 대부분이라 옵티마이저가 인덱스를 버리기도 한다.
created_at을 뒤에 붙여야 범위가 잘린다.

### 최종 구조 한눈에

```text
orders 누가, 언제, 얼마를 (헤더)
├── order_items 무엇을 몇 개, 그때 가격으로 (스냅샷)
│ └── order_discounts 상품 단위 할인
├── order_discounts 주문 단위 할인 (order_item_id NULL)
└── order_status_history 언제 어떤 상태로 바뀌었나
```

테이블 넷.
처음의 orders 하나보다 복잡해 보인다.
하지만 이 넷은 첫 환불, 첫 상품명 변경, 첫 쿠폰 중복 사용에서 `ALTER TABLE` 없이 버틴다.

### DBA 관점에서의 정리

주문 테이블은 설계 시점에 가장 단순하고 운영 3년 차에 가장 복잡해지는 테이블이다.
주문 헤더와 주문 상품을 분리하라.
주문 시점의 값은 참조하지 말고 복사하라.
상태는 덮어쓰지 말고 이력으로 쌓아라.
금액은 계산하지 말고 저장하고 검증하라.
PK와 주문번호를 분리하라.
DBA가 이 테이블을 만나는 건 대개 수억 건이 쌓인 뒤다.
그때 라인을 분리하고 스냅샷 컬럼을 채워 넣는 마이그레이션은 처음 설계의 수십 배 비용이 되기도 한다.
주문 테이블은 CRUD가 아니라 장부다.
장부는 고쳐 쓰지 않고 덧붙여 쓴다.

## 로그인이 DB에 주는 영향: 출근 시간에 서버가 느려지는 이유

매일 오전 9시. 수만 명이 동시에 로그인한다.
대시보드가 느려지고, API 응답이 밀린다.
느린 건 비즈니스 로직이 아니다. 로그인이다.
로그인 한 번에 DB로 가는 쿼리는 생각보다 많다.
사용자 조회, 세션 생성, 마지막 접속 갱신, 권한 로딩.
하나하나는 가벼워도 수만 명이 동시에 치면 무겁다.

1. 세션 테이블은 INSERT와 DELETE가 교차하는 핫 테이블로 설계하라.
2. JWT를 쓰더라도 블랙리스트와 refresh token의 DB 비용을 계산하라.
3. 소셜 로그인의 upsert 패턴이 만드는 락을 인지하라.
4. 로그인 스파이크 시간대에 맞춰 커넥션 풀 여유를 확보하라.
5. 세션 스토어를 DB에서 분리하는 시점을 판단하라.

로그인은 매일 반복되는 부하다. 피크가 예측 가능하다는 게 오히려 함정이다.

### 세션 테이블에 무슨 일이 벌어지는가

전통적인 세션 기반 인증에서 로그인 한 번은 DB에 이런 흔적을 남긴다.

```text
SELECT: 사용자 아이디와 비밀번호 조회.
INSERT: 세션 테이블에 세션 ID, 만료시간, 사용자 정보 저장.
UPDATE: 사용자 테이블의 last_login_at 갱신.
```

로그아웃하면 DELETE. 세션이 만료되면 배치로 DELETE.
하나의 테이블에 INSERT, SELECT, DELETE가 끊임없이 교차한다.
이런 테이블은 인덱스 단편화가 빠르게 진행된다.
auto_increment PK가 계속 올라가면서 페이지 스플릿이 반복된다.
세션 테이블은 로그 테이블이 아니다. 살아 있는 데이터와 죽는 데이터가 동시에 존재하는 핫 테이블이다.

### JWT로 전환하면 DB 부하가 사라지는가

JWT는 서버에 상태를 저장하지 않는다.
토큰 자체에 사용자 정보가 들어 있으니 세션 테이블이 필요 없다.
그러면 DB 부하가 0이 되는가. 아니다.

[블랙리스트]
로그아웃한 토큰을 무효화해야 한다.
토큰이 만료될 때까지 블랙리스트에 보관해야 한다.
이 블랙리스트를 어딘가에 저장해야 한다.

[Refresh Token]
access token은 짧게, refresh token은 길게.
refresh token은 DB에 저장하는 경우가 많다.
탈취 대응을 위해 rotation을 하면 UPDATE가 추가된다.

[권한 변경 반영]
JWT 안에 담긴 권한 정보는 발급 시점 기준이다.
권한이 바뀌면 기존 토큰의 정보는 틀리다.
실시간 반영이 필요하면 매 요청마다 DB를 조회해야 한다.
세션 테이블 하나는 사라지지만 다른 형태의 DB 부하가 생긴다.

### 소셜 로그인이 만드는 추가 쿼리

카카오, 네이버, 구글 로그인. OAuth 콜백이 오면 DB에서 벌어지는 일이다.
먼저 provider + provider_user_iid 조합으로 기존 계정을 찾는다.
없으면 새 계정을 만든다. 있으면 토큰 정보를 갱신한다.
이것이 upsert다.

```sql
INSERT INTO social_accounts (provider, provider_user_iid, user_iid)
VALUES ('kakao', '12345', 42)
ON DUPLICATE KEY UPDATE updated_at = NOW();
```

MySQL에서 ON DUPLICATE KEY UPDATE는 내부적으로 exclusive lock을 잡는다.
동시에 같은 사용자가 여러 기기에서 로그인하면 같은 행에 락이 경합한다.
소셜 로그인은 편하지만 DB에는 일반 로그인보다 쿼리가 많다.
provider별 테이블 분리, 유니크 인덱스 설계가 성능을 좌우한다.

### 출근 시간 스파이크 패턴

B2B SaaS, 사내 시스템, 그룹웨어.
이런 서비스의 트래픽 그래프에는 뾰족한 봉우리가 두 개 있다.
오전 9시와 오후 1시. 출근 직후와 점심 직후. 수만 명이 거의 동시에 로그인한다.
이 스파이크는 선착순 이벤트와 다르다.
선착순은 예고된 1회성이지만 출근 스파이크는 매일 반복된다.
매일 반복된다는 건 DB가 매일 이 부하를 견뎌야 한다는 뜻이다.
인덱스 단편화도 매일 쌓이고 세션 만료 DELETE도 매일 돌아야 한다.
피크가 예측 가능하니까 대비도 가능하다고 생각하기 쉽다.
하지만 예측 가능한 피크를 매일 방치하면 그게 만성 장애의 씨앗이 된다.

### 세션 스토어를 Redis로 옮기면 해결되는가

세션을 DB 대신 Redis에 저장하면 INSERT/SELECT/DELETE가 전부 Redis로 간다.
DB 부하가 확실히 줄어든다.
하지만 새로운 질문이 생긴다.
Redis가 죽으면 전원이 로그아웃된다.
영속성을 원하면 AOF나 RDB 스냅샷을 켜야 한다.
그러면 Redis의 장점인 속도가 줄어든다.
세션 데이터 크기도 문제다.
세션에 장바구니, 최근 본 상품 같은 데이터를 넣으면 키 하나가 수 KB가 된다.
동시 접속 10만이면 메모리가 수 GB다.
Redis로 옮기는 건 해결이 아니라 전환이다. 문제의 장소가 바뀌는 것이다.
Redis의 메모리 정책, 복제, 장애 대응까지 설계해야 옮긴 의미가 있다.

### 실전 최적화 패턴

[last_login_at 갱신 분리]
로그인할 때마다 사용자 테이블을 UPDATE하면 사용자 테이블에 쓰기 경합이 생긴다.
비동기로 분리하거나 별도 테이블로 빼는 것이 낫다.

[세션 만료 배치]
expired된 세션을 실시간으로 DELETE하지 않는다.
새벽 시간대에 배치로 정리한다.
DELETE가 많으면 파티셔닝을 걸어 DROP PARTITION으로 처리한다.

[인증 캐시]
같은 사용자가 5분 안에 다시 로그인하면 DB 조회 없이 캐시에서 인증 정보를 반환한다.
브라우저 새로고침 폭풍을 막는 패턴이다.
작은 최적화들이 모여 스파이크를 흡수한다.

### DBA 관점에서의 정리

로그인은 기능적으로는 단순하다.
아이디 확인하고, 세션 만들고, 끝.
그런데 DB 입장에서는 가장 부하가 집중되는 시간대를 만드는 주범이다.
DBA가 모니터링 대시보드를 볼 때 매일 9시에 CPU가 치솟으면 가장 먼저 의심하는 게 로그인이다.
SHOW PROCESSLIST를 찍으면 세션 테이블 쿼리가 줄줄이 나온다.

1. 세션 테이블은 INSERT와 DELETE가 교차하는 핫 테이블로 설계하라.
2. JWT를 쓰더라도 블랙리스트와 refresh token의 DB 비용을 계산하라.
3. 소셜 로그인의 upsert 패턴이 만드는 락을 인지하라.
4. 로그인 스파이크 시간대에 맞춰 커넥션 풀 여유를 확보하라.
5. 세션 스토어를 DB에서 분리하는 시점을 판단하라.

로그인은 매일 반복되는 부하다. 피크가 예측 가능하다는 게 오히려 함정이다.

## 배포가 DB에 주는 영향: Rolling Update 중에 스키마가 달라지면 생기는 일

배포는 애플리케이션의 일이고 DB는 가만히 있는다고 생각하기 쉽다. 그렇지 않다.
Rolling Update 중에는 v1 서버와 v2 서버가 동시에 떠 있다. 둘 다 같은 DB를 바라본다.
v2가 새 컬럼을 기대하는데 아직 없으면 에러가 난다.
v1이 삭제된 컬럼을 읽으려 하면 에러가 난다.
코드는 두 버전인데 DB는 하나다. 이 간극이 장애를 만든다.

1. 컬럼 추가는 코드 배포 전에 먼저 하라.
2. 컬럼 삭제는 코드 배포 후에 나중에 하라.
3. 컬럼 이름 변경은 하지 마라. 새 컬럼 추가로 대체하라.
4. NOT NULL 제약은 DEFAULT 없이 추가하지 마라.
5. 스키마 버전과 앱 버전을 분리해서 관리하라.

DB 스키마는 앱보다 먼저 준비되고, 앱보다 늦게 정리되어야 한다.

### v1과 v2가 동시에 DB를 바라보는 순간

Rolling Update는 서버를 한 대씩 교체한다.
10대 중 3대가 v2로 올라갔고 7대는 아직 v1이다.
이 순간 DB에는 v1의 쿼리와 v2의 쿼리가 섞여 들어온다.
v2가 새 컬럼 memo를 INSERT한다.
v1은 memo 컬럼을 모른다.
v1의 INSERT에는 memo가 없다.
memo에 NOT NULL 제약이 걸려 있으면 v1의 INSERT가 실패한다.
배포 자체는 성공했는데 v1 서버에서 500 에러가 쏟아진다.
롤백해도 이미 v2가 쓴 데이터에 memo 값이 들어가 있다.
코드 배포와 스키마 변경이 동시에 일어나면 이런 창이 반드시 생긴다.

### 컬럼 추가는 안전한데 컬럼 삭제는 왜 위험한가

컬럼을 추가하는 건 비교적 안전하다.
v1은 새 컬럼을 모르지만 무시하면 된다.
`SELECT *`를 쓰지 않는 한 영향이 없다.
INSERT 시 새 컬럼에 DEFAULT가 있으면 문제없다.
컬럼 삭제는 다르다. v1이 아직 그 컬럼을 읽고 있다.
`SELECT old_column FROM users` 라는 쿼리가 돌고 있다.
컬럼을 지우는 순간 v1의 쿼리가 전부 실패한다.
컬럼 이름 변경도 마찬가지다.
old_name을 new_name으로 바꾸면 old_name을 참조하는 모든 코드가 깨진다.
이름 변경은 사실상 삭제 후 추가와 같다.
핵심 원칙은 간단하다.
추가는 코드보다 먼저. 삭제는 코드보다 나중에.

### Expand-Contract 패턴

스키마 변경의 표준 패턴이다.
확장하고, 마이그레이션하고, 수축한다.

[Expand]
새 컬럼을 추가한다. 기존 컬럼은 그대로 둔다.
v1과 v2 모두 정상 동작한다.

[Migrate]
v2를 전체 배포한다.
새 컬럼에 데이터를 채운다.
기존 컬럼의 데이터를 새 컬럼으로 옮긴다.

[Contract]
v1이 완전히 사라진 뒤에 기존 컬럼을 삭제한다.

세 단계가 각각 별도의 배포다.
한 번에 하려는 유혹을 참아야 한다.
급할수록 Expand-Contract가 빠르다.
한 번에 하면 롤백이 불가능하기 때문이다.

### Blue-Green 배포에서 DB가 병목이 되는 이유

Blue-Green은 두 환경을 통째로 준비한다.
Green이 준비되면 트래픽을 한 번에 전환한다.
Rolling Update의 혼재 문제가 없다.
애플리케이션은 그렇다. DB는 아니다.
Blue와 Green이 같은 DB를 쓰면 결국 두 버전이 같은 DB를 바라보는 것이다.
Rolling Update와 같은 문제가 생긴다.
DB도 분리하면 해결되지 않을까.
그러면 Blue DB의 데이터를 Green DB로 동기화해야 한다.
실시간 동기화는 복제 래그 문제가 있고 전환 순간의 데이터 정합성을 보장하기 어렵다.
결국 DB는 하나를 공유할 수밖에 없고 스키마 호환성은 애플리케이션이 책임져야 한다.
배포 전략이 뭐든 DB 호환성 문제는 피할 수 없다.

### 스키마 버전과 앱 버전을 분리해서 관리하는 법

앱 버전이 v2.3.1이고 DB 스키마가 migration_047이다.
이 둘은 독립적으로 관리해야 한다.
Flyway나 Liquibase 같은 마이그레이션 도구를 쓰면 스키마 변경에 고유 번호가 붙는다.
어떤 앱 버전이 어떤 스키마 버전을 필요로 하는지 명시한다.
중요한 규칙이 있다. 마이그레이션은 항상 전진만 한다.
롤백 마이그레이션은 만들지 않는다.
삭제가 필요하면 새 마이그레이션으로 삭제를 명시한다.
v2.3.1은 migration_045 이상이면 동작한다.
v2.4.0은 migration_047 이상이면 동작한다.
이런 식으로 호환 범위를 정의해두면 배포 순서를 자유롭게 조절할 수 있다.

### 실전에서 흔한 실수들

[NOT NULL 함정]
새 컬럼을 NOT NULL로 추가하면서 DEFAULT를 안 준다.
기존 행에 값이 없으니 마이그레이션이 실패한다.
반드시 DEFAULT를 함께 지정하거나 NULL 허용으로 시작한다.

[ENUM 추가]
MySQL의 ENUM에 값을 추가하는 건 DDL이다.
v2가 새 ENUM 값을 쓰는데 스키마에 아직 없으면 INSERT가 실패한다.
ENUM 추가는 코드 배포 전에 먼저 해야 한다.

[ORM의 자동 마이그레이션]
Django의 migrate, Rails의 db:migrate.
개발 환경에서는 편하지만 운영에서 자동 실행하면 위험하다.
ALTER TABLE이 언제 어떤 락을 잡는지 ORM은 신경 쓰지 않는다.

### DBA 관점에서의 정리

DBA에게 배포일은 긴장의 날이다.
슬로우 쿼리 알람이 울리면 가장 먼저 확인하는 게 "오늘 배포 있었나"다.
스키마 변경이 포함된 배포는 반드시 DBA와 사전 협의한다.
DDL이 어떤 락을 잡는지, 얼마나 걸리는지 DBA가 판단해야 한다.

1. 컬럼 추가는 코드 배포 전에 먼저 하라.
2. 컬럼 삭제는 코드 배포 후에 나중에 하라.
3. 컬럼 이름 변경은 하지 마라. 새 컬럼 추가로 대체하라.
4. NOT NULL 제약은 DEFAULT 없이 추가하지 마라.
5. 스키마 버전과 앱 버전을 분리해서 관리하라.
6. DB 스키마는 앱보다 먼저 준비되고, 앱보다 늦게 정리되어야 한다.

## 면접에서 SQL vs NoSQL을 물으면: 정답이 아니라 판단을 본다

"SQL과 NoSQL 차이점을 설명해주세요."
면접장에서 이 질문을 받으면 대부분 정의부터 읊는다.
ACID, BASE, CAP 정리. 관계형은 테이블, 비관계형은 도큐먼트.
틀린 답은 아니다. 하지만 합격하는 답도 아니다.
면접관이 진짜 보고 싶은 건 당신이 얼마나 아느냐가 아니라 어떤 상황에서 어떤 판단을 내리느냐다.

### 면접관이 듣고 싶은 것

"SQL과 NoSQL의 차이가 뭔가요?"
이 질문의 채점 기준은 정확성이 아니다.
면접관은 세 가지를 본다.
트레이드오프를 이해하는가. 실제로 선택해본 경험이 있는가. 그 선택의 근거를 논리적으로 설명할 수 있는가.
교과서적 정의는 5초면 충분하다.
나머지 시간은 "왜 그 상황에서 그걸 골랐는지"에 써야 한다.
"정답을 아는 사람"은 많다. "판단을 내릴 수 있는 사람"은 드물다.

### 이분법은 적신호다

면접에서 가장 위험한 답.
"NoSQL이 더 빠릅니다.", "RDBMS가 항상 안전합니다."
이런 단정은 면접관에게 "이 사람은 실무에서 안 써봤구나"라는 신호를 보낸다.
NoSQL이 빠른 건 특정 패턴에서다.
RDBMS가 안전한 건 특정 요구사항에서다.
조건 없는 단정은 기술 면접에서 가장 확실한 감점 요인이다.
"~한 경우에는 ~가 더 적합하다."
이 구조로 말하는 순간 시니어의 냄새가 난다.

### CAP 정리를 면접에서 쓰는 법

CAP 정리를 교과서처럼 설명하지 마라.
"Consistency, Availability, Partition tolerance 셋 중 둘만 고를 수 있습니다."
여기서 끝나면 위키피디아 수준이다. 면접관이 듣고 싶은 건 이거다.
"새벽 3시에 네트워크 파티션이 발생하면 당신의 서비스는 어떻게 되나요?"
CP를 택한 시스템은 응답을 거부한다.
AP를 택한 시스템은 옛날 데이터를 내보낸다.
결제 시스템이라면 CP다. 틀린 잔액보다 일시 중단이 낫다.
타임라인이라면 AP다. 3초 전 게시물이 안 보이는 건 괜찮다.

### RDBMS가 이기는 자리

모든 기술에는 홈그라운드가 있다. RDBMS의 홈은 명확하다.

[트랜잭션이 필수인 곳]
주문 생성 + 재고 차감 + 포인트 차감.
이 세 개가 원자적으로 묶여야 하면 BEGIN/COMMIT 한 줄이면 되는 RDBMS가 답이다.

[데이터 간 관계가 복잡한 곳]
사용자 → 주문 → 상품 → 카테고리.
JOIN 네 번이면 끝나는 걸 NoSQL에서는 비정규화 설계로 풀어야 한다.

[정합성이 돈과 직결되는 곳]
1원이라도 안 맞으면 감사 대상이 되는 금융.
Eventual Consistency는 선택지가 아니다.

### NoSQL이 이기는 자리

NoSQL이 빛나는 곳도 분명하다.

[스키마가 유동적인 곳]
상품 카탈로그. 의류는 사이즈/색상, 가전은 전압/와트.
항목마다 속성이 다르면 ALTER TABLE 없이 필드를 자유롭게 쓸 수 있는 도큐먼트 모델이 자연스럽다.

[수평 확장이 전제인 곳]
하루 10억 건의 이벤트 로그.
단일 서버의 쓰기 한계를 넘어서면 샤딩이 내장된 NoSQL이 유리하다.

[읽기 패턴이 고정된 곳]
"사용자 ID로 피드 조회."
접근 패턴이 확정돼 있으면 키 기반 조회로 단일 자릿수 밀리초가 나온다.

### 현실은 혼합이다

실제 프로덕션에서 하나의 DB만 쓰는 서비스는 드물다.
주문은 MySQL이다. 세션과 캐시는 Redis다. 검색은 Elasticsearch다. 로그는 또 다른 저장소다.
이게 Polyglot Persistence다. 데이터의 성격에 맞는 DB를 골라 쓰는 것.
면접에서 "둘 다 씁니다"라고 답하면 "어떤 기준으로 나누셨나요?"가 후속 질문이다.
"결제는 트랜잭션이 필수라 MySQL, 실시간 랭킹은 정렬 연산이 핵심이라 Redis Sorted Set"
이런 답이 나와야 한다.

### MongoDB에 대한 오해

"MongoDB는 스키마가 없다." 가장 널리 퍼진 오해다.
정확히는 "스키마를 DB가 강제하지 않는다"는 뜻이다.
스키마는 사라지지 않는다. 애플리케이션 코드로 옮겨갈 뿐이다.
스키마 없이 아무 구조나 넣으면 3개월 뒤 데이터 늪이 된다.
MongoDB의 진짜 강점은 스키마 진화(Schema Evolution)다.
필드 추가에 ALTER TABLE이 필요 없다.
다운타임 없이 구조를 점진적으로 바꿀 수 있다.
면접에서 "schemaless"라고 답하면 "schema-flexible"로 정정할 줄 아는 게 깊이다.

### DynamoDB의 사고방식

DynamoDB는 빠르다. 어떤 스케일에서도 단일 자릿수 밀리초.
대신 쿼리 모델이 완전히 다르다.
RDBMS처럼 아무 컬럼으로나 검색할 수 없다.
파티션 키를 모르면 풀 스캔이다.
GSI를 안 만들어두면 새 패턴을 못 쓴다.
"DynamoDB는 설계가 곧 성능이다."
테이블을 만들기 전에 접근 패턴을 전부 정의해야 한다.
RDBMS에서 "일단 넣고 나중에 쿼리"하던 습관은 DynamoDB에서 재앙이 된다.
면접에서 DynamoDB를 말하려면 싱글 테이블 디자인과 핫 파티션을 같이 말해야 한다.

### Redis는 데이터베이스일까?

Redis를 DB 대체제로 쓰면 안 된다.
Redis는 데이터 구조 서버다.
String, Hash, List, Set, Sorted Set, Stream. 각 자료구조가 특정 문제를 푸는 도구다.

- 세션 저장? Hash.
- 실시간 랭킹? Sorted Set.
- 메시지 큐? Stream.
- 분산 락? SET NX EX.

"Redis로 DB를 대체했습니다"라고 말하면 면접관은 "영속성은요?"라고 묻는다.
RDB/AOF가 있지만 RDBMS 수준의 내구성은 아니다.
Redis는 "빠른 계층"이지 "유일한 저장소"가 아니다.
면접에서 Redis를 언급할 때는 캐시 전략(Look-aside, Write-through)까지 묶어야 한다.

### 실패한 선택의 교훈

현장에서 본 실패들이다.

[NoSQL에 트랜잭션을 구현한 팀]
결제를 MongoDB로 만들었다. "멀티 도큐먼트 트랜잭션 지원하니까."
6개월 뒤 정합성 이슈가 터졌다.
결국 MySQL로 마이그레이션.
3개월이 걸렸다.

[RDBMS에 시계열을 넣은 팀]
IoT 센서 로그를 MySQL에 넣었다. 하루 5천만 건.
3개월 뒤 테이블이 45억 행이 됐다.
파티셔닝을 해도 집계가 수 분 걸렸다.

두 경우 모두 "이 데이터의 성격이 뭔가"를 먼저 묻지 않았다.
기술의 한계가 아니라 판단의 부재였다.

### 면접에서 답하는 순서

SQL vs NoSQL을 물으면 기술이 아니라 데이터 모델부터 시작하라.

1. 1단계: 데이터의 성격을 먼저 말한다.
   1. "이 데이터는 트랜잭션이 필수입니다."
   2. "이 데이터는 쓰기가 읽기보다 100배 많습니다."
2. 2단계: 요구사항을 정리한다.
   1. "정합성이 최우선입니다."
   2. "수평 확장이 전제입니다."
3. 3단계: 그 요구사항에 맞는 기술을 고른다.
   1. "그래서 이 경우에는 MySQL이 적합합니다."
   2. "그래서 이 경우에는 DynamoDB가 적합합니다."

기술 → 요구사항 순서로 말하면 주니어다.
요구사항 → 기술 순서로 말하면 시니어다.

### 면접관에게 역질문하라

시니어 면접에서는 답하는 것보다 질문하는 것이 더 중요할 때가 있다.
"그 서비스의 읽기/쓰기 비율이 어떻게 되나요?"
읽기 95%면 캐시 전략이 핵심이다. 쓰기 50% 이상이면 DB 선택이 완전히 달라진다.
"정합성 요구 수준이 어느 정도인가요?"
Strong Consistency가 필수면 RDBMS 방향이다. Eventual이 허용되면 선택지가 넓어진다.
"현재 데이터 규모와 증가율은요?"
100GB면 단일 서버로 충분하다. 10TB면 수평 확장을 고려해야 한다.
이런 질문을 던지는 것 자체가 "이 사람은 실무에서 이런 판단을 해봤다"는 증거다.

### 면접에서 절대 하면 안 되는 말

경험상 감점이 확실한 패턴들이다.

- "NoSQL이 트렌드라서요."
  - 기술 선택의 근거가 유행이면 신뢰를 잃는다.
- "확장성 때문에 처음부터 NoSQL로 갔습니다."
  - 사용자 1,000명인데 수평 확장을 대비하면 오버엔지니어링이다.
- "JOIN이 느려서 NoSQL을 선택했습니다."
  - JOIN이 느린 건 인덱스 설계 문제일 확률이 높다.

도구를 바꾸기 전에 사용법을 점검했는지가 먼저다.
"MongoDB가 스키마 없으니까 편해서요."
스키마 관리를 코드로 떠넘긴 것이다.
편한 게 아니라 책임이 이동한 것이다.

### DBA 관점에서의 정리

1,000개 넘는 클러스터를 운영하면서 가장 많이 본 실패 패턴이 있다.
"왜 이 DB를 쓰세요?" -> "원래 쓰던 거라서요."
기술 선택에 이유가 없는 것. 이게 가장 비싼 실패다.
면접에서 SQL vs NoSQL을 물을 때 면접관이 원하는 건 정답이 아니다.
"이 데이터의 성격은 이렇고, 이 요구사항에서는 이 트레이드오프가 발생하고, 그래서 이걸 골랐고, 이 단점은 이렇게 보완했다."
이 흐름을 자기 언어로 말할 수 있으면 어떤 DB 질문이 와도 흔들리지 않는다.

### 마무리

SQL vs NoSQL은 어느 쪽이 낫냐의 문제가 아니다.
어느 쪽이 이 상황에 맞느냐의 문제다.
면접관은 당신의 암기력을 테스트하지 않는다.
당신이 트레이드오프 앞에서 어떤 논리로 결정을 내리는지를 본다.
정의를 외우지 마라. 판단을 연습하라.
"이 데이터는 어떤 성격인가?"
"가장 비싼 실패는 뭔가?"
"그래서 어떤 DB가 맞는가?"
이 세 질문에 답할 수 있으면 SQL vs NoSQL 문제는 이미 풀린 것이다.

## 기술만으로 해결되지 않는 것들: 배치 시간, 소통, 그리고 마케팅

DB CPU가 100%를 찍었다. 슬로우 쿼리를 잡았다.
인덱스를 걸었다. 스펙을 올렸다.
그런데 한 달 뒤 또 터진다. 같은 시간, 같은 패턴으로.
원인을 파보면 쿼리가 느린 게 아니라 그 시간에 모든 게 몰려 있었던 거다.
기술로 풀 수 있는 문제의 한계가 있다.
나머지는 사람이 풀어야 한다.

### 피크 시간에 배치를 돌리는 사람들

새벽 2시에 돌던 배치가 있다.
어느 날 담당자가 바뀌고 "출근하면 결과를 보고 싶다"는 이유로 오전 9시로 옮겼다.
오전 9시. 서비스 트래픽이 올라오는 시간이다.
배치가 풀스캔을 돌리는 동안 서비스 쿼리의 응답 시간이 2배로 뛴다.
기술적 해결?
리플리카를 하나 더 만들어서 배치 전용으로 쓸 수 있다.
비용은 월 수십만 원에서 수백만 원.
실제 해결?
"이 배치, 새벽으로 돌려도 되나요?"
슬랙 메시지 한 줄이면 끝난다.

### 마케팅이 DB를 죽이는 순간

"내일 오전 10시 타임세일 오픈합니다."
푸시 알림이 300만 명에게 동시에 나간다.
10시 정각, 트래픽이 평소의 20배로 치솟는다.
커넥션 풀이 고갈된다.
데드락이 터진다.
재고 차감 쿼리가 경합에 빠진다.
DBA는 장애 대응에 들어간다.
하지만 이건 DB의 문제가 아니다. 마케팅의 문제도 아니다.
둘 사이에 대화가 없었던 게 문제다.
"10시에 트래픽 터집니다"를 알았으면 오토스케일링을 미리 걸거나 커넥션 풀을 늘려두거나 재고 캐시를 워밍할 수 있었다.

### 10시 정각이 아니어도 되는 이유

쿠팡의 로켓와우 세일을 보자. 타임세일 진입 시 대기열이 뜬다.
"앞에 12,345명이 기다리고 있습니다."
이건 서버가 감당을 못 해서가 아니다.
트래픽을 의도적으로 흘려보내는 거다.
네이버 예약 시스템도 마찬가지다.
수강 신청 시 랜덤 대기열을 부여한다.
정각에 몰리는 부하를 30초로 분산시킨다.
기술적으로 DB를 강화할 수도 있었다.
하지만 UX로 부하 자체를 깎은 거다.
"트래픽을 받아내는 기술"이 아니라 "트래픽이 한꺼번에 오지 않게 만드는 설계."
가장 좋은 장애 대응은 장애가 일어나지 않게 하는 것이다.

### "언제 하세요?"라는 질문의 위력

DBA가 가장 많이 하는 질문 중 하나다. "이 작업, 언제 하실 건가요?"
DDL을 언제 실행할 건지.
데이터 마이그레이션을 언제 돌릴 건지.
대용량 DELETE를 몇 시에 시작할 건지.
같은 ALTER TABLE이라도 피크 시간에 하면 장애고 새벽에 하면 그냥 작업이다.
같은 쿼리가 월요일 오전에는 서비스를 멈추고 일요일 새벽에는 흔적도 없이 끝난다.
기술이 바뀐 게 아니다.
시점이 바뀐 것뿐이다.

### 개발팀이 모르는 것

개발자는 코드를 본다. DBA는 시간대를 본다.
개발자가 짠 배치가 느리다고 쿼리를 튜닝해달라는 요청이 온다.
쿼리를 보면 문제없다. 풀스캔도 아니고 인덱스도 잘 타고 있다.
그런데 왜 느리냐고?
그 시간에 다른 배치 세 개가 같은 테이블을 동시에 긁고 있어서다.
이건 쿼리 튜닝으로 못 푼다. 배치 스케줄을 조율해야 한다.
"A팀 배치를 30분 앞으로 당기고 B팀 배치를 1시간 뒤로 미루면 셋 다 제 시간에 끝납니다."
이 한마디가 인덱스 열 개보다 효과적일 때가 있다.

### 쿠폰을 뿌리는 방법

"선착순 1만 명 쿠폰 지급."
기술팀은 Redis 분산 락을 도입한다.
재고 차감을 원자적으로 처리한다.
큐를 넣고, 비동기로 처리한다.
전부 필요한 기술이다.
하지만 근본적인 질문이 있다.
"선착순이어야 하나?"
선착순 대신 응모로 바꾸면 10시 정각의 트래픽 스파이크가 사라진다.
하루 동안 고르게 분산된다.
선착순 대신 랜덤 추첨으로 바꾸면 1초에 100만 요청이 24시간에 걸쳐 천천히 들어온다.
DB 입장에서 보면 TPS 100만을 1초에 처리하는 것과 TPS 12를 하루에 걸쳐 처리하는 것은 완전히 다른 세계다.
마케팅 방식 하나 바꾸는 것이 서버 10대 증설보다 효과적일 수 있다.

### 공지 한 줄의 가치

점검 공지를 잘 쓰는 것도 기술이다.
"8월 7일 02:00~04:00 서버 점검" 이 한 줄이 새벽 2시 배포의 리스크를 절반으로 줄인다.
사용자가 "장애"가 아니라 "점검"으로 인식한다.
반대로, 예고 없이 새벽에 배포했다가 한 명이 에러를 만나면 커뮤니티에 "서버 터짐"이 올라온다.
같은 다운타임이라도 예고하면 점검이고 예고 안 하면 장애다.
인식을 바꾸는 것도 문제 해결이다.

### 캐시보다 나은 해결

"상품 상세 페이지가 느립니다."
Redis 캐시를 도입한다.
TTL을 5분으로 설정한다.
DB 부하가 80% 줄어든다.
하지만 다른 접근도 가능하다.
상품 상세의 실시간성이 정말 필요한 정보는 가격과 재고뿐이다.
나머지는 한 시간에 한 번 바뀔까 말까다.
정적 부분을 CDN으로 밀어내고 가격과 재고만 API로 호출하면 DB 쿼리 자체가 1/10로 줄어든다.
캐시를 도입하는 것보다 "무엇이 실시간이어야 하는지"를 정의하는 대화가 먼저다.

### 소통이 아키텍처다

넷플릭스의 카오스 엔지니어링은 기술 이야기로 많이 회자된다.
하지만 그 뒤에는 "장애는 일어난다"는 전제를 조직 전체가 공유한 문화가 있다.
장애가 일어났을 때 "누구 책임이냐"를 따지는 조직과 "어떻게 복구하느냐"를 따지는 조직은 같은 기술을 써도 결과가 다르다.
포스트모템을 쓰는 문화.
장애 공유 채널에 타임라인을 올리는 습관.
"이거 혹시 영향 있나요?"를 묻는 자세.
이런 것들이 모이면 아키텍처보다 단단한 시스템이 된다.

### DBA 관점에서의 정리

11년 동안 DB를 운영하면서 가장 효과적이었던 해결이 뭐였냐고 묻는다면 인덱스를 건 것도 아니고 스펙을 올린 것도 아니다.
"이 배치, 새벽으로 옮겨주실 수 있나요?"
"이 이벤트, 선착순 말고 응모로 바꿀 수 있나요?"
"이 작업, 피크 시간 피해서 해주실 수 있나요?"
이런 대화였다.
기술은 도구다. 강력한 도구다.
하지만 도구를 쓰기 전에 문제 자체를 없앨 수 있는지 먼저 봐야 한다.
트래픽을 받아내는 것도 실력이지만 트래픽이 몰리지 않게 만드는 것도 실력이다.
가장 좋은 튜닝은 튜닝이 필요 없는 상황을 만드는 것이다.

## 클라우드 시대에 DB를 공부해야 하는 이유

"AWS가 다 해주는데 DB를 왜 공부해요?"
이 질문을 받을 때마다 같은 생각을 한다.
인테리어 업체가 다 해주는데 집 구조를 왜 알아야 하냐는 질문과 같다.
모르면 시키는 대로 산다. 알면 시킬 수 있다.
그 차이가 연봉이 되고, 커리어가 되고, 결국 시장에서 살아남느냐 마느냐가 된다.
클라우드가 다 해준다는 말은 반만 맞다. 운영은 해준다.
이해는 해주지 않는다.

### 클라우드가 해주는 것

솔직히 말하면 많이 해준다.

- 백업
  - 자동이다. 스냅샷 찍히고 보관된다.
- 장애 복구
  - 멀티 AZ 띄워놓으면 자동 페일오버된다.
- 스케일링
  - 버튼 하나로 스펙을 올린다.
- 패치
  - 마이너 버전 자동 업그레이드도 된다.

MSP까지 붙이면 황제가 부럽지 않다.
모니터링도 해주고, 알람도 걸어주고, 장애 나면 새벽에 대신 전화도 받아준다.
그래서 착각한다. "나는 DB를 몰라도 된다."

### 모르면 어떻게 되는가

클라우드 콘솔에서 백업이 켜져 있다. 안심한다.
그런데 묻는다.
"PITR 복구 가능 시점이 언제까지인지 아세요?" 모른다.
"복구 테스트 해보셨어요?" 안 해봤다.
"백업 보관 주기가 며칠인지 아세요?" 기본값인 것 같다.
백업이 있는 것과 복구할 수 있는 것은 다르다.
이걸 모르는 사람이 장애를 만나면 할 수 있는 게 없다.
MSP에 전화해서 "복구해주세요" 한마디. 그리고 기다린다.

### 알면 어떻게 달라지는가

같은 상황에서 DB를 아는 사람은 다르게 움직인다.
"이 클러스터 PITR 보관이 1일이네요. 최소 7일로 늘려주세요."
요청이 아니라 지시가 된다.
"이 파라미터 그룹에 slow_query_log가 꺼져 있네요. 켜주시고 long_query_time은 1초로 잡아주세요."
MSP가 제안하기 전에 내가 먼저 말한다.
"리더 인스턴스 추가하면 비용이 얼마 늘어나는데 읽기 분산 효과 대비 ROI가 안 나와요. 커넥션 풀링부터 점검하겠습니다."
비용까지 판단한다.
모르면 수동적으로 문의한다.
알면 적극적으로 설계한다.
이 차이가 회의실에서 드러난다.

### MSP는 내 커리어를 책임지지 않는다

MSP는 좋은 서비스다. 운영 부담을 줄여준다. 새벽 장애 대응도 해준다.
그런데 MSP가 해주는 건 내 회사의 서비스 안정성이지 내 커리어의 안정성이 아니다.
MSP에 기대서 3년을 보내면 이력서에 쓸 게 없다.
"AWS RDS 운영 경험"이라고 적지만 실제로는 콘솔 클릭과 티켓 발행뿐이다.
면접관이 묻는다.
"장애 상황에서 어떻게 대응하셨나요?"
"MSP에 연락했습니다."
그 다음 질문은 없다.

### 알고 시키는 것과 모르고 시키는 것

둘 다 결과는 같을 수 있다.
DB가 잘 돌아간다. 장애가 나도 복구된다.
하지만 과정이 다르다.
모르고 시키면 기다린다. MSP가 답을 줄 때까지 기다린다.
답이 맞는지 틀린지도 모른다.
"전문가가 했으니까 맞겠지."
알고 시키면 확인한다.
내가 원하는 방향을 제시하고 결과를 검증한다.
틀리면 다시 요청한다.
전자는 의존이다. 후자는 위임이다.
위임할 줄 아는 사람이 리더가 된다.
의존하는 사람은 대체된다.

### 클라우드가 가린 것들

클라우드는 복잡한 것들을 버튼 뒤에 숨겼다. 덕분에 편해졌다.
대신 보이지 않게 됐다.
스토리지 I/O가 어떻게 동작하는지.
인덱스가 왜 이 쿼리에서 안 타는지.
커넥션이 왜 부족한지.
락이 왜 걸리는지.
레플리카 지연이 왜 발생하는지.
이런 것들은 콘솔에 버튼이 없다.
CloudWatch 그래프만 봐서는 원인을 모른다.
"CPU가 높아요"는 증상이다.
"풀스캔 쿼리 3개가 동시에 돌고 있어요"가 원인이다.
증상만 보는 사람과 원인을 찾는 사람.
클라우드가 아무리 좋아져도 이 차이는 줄어들지 않는다.

### DB를 공부하면 생기는 것

이력서에 쓸 수 있는 경험이 생긴다.
"쿼리 튜닝으로 응답 시간을 줄였다."
"인덱스 재설계로 CPU 사용률을 낮췄다."
"커넥션 풀링 최적화로 장애를 예방했다."
이런 한 줄이 면접에서 30분짜리 이야기가 된다.
DB를 모르면 인프라 위에서 앱만 돌린 사람이다.
DB를 알면 인프라를 설계할 수 있는 사람이 된다.
시니어와 주니어의 차이는 연차가 아니다. "왜"를 설명할 수 있느냐의 차이다.
DB는 그 "왜"를 가장 많이 만들어주는 영역이다.

### 마무리

클라우드가 다 해준다는 말은 반만 맞다.
운영은 해준다. 이해는 해주지 않는다.
MSP가 다 해준다는 말도 반만 맞다.
서비스는 지켜준다. 커리어는 지켜주지 않는다.
알고 시키는 사람은 어디서든 일할 수 있다.
모르고 시키는 사람은 그 자리에서만 일할 수 있다.
DB를 공부해야 하는 이유는 단순하다.
클라우드가 해주지 않는 영역이 내 시장 가치를 결정하기 때문이다.

## MySQL vs PostgreSQL: 뭘 고르든 후회하는 이유

"MySQL이 좋아요, PostgreSQL이 좋아요?"
DBA한테 가장 많이 들어오는 질문이다.
솔직하게 답하면 "둘 다 좋고, 둘 다 불편하다."
뭘 고르든 어느 시점에 후회한다.
MySQL을 쓰면 PostgreSQL의 기능이 부럽고, PostgreSQL을 쓰면 MySQL의 생태계가 그립다.
이 글은 "뭐가 더 좋냐"가 아니라 "뭐가 다르냐"를 정리한다.

### 철학부터 다르다

MySQL은 "빠르고 쉽게"에서 출발했다.
웹 서비스 백엔드로 태어났다. 읽기가 많고 스키마가 단순한 서비스에 최적화.
PostgreSQL은 "정확하고 확장 가능하게"에서 출발했다.
학술 프로젝트(POSTGRES)에서 시작했다.
SQL 표준 준수, 타입 확장, 복잡한 쿼리 처리.
이 철학 차이가 30년 뒤에도 남아 있다.
MySQL은 단순한 것을 빠르게 한다.
PostgreSQL은 복잡한 것을 정확하게 한다.

### MVCC 구현이 완전히 다르다

둘 다 MVCC를 쓰지만 방식이 정반대다.

[MySQL InnoDB]
행을 수정하면 원본을 undo log에 복사한다.
현재 데이터 페이지에는 최신 버전만 남는다.
읽기가 이전 버전을 원하면 undo log에서 재구성한다.

[PostgreSQL]
행을 수정하면 새 버전을 힙에 직접 추가한다.
이전 버전도 같은 테이블 안에 남아 있다.
죽은 튜플이 쌓이고, VACUUM이 정리한다.

MySQL은 오래된 트랜잭션이 undo를 잡으면 history list length가 폭증한다.
PostgreSQL은 VACUUM이 못 돌면 dead tuple이 쌓여 테이블이 부풀어 오른다.
최악에는 XID wraparound가 터진다.
어느 쪽이든 오래된 트랜잭션이 적이다.

### 기본 격리 수준이 다르다

MySQL InnoDB의 기본은 Repeatable Read.
트랜잭션 시작 시점의 스냅샷을 끝까지 유지한다.
Gap Lock으로 Phantom Read까지 막는다.
PostgreSQL의 기본은 Read Committed.
매 쿼리마다 새로운 스냅샷을 찍는다.
같은 트랜잭션 안에서 같은 SELECT가 다른 결과를 줄 수 있다.
MySQL DBA는 Gap Lock 데드락에 익숙하다.
PostgreSQL DBA는 Non-Repeatable Read를 감수한다.
두 DB를 넘나드는 개발자가 가장 헷갈리는 지점이다.
"같은 코드인데 왜 동작이 다르지?"
격리 수준이 다르기 때문이다.

### 복제 방식이 다르다

[MySQL]
binlog 기반 복제.
Statement, Row, Mixed 세 가지 포맷.
비동기 복제가 기본이고 Semi-sync로 한 단계 올릴 수 있다.
Group Replication으로 멀티마스터도 가능하다.

[PostgreSQL]
WAL(Write-Ahead Log) 기반 스트리밍 복제.
물리 복제가 기본이고 논리 복제(Logical Replication)도 지원한다.
논리 복제는 테이블 단위 선택이 가능해서 부분 복제가 자유롭다.

MySQL의 binlog는 생태계가 풍부하다. Debezium, Maxwell, Canal.
CDC 파이프라인 구축이 훨씬 쉽다.
PostgreSQL의 논리 복제는 유연하지만 도구 생태계가 아직 MySQL에 못 미친다.

### DDL 차이가 실무에서 크다

MySQL의 ALTER TABLE은 오래 전부터 악명이 높았다.
테이블 전체를 복사하는 Online DDL.
pt-online-schema-change, gh-ost 같은 외부 도구 없이는 대규모 테이블 변경이 무섭다.
PostgreSQL은 대부분의 ALTER TABLE이 즉시 완료된다.
컬럼 추가는 메타데이터만 바꾸면 된다.
NOT NULL 제약도 빠르게 붙는다.
대신 PostgreSQL의 컬럼 타입 변경은 테이블 전체를 다시 쓰는 경우가 있다.
그리고 ALTER TABLE에 ACCESS EXCLUSIVE LOCK이 걸리면 그 순간 모든 읽기/쓰기가 멈춘다.
어느 쪽이든 DBA는 DDL 앞에서 긴장한다.
방식이 다를 뿐 위험은 같다.

### MySQL이 한국에서 압도적인 이유

솔직히 기술적 이유보다 역사적 이유가 크다.
한국 IT 성장기에 LAMP 스택이 들어왔다.
PHP + MySQL 조합이 웹 서비스의 표준이었다.
네이버, 다음, 초기 커머스 서비스 전부 MySQL이었다.
MySQL 경험자가 많다. 채용이 쉽다. 문서가 많다. 커뮤니티가 크다.
AWS Aurora MySQL이 킬러 서비스가 됐다.
관리형 서비스에서의 편의성이 MySQL 선택을 더 굳혔다.
기술 선택은 진공 상태에서 이뤄지지 않는다.
"사람을 구할 수 있는가"가 종종 아키텍처보다 중요하다.

### PostgreSQL이 빠르게 치고 올라오는 이유

2020년 이후 분위기가 확실히 바뀌었다.

[클라우드 네이티브]
Aurora PostgreSQL이 안정화됐다.
Supabase가 PostgreSQL 위에서 BaaS를 만들었다.
Neon이 서버리스 PostgreSQL을 내놓았다.

[기능 확장]
JSON 지원이 MySQL보다 강력하다.
JSONB 타입, GIN 인덱스, JSON 경로 쿼리.
파티셔닝도 선언적이라 쉽다.

[분석 워크로드]
Window Function, CTE, 재귀 쿼리.
OLTP와 가벼운 OLAP을 하나의 DB로 커버한다.
스타트업 신규 프로젝트에서 PostgreSQL을 선택하는 비율이 체감상 5년 전의 두 배 이상이다.

### MySQL이 여전히 강한 영역

대규모 웹 서비스 백엔드.
읽기 비율이 높고 스키마가 단순한 서비스.
MySQL은 이 영역에서 30년 검증됐다.
Facebook이 MySQL 포크(MyRocks)를 쓰고, Slack이 Vitess 위에 MySQL을 올렸다.
InnoDB의 클러스터 인덱스 구조는 PK 기반 포인트 룩업이 빠르다.
Buffer Pool의 메모리 효율이 좋다.
그리고 무엇보다 운영 도구와 모니터링 생태계가 성숙하다.
Percona Toolkit, orchestrator, ProxySQL.

### PostgreSQL이 더 나은 영역

복잡한 도메인 모델링.
JSON, 배열, 사용자 정의 타입. GIS 데이터(PostGIS).
분석과 트랜잭션이 공존하는 서비스.
물류, 결제, ERP처럼 복잡한 쿼리와 정합성이 둘 다 필요한 곳.
확장 생태계도 다르다.
pg_stat_statements로 쿼리 통계를 꺼내고, Foreign Data Wrapper로 외부 DB를 조인하고, Extension으로 기능을 확장한다.
PostgreSQL은 "DB 안에서 다 하겠다"는 사상이다.
MySQL은 "DB는 저장소, 나머지는 밖에서"라는 사상이다.

### 실무에서 겪는 차이들

DBA가 두 DB를 운영하면 사소한 차이에서 자꾸 발이 걸린다.
MySQL의 utf8은 3바이트다. 이모지를 넣으려면 utf8mb4를 써야 한다.
PostgreSQL은 처음부터 UTF-8이 UTF-8이다.
MySQL은 빈 문자열과 NULL을 구분하지만 INSERT 시 NOT NULL 컬럼에 빈 문자열을 허용한다.
PostgreSQL은 NOT NULL이면 빈 문자열도 NOT NULL이다.
MySQL의 GROUP BY는 관대하다. SELECT에 집계되지 않은 컬럼이 있어도 돌아간다.
PostgreSQL은 칼같이 에러를 뱉는다.
이런 차이가 마이그레이션 때 수백 건의 쿼리 수정으로 돌아온다.

### 뭘 고를 것인가

"새 프로젝트인데 뭘 쓸까요?"
팀에 MySQL 경험이 많으면 MySQL.
팀에 PostgreSQL 경험이 많으면 PostgreSQL.
둘 다 비슷하면 서비스 특성으로 판단.

- 읽기 위주 + 단순 스키마 + CDC 필요 = MySQL.
- 복잡한 도메인 + JSON + 분석 쿼리 = PostgreSQL.

"팀에 아무도 경험이 없는데요?"
그러면 MySQL.
채용 풀이 넓고 장애 시 도움받을 곳이 많다.

### DBA 관점에서의 정리

MySQL과 PostgreSQL은 같은 문제를 다른 방향에서 푼다.
MVCC 구현이 다르고, 기본 격리 수준이 다르고, 복제 방식이 다르고, DDL 처리가 다르다.
"뭐가 더 좋냐"는 질문에는 답이 없다. "어떤 상황에 맞느냐"에는 답이 있다.
둘 다 써본 DBA로서 말하자면 뭘 골라도 어느 시점엔 후회한다.
MySQL을 쓰면 PostgreSQL의 DDL이 부럽고, PostgreSQL을 쓰면 MySQL의 도구들이 그립다.
완벽한 DB는 없다. 자기 서비스에 맞는 DB가 있을 뿐이다.
그 판단을 내리는 게 DBA의 일이다.

## JPA와 MyBatis: 프레임워크가 아니라 철학의 차이다

자바 진영에서 DB를 다루는 방법은 크게 둘이다. JPA와 MyBatis.
면접에서도 자주 나오고 팀마다 종교 전쟁 수준으로 갈린다.
"JPA가 표준이니까 JPA 써야죠" "MyBatis가 쿼리를 직접 제어하니까 낫죠"
둘 다 틀렸다.
이건 좋고 나쁨의 문제가 아니라 철학의 차이다.
객체 중심으로 생각하느냐, 쿼리 중심으로 생각하느냐.
그 차이가 아키텍처 전체를 바꾼다.

### JPA란 무엇인가

자바 표준 ORM 스펙이다. 구현체는 Hibernate가 사실상 독점.
핵심 사상은 하나다.
"개발자는 객체를 다루고, SQL은 프레임워크가 만든다."

```java
@entity
public class Order {
    Id @GeneratedValue
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY)
    private User user;

    private String status;
}
```

엔티티를 정의하면 테이블 매핑, SQL 생성, 변경 감지까지 JPA가 알아서 한다.
개발자는 SQL을 몰라도 된다. 이게 장점이자 함정이다.

### MyBatis란 무엇인가

SQL Mapper. 개발자가 SQL을 직접 쓴다.
MyBatis는 그 SQL과 자바 객체를 연결해준다.

```xml
<select id="findOrderById" resultType="Order">
    SELECT o.id, o.status, u.name as userName
    FROM orders o
    JOIN users u ON o.user_id = u.id
    WHERE o.id = #{orderId}
</select>
```

SQL이 그대로 보인다.
무슨 쿼리가 나가는지 개발자가 이미 알고 있다.
ORM이 아니다. 객체-관계 매핑을 자동으로 해주지 않는다.
SQL의 결과를 객체에 담아줄 뿐이다.

### 철학의 차이: 객체냐 쿼리냐

JPA는 객체 중심이다.
"데이터베이스를 잊어라. 객체의 관계를 설계하라."
MyBatis는 쿼리 중심이다.
"SQL이 곧 인터페이스다. DB가 어떻게 동작하는지 알고 써라."
도메인 주도 설계를 하는 팀은 JPA가 자연스럽다.
엔티티가 곧 도메인 모델이 된다.
데이터 중심 설계를 하는 팀은 MyBatis가 자연스럽다.
테이블 구조가 곧 모델이다.
어느 쪽이 낫냐가 아니라 팀이 어떤 방식으로 생각하느냐의 문제다.

### JPA의 강점: 생산성

CRUD는 코드를 안 써도 된다.

```java
public interface OrderRepository extends JpaRepository<Order, Long> {
    List<Order> findByStatus(String status);
}
```

메서드 이름만으로 쿼리가 만들어진다.
인터페이스 하나로 기본 CRUD가 끝난다.
변경 감지도 강하다.
엔티티의 필드를 바꾸면 트랜잭션 커밋 시점에 UPDATE가 자동 실행된다.

```java
order.setStatus("COMPLETED");
// save를 안 불러도 UPDATE가 나간다
```

단순 서비스에서의 개발 속도는 MyBatis와 비교가 안 된다.

### JPA의 강점: 영속성 컨텍스트

JPA의 핵심 메커니즘. 1차 캐시, 변경 감지, 쓰기 지연.
같은 트랜잭션 안에서 같은 엔티티를 두 번 조회하면 두 번째는 DB에 안 간다.
1차 캐시에서 꺼낸다.
변경된 필드만 감지해서 UPDATE한다.
INSERT도 모아서 한 번에 보낸다.
JDBC Batch가 자동으로 동작한다.
이 메커니즘을 이해하면 JPA는 강력한 도구다.
이해하지 못하면 예측 불가능한 블랙박스다.

### JPA가 DBA를 힘들게 하는 순간

DBA한테 날아오는 슬로우 쿼리.
JPA가 만든 쿼리에서 자주 보이는 패턴이 있다.

[N+1]
주문 100건을 조회하면서 각 주문의 사용자 정보를 하나씩 쿼리. 101번.

[SELECT *]
이름만 필요한데 엔티티 전체를 가져온다.
커버링 인덱스를 탈 수 있었던 쿼리가 테이블 풀 액세스로 바뀐다.

[무분별한 Eager Loading]
FetchType.EAGER가 걸린 연관 엔티티가 어디서든 항상 JOIN된다.

[대량 UPDATE]
1만 건을 수정하는데 건건이 SELECT + UPDATE.
SQL 한 줄이면 끝나는 일이 2만 번의 쿼리가 된다.

### MyBatis의 강점: SQL 제어

MyBatis의 최대 장점. SQL을 개발자가 직접 쓴다.
필요한 컬럼만 SELECT.
인덱스를 타도록 WHERE절 설계.
EXPLAIN으로 확인하고 튜닝.

```xml
<select id="getOrderSummary">
    SELECT o.id, o.status, o.created_at
    FROM orders o
    WHERE o.user_id = #{userId}
    AND o.status = #{status}
    ORDER BY o.created_at DESC
    LIMIT 20
</select>
```

DBA가 이 쿼리를 보면 인덱스 전략을 바로 세울 수 있다.
실행 계획이 눈에 보인다.
JPA가 만든 쿼리에서는 이게 쉽지 않다.

### MyBatis의 강점: 복잡한 쿼리

JPA가 어려워하는 영역에서 MyBatis가 빛난다.

[다중 테이블 집계]

```sql
SELECT dept_name, COUNT(order_id), SUM(amount)
FROM departments
JOIN users ON departments.dept_id = users.dept_id
JOIN orders ON users.user_id = orders.user_id
WHERE orders.created_at >= #{startDate}
GROUP BY dept_name
HAVING SUM(amount) > 1000000
```

JPQL이나 Criteria API로 이걸 표현하면 코드가 세 배는 길어진다.

[동적 쿼리]
MyBatis의 `<if>`, `<choose>`, `<foreach>`는 조건에 따라 SQL을 유연하게 조립한다.
검색 조건이 열 개인 화면에서 깔끔하게 대응할 수 있다.

### MyBatis의 약점

SQL을 직접 쓰는 대가가 있다.

[보일러플레이트]
테이블이 50개면 INSERT, UPDATE, SELECT, DELETE를 50번 반복해서 써야 한다.
JPA는 인터페이스 하나로 끝난다.

[DB 종속성]
MySQL 문법으로 쓴 SQL은 PostgreSQL에서 안 돌아갈 수 있다.
LIMIT과 FETCH FIRST, IFNULL과 COALESCE.
JPA는 방언이 알아서 변환해준다.

[매핑 노동]
ResultMap을 직접 작성해야 한다.
엔티티 구조가 바뀌면 XML도 같이 고쳐야 한다.
이게 싫어서 JPA로 가는 팀이 많다. 이해한다.

### JPA의 약점

ORM의 추상화에는 비용이 있다.

[학습 곡선]
영속성 컨텍스트, 프록시, 페치 전략, 1차 캐시, 2차 캐시, OSIV, Cascade, orphanRemoval.
제대로 쓰려면 배울 게 많다.

[디버깅 난이도]
문제가 생겼을 때 "어떤 SQL이 나갔는지"부터 파악해야 한다.
Hibernate가 만든 SQL은 사람이 쓴 것과 구조가 다르다.

[성능 튜닝 한계]
옵티마이저 힌트를 주기 어렵다.
네이티브 쿼리로 내려가면 JPA를 쓰는 의미가 줄어든다.
MyBatis는 처음부터 SQL이 보이니까 이런 문제가 없다.

### 한국 시장의 현실

한국 SI, 금융, 대기업에서는 MyBatis가 아직도 압도적이다. 이유가 있다.
금융 시스템은 SQL을 직접 제어해야 한다.
DBA가 쿼리를 리뷰하고 승인한다.
JPA가 만든 쿼리를 DBA가 검증하기란 현실적으로 어렵다.
오라클 기반 레거시가 많다.
프로시저, 힌트, 다이나믹 SQL.
MyBatis가 이걸 자연스럽게 감싼다.
"JPA가 표준이니까 써야 한다"는 기술의 표준이지 산업의 표준이 아니다.
스타트업과 커머스에서는 JPA + QueryDSL 조합이 대세다.
환경이 다르면 선택도 다르다.

### QueryDSL이라는 제3의 선택지

JPA의 약점을 보완하는 도구.

```java
List<OrderDto> result = queryFactory
    .select(Projections.constructor(
        OrderDto.class,
        qOrder.orderId, qOrder.status, qUser.userName))
    .from(qOrder)
    .join(qOrder.user, qUser)
    .where(qOrder.status.eq("PENDING"))
    .orderBy(qOrder.createdAt.desc())
    .limit(20)
    .fetch();
```

SQL에 가까운 구조. 타입 안전성. 필요한 컬럼만 프로젝션.
JPA 진영에서 "복잡한 쿼리는 QueryDSL로"가 사실상 공식 답이 됐다.
MyBatis의 SQL 제어력과 JPA의 타입 안전성 사이.
그 적당한 지점에 있다.

### 실무에서의 선택 기준

[JPA가 맞는 경우]
CRUD 중심의 서비스.
도메인 모델이 복잡한 DDD 프로젝트.
빠른 개발 속도가 필요한 초기 스타트업.
단순한 조회가 대부분인 서비스.

[MyBatis가 맞는 경우]
복잡한 조회와 집계가 많은 서비스.
DBA와 협업이 긴밀한 환경.
대량 배치 처리가 핵심인 시스템.
SQL 튜닝이 서비스 품질에 직결되는 곳.

[둘 다 쓰는 경우]
JPA로 기본 CRUD를 처리하고 복잡한 조회는 MyBatis나 QueryDSL.
현실에서 가장 많이 보이는 패턴이다.

### 면접에서 이 질문이 나오면

"JPA와 MyBatis 중 어떤 걸 선호하세요?"

[감점 답변]
"JPA요. 표준이니까요."
왜 표준인지, 한계가 뭔지 모르는 것으로 보인다.
"MyBatis요. 쿼리를 직접 쓸 수 있으니까요."
ORM의 장점을 모르는 것으로 보인다.

[득점 답변]
"CRUD 중심이면 JPA로 생산성을 높이고, 복잡한 조회는 QueryDSL이나 네이티브 SQL로 풉니다.
N+1이나 `SELECT *` 같은 패턴은 쿼리 로그를 켜서 개발 단계에서 잡고, 대량 배치는 JDBC Template을 직접 씁니다."
도구의 장단을 알고 상황에 맞게 조합한다는 걸 보여줘라.

### DBA 관점에서의 정리

JPA든 MyBatis든 DBA한테 중요한 건 하나다.
프로덕션에 나가는 쿼리가 뭔지 아느냐.
JPA를 쓰면서 show-sql도 안 켜본 개발자가 "갑자기 느려졌어요"라고 한다.
MyBatis를 쓰면서 EXPLAIN 한 번 안 찍어본 개발자가 "인덱스 추가해주세요"라고 한다.
프레임워크는 도구다.
도구가 만드는 결과를 이해하지 못하면 어떤 도구를 쓰든 같은 장애를 만든다.
JPA가 맞느냐 MyBatis가 맞느냐. 그건 팀과 서비스가 결정한다.
다만 어떤 걸 쓰든 쿼리를 읽을 줄 알고, 실행 계획을 이해하고, 느릴 때 왜 느린지 설명할 수 있어야 한다.
프레임워크는 바뀐다.
SQL을 이해하는 능력은 남는다.

## SQL vs ORM: 편한 건 알겠는데, 그 쿼리가 뭔지는 아는가

개발자가 SQL을 직접 쓰는 시대는 지났다고 말한다.
JPA, SQLAlchemy, Prisma, TypeORM. ORM이 다 해준다.
근데 DBA한테 날아오는 슬로우 쿼리를 보면 대부분 ORM이 만든 쿼리다.
`SELECT *`에 N+1에 불필요한 JOIN에 서브쿼리가 서브쿼리를 부른다.
ORM이 문제가 아니다. ORM이 만드는 SQL을 모르는 게 문제다.
면접에서 "SQL을 직접 쓰세요, ORM을 쓰세요?"라고 물으면 둘 중 하나를 고르는 게 아니라 둘 다 안다는 걸 보여줘야 한다.

### ORM이 해결한 것

ORM이 등장한 이유는 명확하다.
SQL을 문자열로 조립하는 건 실수가 많고 유지보수가 힘들다.

```java
String sql = "SELECT * FROM users WHERE id = " + userId;
```

SQL 인젝션, 타입 불일치, 오타. 문자열 SQL은 컴파일 타임에 잡히지 않는다.
ORM은 이걸 해결했다.
객체로 매핑하고, 타입을 보장하고, SQL을 자동으로 생성한다.
개발 속도가 빨라졌다. 실수가 줄었다.
이건 진짜 장점이다.

### ORM이 숨기는 것

ORM은 SQL을 숨긴다.
숨기는 게 장점이자 문제다.

```python
users = User.objects.filter(age__gt=25).select_related('team')
```

이 한 줄이 어떤 SQL이 되는지 확인하지 않는 개발자가 많다.

```sql
SELECT users.*, team.*
FROM users
INNER JOIN team ON users.team_id = teaem._id
WHERE users.age > 25;
```

지금은 괜찮다.
users가 100만 건이 되고 team에 인덱스가 없으면 이 한 줄이 장애가 된다.
ORM이 숨긴 건 SQL이 아니라 성능의 책임이다.

### N+1 문제: ORM의 고전적 실수

ORM을 쓰면 거의 반드시 만나는 문제다.

```python
orders = Order.objects.all() # 쿼리 1번
for order in orders:
print(order+user.name) # 주문 수만큼 반복
```

주문이 100건이면 쿼리가 101번 나간다.
SQL로 직접 쓰면 JOIN 한 번이다.

```sql
SELECT o.*, u+name FROM orders o
JOIN users u ON o.user_id = u+id;
```

ORM에서도 해결할 수 있다. `select_related`, `prefetch_related` 등.
하지만 이걸 쓰려면 N+1이 뭔지 먼저 알아야 한다.

### Lazy Loading vs Eager Loading

N+1의 뿌리는 Lazy Loading이다.

[Lazy Loading]
연관 객체를 실제로 접근할 때 쿼리를 날린다.
메모리는 아끼지만 쿼리가 늘어난다.
대부분의 ORM이 기본값으로 쓴다.

[Eager Loading]
연관 객체를 처음부터 JOIN으로 가져온다.
쿼리는 줄지만 불필요한 데이터까지 읽을 수 있다.

정답은 없다.
"이 화면에서 연관 데이터를 쓰는가"에 따라 전략이 달라져야 한다.
문제는 전략 없이 기본값에 맡기는 것이다.
기본값은 대부분 Lazy다.
Lazy의 기본값이 N+1의 기본값이다.

### `SELECT *`의 비용

ORM은 기본적으로 모든 컬럼을 가져온다.
엔티티에 매핑된 필드 전체.

```java
User user = userRepository.findById(1L);
// SELECT * FROM users WHERE id = 1
```

이름만 필요한데 프로필 사진 BLOB까지 읽는다.
20개 컬럼 중 2개만 쓰는데 전부 전송된다.
커버링 인덱스를 탈 수 있던 쿼리가 `SELECT *` 때문에 테이블 lookup을 한다.
SQL이라면 필요한 컬럼만 쓴다.

```sql
SELECT name, email FROM users WHERE id = 1;
```

ORM에서도 프로젝션을 쓸 수 있다. DTO 프로젝션, `values()`, `only()`.
하지만 기본 동작이 아니다.

### ORM이 만드는 비효율적인 쿼리

ORM이 생성하는 SQL에서 DBA가 자주 보는 패턴들이 있다.

[불필요한 서브쿼리]
ORM이 조건을 중첩하면서 서브쿼리가 서브쿼리를 감싼다.
플래너가 최적화하기 어려운 구조가 된다.

[DISTINCT 남발]
JOIN이 잘못돼서 중복이 생기면 ORM이 DISTINCT를 붙여서 해결한다.
근본은 JOIN 구조가 틀린 것이다.

[ORDER BY + LIMIT 없는 전체 조회]
페이지네이션 없이 전체를 가져온 뒤 애플리케이션에서 자르는 패턴.
100만 건을 읽고 10건만 쓴다.

전부 SQL을 보면 바로 보이는 문제다.
ORM만 보면 안 보인다.

### SQL을 직접 쓰면 좋은 경우

ORM이 만능이 아닌 영역이 있다.

[복잡한 집계]
여러 테이블을 조인하고 GROUP BY, HAVING, 윈도우 함수를 쓰는 쿼리.
ORM으로 표현하면 코드가 SQL보다 길어진다.

[대량 배치 처리]
100만 건을 UPDATE할 때 ORM은 건건이 처리하려 한다.
SQL 한 줄이면 끝나는 일이다.

```sql
UPDATE orders SET status = 'EXPIRED'
WHERE created_at < '2025-01-01' AND status = 'PENDING';
```

[성능 크리티컬 쿼리]

밀리초가 중요한 쿼리는 SQL로 직접 쓰고 실행 계획을 확인해야 한다.
ORM이 어떤 SQL을 만들지 예측하는 것보다 직접 쓰는 게 확실하다.

### ORM을 쓰면 좋은 경우

반대로 ORM이 확실히 나은 영역도 있다.

[CRUD 중심 서비스]
단순 생성, 조회, 수정, 삭제.
이걸 매번 SQL로 쓰면 보일러플레이트가 넘친다. ORM의 본업이다.

[스키마 마이그레이션]
ORM의 마이그레이션 도구가 DDL 관리를 자동화해준다.
Django의 makemigrations, Alembic, Flyway.

[타입 안전성]
컴파일 타임에 쿼리 오류를 잡을 수 있다.
문자열 SQL은 런타임에 터진다.

[빠른 프로토타이핑]
비즈니스 로직에 집중해야 할 때 SQL 작성 시간을 절약해준다.

### 하이브리드가 정답이다

현실의 프로젝트는 ORM과 SQL을 섞어 쓴다.

- CRUD → ORM
- 복잡한 조회 → Native SQL 또는 QueryDSL
- 배치 처리 → 직접 SQL
- 리포트 → 직접 SQL

JPA에서도 `@Query`로 네이티브 SQL을 쓸 수 있다.
Django에서도 `raw()`나 `connection.cursor()`가 있다.
ORM 100%도, SQL 100%도 현실적이지 않다.
"이 쿼리는 ORM으로 충분한가, 직접 써야 하는가"를 판단할 수 있는 게 실력이다.

### ORM 쿼리를 반드시 확인하는 법

ORM을 쓰더라도 생성되는 SQL을 반드시 확인해야 한다.

[Django]

```python
print(queryset.query)
# 또는 settings.py에서
LOGGING = {'loggers': {'django.db.backends': ...}}
```

[JPA/Hibernate]

```yml
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

[SQLAlchemy]

```python
engine = create_engine(url, echo=True)
```

쿼리 로그를 켜고 개발하라.
느린 건 프로덕션에서 발견하지 말고 개발 환경에서 잡아라.

### 면접에서 이 질문이 나오면

"SQL을 직접 쓰세요, ORM을 쓰세요?"

[감점 답변]
"ORM만 씁니다. 편하니까요."
→ SQL을 모르는 것으로 판단된다.
"SQL만 씁니다. ORM은 느리니까요."
→ 생산성을 포기하는 것으로 판단된다.

[득점 답변]
"CRUD는 ORM, 복잡한 쿼리는 SQL로 씁니다.
ORM이 만드는 쿼리를 항상 확인하고 N+1이나 불필요한 풀스캔이 있으면 네이티브 쿼리로 전환합니다."

도구를 고르는 게 아니라 상황에 따라 판단한다는 것을 보여줘라.

### DBA가 개발자에게 바라는 것

DBA 입장에서 말하면 ORM을 쓰든 SQL을 쓰든 상관없다.
다만 한 가지. 프로덕션에 나가는 쿼리가 뭔지는 알아달라.
슬로우 쿼리가 잡혔을 때 "그거 ORM이 만든 거라 잘 모르겠어요"가 가장 힘든 대답이다.
EXPLAIN을 찍어보고 인덱스를 확인하고 실행 계획을 읽을 줄 알면 ORM이든 SQL이든 문제없다.
도구는 도구일 뿐이다.
책임은 쿼리를 쓴 사람에게 있다.

### 마무리

ORM은 좋은 도구다. SQL도 좋은 도구다.
문제는 도구가 아니라 도구 뒤에서 일어나는 일을 모르는 것이다.
ORM이 만든 쿼리를 읽을 수 있는가.
그 쿼리의 실행 계획을 이해하는가.
느릴 때 직접 SQL로 대체할 수 있는가.
이 세 가지에 "네"라고 답할 수 있으면 ORM을 써도 된다.
아니라면 SQL부터 배워라.
편한 건 좋은 것이다.
편한 게 뭘 하는지 아는 것이 더 좋은 것이다.
