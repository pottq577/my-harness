# BEAR DBA

## 알림 시스템과 DB: 보내는 건 쉬운데 안 보내는 게 어렵다

"알림 기능 넣으려는데, 테이블 하나면 되지 않나요?"
알림을 보내는 건 INSERT 하나다. 누구에게, 어떤 내용을, 언제.
그런데 진짜 문제는 보내는 게 아니다.

- 같은 알림을 두 번 보내면 스팸이다.
- 사용자가 끈 알림을 보내면 민원이다.
- 100만 명에게 동시에 보내면 DB가 죽는다.

보내는 건 쉽다. 안 보내야 할 걸 안 보내는 게 어렵다.

- 중복은 멱등 키로 막아라.
- 구독 설정은 캐시 없이 대량 발송이 불가능하다.
- 예약 발송은 분산 락이 필요하다.
- 안 읽은 수는 카운터로 분리하라.
- 보존 기간은 설계 시점에 정하라.

### 알림 테이블은 가장 빨리 커진다

댓글이 달리면 알림. 좋아요가 오면 알림. 배송이 출발하면 알림. 쿠폰이 발급되면 알림.
서비스의 모든 이벤트가 알림을 만든다.
사용자 100만 명. 하루에 인당 알림 5건.
하루 500만 건. 한 달이면 1억 5천만 건.
주문 테이블보다 빨리 커진다.
게시글 테이블보다 빨리 커진다.
알림 테이블이 DB에서 가장 큰 테이블이 되는 건 시간 문제다.

### 같은 알림을 두 번 보내면

주문 상태가 바뀌면 알림을 보낸다.
이벤트가 두 번 발행되면 알림도 두 번 간다.
"주문이 접수되었습니다"가 두 번 뜨면 사용자는 두 번 주문된 줄 안다.
중복 방지가 필요하다.
이벤트 ID + 사용자 ID로 유니크 키를 잡거나 발송 전에 최근 N분 이내 동일 알림을 체크한다.

```sql
SELECT COUNT(*) FROM notifications
WHERE user_id = 42
AND event_id = 'order-123-accepted'
```

이 체크 쿼리가 알림마다 한 번씩 돈다.
대량 발송 시에는 이 체크 자체가 부하다.
Redis에 발송 이력을 캐시하는 게 현실적이다.

### 구독과 해지의 설정 테이블

마케팅 알림을 끈 사용자에게 보내면 정보통신망법 위반이다.
사용자별 알림 설정이 필요하다.
마케팅, 주문, 배송, 이벤트.
채널별로도 다르다. 푸시, SMS, 이메일.
설정 테이블이 생긴다.
사용자 × 알림 유형 × 채널.
100만 명 × 4유형 × 3채널 = 1200만 건.
알림을 보내기 전에 이 테이블을 조회한다.
100만 명에게 보내려면 100만 번 조회한다.
설정 테이블은 작지만 조회 빈도가 극도로 높다.
캐시 없이는 대량 발송이 불가능하다.

### 예약 발송은 누가 트리거하는가

"내일 오전 10시에 쿠폰 알림 발송."
DB에 예약 레코드를 넣는다.
`send_at = '2026-08-12 10:00:00'`.
10시가 되면 누가 이걸 꺼내서 보내는가.
1분마다 배치가 돌면서

```sql
SELECT * FROM scheduled_notifications
WHERE send_at <= NOW()
AND status = 'pending'
LIMIT 1000
```

이 쿼리가 1분마다 전체를 스캔한다.
인덱스가 (status, send_at)에 없으면 느리다.
서버가 두 대면 같은 알림을 두 대가 동시에 가져갈 수 있다.
`SELECT FOR UPDATE`나 분산 락이 필요하다.
예약 발송은 기능은 한 줄이지만 안정적으로 돌리려면 인프라가 필요하다.

### 읽음과 안 읽음

알림 목록에 빨간 점이 뜬다. "안 읽은 알림 3건."
채팅의 안 읽은 메시지와 같은 문제다.
사용자가 알림 목록을 열 때

```sql
SELECT COUNT(*) FROM notifications
WHERE user_id = 42
AND is_read = false
```

이 쿼리가 앱을 열 때마다 실행된다.
사용자 10만 명이 동시에 열면 10만 번의 COUNT.
`is_read` 인덱스가 없으면 풀 스캔이다.
있어도 false가 대부분이면 인덱스 효율이 낮다.
안 읽은 수를 별도 카운터로 관리하면 알림 발송 시 +1, 읽음 처리 시 -1.
COUNT 쿼리 자체가 사라진다.

### 채널이 늘어나면

처음에는 앱 푸시만 있었다.
SMS가 추가됐다. 이메일이 추가됐다. 카카오 알림톡이 추가됐다.
알림 하나에 채널이 네 개다. DB에 어떻게 넣는가.
알림 테이블에 channel 컬럼을 넣으면 같은 알림이 네 건으로 늘어난다.
이미 빠르게 커지는 테이블이 네 배로 커진다.
알림 마스터와 발송 내역을 분리한다.
알림은 한 건, 발송 시도는 채널별 한 건씩.
발송 실패 시 재시도도 채널별로 관리한다.
푸시는 성공했는데 SMS는 실패.
부분 성공이라는 상태가 생긴다.

### 오래된 알림을 어떻게 할 것인가

6개월 전 알림을 사용자가 볼 일이 있는가. 거의 없다.
그런데 DB에는 그대로 있다.
알림은 삭제해도 되는 데이터다.
결제 내역과 다르다. 법적 보존 의무가 없다.
90일 이후 알림을 자동 삭제하는 배치를 만든다.
혹은 파티셔닝으로 월별 분리한 뒤 오래된 파티션을 DROP한다.
`DELETE`보다 `DROP PARTITION`이 빠르다.
1억 건을 `DELETE`하면 DB가 멈추지만 파티션 하나를 DROP하면 순식간이다.
알림 테이블은 설계 시점에 파티셔닝을 고려해야 하는 대표적인 케이스다.

### DBA 관점에서의 정리

알림은 단순한 INSERT로 시작하지만 운영하면 DB에서 가장 큰 골칫거리가 된다.

- 중복은 멱등 키로 막아라.
- 구독 설정은 캐시 없이 대량 발송이 불가능하다.
- 예약 발송은 분산 락이 필요하다.
- 안 읽은 수는 카운터로 분리하라.
- 보존 기간은 설계 시점에 정하라.

나중에 바꾸려면 억 단위 레코드를 마이그레이션해야 한다.
보내는 건 쉽다. 안 보내야 할 걸 안 보내는 게 어렵다.

## Optimistic Lock vs Pessimistic Lock: 충돌을 막느냐, 충돌을 받아들이느냐

두 사람이 같은 좌석을 예매하려 한다.
한 명이 먼저 앉으면 다른 한 명은 못 앉는다.
여기서 갈림길이 생긴다.
미리 좌석을 잠글 것인가, 일단 둘 다 예매하게 두고 나중에 충돌을 처리할 것인가.
전자가 비관적 락이고 후자가 낙관적 락이다.
이름에 "락"이 들어 있지만 비관적 락만 DB 락을 쓴다.
낙관적 락은 락을 안 건다.
충돌을 감지하는 전략이지 잠그는 전략이 아니다.

### 비관적 락의 철학

"충돌이 날 거야. 미리 막자."
이 생각이 출발점이다.
데이터를 읽을 때부터 잠근다.
내가 다 쓸 때까지 아무도 건드리지 못하게 한다.

```sql
SELECT * FROM seats
WHERE seat_id = 'A1' FOR UPDATE;
```

이 순간 `seat_id = 'A1'` 행에 X Lock이 걸린다.
다른 트랜잭션이 같은 행을 읽으려 해도 `FOR UPDATE`가 걸려 있으면 기다려야 한다.
확실하다. 충돌 자체가 발생하지 않는다.

### 비관적 락이 빛나는 곳

[재고 차감]
남은 수량이 1개인데 동시에 3명이 주문한다.
읽고 확인하고 차감하는 사이에 누군가 먼저 가져가면 재고가 마이너스가 된다.
`FOR UPDATE`로 선점하면 순서가 강제된다.

[포인트 차감]
잔액 10,000원에서 7,000원과 5,000원을 동시에 쓴다.
둘 다 잔액을 읽고 "충분하다"고 판단하면 합계 12,000원이 빠진다.
비관적 락으로 직렬화하면 두 번째는 잔액 부족으로 실패한다.

[좌석 예매]
같은 좌석을 두 명이 동시에 잡는 건 허용 불가다.
충돌 비용이 크다. 미리 막는 게 맞다.

### 비관적 락의 대가

1. 잠그는 순간 다른 트랜잭션은 기다린다.
2. 기다리는 시간이 곧 응답 시간이다.
3. 트랜잭션이 길어지면 대기열이 쌓인다.
4. 대기열이 쌓이면 커넥션 풀이 고갈된다.
5. 커넥션 풀이 고갈되면 서비스가 멈춘다.
6. 그리고 데드락.

A가 행 1을 잡고 행 2를 기다린다.
B가 행 2를 잡고 행 1을 기다린다.
비관적 락의 고전적인 함정이다.
비관적 락은 안전하지만 성능과 맞교환하는 전략이다.

### 낙관적 락의 철학

"충돌은 드물어. 일단 진행하자."
잠그지 않는다.
읽을 때 버전을 기억해두고 쓸 때 버전이 바뀌었는지만 확인한다.

```sql
UPDATE orders
SET status = 'confirmed', version = 2
WHERE order_id = 1001 AND version = 1;
```

affected rows가 1이면 성공. 0이면 누군가 먼저 수정한 것이다.
락을 안 걸었으니 대기가 없다.
대기가 없으니 데드락도 없다.

### 낙관적 락이 빛나는 곳

[게시글 수정]
같은 글을 동시에 편집하는 일은 드물다.
읽기가 압도적으로 많은 시스템이다.
매번 `FOR UPDATE`를 거는 건 낭비다.

[장바구니 업데이트]
내 장바구니를 다른 사람이 수정할 일은 없다.
충돌 확률이 거의 0에 가깝다.

[설정값 변경]
관리자가 설정을 바꾸는 건 하루에 몇 번이다.
동시에 같은 설정을 바꿀 확률은 극히 낮다.

핵심은 충돌 빈도다.
충돌이 드물면 낙관적 락이 이긴다.

### 낙관적 락의 대가

충돌이 나면 재시도해야 한다.
그런데 재시도를 구현 안 하는 팀이 많다.

```
UPDATE ... WHERE version = 1;
→ affected rows = 0
→ 그냥 실패 처리
→ 사용자에게 "다시 시도하세요"
```

이건 낙관적 락이 아니다. 그냥 실패를 방치하는 것이다.
낙관적 락을 쓰려면 반드시 재시도 로직이 있어야 한다.

- 읽기부터 다시 한다.
- 최신 버전을 가져오고 다시 시도한다.
- 최대 재시도 횟수도 정해야 한다.

재시도 없는 낙관적 락은 안전벨트 없는 차와 같다.

### 실무에서 흔한 실수 1: 낙관적인데 재시도가 없다

JPA의 `@ @ Version`을 쓰면 `OptimisticLockException`이 자동으로 던져진다.
그런데 그 예외를 catch하는 코드가 없다.
컨트롤러에서 500 에러로 빠진다.
사용자는 "서버 오류"를 본다.
`@ @ Version`을 선언하는 건 시작이지 끝이 아니다.
예외를 잡고, 다시 읽고, 다시 시도하는 것까지가 낙관적 락의 구현이다.

### 실무에서 흔한 실수 2: 비관적인데 범위가 넓다

인덱스 없이 FOR UPDATE를 건다.

```sql
SELECT * FROM orders
WHERE status = 'pending' FOR UPDATE;
```

status에 인덱스가 없으면 InnoDB는 풀 테이블 스캔을 한다.
스캔한 모든 행에 락이 걸린다.
의도한 건 pending 주문 10건인데 실제로는 100만 건에 락이 걸린다.
FOR UPDATE에는 인덱스가 필수다.
인덱스 없는 비관적 락은 문 하나를 잠그려다 건물 전체를 잠그는 것이다.

### 실무에서 흔한 실수 3: 비관적 락 안에서 외부 호출

```
BEGIN;
SELECT ... FOR UPDATE; -- 락 획득
call_payment_api(); -- 외부 API 호출 (2초)
UPDATE ...;
COMMIT; -- 락 해제
```

외부 API가 2초 걸리면 락도 2초 동안 유지된다.
그 사이 같은 행을 원하는 트랜잭션은 전부 대기한다.
트랜잭션 안에서 외부 호출을 하면 안 된다.
락 보유 시간을 최소화하는 것이 철칙이다.
외부 호출은 트랜잭션 밖에서 한다.

### 두 전략의 판단 기준

결정하는 변수는 두 개다.
충돌 빈도와 충돌 비용.

[충돌이 잦고 비용이 크다]
재고, 포인트, 좌석.
비관적 락.
충돌을 허용할 수 없으니 미리 막는다.

[충돌이 드물고 비용이 작다]
게시글, 설정, 프로필.
낙관적 락.
대부분 충돌이 안 나니 잠글 이유가 없다.

[충돌이 잦은데 낙관적 락을 쓰면]
재시도가 폭발한다.
한 번에 될 걸 세 번 네 번 시도한다.
오히려 비관적 락보다 느려진다.

### 하이브리드 전략

둘 다 쓸 수 있다. 같은 시스템 안에서도 상황에 따라 다르다.

- 주문 생성은 낙관적 락.
  - 주문이 겹칠 확률은 낮다.
- 결제 차감은 비관적 락.
  - 잔액이 마이너스가 되면 안 된다.
- 재고 차감은 비관적 락.
  - 동시 접근이 몰리는 핫스팟이다.
- 상품 정보 수정은 낙관적 락.
  - 관리자 한 명이 수정하는 경우가 대부분이다.

도메인별로 다르게 적용하는 게 현실이다.
전부 비관적이면 느리고, 전부 낙관적이면 불안하다.

### 면접에서 이 질문이 나오면

"낙관적 락과 비관적 락의 차이가 뭔가요?"
정의를 설명하는 건 누구나 한다. 면접관이 듣고 싶은 건 그다음이다.

- "그래서 어떤 상황에 어느 쪽을 쓰시겠습니까?"
  - 충돌 빈도와 비용으로 답한다.
- "낙관적 락에서 충돌이 나면 어떻게 처리하나요?"
  - 재시도 로직을 설명한다.
  - 최대 재시도 횟수, 백오프 전략까지 말하면 좋다.
- "비관적 락의 단점은?"
  - 데드락과 트랜잭션 길이 문제를 말하고 접근 순서 통일, 인덱스 필수, 외부 호출 금지를 덧붙인다.

### DBA 관점에서의 정리

DBA에게 낙관적 락은 보이지 않는다.
version 컬럼의 WHERE 절일 뿐이다.
DB 입장에서는 평범한 UPDATE다.
비관적 락은 보인다.
락 대기가 쌓이고 데드락이 터진다.
`SHOW ENGINE INNODB STATUS`에 흔적이 남는다.
그래서 DBA가 더 신경 쓰는 건 비관적 락이다.
FOR UPDATE가 인덱스를 타는지, 트랜잭션이 얼마나 열려 있는지, 외부 호출이 끼어 있진 않은지.
락을 쓰는 건 개발자의 판단이다.
락이 문제가 됐을 때 전화받는 건 DBA다.
그래서 어느 쪽이든 원리를 알아야 한다.

## 커넥션 풀이 필요한 진짜 이유: HikariCP, pgBouncer, 그리고 적정 사이즈

"DB 커넥션 풀 사이즈 얼마로 하면 돼요?" 가장 자주 받는 질문 중 하나다.
그런데 왜 풀이 필요한지부터 물어보는 사람은 거의 없다.
커넥션 하나 여는 데 무슨 일이 벌어지는지 모르면 적정 사이즈도, 장애 원인도, 튜닝 방향도 모른다.

### 커넥션 하나를 여는 데 무슨 일이 벌어지나

애플리케이션이 DB에 연결하려면 네트워크부터 인증까지 여러 단계를 거친다.

1. TCP 3-way handshake로 소켓을 연다.
2. SSL/TLS가 켜져 있으면 추가 왕복이 생긴다.
3. DB 서버가 인증 요청을 처리한다.

MySQL은 스레드를 할당하고, PostgreSQL은 프로세스를 fork한다.
세션 변수, 타임존, charset을 초기화한다.
커넥션 하나 여는 건 전화기를 들고 상대가 받을 때까지 기다리는 것과 같다.
매 쿼리마다 이걸 반복하면 어떻게 될까.

### 커넥션 생성의 비용

- MySQL은 스레드 기반이다.
  - 커넥션 하나당 OS 스레드 하나가 붙는다.
  - 스레드 생성 자체는 빠르지만 인증과 초기화까지 합치면 수 밀리초가 걸린다.
- PostgreSQL은 프로세스 기반이다.
  - `fork()` 시스템 콜로 새 프로세스를 만든다.
  - 프로세스 생성은 스레드보다 무겁다.
  - 공식 문서에서도 connection 비용을 경고한다.

숫자 자체보다 중요한 건 빈도다.
초당 수천 요청이 들어오는 서비스에서 매번 커넥션을 만들고 끊으면 DB CPU의 상당 부분이 커넥션 관리에 소비된다.

### 커넥션 풀이 존재하는 이유

답은 간단하다. 비싼 걸 미리 만들어두고 돌려쓰자.
커넥션을 매번 만들지 않고 미리 만들어둔 커넥션을 빌려 쓰고 돌려준다.
TCP handshake, 인증, 프로세스 생성을 부팅 시 한 번만 치르는 것이다.
DB 입장에서도 좋다.
동시 커넥션 수가 예측 가능해지고 프로세스/스레드 생성·소멸의 진동이 사라진다.
안정적인 부하 패턴이 성능의 기본이다.

### 커넥션 풀의 동작 원리

풀은 세 가지 동작으로 구성된다.

[초기화]
애플리케이션이 뜰 때 최소 개수만큼 커넥션을 미리 연다.
이걸 minimum idle이라 부른다.

[대여]
쿼리를 실행할 때 풀에서 유휴 커넥션을 하나 꺼낸다.
없으면 새로 만들거나, 최대치면 대기한다.

[반납]
쿼리가 끝나면 커넥션을 끊지 않고 풀에 돌려놓는다.
다음 요청이 재사용한다.
도서관의 대출·반납과 같다.
책을 읽을 때마다 사지 않고 빌려 쓰고 돌려놓는 것이다.

### HikariCP — Java 생태계의 표준

Spring Boot의 기본 커넥션 풀이다.
왜 HikariCP가 살아남았을까.

[ConcurrentBag]
락 없이 커넥션을 대여·반납하는 자료구조다.
ThreadLocal 캐시로 같은 스레드가 쓰던 커넥션을 우선 재사용한다.
CPU 캐시 히트율이 올라간다.

[바이트코드 최소화]
풀 내부 코드가 극도로 짧다.
JIT 컴파일러가 인라인하기 좋은 크기로 설계됐다.

[빠른 실패]
커넥션을 못 빌리면 길게 기다리지 않는다.
기본 connectionTimeout이 30초다.
장애 전파를 끊는 설계다.

### pgBouncer — PostgreSQL 앞단의 프록시

PostgreSQL의 fork 비용은 크다. 그래서 DB 앞에 프록시를 놓는다.
pgBouncer가 그 역할을 한다.
애플리케이션은 pgBouncer에 연결하고 pgBouncer가 실제 PostgreSQL 커넥션을 관리한다.
수천 클라이언트가 붙어도 실제 DB 커넥션은 수십 개만 유지할 수 있다.
세 가지 모드가 있다.

[Session mode]
클라이언트가 끊을 때까지 커넥션을 점유한다.
풀링 효과가 가장 낮다.

[Transaction mode]
트랜잭션이 끝나면 커넥션을 반납한다.
가장 널리 쓰이는 모드다.

[Statement mode]
쿼리 하나마다 커넥션을 반납한다.
multi-statement 트랜잭션을 못 쓴다.

### 풀 사이즈 공식

PostgreSQL wiki에 유명한 공식이 있다.

$\mathrm{connections} = (2 \times \mathrm{core\_count}) + \mathrm{effective\_spindle\_count}$

4코어 서버에 SSD 1개라면 `(4 * 2) + 1 = 9`개다.
직관과 다르다.
"커넥션이 많을수록 빠르지 않나?"
아니다.
DB는 CPU 코어 수만큼만 동시에 일할 수 있다.
그 이상은 대기열에 쌓이고 컨텍스트 스위칭만 늘어난다.
이 공식은 출발점이다.
워크로드에 따라 조정이 필요하지만 방향은 명확하다. 적을수록 빠르다.

### 커넥션이 너무 많으면

MySQL의 max_connections 기본값은 151이다.
이걸 500, 1000으로 올리는 팀이 많다.

[메모리 폭발]
커넥션 하나당 스레드 스택, sort buffer, join buffer, read buffer가 할당된다.
커넥션 수에 비례해서 메모리가 늘어난다.

[컨텍스트 스위칭]
CPU 코어보다 스레드가 많으면 OS가 끊임없이 스레드를 교체한다.
실제 일하는 시간보다 전환 비용이 커진다.

[락 경합]
동시에 같은 행을 건드리는 트랜잭션이 늘면 대기 시간이 기하급수적으로 증가한다.

max_connections를 올리는 건 해결이 아니다.
도로가 좁은데 차를 더 넣는 것과 같다.

### 커넥션이 너무 적으면

애플리케이션 스레드가 커넥션을 못 빌리면 대기열에 쌓인다.
HikariCP의 connectionTimeout이 지나면 예외가 터진다.
한 서비스의 지연이 다른 서비스로 전파된다.
MSA에서 이게 cascading failure의 시작이다.
풀 사이즈가 3인데 한 트랜잭션이 느린 쿼리로 10초를 잡으면 나머지 2개로 전체 트래픽을 감당해야 한다.
금방 고갈된다.
적정 사이즈는 "평균"이 아니라 "피크 시 느린 쿼리가 몇 개나 동시에 뜨는가"로 결정해야 한다.

### 커넥션 누수 — 돌아오지 않는 커넥션

풀에서 빌려간 커넥션이 반납되지 않는 것.
이걸 커넥션 누수라 한다.
흔한 원인은 예외 처리 누락이다.

```sql
-- 이런 코드가 문제다
conn = pool.getConnection()
result = conn.execute("SELECT ...")
conn.close() -- 예외 발생 시 여기까지 안 온다
```

HikariCP는 leakDetectionThreshold를 제공한다.
빌려간 지 N초가 지나도 안 돌아오면 경고 로그를 남긴다.
기본값은 0(비활성)이다.
운영 환경에서는 반드시 켜야 한다.
DBA 입장에서 보면 `SHOW PROCESSLIST`에 Sleep 상태가 쌓여 있고 앱은 "커넥션 부족"을 외치는 상황이 바로 누수다.

### wait_timeout과 커넥션 수명

DB 쪽에서도 유휴 커넥션을 정리한다.
MySQL의 wait_timeout 기본값은 28800초(8시간)다.
이 시간 동안 아무 쿼리도 안 오면 서버가 끊는다.
문제는 풀이 이걸 모른다는 것이다.
풀은 커넥션이 살아 있다고 믿지만 서버는 이미 끊었다.
다음 쿼리에서 "MySQL server has gone away"가 뜬다.
그래서 풀에도 수명 설정이 있다.

[maxLifetime]
HikariCP 기본값은 30분이다.
이 시간이 지나면 커넥션을 폐기하고 새로 만든다.
반드시 DB의 wait_timeout보다 짧아야 한다.

[validationQuery]
빌려주기 전에 살아 있는지 확인하는 쿼리다.
`SELECT 1`이 대표적이다.

### Serverless의 커넥션 폭발

Lambda 같은 서버리스 환경에서는 인스턴스가 동시에 수백 개 뜬다.
각 인스턴스가 커넥션 풀을 따로 만든다.
`100개 인스턴스 x 풀 사이즈 10 = 커넥션 1000개`.
cold start가 몰리면 순간적으로 폭발한다.
DB는 max_connections를 넘기고 죽는다.
AWS RDS Proxy가 이 문제를 풀기 위해 나왔다.
Lambda와 DB 사이에 프록시를 두고 실제 DB 커넥션 수를 제어한다.
pgBouncer의 클라우드 관리형 버전이라 보면 된다.
서버리스에서 DB를 쓸 거라면 커넥션 관리 전략이 아키텍처의 핵심이다.

### DBA 관점에서의 정리

커넥션은 공짜가 아니다.
TCP, 인증, 프로세스 생성. 매번 치르기엔 너무 비싸서 풀이 생겼다.
풀 사이즈는 크면 좋은 게 아니다.
CPU 코어 수 기반으로 시작하고 모니터링으로 조정하는 게 정석이다.
HikariCP는 애플리케이션 레벨, pgBouncer는 DB 앞단 프록시 레벨.
둘은 경쟁이 아니라 레이어가 다르다.
운영에서 가장 무서운 건 누수다.
Sleep 커넥션이 쌓이는데 앱은 풀 부족을 호소하면 코드의 finally 블록부터 의심하라.

### 마무리

"풀 사이즈 얼마요?"에 답하려면 커넥션 하나가 얼마나 비싼지, DB가 동시에 몇 개를 감당하는지, 장애 시 어디서 터지는지를 알아야 한다.
숫자 하나 정하는 문제가 아니다.
시스템 전체를 이해하는 문제다.

## 무중단 스키마 변경: ALTER TABLE이 서비스를 멈추는 이유

"온라인 DDL 해보셨어요?"
면접에서 이 질문이 나오면 주니어와 시니어가 갈린다.
컬럼 하나 추가하는 게 뭐가 어렵냐고 생각하겠지만, 수억 건짜리 테이블에서 ALTER TABLE을 날리면 서비스가 멈출 수 있다.
왜 멈추는지 모르면 운영을 맡길 수 없다.

### ALTER TABLE의 실체

MySQL에서 ALTER TABLE은 원래 이렇게 동작했다.

1. 새 테이블을 만든다.
2. 기존 데이터를 전부 복사한다.
3. 원본을 삭제하고 새 테이블을 원본 이름으로 바꾼다.

10GB 테이블이면 10GB를 통째로 복사한다.
그 동안 쓰기는 차단된다.
복사 시간이 곧 장애 시간이다.
이걸 "Table Copy" 방식이라 한다.
MySQL 5.5 이전의 기본 동작이었다.

### MySQL Online DDL의 등장

MySQL 5.6부터 InnoDB에 Online DDL이 추가됐다.

```sql
ALTER TABLE orders
ADD COLUMN memo VARCHAR(200),
ALGORITHM=INPLACE, LOCK=NONE;
```

`ALGORITHM=INPLACE`는 테이블 복사 없이 InnoDB 내부에서 직접 변경한다.
`LOCK=NONE`은 변경 중에도 읽기/쓰기를 허용한다.
모든 변경이 이렇게 되면 좋겠지만, 그렇지 않다.

### 되는 것과 안 되는 것

Online DDL이라고 다 "온라인"은 아니다.

[INPLACE 가능]
컬럼 추가, 인덱스 추가/삭제, 컬럼 이름 변경, VARCHAR 길이 확장(제한적).

[COPY 필요 — 쓰기 차단]
컬럼 타입 변경 (INT→BIGINT), 문자셋 변경, PK 삭제.
컬럼 타입을 바꾸면 모든 행을 다시 써야 한다.
INPLACE로 할 수 없다.

면접에서 "어떤 ALTER가 온라인이고 어떤 게 아닌지" 물어보면 이 구분을 대답해야 한다.

### Instant DDL

MySQL 8.0.12부터 `ALGORITHM=INSTANT`가 추가됐다.

```sql
ALTER TABLE orders
ADD COLUMN memo VARCHAR(200),
ALGORITHM=INSTANT;
```

메타데이터만 변경한다. 데이터를 건드리지 않는다.
테이블이 1TB여도 1초 안에 끝난다.
단, 제약이 있다.
컬럼 추가는 테이블 끝에만 가능하고, 컬럼 삭제나 순서 변경은 8.0.29부터다.
인덱스 추가는 Instant로 안 된다.

### Metadata Lock 문제

Online DDL이라도 시작과 끝에서 Metadata Lock(MDL)을 잡는다.
문제는 이 MDL이 "줄 서기"를 만든다는 것이다.

1. 트랜잭션 A가 SELECT 실행 중 (MDL shared 보유)
2. ALTER TABLE이 MDL exclusive 대기
3. 이후 모든 SELECT가 ALTER 뒤에 줄을 선다

장시간 실행 쿼리 하나가 ALTER를 막고, ALTER가 뒤따르는 모든 트래픽을 막는다.
쿼리 하나 → DDL → 전체 서비스 중단.
DBA가 DDL 전에 long query부터 확인하는 이유다.

### pt-online-schema-change

Percona에서 만든 도구다.
MySQL의 Online DDL 한계를 우회한다.

[동작 원리]

1. 원본과 같은 구조의 빈 테이블을 만든다
2. 빈 테이블에 ALTER를 적용한다
3. 원본에 트리거 3개를 건다 (INSERT/UPDATE/DELETE)
4. 원본 데이터를 청크 단위로 복사한다
5. 트리거가 실시간 변경분을 반영한다
6. 복사 완료 후 RENAME TABLE로 교체한다

원본 테이블은 변경 중에도 정상 운영된다.
RENAME은 원자적이라 순간적으로 전환된다.

### gh-ost

GitHub에서 만든 도구다.
pt-osc의 트리거 방식이 싫어서 만들었다.

[동작 원리]

1. 빈 shadow 테이블을 만든다
2. 원본 데이터를 청크 단위로 복사한다
3. binlog를 구독해서 변경분을 반영한다
4. 복사 완료 후 cut-over로 교체한다

트리거 대신 binlog를 쓴다.
트리거가 원본 테이블에 부하를 주는 문제가 없다.
쓰로틀링도 외부에서 제어할 수 있다.
replication lag이 올라가면 자동으로 멈추고, 내려가면 다시 진행한다.

### pt-osc vs gh-ost

둘 다 쓰는 곳이 있고, 하나만 쓰는 곳도 있다.

[pt-osc가 유리한 경우]
FK(Foreign Key)가 있는 테이블.
gh-ost는 FK를 지원하지 않는다.
설정이 단순하고 빠르게 실행할 때.

[gh-ost가 유리한 경우]
대형 테이블에서 부하 제어가 중요할 때.
트리거 오버헤드를 피하고 싶을 때.
실시간 쓰로틀링이 필요할 때.

면접에서 "둘 중 뭘 쓰나요?"보다 "왜 그걸 선택했나요?"가 더 중요하다.
근거를 말할 수 있어야 한다.

### PostgreSQL은 다르다

PostgreSQL에서 대부분의 ALTER TABLE은 논블로킹이다.

```sql
ALTER TABLE orders ADD COLUMN memo TEXT;
```

이건 메타데이터만 바꾼다.
테이블 크기와 무관하게 즉시 끝난다.
MySQL과 근본적으로 다른 점이다.
인덱스 추가도 CONCURRENTLY 옵션으로 락 없이 가능하다.

```sql
CREATE INDEX CONCURRENTLY idx_memo
ON orders(memo);
```

PostgreSQL DBA는 pt-osc 같은 도구가 왜 필요한지 잘 모를 수 있다.

### PostgreSQL 11 이전의 함정

PostgreSQL도 함정은 있었다.
11 이전에는 DEFAULT가 있는 컬럼 추가가 모든 행을 다시 써야 했다.

```sql
-- PG 10 이하: 전체 행 rewrite 발생
ALTER TABLE orders
ADD COLUMN status TEXT DEFAULT 'pending';
```

테이블이 크면 오래 걸렸다.
그래서 컬럼을 NULL로 추가하고 나중에 DEFAULT를 설정하는 우회가 필요했다.
PostgreSQL 11부터 non-volatile DEFAULT는 메타데이터만 변경한다.
이 개선 하나로 운영 부담이 크게 줄었다.

### 대형 테이블 마이그레이션 패턴

도구 하나로 안 되는 경우도 있다.
수십억 건, 수백GB 테이블의 구조 변경은 전략이 필요하다.

[배치 업데이트]
새 컬럼 추가 후 값을 채울 때 한 번에 UPDATE하면 락과 로그가 폭발한다.
1만 건씩 나눠서 실행한다.

[듀얼 라이트]
새 테이블에 쓰기를 병행하고, 배치로 구 데이터를 이관한 뒤, 읽기를 전환하고, 구 테이블을 제거한다.

[블루-그린]
새 구조의 레플리카를 준비하고, 동기화 완료 후 트래픽을 전환한다.

### 무엇이 잘못될 수 있는가

스키마 변경 도구를 쓰더라도 실패하는 경우는 있다.

[디스크 공간]
shadow 테이블은 원본과 같은 크기다.
100GB 테이블이면 100GB가 추가로 필요하다.
디스크가 부족하면 도중에 실패한다.

[레플리케이션 랙]
복사 부하로 replica가 밀린다.
gh-ost는 자동 쓰로틀링이 되지만, pt-osc는 설정을 안 하면 계속 밀어붙인다.

[교체 시점 데드락]
RENAME TABLE 순간에 진행 중인 트랜잭션과 충돌할 수 있다.
짧지만 실패 가능성이 존재한다.

### DBA 관점에서의 정리

운영에서 DDL은 가장 긴장되는 작업이다.
실행 전 확인하는 체크리스트가 있다.
long query 없는지, 디스크 여유 있는지, 레플리케이션 정상인지, 트래픽 낮은 시간대인지.
도구 선택도 중요하지만 "언제, 어떤 조건에서 실행하는가"가 사고를 막는 핵심이다.
면접에서 "ALTER TABLE 날려본 적 있나요?"가 아니라 "서비스 중에 스키마를 바꿔본 적 있나요?"가 진짜 질문이다.

### 마무리

ALTER TABLE은 단순한 명령어가 아니다.
테이블 복사, 메타데이터 락, 레플리케이션 부하.
이 세 가지가 서비스를 멈추는 원인이다.
MySQL은 pt-osc와 gh-ost로 우회하고, PostgreSQL은 대부분 즉시 끝나지만 DEFAULT 컬럼의 함정은 알아야 한다.
무중단 스키마 변경의 핵심은 "데이터를 복사하지 않는 것"이다.
복사하지 않으면 시간이 걸리지 않고, 시간이 걸리지 않으면 서비스가 멈추지 않는다.
도구를 아는 것보다 왜 그 도구가 필요한지 아는 것이 면접에서도, 운영에서도 더 중요하다.

## Aurora MySQL failover 62초의 비밀: JDBC URL 한 줄이 만드는 차이

> failover 순단이 왜 길었는지 못 찾은 개발자에게 바치는 글

failover 순단은 10초쯤이라고들 한다.
같은 클러스터, 같은 순간에 한 앱은 9.5초, 다른 앱은 62초.
차이는 URL 프로토콜 한 단어다.
11번 중 8번이 62초였다.
62초가 기본값이고 10초가 예외다.

- URL 프로토콜을 aurora로 쓰라.
- URL host에 cluster-ro를 반드시 병기하라.
- 드라이버는 MariaDB Connector/J 2.7.x를 쓰라.
- max-lifetime은 50초~58초 사이에 두라.
- 설정 파일이 아니라 런타임 적용값을 확인하라.

62초가 기본값인 줄 모르면 10초라는 기대가 사고가 된다.

### aurora 프로토콜이 뭘 하는가

`jdbc:mysql:aurora://`는 드라이버에게 한 가지를 알린다.
"이 주소는 서버 한 대가 아니라 클러스터다."
이 표시가 있으면 드라이버가 현재 writer를 계속 확인한다.
failover로 writer가 바뀌면 스스로 옮겨간다.
빼면 평범한 MySQL 서버 한 대로 본다.
끊기면 URL 주소로 다시 붙을 뿐, 붙은 노드가 writer인지 확인하지 않는다.
cluster endpoint는 DNS다.
failover 직후 잠깐은 옛 노드를 가리킨다.
DNS 갱신이 먼저냐, 재접속이 먼저냐. 거기서 갈린다.

### 62초가 만들어지는 구조

재접속이 DNS 갱신보다 빠르면 드라이버는 강등된 옛 writer에 붙는다.
강등된 옛 writer는 죽지 않는다.
접속도 받고 읽기도 정상 처리한다.
쓰기만 read-only 에러로 거부한다.
풀의 health check를 통과한다.
그래서 계속 재사용된다.
이 커넥션을 버릴 수단은 하나다.
수명 만료. HikariCP의 `max-lifetime`.
62초 = 재접속 12초 + max-lifetime 50초.
DNS가 먼저 갱신되어 10초에 끝난 건 11번 중 2번이었다.

### 함께 어기면 복구가 안 된다

aurora 없이 JVM DNS 캐시를 무기한으로 두면?
712초가 지나도 복구되지 않았다. 3번 전부.
aurora가 없으면 수명 만료가 유일한 회복 경로다.
DNS 캐시를 무기한으로 두면 그 경로까지 막힌다.
JVM DNS TTL은 5초로 둔다.
max-lifetime을 20초로 줄이면?
HikariCP가 30초 미만을 기각한다.
경고 한 줄 남기고 기본값 30분으로 돌아간다.
파일만 보면 20초다.
순단은 max-lifetime + 약 12초에 수렴한다.
70초면 81.7초, 35초면 47.0초.
aurora를 지킨 앱에서는 나머지를 어겨도 차이가 측정되지 않았다.

### reader를 지우면 1,533건이 터진다

failover만 위험한 게 아니다.
reader 삭제에서 더 극적인 차이가 난다.
writer cluster endpoint만 쓰는 앱에서 부하 중 최다 사용 reader를 지웠다.
에러 1,533건. 순단 71.7초.
같은 설정에 `cluster-ro`를 병기하면 에러 0건. 순단 0초.
드라이버 버전, socketTimeout, max-lifetime을 바꿔도 결과는 같았다.
cluster-ro 병기만이 전 조합에서 0이다.
매일 새벽 reader가 삭제되는 운영 서비스에서도 없는 쪽은 16~24건 버스트, 있는 쪽은 0건이었다.

### Blue/Green은 다른 게임이다

B/G 스위치오버는 클라이언트 설정으로 줄일 수 없다.
failover에서 가장 좋았던 구성이 B/G에서 가장 나빴다.
읽기 순단 1.2초가 18.7초로.
순단이 DNS 재작성 대기에 지배되기 때문이다.
어떤 조합으로도 5초 아래로 내려가지 않았다.
더 조심할 것이 있다.
aurora 앱이 폐기된 blue로 55초간 읽기를 보냈다.
1,060건 전부 성공. p99 0ms. 순단 지표에 잡히지 않는다.
구 blue는 복제가 끊긴 독립 클러스터라 그 사이 새 클러스터의 쓰기가 반영되지 않는다.
에러 없는 오염이다.

### 설정 파일 값과 런타임 값이 다르다

이 패턴이 세 번 나왔다.
셋 다 파일만 grep하는 감사를 통과한다.
max-lifetime 20000을 썼다. 런타임은 1800000.
30초 미만이라 HikariCP가 기각했다.
maxLifeTime 58000을 썼다. 런타임은 180000.
공용 라이브러리 기본값으로 떨어졌다.
기동 에러도, 경고도 없었다.
세 번째는 이 글을 보충하게 한 사건이다.
failover 작업 일주일 전 점검에서 온라인 서빙 두 서비스가 같은 이유로 3분 타이머 위에 있었다.
예측 순단 192초.

### yml에서 풀까지, 값이 끊기는 자리

설정값은 여러 손을 거친다.
yml, 설정 바인딩 클래스, Properties 조립, 공용 라이브러리, 그리고 풀.
끊긴 곳은 두 번째였다.
클래스에 username, password, resource만 있고 maxLifeTime 필드가 없다.
Spring Boot의 ignoreUnknownFields 기본값은 true다.
모르는 키는 에러 없이 버린다.
기동은 정상, 로그는 조용, 값은 없다.
라이브러리는 키를 못 찾으면 catch 블록에서 기본값 180000을 돌려준다.
관측된 180초의 정체다.
필드 하나가 3분을 만들었다.

### 세 번의 failover가 증명한 것

같은 앱에 failover를 세 번 일으켰다.
1차, 설정 전: 쓰기 순단 175.65초.
2차, maxLifeTime 58000 배포 직후: 175.66초.
3차, 값이 실제로 실린 뒤: 21.10초.
1차와 2차 차이는 12ms다.
트래픽이 달랐는데 순단은 같았다.
순단을 정하는 건 트래픽이 아니라 고정 타이머라는 뜻이다.
180초 타이머에 재접속 12초를 더하면 실험실 공식 그대로다.
값이 실리자 175초가 21초가 됐다.
파일에 58000이 적힌 건 2차부터였다.
적힌 것과 실린 것은 다르다.

### 같은 라이브러리를 쓰는 레포 다섯 곳

한 곳에서 찾은 구멍은 대개 한 곳이 아니다.
같은 공용 라이브러리로 DB 설정을 받는 레포 다섯 곳을 훑었다.
온라인 서빙 모듈에 필드가 있는 곳 0.
배치 모듈에는 있는 곳이 둘.
yml에 값을 적어 둔 곳도 있었다. 필드가 없으니 무효다.
설정 클래스를 복사하면 구멍도 복사된다.
문제를 인지한 팀조차 배치만 고치고 서빙은 놓쳤다.
확인 수단도 막혀 있었다.
actuator가 health만 열고 configprops는 404였다.
런타임 값을 볼 창이 없으면 감사는 추측이 된다.

### AWS JDBC Wrapper라는 선택지

Spring Boot 3.x BOM이 3.5.x를 가리킨다.
버전업하면 3.x가 되고, 3.x는 aurora 프로토콜을 못 쓴다.
이번 점검에서도 3.0.9가 나왔다.
2.7.12인데 스킴만 빠진 앱도 있었다. 이쪽은 URL 한 줄이다.
3.x에는 AWS JDBC Wrapper가 틈을 메운다.

- 3.5.7 단독: 62.6초.
- 3.5.7 + Wrapper(mariadb 스킴): 9.3초.
- 9.1.0 + Wrapper(mysql 스킴): 2.6초.
- B/G에서는 기준 앱 17~70초가 Wrapper 3.7~4.5초로.

표준은 두 갈래다. mariadb 2.7 + aurora, 또는 mysql + Wrapper.

### Wrapper를 쓰려면 함께 지켜야 할 것

넷 다 "안 하면 조용히 잘못 동작"한다.

[rds_topology 읽기 권한]
B/G 생성 전에 GRANT SELECT.
없으면 bg 플러그인이 에러 없이 무력화된다. 3.7초가 20초대로.

[clusterId와 bgdId]
기본값이 둘 다 "1"이다.
한 JVM에 클러스터가 둘이면 토폴로지 캐시를 공유해 엉뚱한 곳으로 라우팅한다.

[Hibernate dialect 명시]
mariadb 스킴 + ddl-auto validate에서 기동 실패.
메시지는 missing table인데 실제는 DB 이름을 대문자로 조회한 것이다.

[스킴은 mysql]
mariadb 스킴은 failover가 4배 느리고 dialect 문제도 여기서만 난다.

### failover 작업 전 5분 점검

일정이 잡혔다면 순서대로 본다.

1. 드라이버 버전. 3.x면 aurora 스킴은 선택지가 아니다.
2. URL 스킴. 2.7인데 `:aurora`가 빠진 앱은 코드 없이 URL만 고친다.
3. cluster-ro 병기 여부.
4. 런타임 max-lifetime. actuator configprops로 본다. 파일 말고.
5. JVM DNS TTL.

클라이언트 교체는 영향도가 크다.
작업이 코앞이면 max-lifetime부터 맞춘다.
그것만으로 3분이 1분 아래로 내려온다.
드라이버 표준화는 그 다음 일이다.

## 당신의 Upsert는 진짜로 쓰고 있는가

```sql
INSERT ... ON DUPLICATE KEY UPDATE
```

MySQL에서 가장 편리한 구문 중 하나다.
있으면 수정하고, 없으면 넣는다.
한 줄이면 끝이니까 누구나 고민 없이 쓴다.
문제는 "고민 없이"라는 부분이다.
값이 바뀌었든 안 바뀌었든 매번 전건 upsert를 보내는 배치가 있다면, 그 DB는 아무 의미 없는 쓰기를 반복하고 있다.

- 변하지 않는 값을 매번 덮어쓰지 마라.
- INSERT:UPDATE 비율이 1:1이면 의심하라.
- row 수 대비 upsert 횟수가 100배를 넘으면 경고다.

DB는 "같은 값이면 무시"해주지 않는다.
affected_rows가 0인 건수를 세라.
쉽다고 생각한 순간부터 한 줄짜리 upsert가 사고가 된다.

### Upsert는 뭘 하는가

MySQL에서 `ON DUPLICATE KEY UPDATE`는 INSERT를 먼저 시도한다.
Primary Key나 Unique Key에 충돌이 없으면 그냥 INSERT. 충돌이 있으면 UPDATE로 전환한다.
한 줄로 "있으면 수정, 없으면 삽입"을 해결하니까 배치, 스케줄러, 동기화 파이프라인에서 습관처럼 쓰인다.

```sql
INSERT INTO feed (feed_id, content, updated_at)
VALUES (?, ?, NOW())
ON DUPLICATE KEY UPDATE
content = VALUES(content),
updated_at = VALUES(updated_at);
```

간결하다. 그래서 위험하다.

### 어디서 문제가 시작되는가

값이 바뀌었든 아니든 매번 전건 upsert를 날리는 배치.
피드를 5분마다 동기화한다고 하자.
테이블에 row가 400만 개 있다.
5분마다 400만 건 upsert. 하루 288번. 하루 11.5억 건. 한 달이면 345억 건.
이 중에서 실제로 값이 바뀐 건 몇 퍼센트나 될까?
피드 내용이 5분마다 바뀌는 row는 전체의 1%도 안 될 수 있다.
나머지 99%는 똑같은 값을 똑같은 자리에 덮어쓰고 있을 뿐이다.

### DB는 "같은 값"을 알아서 무시해주지 않는다

흔한 오해가 있다.
"값이 같으면 MySQL이 알아서 skip 하지 않나?"
반은 맞고 반은 틀리다.
MySQL은 값이 동일하면 `affected_rows = 0`을 반환한다.
실제로 디스크에 쓰지 않는다.
하지만 그 이전 단계에서 이미 비용이 발생한다.

- row lock을 획득한다.
- binlog에 이벤트를 기록한다.
- Reader에 복제한다.

값이 같아도 lock과 binlog와 replication은 돌아간다.
DB가 "같은 값"을 무시해주는 건 디스크 쓰기뿐이다.

### 눈에 보이지 않는 비용들

upsert 한 건이 내부에서 하는 일을 따라가 보자.

1. INSERT를 시도한다.
2. PK/Unique 인덱스에서 기존 row를 검색한다.
3. 충돌을 발견한다.
4. INSERT intention lock을 잡는다.
5. S lock에서 X lock으로 전환한다.
6. row를 갱신한다.
7. binlog에 기록한다.
8. redo log에 기록한다.
9. Reader로 복제한다.

값이 바뀌든 안 바뀌든 이 과정을 전부 탄다.
400만 건을 매번 이렇게 처리하면 Buffer Pool에는 이 row들의 페이지가 올라오고 정작 서비스 쿼리가 쓸 hot 페이지를 밀어낸다.

- Buffer Pool 오염.
- 복제 지연.
- I/O 비용.
- lock 경합.

전부 "같은 값 덮어쓰기"에서 나온다.

### 실제 사례 --- row 400만에 upsert 32억

실제 프로덕션 클러스터에서 Performance Schema를 조회했다.
`schedule_feed_32` 테이블.
실제 row 수는 414만. 누적 upsert 횟수는 32억.
row 하나당 평균 770번 덮어쓴 셈이다.
InnoDB 전체 쓰기의 83%가 upsert에서 UPDATE로 전환된 것이었다.
digest를 확인하니 99.99%가 `ON DUPLICATE KEY UPDATE`.
순수 INSERT는 1,792건.
32억 건 중 진짜 새로운 row는 0.000056%.
나머지 99.999%는 있는 row에 같은 값을 덮어쓰고 있었다.

### ON DUPLICATE KEY UPDATE vs 순수 UPDATE

"그러면 UPDATE로 바꾸면 해결되는 거 아닌가?"
row를 찾아서 갱신하는 건 어차피 UPDATE나 upsert나 같다.
차이는 upsert의 INSERT 시도 과정이다.

[ON DUPLICATE KEY UPDATE]

1. INSERT intention lock 획득
2. PK 충돌 발견
3. S lock → X lock 전환
4. UPDATE 수행

[순수 UPDATE]

1. X lock 획득
2. UPDATE 수행

lock 전환 과정에서 동시성이 높으면 deadlock 확률이 올라간다.
하지만 핵심은 거기가 아니다.
UPDATE로 바꿔도 "같은 값 덮어쓰기"는 남는다.
진짜 해결은 **값이 안 바뀌었으면 아예 안 보내는 것**이다.

### 해결 --- 보내지 않는 것이 최선이다

쿼리를 바꾸는 게 아니다.
쿼리를 보낼지 말지를 판단하는 것이다.
앱에서 이전 값과 새 값을 비교한다.
4개 컬럼이 전부 같으면 skip. 하나라도 다르면 기존처럼 upsert.
비교는 DB에 SELECT를 추가로 날리는 게 아니다.
앱이 이미 갖고 있는 캐시에서 한다.
DB 부하는 오히려 줄기만 한다.
skip하면 INSERT 시도도 안 하고 UPDATE도 안 한다.
binlog도 안 쓰고 Reader에 복제도 안 한다.
32억 건 중 90%가 동일 값이라면 28.8억 건의 쓰기가 사라진다.

### 그런데 upsert가 다 나쁜 건 아니다

`ON DUPLICATE KEY UPDATE`를 쓴다고 무조건 안티패턴인 것은 아니다.
워크플로우 엔진에서 이벤트 소싱의 idempotency를 보장하기 위해 upsert를 쓰는 경우가 있다.
이때는 INSERT가 대부분이고 UPDATE는 거의 발생하지 않는다.
실제로 다른 클러스터를 조회하니 INSERT 7.79억에 UPDATE 4.8만. UPDATE 비율 0.006%.
이건 "같은 row를 반복 덮어쓰는 것"이 아니라 "중복 방지 안전장치"로 쓰는 것이다.
구분 기준은 간단하다.

- INSERT:UPDATE가 1:1이면 안티패턴.
- INSERT가 압도적이면 정상.

### DBA는 어떻게 찾는가

Performance Schema에서 두 가지를 본다.
`table_io_waits_summary_by_table`에서 `count_insert`와 `count_update`가 1:1인 테이블.
`events_statements_summary_by_digest`에서 ON DUPLICATE KEY UPDATE가 있는 digest.
그리고 `information_schema.tables`에서 `table_rows`와 upsert 횟수를 비교한다.
row 414만에 upsert 32억이면 770배 덮어쓰기.
이 세 가지가 모이면 개발팀에 숫자를 보여줄 수 있다.
"이 테이블, row당 770번 같은 값 덮어쓰고 있습니다."
숫자가 있으면 설득이 된다.
감으로는 안 된다.

### DBA 관점에서의 정리

- 변하지 않는 값을 매번 덮어쓰지 마라.
- INSERT:UPDATE 비율이 1:1이면 의심하라.
- row 수 대비 upsert 횟수가 100배를 넘으면 경고다.
- DB는 "같은 값이면 무시"해주지 않는다.
- affected_rows가 0인 건수를 세라.

OFFSET/LIMIT이 읽기의 대표적 안티패턴이라면 무조건 upsert는 쓰기의 대표적 안티패턴이다.
둘 다 "일단 동작하니까" 전건 처리하는 습관에서 온다.
둘 다 규모가 커지면서 비용이 폭발한다.
둘 다 DB 단에서 발견할 수 있고, 둘 다 고치는 건 앱 쪽의 몫이다.
DBA가 할 수 있는 건 문제를 숫자로 보여주는 것이다.
"row 414만에 upsert 32억"이라는 한 줄이 개발팀을 움직이게 한다.
쉽다고 생각한 순간부터 한 줄짜리 upsert가 사고가 된다.

## 채팅과 DB: 읽었는지 안 읽었는지, 그게 이렇게 어려운 일

"채팅 기능 하나 붙이려는데, DB는 뭘 신경 써야 해요?"
메시지를 저장하고 불러오면 끝이라고 생각한다. 그건 게시판이다.
채팅은 다르다.
누가 읽었는지를 추적해야 하고 안 읽은 메시지를 세야 하고 방 목록을 실시간으로 정렬해야 한다.
보내는 건 INSERT 하나지만 읽었는지를 관리하는 게 채팅 DB의 진짜 문제다.

- 안 읽은 수는 카운터로 분리하라.
- 그룹 채팅의 읽음 확인은 곱셈이다.
- 방 목록 정렬은 쓰기와 충돌한다.
- 오래된 메시지는 파티셔닝으로 분리하라.
- 채팅 검색은 DB 밖에서 하라.

### 메시지 저장은 쉽다

채팅 메시지는 append-only다. 시간 순서대로 쌓기만 한다.
수정도 드물고 삭제는 더 드물다.
INSERT는 빠르다.
auto_increment에 timestamp 인덱스만 있으면 초당 만 건도 문제 없다.
문제는 읽기다.
"이 방의 최근 50건"은 쉽다.
"이 방의 2024년 3월 메시지"는 어렵다.
방 하나에 메시지 500만 건이 쌓이면 인덱스를 타도 범위가 넓다.
쓰기는 쉬운데 읽기가 어려운 구조.
보통의 서비스와 반대다.

### 안 읽은 메시지 N건의 실체

카카오톡을 열면 숫자가 보인다. "안 읽은 메시지 3건."
이걸 구현하려면 어떤 데이터가 필요한가.
사용자별, 채팅방별로 마지막으로 읽은 메시지 ID를 저장해야 한다.

```sql
SELECT COUNT(*) FROM messages
WHERE room_id = 42
AND message_id > 1523
```

방이 100개면 이 쿼리가 100번 돈다.
사용자 10만 명이 앱을 열면 100만 번의 COUNT가 동시에 실행된다.
채팅방 목록을 열 때마다 이 비용이 든다.
캐시하지 않으면 DB가 버틸 수 없다.

### 채팅방 목록의 정렬 비용

채팅방 목록은 최신 메시지 순으로 정렬된다.
메시지가 오면 그 방이 맨 위로 올라간다.
이걸 DB로 하면 메시지가 올 때마다 채팅방 테이블의 last_message_at을 UPDATE해야 한다.
초당 메시지 1000건이면 초당 UPDATE 1000건이다.
방마다 다른 row라서 lock 경합은 적지만 인덱스 재정렬 비용이 쌓인다.
사용자가 방 목록을 열면

```sql
SELECT * FROM rooms
WHERE user_id = 7
ORDER BY last_message_at DESC
```

이 쿼리가 빨라야 한다.
메시지 INSERT와 방 목록 정렬.
둘 다 빨라야 하는데 서로 충돌한다.

### 1:1은 되는데 그룹채팅에서 터진다

1:1 채팅은 단순하다.
메시지를 쓰면 상대 한 명에게 간다.
그룹 채팅은 다르다.
500명이 있는 방에 메시지를 보내면 499명의 읽음 상태를 관리해야 한다.
읽음 확인 테이블이 폭발한다.
메시지 1건 × 참여자 500명 = 500건.
하루에 메시지 1000건이면 읽음 레코드 50만 건이 하루 만에 쌓인다.
방이 100개면 5000만 건. 한 달이면 15억 건.
그룹 채팅의 읽음 확인을 메시지 단위로 관리하면 DB가 감당할 수 없다.
카카오톡이 "몇 명이 안 읽었는지"만 보여주는 건 기술적 타협이다.

## 예약 시스템과 DB: 같은 시간에 두 명이 예약하면 생기는 일

"예약 기능 만들려는데, 그냥 INSERT 하면 되지 않나요?"
시간과 자리를 고르고 저장한다. 달력에 표시한다.
끝이라고 생각한다.
그런데 같은 시간에 두 명이 동시에 예약하면 둘 다 성공한다.
DB에는 같은 슬롯에 두 건이 들어간다.
예약은 데이터를 넣는 게 아니라 자리를 점유하는 것이다.
점유를 보장하는 건 INSERT가 아니라 락이다.

- 슬롯은 유니크 제약으로 보호하라.
- 대기열은 상태 머신으로 관리하라.
- 반복 예약은 규칙과 예외를 분리하라.
- no-show는 외부 스케줄러가 처리하라.
- 시간은 timezone 없이 저장하지 마라.

### 같은 시간, 같은 자리, 두 명

A가 오후 3시를 선택한다.
빈 자리를 확인하고 예약 버튼을 누른다.
그 사이 B도 오후 3시를 선택한다.
빈 자리를 확인하고 예약 버튼을 누른다.
둘 다 SELECT 시점에는 비어 있었다.
둘 다 INSERT에 성공한다.
더블 부킹이다.
UNIQUE 제약조건을 걸면 간단하다.
(resource_id, slot_time)에 유니크 인덱스.
두 번째 INSERT가 실패한다.
하지만 연속 슬롯을 잡아야 하면 유니크만으로는 부족하다.
2시간짜리 예약이 기존 1시간 예약과 겹치는지 범위 검증이 필요하다.

### 시간 슬롯을 어떻게 설계하는가

방법은 두 가지다.

[슬롯 테이블 방식]
30분 단위로 슬롯을 미리 만들어둔다.
예약하면 해당 슬롯의 상태를 occupied로 바꾼다.
단순하지만 유연하지 않다.
45분짜리 예약은 슬롯 두 개를 먹는다.

[시작-종료 시간 방식]
start_time과 end_time을 저장한다.
예약 전에 겹치는 구간이 있는지 쿼리한다.

```sql
SELECT COUNT(*) FROM reservations
WHERE resource_id = 5
AND start_time < '15:00'
AND end_time > '13:00'
```

유연하지만 겹침 검증 쿼리가 매번 필요하다.
동시 요청이 많으면 경합이 생긴다.

### 캘린더 뷰라는 비싼 쿼리

사용자가 달력을 열면 한 달치 예약을 한 번에 보여줘야 한다.
리소스가 회의실 10개라면 10개 × 30일 × 시간 슬롯.
한 번의 화면 렌더링에 수백 건의 예약 레코드를 읽는다.
여기에 "빈 시간 보기" 필터를 넣으면 예약이 없는 슬롯을 계산해야 한다.
없는 것을 찾는 건 있는 것을 찾는 것보다 비싸다.
인덱스는 (resource_id, start_time)이 기본이다.
날짜 범위 쿼리가 빈번하므로 파티셔닝까지 고려하게 된다.

### 취소와 대기열의 순서

예약이 꽉 찼다.
대기열에 3명이 있다.
1번 예약자가 취소한다.
누구에게 기회가 가는가.
대기 1번에게 알림을 보낸다.
5분 안에 확정하지 않으면 2번에게 넘어간다.
이 로직은 DB만으로 안 된다.
타이머가 필요하다. 상태 전이가 필요하다.
대기 → 알림 발송 → 확정 대기 → 확정 or 만료.
상태가 4개이고 시간 제한이 있으면 스케줄러나 메시지 큐 없이는 관리할 수 없다.
예약 취소 한 건이 이렇게 복잡하다.

### 반복 예약의 저장 문제

"매주 월요일 오전 10시."
사용자는 한 문장이다. DB는 어떻게 저장하는가.

[방법 1: 전부 펼쳐서 저장]
52주면 52건의 레코드를 만든다.
단순하지만 "매주 월요일" 전체를 취소하려면 52건을 다 지워야 한다.

[방법 2: 규칙으로 저장]
반복 규칙을 별도 테이블에 넣는다.
RRULE 형식. 매주, 월요일, 시작일, 종료일.
단순하지만 "다음 주만 취소"가 어렵다.
예외 테이블이 하나 더 필요하다.
반복 규칙 + 예외 목록 + 실체화된 인스턴스.
테이블 세 개가 엮인다.
캘린더 앱이 복잡한 이유다.

### no-show 처리는 누가 하는가

예약 시간이 지났는데 안 왔다.
상태를 no-show로 바꿔야 한다.
사용자가 트리거하는 게 아니라 시간이 트리거하는 이벤트다.
DB에 스케줄러를 넣을 수 있다. MySQL EVENT나 pg_cron.
그런데 분 단위로 수만 건을 스캔하면 DB에 부하를 준다.
외부 스케줄러가 주기적으로 "시간 지난 예약"을 배치로 상태 변경하는 게 낫다.

```sql
UPDATE reservations
SET status = 'no_show'
WHERE status = 'confirmed'
AND end_time < NOW() - INTERVAL 30 MINUTE
```

비즈니스 로직인데 실행 주체가 DB 밖에 있다.
누가 돌릴지를 정해야 한다.

### 시간대의 함정

서울에서 오후 3시에 예약했다. DB에는 UTC 06:00으로 저장됐다.
도쿄 사용자가 같은 시스템을 쓴다.
오후 3시를 선택했는데 서울의 오후 3시와 같은 슬롯이 아니다.
UTC로 저장하는 건 맞다.
문제는 보여줄 때다.
사용자의 timezone을 알아야 하고 서머타임이 있는 나라면 계절마다 바뀐다.
"매주 월요일 10시"를 UTC로 저장했는데 서머타임이 바뀌면 현지 시각이 달라진다.
사용자는 예약 시간이 바뀐 줄 안다.
시간은 숫자가 아니라 맥락이다.
timezone 없는 시간 데이터는 불완전하다.

### DBA 관점에서의 정리

예약 시스템은 달력 UI 뒤에 동시성 제어가 숨어 있다.

- 슬롯은 유니크 제약으로 보호하라.
- 대기열은 상태 머신으로 관리하라.
- 반복 예약은 규칙과 예외를 분리하라.
- no-show는 외부 스케줄러가 처리하라.
- 시간은 timezone 없이 저장하지 마라.

더블 부킹이 처음 발생했을 때 고치는 비용보다 처음부터 유니크 제약을 거는 비용이 싸다.
예약은 데이터를 넣는 게 아니라 자리를 점유하는 것이다.
점유를 보장하는 건 INSERT가 아니라 락이다.

## ID를 만든다는 것: AUTO_INCREMENT가 1, 2, 3이 아닌 이유

테이블에 row를 넣으면 ID가 1, 2, 3으로 붙는다.
당연한 것 같지만, 실제 프로덕션 테이블을 열어보면 `1, 2, 5, 8, 14, 27`.
"3번은 어디 갔나요? 데이터 유실인가요?"
개발자가 가장 자주 하는 질문이다. 유실이 아니다.

- AUTO_INCREMENT는 연속을 보장한 적이 없다.
- gap을 두려워하지 마라.
- UUID를 PK로 쓸 때는 순서를 확보하라.
- ID에 비즈니스 의미를 담지 마라.
- 순차 ID를 외부에 노출하지 마라.
- PK 설계는 테이블을 만들기 전에 끝내라.

ID는 단순해 보이지만 시스템의 뼈대다.

### 왜 ID에 빈 번호가 있는가

"3번 주문이 없어요. 데이터가 사라진 건가요?"
개발자가 DBA에게 가장 자주 묻는 질문이다.
답은 항상 같다. "사라진 게 아니라 처음부터 없었습니다."
AUTO_INCREMENT는 연속된 번호를 약속하지 않는다.
번호를 발급하되, 그 번호가 실제 row로 남을지는 보장하지 않는다.
빈 번호는 유실이 아니라 정상 동작의 흔적이다.

### AUTO_INCREMENT의 동작 원리

InnoDB는 메모리에 카운터를 유지한다.
INSERT가 들어오면 카운터를 1 올리고 그 값을 새 row에 부여한다.
핵심은 이것이다. 번호는 INSERT 시점에 소비된다.
INSERT가 성공했느냐는 별개의 문제다.
트랜잭션이 롤백되면?
row는 사라지지만 번호는 돌아오지 않는다.
이미 써버린 번호를 되돌리면 동시에 같은 번호를 받은 다른 트랜잭션과 충돌할 수 있기 때문이다.
카운터는 앞으로만 간다.

### gap이 생기는 이유

빈 번호가 생기는 경로는 여러 가지다.

[롤백]
INSERT 후 ROLLBACK하면 번호는 소비되고 row는 없다.

[INSERT IGNORE]
중복 키 충돌로 무시되어도 번호는 이미 올라갔다.

[REPLACE]
DELETE + INSERT이므로 새 번호가 발급된다.

[벌크 INSERT]
여러 row를 한 번에 넣으면 번호를 미리 예약한다.
일부가 실패하면 예약된 번호가 비어진다.

[서버 재시작]
MySQL 5.7까지는 카운터가 메모리에만 있었다.
재시작하면 MAX(id)+1로 재계산했고 중간에 삭제된 번호가 재사용될 수 있었다.
8.0부터 redo log에 기록하여 이 문제를 해결했다.

### 복제 환경에서의 충돌

Source가 두 개 이상인 환경에서 양쪽이 같은 번호를 발급하면 충돌한다.
MySQL은 이를 위해 두 개의 시스템 변수를 제공한다.

```sql
-- Source A
auto_increment_increment = 2
auto_increment_offset = 1
-- 1, 3, 5, 7 ...
-- Source B
auto_increment_increment = 2
auto_increment_offset = 2
-- 2, 4, 6, 8 ...
```

홀수/짝수로 나누어 절대 겹치지 않게 한다.
Source가 3개면 increment를 3으로 놓고 offset을 1, 2, 3으로 분배한다.
gap은 더 넓어지지만 충돌은 사라진다.

### INT의 한계와 BIGINT

AUTO_INCREMENT 타입이 INT면 최대 약 21억. UNSIGNED면 약 42억.
하루 100만 건이면 UNSIGNED INT는 약 11년이다.
한계에 도달하면 INSERT가 실패한다.
`Duplicate entry for key 'PRIMARY'` 에러 한 줄로 서비스가 멈춘다.
BIGINT는 약 922경이다. 사실상 무한.
INT에서 BIGINT로 바꾸는 건 고통스럽다.
ALTER TABLE이 락을 잡고 전체를 재구성한다.
새 테이블의 PK는 BIGINT로 시작하라.

### UUID: 무작위의 대가

AUTO_INCREMENT의 한계를 넘으려면 애플리케이션에서 ID를 만들면 된다.
UUID가 대표적이다.
충돌 확률은 사실상 0.
서버 간 조율 없이 어디서든 생성 가능.
글로벌 유니크.
하지만 대가가 있다. 36바이트 문자열.
BIGINT(8바이트)의 4.5배.
정렬 불가. 시간 순서가 없다.
인덱스 효율이 나쁘다.
UUID는 충돌 문제를 해결하지만 성능 문제를 만든다.

### UUID의 인덱스 문제

InnoDB의 PK는 클러스터드 인덱스다.
데이터가 PK 순서대로 물리적으로 저장된다.
순차 ID면 새 row는 항상 끝에 붙는다.
B-Tree의 맨 오른쪽 리프에만 쓰기가 발생한다.

랜덤 UUID는 다르다.
새 row가 B-Tree의 아무 곳에나 들어간다.
이미 꽉 찬 페이지에 끼어들면 페이지 분할(page split)이 발생한다.
한 페이지를 둘로 쪼개고 데이터를 재배치한다.
페이지 분할은 쓰기 증폭이다.
단편화가 누적되면 읽기도 느려진다.
INSERT 속도가 테이블 크기에 비례해 급격히 떨어지는 이유다.

### UUIDv7과 ULID

UUID의 인덱스 문제를 해결하려면 순서가 있으면 된다.
UUIDv7은 앞 48비트에 밀리초 타임스탬프를 넣는다.
시간 순서대로 정렬된다.
B-Tree 끝에 순차 삽입이 가능하다.
ULID도 같은 아이디어다.
타임스탬프 + 랜덤으로 구성된다.
Crockford Base32 인코딩이라 문자열 정렬도 된다.
UUIDv7은 2024년 RFC 9562로 표준이 됐다.
신규 시스템에 UUID를 쓸 거면 v7을 쓰는 게 맞다.

### Snowflake ID

Twitter가 2010년에 만든 분산 ID 체계다.
64비트 BIGINT 하나에 세 가지 정보를 담는다.

| 1 bit  | 41 bit     | 10 bit  | 12 bit |
| ------ | ---------- | ------- | ------ |
| 미사용 | 타임스탬프 | 머신 ID | 시퀀스 |

41비트 타임스탬프는 약 69년.
10비트 머신 ID는 1,024대.
12비트 시퀀스는 밀리초당 4,096개.
BIGINT에 담기니까 인덱스 효율이 좋다.
시간 순서가 있어 정렬도 된다.
Discord, Instagram도 같은 구조를 쓴다.
단점은 시계 동기화(NTP)에 의존한다는 것.
시계가 뒤로 가면 중복 위험이 있다.
대부분의 구현체는 시계 후퇴 시 대기하는 방어 로직을 넣는다.

### ID로 정보가 유출된다

순차 ID를 외부에 노출하면 의도하지 않은 정보를 준다.
주문 ID가 100,000이라면 "이 서비스는 지금까지 10만 건 주문이 들어왔구나."
오늘 아침에 100,000이었고 저녁에 100,500이라면 "하루 주문이 500건이구나."
경쟁사가 매일 한 번 주문해보면 일별 성장률을 추적할 수 있다.
사용자 ID도 마찬가지다. 가입 순서, 총 사용자 수, 성장 속도.
순차 ID 하나로 전부 추정 가능하다.
외부 API에는 UUID나 난수 기반 ID를 쓰고 내부 PK는 따로 관리하는 게 안전하다.

## Document라는 사고방식: MongoDB가 테이블을 버린 이유

RDB는 데이터를 어떻게 저장할지 먼저 생각한다.
MongoDB는 데이터를 어떻게 읽을지 먼저 생각한다.
이 차이가 전부다.
정규화된 테이블 다섯 개를 JOIN해서 하나의 화면을 만드는 게 RDB라면 하나의 Document에 화면이 필요한 모든 걸 담는 게 MongoDB다.

- 읽기 패턴을 먼저 정의하라.
- 정규화 본능을 의심하라.
- Embed와 Reference의 경계를 수치로 판단하라.
- 16MB 문서 제한을 설계에 반영하라.
- 스키마는 없는 게 아니라 코드에 있는 것이다.
- 테이블을 버린 건 구조를 버린 게 아니다. 관점을 바꾼 것이다.

### 왜 Document인가

RDB에서 "주문 상세"를 보려면 `orders`, `order_items`, `users`, `products`, `payments`.
최소 다섯 테이블을 JOIN한다.
MongoDB는 이걸 하나의 Document로 담는다.
주문 안에 아이템이 있고, 결제가 있고, 사용자 정보가 있다. 한 번의 읽기로 끝난다.
이게 가능한 이유는 Document가 중첩 구조를 허용하기 때문이다.
배열 안에 객체가 들어가고 객체 안에 다시 배열이 들어간다.
데이터의 모양이 애플리케이션의 모양과 같아진다.
ORM이 테이블과 객체 사이에서 벌이는 임피던스 불일치가 사라진다.

### BSON이라는 포맷

MongoDB는 JSON을 저장하지 않는다. BSON을 저장한다. Binary JSON.
JSON은 텍스트다. 파싱이 느리다.
BSON은 바이너리다. 타입 정보가 앞에 붙어 있어서 파싱 없이 필드를 건너뛸 수 있다.
JSON에 없는 타입도 지원한다. Date, ObjectId, Decimal128, Binary Data.
"2026-08-26"이 문자열이 아니라 진짜 날짜 타입으로 들어간다.
하나의 BSON Document 최대 크기는 16MB.
이건 설계의 제약이자 가이드라인이다.
"하나의 Document에 모든 걸 담으라"는 뜻이 아니라 "읽기 단위를 16MB 안에서 설계하라"는 뜻이다.

### Embed: 함께 읽히면 함께 저장한다

주문과 주문 아이템은 항상 같이 읽힌다.
주문만 보여주는 화면은 없다.
이런 관계는 Embed한다.

```json
{
  "order_iid": "ORD-001",
  "items": [
    { "product": "치킨", "qty": 2 },
    { "product": "콜라", "qty": 1 }
  ],
  "total": 25000
}
```

Embed의 장점은 명확하다.
한 번의 읽기. 한 번의 쓰기. 원자적 업데이트.
별도 트랜잭션 없이 items 배열 전체가 한 번에 바뀐다.

### Reference: 독립적으로 변하면 분리한다

상품 정보는 주문과 독립적으로 변한다.
가격이 바뀌고, 이름이 바뀌고, 이미지가 바뀐다.
이런 관계는 Reference한다.

```json
{
    "order_iid": "ORD-001",
    "user_iid": ObjectId("64a..."),
    "items": [
        { "product_iid": ObjectId("64b..."), "qty": 2 }
    ]
}
```

Reference는 RDB의 외래키와 비슷하지만 다르다.
MongoDB는 JOIN을 강제하지 않는다.
$lookup으로 할 수 있지만 비용이 크다.
Reference를 쓴다는 건 "이 데이터는 따로 읽어도 된다"는 설계 선언이다.

### 판단 기준: 언제 Embed하고 언제 Reference하는가

세 가지만 물으면 된다.

[함께 읽히는가?]
주문-아이템처럼 항상 같이 조회되면 Embed.
사용자-주문처럼 따로 조회되면 Reference.

[N이 무한히 커지는가?]
댓글이 만 개 달리는 게시글이라면 Embed하면 안 된다.
16MB를 넘길 수 있고, 배열이 커질수록 업데이트 비용이 증가한다.
N이 수십 이하로 제한되면 Embed. 제한 없으면 Reference.

[독립적으로 갱신되는가?]
상품 가격이 바뀔 때 모든 주문의 Embed된 가격을 고치는 건 비현실적이다.
자주 변하는 데이터는 Reference.

### 16MB의 벽

BSON Document 하나의 최대 크기는 16MB.
초과하면 insert 자체가 실패한다.
"16MB면 충분하지 않나?" 텍스트만이면 그렇다.
하지만 배열이 자라면 빠르게 도달한다.
IoT 센서 데이터를 분 단위로 Embed하면 하루에 1440건. 한 달이면 43,200건.
각 건이 100바이트면 4MB. 석 달이면 넘는다.
이건 설계 실수를 잡아주는 안전장치이기도 하다.
하나의 Document가 16MB에 근접한다면 그건 "쪼개라"는 신호다.

### 설계 패턴: Bucket Pattern

시계열 데이터에 강력하다.
분 단위 센서 값을 개별 Document로 저장하면
하루에 1440개. 한 달에 43,200개.
Collection이 폭발한다.
Bucket Pattern은 시간 단위로 묶는다.

```json
{
  "sensor": "temp-01",
  "date": "2026-08-26",
  "hour": 14,
  "readings": [
    { "min": 0, "val": 23.1 },
    { "min": 1, "val": 23.2 }
  ],
  "count": 60
}
```

한 시간 = 하나의 Document. 하루 24개. 한 달 720개.
Document 수가 60분의 1로 줄어든다.
인덱스 크기도, 쿼리 비용도 줄어든다.

### 설계 패턴: Subset Pattern

영화 정보 Document에 리뷰가 수천 개 달려 있다.
목록 화면에서는 최신 리뷰 5개만 보여준다.
전체를 읽어오는 건 낭비다.
Subset Pattern은 자주 쓰는 부분만 Embed한다.

```json
{
  "title": "인셉션",
  "recent_reviews": [
    { "user": "A", "text": "최고", "date": "2026-08-25" },
    { "user": "B", "text": "또 볼 예정", "date": "2026-08-24" }
  ]
}
```

전체 리뷰는 별도 Collection에 Reference로 둔다.
상세 페이지에서만 조회하면 된다.
읽기의 80%가 최신 5개만 필요하다면 80%의 읽기를 가볍게 만드는 패턴이다.

### 설계 패턴: Polymorphic Pattern

하나의 Collection에 구조가 다른 Document가 공존한다.
이게 RDB에서는 어색하지만 MongoDB에서는 자연스럽다.
스포츠 이벤트를 저장한다고 하자.
축구는 home_team, away_team이 있다.
마라톤은 participants 배열이 있다.
수영은 lanes 배열이 있다.

```json
{"type": "soccer", "home_team": "...", "away_team": "..."}
{"type": "marathon", "participants": [...]}
{"type": "swimming", "lanes": [...]}
```

type 필드로 구분하고 애플리케이션이 분기한다.
RDB였다면 테이블을 세 개 만들거나 모든 컬럼을 하나의 테이블에 우겨 넣었을 것이다.

### Schema Validation

"MongoDB는 스키마가 없다"는 반만 맞다.
스키마를 강제하지 않을 뿐이다. 원하면 걸 수 있다.

```json
{
  "validator": {
    "$jsonSchema": {
      "required": ["order_iid", "items"],
      "properties": {
        "order_iid": { "bsonType": "string" },
        "items": {
          "bsonType": "array",
          "minItems": 1
        }
      }
    }
  }
}
```

strict로 두면 스키마에 맞지 않는 insert가 거부된다.
moderate로 두면 기존 Document는 허용하고 신규만 검증한다.
프로덕션에서는 Validation을 거는 게 맞다.

### Anti-pattern: 하지 말아야 할 것들

[무한 성장 배열]
댓글, 로그, 이벤트를 배열로 계속 push하면 Document가 16MB를 향해 달린다.
`$push`할 때마다 Document 전체를 재할당한다.

[깊은 중첩]
5단계 이상 중첩된 Document는 쿼리도 어렵고 인덱싱도 어렵다.
`$set`으로 업데이트할 경로가 길어지면 실수가 늘어난다.

[RDB를 그대로 옮기기]
테이블 하나당 Collection 하나로 1:1 매핑하면 MongoDB를 쓰는 이유가 사라진다.
JOIN 없이 RDB 구조를 재현한 것일 뿐이다.

[모든 걸 하나에 Embed]
"한 번에 읽으려고" 모든 관계를 Embed하면 쓰기 비용이 폭증한다.
읽기 최적화와 쓰기 비용의 균형이 설계다.

### DBA 관점에서의 정리

- 읽기 패턴을 먼저 정의하라.
- 정규화 본능을 의심하라.
- Embed와 Reference의 경계를 수치로 판단하라.
- 16MB 문서 제한을 설계에 반영하라.
- 스키마는 없는 게 아니라 코드에 있는 것이다.

RDB에서 10년을 일하면 정규화가 손에 배어 있다.
중복을 없애고, 관계를 풀고, 키로 연결하는 본능. MongoDB에서는 그 본능이 방해가 된다.
"이 데이터가 어디에 속하는가"가 아니라 "이 데이터가 어떻게 읽히는가"로 생각해야 한다.
데이터의 구조가 아니라 데이터의 쓰임이 설계를 결정한다.
테이블을 버린 건 구조를 버린 게 아니다. 관점을 바꾼 것이다.
